## 1. 方案概述

本模块采用**轻量路线**：不新增任何表、不改任何 PG 枚举，Liquor Vendor 落地为 `company_type` 表中 `category='VENDOR'` 的第 7 行种子数据。已在 v20260705 代码中逐点核实的关键前提是——多类型体系（`company_company_type` 关联 + category 推导）已完备：onboarding 的 `add_company_type`（`internal/core/onboardings/services.py` L172）只校验所选 type_ids 共享同一 category 并据此推导 `company.type`，`GET /companies/types` 全量读表返回，`/me` 只返回粗粒度 `type='vendor'`，前端 Sidebar 与卖方路由分支（`src/utils/businessType.ts`）均按 `'vendor'` 值分派。因此**种下一行数据，整个 Vendor 能力面（订单/产品/发票/月结/团队/报表/通知）即自动继承**，满足译文 §4.2。

后端改动收敛为三个种子迁移（M1 实体类型、M2 权限实体、M3 合规经理角色）加两处应用层 StrEnum 追加（`APIEntityName` 四值、`RoleName.COMPLIANCE_MANAGER`），全部仿照原团队现成范式（`seed_company_hierarchy`、`seed_manufacturer_api_entities`、`seed_manufacturer_roles`）编写，幂等且可 downgrade。M2 种下的 `price_tier / customer_license / license_review / compliance_override` 四个 `api_entity` 是模块 04（价格等级）与模块 05（执照合规）全部新端点的权限载体——本模块先行铺轨，后续模块的 handler 直接写 `check_permissions(required_permissions=['view__customer_license'], required_roles=[...])` 即可。

前端改动同样收敛：`CompanyTypes` 枚举加一个成员、三个常量映射表补一条、onboarding 加第 7 张业务卡（现成 `Icons.colored.cocktail` 图标可用）、`UserRole` 加一个与 M3 双写一致的固定 UUID、abac rules 补新角色条目并顺手清偿 FR-A5 技术债。登录后的运行时行为（菜单、路由、team/chat 的 business_type 段位）经核实**零改动**。

接口层面本模块**没有新增端点**：14 个相关接口中 13 个是"现有接口自动生效"（其中 5 个需要回归验证），1 个为可选改造（`GET /me` 补细粒度类型，为模块 04/05 的菜单显隐铺路）。风险集中在两点：前端 `NAME_TO_COMPANY_TYPE` 不补则卡片静默不出现（映射查不到即丢弃）；abac rules 不补则新角色登录后全页面静默不可见——均已列入验收标准与测试要点。

## 2. 表结构设计

本模块**无表结构变更（无 DDL）**。原因：新版多类型体系（`company_company_type` + `category`）与 RBAC 四表（role / permission / api_entity / company_role_permission）已完备，新实体类型与新权限均为**纯种子数据**。以下 SQL 逐字摘自[表结构设计 §3.1](../开发方案-表结构设计.md)：

```sql
-- 迁移 ①：seed_liquor_vendor_company_type
INSERT INTO company_type (id, name, category, created_at, updated_at)
VALUES ('<固定UUID>', 'Liquor Vendor', 'VENDOR', now(), now());
-- 按 seed_company_hierarchy（c5c2f5a9b5be）同样模式补：
--   company_category('Liquor Vendor') + company_type_category 关联
--   （如产品要求子分类，再补 company_subcategory 关联，首期可不做）

-- 迁移 ②：seed_liquor_api_entities_and_permissions
INSERT INTO api_entity (id, name) VALUES
  ('<UUID>', 'price_tier'), ('<UUID>', 'customer_license'),
  ('<UUID>', 'license_review'), ('<UUID>', 'compliance_override');
-- permission 行（create/view/edit/delete × 新实体）+ company_role_permission 授权：
--   price_tier / customer_license：授予 CEO/CFO/Manager
--   license_review / compliance_override：仅 CEO/CFO（+ Compliance Manager，见下）

-- 迁移 ③（视 Q7 确认）：seed_compliance_manager_role
INSERT INTO role (id, type, belongs_to_company, name)
VALUES ('<固定UUID>', 'VENDOR', true, 'Compliance Manager');
-- ⚠️ 此 UUID 必须同步硬编码到前端 constants/roles.ts 的 UserRole
```

**逐迁移设计说明**（结合 v20260705 代码核实）：

### 迁移 ①（M1）`seed_liquor_vendor_company_type`

- 照抄 `2025_11_18_1300-c5c2f5a9b5be_seed_company_hierarchy.py` 的写法：`ON CONFLICT (name) DO UPDATE` 保证幂等；同步插 `company_category('Liquor Vendor')` 与 `company_type_category` 关联（onboarding 的 categories 接口依赖该关联）。
- `company_type.id` 使用**固定 UUID**（区别于 `c5c2f5a9b5be` 用 `uuid4()`）：前端不硬编码此 UUID（靠 `NAME_TO_COMPANY_TYPE` 按 name 映射），但固定 UUID 便于多环境（dev/test/preprod/prod）数据一致与排障，且与 M3 风格统一。
- 首期不插 `company_subcategory` 关联，onboarding 子分类接口对该类型返回空列表（现有 UI 对空子分类的行为需前端联调确认，见 §6 测试要点）。
- downgrade：按 name 删 `company_type_category` → `company_category` → `company_type`（仿基准迁移 downgrade），若已有公司关联（`company_company_type` 引用）则拒绝执行并提示。

### 迁移 ②（M2）`seed_liquor_api_entities_and_permissions`

- `api_entity` 4 行照抄 `2026_05_15_1437-e5a26b50ffc2_seed_manufacturer_api_entities.py`：先查已存在集合再插，引用应用层 `APIEntityName` 枚举值（本迁移前需先在 `internal/core/roles/domains.py::APIEntityName` 追加 `PRICE_TIER = 'price_tier'` 等 4 值）。
- ⚠️ **待确认（与基准文档表述的出入，不擅改）**：基准注释写"permission 行（create/view/edit/delete × 新实体）"，但 v20260705 实际模型中 `permission` 表是**按 action 的全局 4 行**（`create/view/edit/delete`，见 `2024_06_12_0919-d2cfa5cf0e97_add_api_entity.py::fill_api_entity_and_permissions` 与 `roles/domains.py::PermissionType`），实体维度由 `company_role_permission.entity_id` 三元组表达——**无需新增任何 permission 行**。建议 M2 实际只插 `api_entity` 4 行；此差异已反馈基准文档维护人。
- ⚠️ **待确认（授权种子的落地方式）**：`company_role_permission` 是**按公司**的（`get_company_role_permissions(company_id=...)`），历史上 `d2cfa5cf0e97` 曾为存量公司批量种默认授权，而 2026 年的 `e5a26b50ffc2` 只种 api_entity、把授权留给 onboarding 权限矩阵/设置页配置。因 Ocean Island 是**新入驻**（onboarding 时权限矩阵自动含新实体，管理员勾选即落库；CEO 作为 Owner 天然全通过），建议 M2 不做 company_role_permission 种子；若后续要为**存量** vendor 公司开通酒类能力，再补一个按 company 维度的数据迁移（基准注释中的授权矩阵——price_tier/customer_license 给 CEO/CFO/Manager，license_review/compliance_override 仅 CEO/CFO+Compliance Manager——届时作为该迁移的默认值）。

### 迁移 ③（M3，视 Q7）`seed_compliance_manager_role`

- 照抄 `2026_05_18_1059-bdefba9dd079_seed_manufacturer_roles.py`：固定 UUID、`Role(type=BusinessType.VENDOR, belongs_to_company=True, name='Compliance Manager')`；downgrade 前先数 `company_member` / `company_role_permission` 引用，有引用则 raise 拒绝。
- 是否需要 `belongs_to_company=False` 的同名 store 级角色行：现有 vendor 角色体系公司级/门店级成对出现（见 `bdefba9dd079` 的 company_roles/subdivision_roles 两组），合规审批按需求属公司级职能，**首期只种公司级 1 行**；若团队页在 store 维度邀请时也要选此角色再补 store 行。⚠️ 未确认，随 Q7 一并向产品确认。
- 注意基准提示：新版已删除 VENDOR 的 Chef 角色（迁移 `a3f1c9d27b84`），任何授权种子不要引用它。
- `RoleName` StrEnum 同步追加 `COMPLIANCE_MANAGER = 'Compliance Manager'`（供模块 04/05 端点的 `required_roles=[...]` 使用）。

迁移序号与风险对照[表结构设计 §四](../开发方案-表结构设计.md)：M1、M2 风险低（纯 INSERT，downgrade=DELETE）；M1-M3 全部向后兼容，老代码可与新数据共存，可先 `alembic upgrade` 再滚动发镜像。执行环境遵循基准约束：开发库用 v20260705 空库 `upgrade head` 或 preprod dump 恢复，**禁止对旧 css_dev（GitHub main 版）执行**。

## 3. 接口设计

本模块无新增端点。相关接口共 **14 个**，分三类：**A 零改动自动生效**（种子上线即生效，联调时点验）、**B 零改动但需回归验证**（动态矩阵/角色校验链路，需专门回归）、**C 改造接口**（可选）。所有路径挂在 `/api` 前缀下（nginx 网关 `X-API-KEY` 守卫），鉴权为 Bearer access token（`Security(check_access_token)`），与 `internal/main_app/*/transport/handlers.py` 现状一致；请求/响应体为 snake_case（前端 axios 经 humps 自动转换 camelCase）。

### 3.1 A 类：零改动自动生效接口

#### 1. GET /companies/types

- **用途**：onboarding 选择业务类型步骤的数据源（前端 `api/companies.ts::getCompanyTypes`，QueryKey `COMPANY_TYPES`）。M1 种子后本接口**不改一行代码**即返回第 7 行。
- **实现位置**：`internal/main_app/companies/transport/handlers.py::get_company_types`（L175-191）→ `CompaniesService.get_company_types`（全表查询）。
- **请求参数**：无。
- **响应体示例**（`ListResponse[CompanyTypeOut]`，`category` 为 `CompanyTypeEnum` 小写值）：

```json
{
  "items": [
    { "id": "b3c1…", "name": "Food Vendor", "category": "vendor" },
    { "id": "9f2a…", "name": "E&S Dealer", "category": "vendor" },
    { "id": "77d4…", "name": "Broadliner Dealer", "category": "vendor" },
    { "id": "c05e…", "name": "E&S Manufacturer", "category": "manufacturer" },
    { "id": "12aa…", "name": "Food Manufacturer", "category": "manufacturer" },
    { "id": "e8b9…", "name": "Restaurant", "category": "client" },
    { "id": "<M1 固定UUID>", "name": "Liquor Vendor", "category": "vendor" }
  ]
}
```

- **错误码**：401（token 无效，全局）；无业务错误分支。
- **注意**：前端对该查询 `staleTime: Infinity`（`useSelectBusinessStep.ts` L29-31）——种子上线后已打开页面的会话需刷新才能看到新卡（仅会话内缓存，无持久化，风险低）。

#### 2. POST /onboarding/companies/type

- **用途**：onboarding 提交所选实体类型并创建/更新公司。选择 Liquor Vendor 卡后，前端把 `NAME_TO_COMPANY_TYPE` 反查到的 UUID 放入 `type_ids` 提交；服务端 `add_company_type` 校验去重、存在性、**单一共享 category** 后按 category（VENDOR）建企——对新类型零改动。
- **实现位置**：`internal/main_app/onboarding/transport/handlers.py::add_company_type`（L73-106）→ `internal/core/onboardings/services.py::add_company_type`（L172-196）。
- **请求体示例**（`CompanyTypeIn`）：

```json
{ "type_ids": ["<Liquor Vendor company_type UUID>"] }
```

（多选同类别合法，如 Liquor Vendor + Food Vendor 同为 vendor 类别可共存一企。）

- **响应体示例**（`SuccessOut`）：

```json
{ "success": true }
```

- **错误码**：

| HTTP | type | 触发 |
|------|------|------|
| 400 | `invalid_company_types` | type_ids 为空/重复/含不存在的 UUID |
| 400 | `company_types_should_share_category` | 混入不同 category（如 Liquor Vendor + Restaurant） |
| 400 | `onboarding_is_not_inited` / `onboarding_already_completed` | onboarding 状态不符 |

#### 3. GET /onboarding/companies/type/{company_type}/categories

- **用途**：onboarding 后续步骤按粗类别（路径参数为 `CompanyTypeEnum`，即 `vendor`）拉可选分类。依赖 M1 同步种下的 `company_category('Liquor Vendor')` + `company_type_category` 关联，之后自动出现，代码零改动。
- **请求参数**：路径 `company_type` ∈ `vendor|manufacturer|client`。
- **响应体示例**：

```json
{ "items": [ { "id": "a1b2…", "name": "Liquor Vendor" }, { "id": "c3d4…", "name": "Food Vendor" } ] }
```

- **错误码**：400 `onboarding_is_not_inited` / `onboarding_already_completed`。

#### 4. GET /onboarding/companies/type/{company_type_id}/subcategories

- **用途**：按 company_type UUID 拉子分类。Liquor Vendor 首期不种子分类关联（表结构设计 §3.1 注释），返回空列表；代码零改动。
- **响应体示例**：`{ "items": [] }`
- **错误码**：404 `not_found`（company_type UUID 不存在）。
- ⚠️ 未确认：onboarding UI 对空子分类列表的展示行为（跳过/显示空态），联调时验证。

#### 5. GET /companies/roles

- **用途**：按公司类别拉角色列表（团队页、设置页、onboarding 均复用）。`company_type=vendor` 经 `MAPPED_COMPANY_TYPE_TO_BUSINESS_TYPE` 映射为 `BusinessType.VENDOR` 查 role 表——M3 种子后自动包含 Compliance Manager，代码零改动。
- **实现位置**：`internal/main_app/companies/transport/handlers.py::get_company_roles`（L150-172）。
- **请求参数**（query）：`company_type` ∈ `vendor|manufacturer|client`（必填）；`belongs_to_company`: bool（可选，公司级角色传 `true`）。
- **响应体示例**（`ListResponse[RoleOut]`，M3 后）：

```json
{
  "items": [
    { "id": "4641069c-be31-41b2-833e-a9dd843e2e25", "name": "CEO" },
    { "id": "4232069c-be31-41b2-833e-a9dd843e2e27", "name": "CFO" },
    { "id": "2c18cdc0-840d-41e1-9cb2-6a61763f6f51", "name": "Manager" },
    { "id": "<M3 固定UUID>", "name": "Compliance Manager" }
  ]
}
```

- **错误码**：422（company_type 非法枚举值）。

#### 6. GET /onboarding/companies/roles

- **用途**：onboarding 期团队成员步骤的角色下拉（`internal/main_app/onboarding/transport/handlers.py` L592，`companies_router` 嵌套于 `onboarding_router`）。生效机制同 #5，零改动。请求/响应/错误码同 #5（另有 onboarding 状态校验 400）。

#### 7. GET /entities

### 3.2 B 类：零改动但需回归验证的接口

#### 9. GET /settings/companies/{company_id}/permissions

- **用途**：读取该公司当前授权三元组，权限矩阵勾选态数据源。矩阵行列由 #5/#7/#8 动态构建（`usePermissionSettings.tsx` L187-226 三重循环），新实体列/新角色行自动出现——需回归验证矩阵渲染与勾选回显。
- **实现位置**：`internal/main_app/settings/transport/handlers.py::get_company_permissions`（L656-677）。
- **响应体示例**（`ListResponse[RolePermissionOut]`）：

```json
{
  "items": [
    {
      "role_id": "<Compliance Manager UUID>",
      "permission_id": "<view 的 permission UUID>",
      "entity_id": "<customer_license 的 entity UUID>"
    }
  ]
}
```

- **错误码**：403、422。

#### 10. PUT /settings/companies/{company_id}/permissions

- **用途**：全量替换该公司授权三元组。服务端 `validate_roles / validate_permissions / validate_entities` 按表校验——M2/M3 种子后对新实体/新角色的提交自动合法，零改动；需回归验证保存-回读闭环。
- **权限**：`check_permissions(required_permissions=['edit__company'])`。
- **请求体示例**（`ListRequest[RolePermissionIn]`；前端发送 camelCase 由 humps 转 snake_case）：

```json
{
  "items": [
    { "role_id": "<CEO UUID>", "permission_id": "<edit UUID>", "entity_id": "<price_tier UUID>" },
    { "role_id": "<Compliance Manager UUID>", "permission_id": "<view UUID>", "entity_id": "<license_review UUID>" }
  ]
}
```

- **响应体**：`{ "success": true }`
- **错误码**：

| HTTP | type | 触发 |
|------|------|------|
| 400 | `incorrect_roles` | role_id 不属于该公司 BusinessType 或不存在 |
| 400 | `incorrect_permissions` / `incorrect_entities` | permission_id / entity_id 不存在 |
| 403 | `you_have_no_rights_to_work_with_this_resource` | 无 `edit__company` |

#### 11. PUT /onboarding/team-members/roles

- **用途**：onboarding 期首次写入权限矩阵（`internal/main_app/onboarding/transport/handlers.py` L437；服务层 `update_company_team_roles`，`onboardings/services.py` L492-527：validate 三连 + 全删全插）。Liquor Vendor 建企路径的授权入口，语义同 #10。请求/响应/错误码同 #10（另有 onboarding 状态校验）。
- **回归点**：前端 `useOnboardingForm.ts::buildPermissionsMatrix`（L28-60）对 CEO 角色默认全勾——新实体列对 CEO 自动勾选，其他角色默认不勾，符合"敏感权限仅限授权角色"的需求方向；验证提交后 `company_role_permission` 落库含新实体行。

#### 12. POST /team/members　/　13. PUT /team/members/{member_id}

- **用途**：邀请/编辑团队成员（含指派 Compliance Manager）。`business_type`/`business_id` 为 query 参数（vendor 公司传 `business_type=company&business_id={companyId}`，门店维度传 `store`——前端由 `src/utils/businessType.ts::getEntityBusinessType` 推导，Liquor Vendor 走 `'vendor'` 值命中 store/company 分支，零改动）。角色合法性按 role 表校验，M3 后新角色自动放行。
- **实现位置**：`internal/main_app/team/transport/handlers.py`（POST L325-379、PUT L207-）。
- **权限**：POST `create__team`；PUT `edit__team`。
- **请求体示例**（POST `AddTeamMemberIn`，字段以实际 requests.py 为准，示例为核心字段）：

```json
{
  "first_name": "Jane",
  "last_name": "Doe",
  "email": "jane@oceanisland.com",
  "phone_number": "+15550001234",
  "role_id": "<Compliance Manager 固定UUID>"
}
```

- **响应体**：`TeamMemberOut`（成员详情）。
- **错误码**：400（角色/数据非法）、403（无团队权限）、404（business 不存在）、409 `key_already_exists`（邮箱/手机已注册）。
- **回归点**：新角色成员登录后 `/me` 返回 `role.name='Compliance Manager'` + 前端按 `UserRole` UUID 匹配 abac rules——若 F3/F4（前端条目）未上线，该成员将全页面不可见，属发布顺序硬依赖。
