## 1. 方案概述

**技术路线：把"Redis 单值会话"升级为"DB 权威 + Redis 缓存"的多设备会话体系，其余复用现有 JWT 基础设施。** 现有代码已具备双 token、refresh 轮换、`issued_token` 吊销表、JWT `sid` 逐请求校验（`internal/core/auth/tokens/services.py`）——30 天这个数字甚至已是 `refresh_token_ttl` 的默认值（`config/auth_settings.py:17`）。真正缺的是三件事：多会话存储结构、吊销语义（改密/管理员踢出）、前端会话失效处理。因此本方案不动 JWT 签发/验签协议，`sid` 声明含义从"Redis 里那个唯一值"升级为"`user_session` 表主键"，`verify_access_token` / `update_tokens` 的 sid 校验从"等值比较"改为"该 sid 是否活跃（未吊销且未过期）"。

**会话生命周期：绝对 30 天，非滑动。** 登录时创建 `user_session` 行，`expires_at = now() + 生效TTL`；refresh 轮换只刷新 `last_active_at` 与新 token 的绑定，不延长 `expires_at`。到期或被吊销后，access 校验与 refresh 一律返回 401 `session_expired`（错误类型已存在于 `app/pkg/auth/jwt/errors.py:14`），满足需求 §5.1「30 天会话期到期后必须重新登录」。access token TTL 通过 env 从 8h 缩短到 15min（FR-B1），把被盗 access token 的暴露窗口压缩到分钟级，吊销的实时性由"revoked 校验 + 短 access"共同保证。实体级配置走 `company.session_ttl_seconds` 列（NULL=全局默认），Ocean Island 配 2592000。

**吊销语义收敛到一个原语。** 新的 `SessionService.revoke_sessions(user_id, session_ids | ALL, reason, revoked_by)` 统一承载：登出（LOGOUT，仅当前会话）、改密/重置（PASSWORD_CHANGE，全部会话）、管理员踢出（ADMIN_KICK，单个或全部）、到期清理（EXPIRED）。它同时写 `user_session.revoked_at`、按 `issued_token.session_id` 吊销 token、删除 Redis 缓存键，保证三处状态一致。`change_password`（`internal/core/users/services.py:98`）与 `reset_password`（`internal/core/auth/services.py:461`）当前只改 hash 不吊销，是验收标准的直接缺口，本方案在这两个服务函数内补调该原语。

**前端最小侵入。** 保留 localStorage + axios-auth-refresh 现状（httpOnly cookie 改造牵连 CORS 与部署链路，标记为二期安全加固，本期不做）；新增两类改动：① `models/errors.ts` 补 `SESSION_EXPIRED`/`TOKEN_REVOKED` 并在 axios 层做全局"清凭证 + 跳登录页"处理（FR-B6）；② 设置页激活现有 SECURITY tab 占位（`ui/pages/Settings/Settings.tsx:156-161`），挂"登录设备/会话"列表与踢出操作（FR-B4 用户自助侧）。多设备并发按 Q9 建议方案 A 设计；若客户最终选 B，本方案退化为"每用户一个活跃行"，接口与表结构不变。

## 2. 表结构设计

以下 DDL 逐字摘自《开发方案-表结构设计》§3.2（对应迁移 M3 `add_user_session_and_token_session_fk`，基于 `3bdd9e1f06c8` 续写）。

### 2.1 新表 `user_session`

把"Redis 单值会话"升级为"DB 权威 + Redis 缓存"的多设备会话。JWT 的 `sid` 即本表主键：

```sql
CREATE TABLE user_session (
    id              uuid PRIMARY KEY,                -- = JWT sid
    user_id         uuid NOT NULL REFERENCES "user"(id) ON DELETE CASCADE,
    device_id       varchar(36)  NOT NULL,           -- 沿用现有 device_id 语义
    device_name     varchar(255),                    -- 客户端上报（UA 解析），可空
    ip_address      varchar(45),
    user_agent      varchar(512),
    expires_at      timestamptz  NOT NULL,           -- 登录时间 + 会话策略 TTL
    last_active_at  timestamptz  NOT NULL DEFAULT now(),
    revoked_at      timestamptz,                     -- NULL=活跃
    revoked_by_user_id uuid REFERENCES "user"(id) ON DELETE SET NULL,
    revoke_reason   varchar(50),                     -- LOGOUT/PASSWORD_CHANGE/ADMIN_KICK/EXPIRED
    created_at      timestamptz  NOT NULL DEFAULT now(),
    updated_at      timestamptz  NOT NULL,
    deleted_at      timestamptz
);
CREATE INDEX ix_user_session_user_id ON user_session(user_id) WHERE revoked_at IS NULL;
CREATE INDEX ix_user_session_expires_at ON user_session(expires_at);
```

**设计说明**：

- `id` = JWT `sid`：`issue_tokens` 现已生成 `session_id = uuid4()` 并放进 payload（`tokens/services.py:38,47`），本表直接以它为主键，验签路径零协议变更。
- "活跃"判定 = `revoked_at IS NULL AND expires_at > now()`（部分索引 `ix_user_session_user_id` 即按此设计）。
- `revoke_reason` 为 varchar + 应用层 StrEnum（`SessionRevokeReason`），遵循表结构文档"状态类字段一律 varchar"的决策，四值：`LOGOUT` / `PASSWORD_CHANGE` / `ADMIN_KICK` / `EXPIRED`。
- `revoked_by_user_id`：管理员踢出时记录操作人，登出/改密时为本人，满足审计（FR-B8）取数。
- ⚠️ `device_id`"沿用现有语义"需要注意：现有 device_id 是**每次登录时服务端 `uuid4()` 生成**（`internal/core/auth/services.py:250,311`），并非稳定设备标识。即一行 `user_session` ≈ 一次登录实例；`device_name`（UA 解析）才是用户可读的设备信息。DDL 不改，语义在代码注释与本文档中固定，不作为"同一物理设备去重"依据。
- Redis 角色降级为**缓存**：键 `session:{sid}` 缓存活跃判定结果（短 TTL，建议 60s），吊销时同步删除该键，保证踢出在 60s 内全局生效（配合 15min access TTL，实际感知为"下一次请求即失效"，因为 verify 还会查 `issued_token.revoked`）。旧键 `user_session:{user_id}` 在过渡期读不到即视为无会话，发布后自然过期。

### 2.2 修改 `issued_token`

现有列：jti/subject_id/device_id/expired_at/revoked（`internal/core/auth/tokens/models.py:11-19`）：

```sql
ALTER TABLE issued_token ADD COLUMN session_id uuid
    REFERENCES user_session(id) ON DELETE SET NULL;   -- 存量行为 NULL，新签发必填
CREATE INDEX ix_issued_token_session_id ON issued_token(session_id) WHERE NOT revoked;
```

**设计说明**：token 与会话建立外键后，"吊销一个会话"= 按 `session_id` 批量置 `revoked=true`，取代现在按 `(user_id, device_id)` 的近似吊销（`tokens/services.py:148-154`）。存量 token（session_id IS NULL）在过渡期沿用旧路径按 user_id+device_id 吊销，随 access/refresh 自然到期后退出历史舞台。

### 2.3 修改 `company`

实体级会话时长，NULL = 用全局 env 默认；不另建配置表：

```sql
ALTER TABLE company ADD COLUMN session_ttl_seconds integer;  -- Ocean Island 配 2592000（30 天）
```

**设计说明**：

- 生效 TTL 解析（`issue_tokens` 内）：取用户所有关联公司 `session_ttl_seconds` 的**最大值**；均未配置时回退 `auth_settings.refresh_token_ttl`（现 30 天）。⚠️ 待确认（需求.md §5.2 待确认-3）。
- 取值校验建议 `900 ≤ session_ttl_seconds ≤ 7776000`（15 分钟 ~ 90 天），⚠️ 上限待产品确认。
- 修改配置只影响**新登录**创建的会话，存量会话按创建时的 `expires_at` 走完生命周期。

### 2.4 配套代码改动（无 DDL，摘自表结构文档 §3.2 末段）

Redis 键从 `user_session:{user_id}`（单值）改为 per-sid 缓存；`verify_access_token` 的 sid 校验改查"该 sid 是否活跃"而非"是否等于唯一值"；`change_password`/`reset_password` 补"吊销该用户全部 session + token"；新增 admin 端点踢单会话/全部会话（写 `revoked_at/revoke_reason`）；`access_token_ttl` 由 8h 缩短至 15min（env 即可）。

## 3. 接口设计

**通用约定**（与现有代码核实一致）：

- 全部路径挂在 `/api` 前缀下（`internal/main_app/app.py:55`），受 `X-API-KEY` 网关守卫（`check_api_key`）；下表路径省略 `/api`。
- 鉴权写法：登录态 `Security(check_access_token)`（`internal/main_app/middlewares/jwt/services.py`）；平台管理员 `Security(check_admin_role)`（`internal/main_app/middlewares/admin/services.py`，校验 `UserRole.ADMIN`）；公司权限 `Depends(check_permissions(required_permissions=[...], required_roles=[...]))`。
- 请求/响应 JSON 为 **snake_case**（前端 humps 自动转换，`src/config/axios/interseptors.ts:49`）；错误响应统一 `ErrorOut {type, message}`（`app/pkg/responses.py:18`）；成功无载荷用 `SuccessOut {success: true}`；列表用 `ListResponse {items}` / `PaginatedListResponse {count, items}`。
- 动作类端点用 POST + 动词尾段，与现有 `/auth/logout`、`/admin/clients/{client_id}/send-invitation` 风格一致。

#### 3.1.2 POST `/auth/sessions/{session_id}/revoke` — 踢出我的指定会话

- **用途**：用户在设备列表中移除某台设备的登录；`session_id` 为当前会话时等效登出（前端随后走本地登出流程）。
- **权限**：`Security(check_access_token)`；服务层校验 `session.user_id == request.state.user_id`，不满足按 404 处理（不泄露他人会话存在性）。
- **请求体**：无。
- **响应体 200**：`{"success": true}`
- **错误码**：401（同上）；404 `not_found`（会话不存在 / 不属于本人 / 已吊销）。
- **行为**：`revoke_sessions(reason=LOGOUT, revoked_by=本人)` → 写 `revoked_at` + 按 `issued_token.session_id` 吊销 token + 删 Redis 缓存；写审计（FR-B8）。

#### 3.1.3 POST `/auth/sessions/revoke-others` — 踢出我的其它全部会话

- **用途**："在其它所有设备上退出登录"一键操作（怀疑账号泄露时的自救入口）。
- **权限**：`Security(check_access_token)`。
- **请求体**：无。
- **响应体 200**：

```json
{
  "revoked_count": 3
}
```

- **错误码**：401（同上）。
- **行为**：吊销该用户除当前 `sid` 外全部活跃会话（reason=LOGOUT）；`revoked_count` 为实际吊销条数（可为 0）。

#### 3.2.2 POST `/admin/users/{user_id}/sessions/{session_id}/revoke` — 管理员踢出单会话

- **用途**：定点终止某用户某台设备的登录（如已丢失的设备）。
- **权限**：`Security(check_admin_role)`。
- **请求体**（可选原因，用于审计）：

```json
{
  "reason_note": "User reported stolen laptop"
}
```

- **响应体 200**：`{"success": true}`
- **错误码**：401；403 `forbidden`；404 `not_found`（用户/会话不存在或不匹配）；400 `bad_request`（会话已吊销）。
- **行为**：`revoke_sessions(reason=ADMIN_KICK, revoked_by=管理员)`；写审计（前值=活跃、后值=吊销、操作人、IP）。

#### 3.2.3 POST `/admin/users/{user_id}/sessions/revoke-all` — 管理员一键终止全部会话

- **用途**：批注 2「管理员可一键终止某用户的全部活跃会话」；账号被禁用、离职、安全事件时的标准动作。

- **错误码**：401；403 `forbidden`；404 `not_found`（用户不存在）。

### 3.5 改造接口

以下端点**请求/响应结构均不变**（前端零改动即兼容），只变服务端行为。现有结构均已对照 `internal/main_app/auth/transport/{handlers,requests,responses}.py` 核实。

#### 3.5.1 POST `/auth/sign-in`（改造）

- **现状**：请求 `{"confirmation_session_id": "<uuid>"}`；响应 `SignInResultOut`：

```json
{
  "onboarding_step": null,
  "tokens": {
    "access_token": "<jwt>",
    "refresh_token": "<jwt>"
  }
}
```

- **行为变更**：
  1. `issue_tokens`（`internal/core/auth/tokens/services.py:33`）创建 `user_session` 行（id=sid、expires_at=now()+生效TTL、设备元数据），Redis 写 per-sid 缓存，不再覆盖 `user_session:{user_id}` 单值键；
  2. 生效 TTL 解析：用户关联公司 `session_ttl_seconds` 最大值，回退 `auth_settings.refresh_token_ttl`；
  3. 设备元数据采集：handler 透传 `request.headers['user-agent']` 与客户端 IP（`X-Forwarded-For` 首元素，nginx 需配置透传，`deploy/nginx` 侧确认）；`device_name` 由 UA 服务端解析（建议 `user-agents` 库）；
  4. 多设备并发：登录**不再挤掉**旧会话（Q9-A）；
  5. 写审计 `USER_LOGIN`（FR-B8，P1）。
- **错误码**：不变（400 `invalid_confirmation_session` / `user_credentials_has_changed`，422）。

#### 3.5.2 POST `/auth/sign-up`（改造，随动）

- 结构不变（`SignUpResultOut {onboarding_step, tokens}`）。注册链路与登录共用 `issue_tokens`（`internal/core/auth/services.py:250`），自动获得会话行，无独立开发项，列出仅为回归测试圈定范围。

#### 3.5.3 POST `/auth/update-tokens`（改造）

- **现状**：请求 `{"refresh_token": "<jwt>"}`；响应 `TokensOut {"access_token": "...", "refresh_token": "..."}`。
- **行为变更**（`tokens/services.py:113` `update_tokens`）：
  1. sid 校验从"等于 Redis 唯一值"改为"`user_session` 活跃判定"（未吊销且 `expires_at > now()`），否则 400 `session_expired`；
  2. 轮换吊销范围从"该 user+device 全部 token"改为"该 `session_id` 全部 token"（精确化，不误伤其它设备）；
  3. 新签发的 access/refresh 沿用**同一个 sid**（会话生命周期连续），`issued_token.session_id` 写入；
  4. 刷新 `user_session.last_active_at`；**不延长** `expires_at`（绝对 30 天）；
  5. 重放防护保留：已 revoked 的 refresh 被复用 → 吊销该会话全部 token 并 400 `token_already_revoked`。
- **错误码**：400 `invalid_token` / `incorrect_token_type` / `token_already_revoked` / `session_expired`；422。

#### 3.5.4 POST `/auth/logout`（改造）

- **现状**：`Security(check_access_token)`，响应 `{"success": true}`；现按 `(user_id, device_id)` 吊销 token 并**删除用户级唯一 Redis 会话键**（`internal/core/auth/services.py:513-518` → `tokens/services.py:148-154`）——多会话下会误杀全部设备。
- **行为变更**：改为吊销**当前 `sid`** 一个会话（reason=`LOGOUT`），其它设备不受影响；写审计 `USER_LOGOUT`。
- **错误码**：不变（200 / 401）。

#### 3.5.5 POST `/auth/reset-password`（改造）

- **现状**：请求 `{"confirmation_session_id": "<uuid>", "password": "<new>"}`；响应 `{"success": true}`；服务层只更新 password_hash（`internal/core/auth/services.py:461-486`）。
- **行为变更**：更新 hash 成功后调用 `revoke_sessions(user_id, ALL, reason=PASSWORD_CHANGE)` —— 全部会话 + 全部未过期 token 吊销 + Redis 缓存清理；写审计。满足验收「重置密码使现有会话全部失效」。
- **错误码**：不变（400 `invalid_confirmation_session` / `user_credentials_has_changed`，422）。

#### 3.5.6 POST `/team/members/{member_id}/change-password`（改造）

- **现状**：`Security(check_access_token) + Depends(check_permissions(required_permissions=['edit__team']))`，query 带 `business_type`/`business_id`（`internal/main_app/team/transport/handlers.py:382-393`）；服务链 `team/services.py:593 → users/services.py:98 change_password` 只改 hash。
- **行为变更**：`UsersService.change_password` 末尾对 `member_id` 调 `revoke_sessions(ALL, reason=PASSWORD_CHANGE, revoked_by=操作人)`。被改密成员所有设备立即下线。
- **错误码**：不变。
- 说明：全库核实后确认**不存在"本人自助改密"HTTP 端点**（`change_password` 仅被 team 链路调用），故本 FR 的吊销点只有 reset-password 与 team 改密两处；未来若新增自助改密端点，须复用同一原语。

### 6.2 集成测试（API 级）

| 用例 | 场景与断言 |
|------|------------|
| 登录建会话 | sign-in 成功 → `user_session` 新行、字段齐全；JWT `sid` = 行 id；**两次登录两行并存互不影响**（Q9-A） |
| 刷新连续性 | update-tokens 成功 → 同 sid、`last_active_at` 更新、`expires_at` 不变、旧 token 对 revoked |
| 绝对到期 | 冻结时间到 `expires_at` 后：access 校验 401 `session_expired`；refresh 400 `session_expired` |
| 登出只杀当前 | 设备 A logout → A 的 token/会话失效；设备 B 请求正常 |
| 重置密码全吊销 | reset-password 后该用户全部会话 revoked（reason=PASSWORD_CHANGE）；任一旧 refresh 重放 400 `token_already_revoked` |
| team 改密吊销 | change-password 成功 → member 全部会话失效；操作人自己的会话不受影响 |
| 自助踢出 | 踢他人 session_id → 404；踢自己非当前 → 成功且当前会话不受影响；revoke-others → `revoked_count` 精确 |
| 管理员踢出 | 单踢/全踢 → 目标下一请求 401（Redis 缓存已清，无窗口期）；`revoked_by_user_id` = 管理员 |
| 会话策略 | PUT 越界值 422；null 回退默认；GET 三值一致性 |
| 重放防护回归 | 已轮换 refresh 复用 → 该会话全部 token 吊销（现有行为不回归） |

### 6.3 权限与边界用例

| 用例 | 断言 |
|------|------|
| 非 ADMIN 调 `/admin/users/{id}/sessions*` | 403 `forbidden`（`check_admin_role`） |
| 无 access token 调 `/auth/sessions*` | 401 `token_is_not_specified` |
| 缺 X-API-KEY | 401（网关守卫，全部新端点覆盖冒烟） |
| 被踢会话的 access token 调任意端点 | 401 `session_expired`（而非 200） |
| 被踢会话的 refresh token 调 update-tokens | 400，不签发新 token |
| `confirm-password` 错误密码 | 400 `invalid_credentials`；不产生提升标记 |
| team 改密无 `edit__team` 权限 | 403（现有 `check_permissions` 行为回归） |

### 6.4 前端 / E2E（Playwright，仿 `e2e-runner` 惯例）

| 用例 | 场景 |
|------|------|
| 静默续期 | 登录 → 篡改/等待 access 过期 → 发起请求 → axios-auth-refresh 自动换新 → 请求成功、无感知 |
| 会话失效跳转 | mock 401 `session_expired` → 凭证被清、userStore 重置、跳 `/auth`、出 toast；并发多请求只跳一次 |
| 设备列表 | 两个浏览器 context 登录 → 设置页 SECURITY tab 显示 2 行、当前设备徽标正确 → 踢另一设备 → 另一 context 下一操作被登出 |
| 退出其它全部 | 三 context 登录 → revoke-others → 其余两个 context 均被登出，当前不受影响 |
| 管理员踢出（P1） | admin 页踢出目标用户 → 目标浏览器立即失效跳登录 |
| 回归 | 登录/登出/重置密码/团队改密全流程 UI 回归（响应结构未变） |

### 6.5 非功能

- **性能**：verify 路径新增的会话查询必须走 Redis 缓存，压测确认 P99 无明显退化（对比基线）；`ix_user_session_user_id` 部分索引命中验证。
- **兼容**：发布顺序"先迁移后发码"（M3 全部可空/新表，老代码可与新 schema 共存）；发布瞬间存量已登录用户（旧 Redis 单值键 + 无 session 行）需平滑处理——方案：旧 sid 在 `user_session` 无行时视为"遗留会话"，首个 refresh 时补建行（TTL 按剩余 refresh 期），避免全员被登出。⚠️ 此过渡策略需在 B-3 实现并单独测试。
- **安全回归**：改动涉及认证核心，上线前过一轮 security review（改密吊销、重放、管理端点鉴权）。
