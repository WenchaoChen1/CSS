## 1. 业务需求（译文 §5 完整摘编，含原文批注）

### 1.1 需求（译文 §5.1）

Ocean Island 用户要求更长的认证会话时长。

成功登录后，用户应保持登录状态最长 30 天，除非发生以下任一情况：

- 用户手动退出登录；
- 用户修改或重置密码；
- 管理员吊销该会话；
- 用户账户被禁用；
- 出现需要重新认证的安全事件；
- 30 天会话期到期。

会话到期后，用户必须重新登录。

### 1.2 配置（译文 §5.2）

会话时长应可在系统级或实体级配置，而不是永久硬编码。

建议配置：

- 标准 CSS 用户：沿用现有会话策略；
- Ocean Island 酒类供应商用户：30 天持久会话；
- 未来的酒类供应商：由管理员配置。

### 1.3 安全要求（译文 §5.3）

> 📝 批注（Michael Zhang，2026-07-15，锚点在本节标题）：**增加强制踢出功能。**

实现应采用安全的持久化认证机制，而不是签发一个 30 天长期有效的单一访问令牌。

方案应包括：

- 短生命周期的访问令牌（Access Token）；
- 安全的刷新令牌（Refresh Token）轮换；
- 服务端会话吊销；
- 适用场景下的安全 Cookie 存储；
- 设备与会话跟踪；
- 修改密码时使会话失效；
- 防止已吊销刷新令牌被重放使用；
- 管理员可一键终止某用户的全部活跃会话。

对于敏感操作（如修改银行信息、批准执照、变更用户权限、覆盖合规限制），系统可要求用户重新输入密码或完成额外认证。

### 1.4 验收标准（译文 §5.4 原文）

- 酒类供应商用户在关闭并重新打开浏览器后仍保持登录状态；
- 用户在最长 30 天内无需再次手动登录即可保持认证状态；
- 点击「退出登录」立即结束当前会话；
- 重置密码会使现有会话全部失效；
- 管理员可以吊销某个用户的活跃会话；
- 会话到期后用户必须重新登录。

### 1.5 相关横切需求（译文 §11 摘录）

审计轨迹须覆盖：**用户登录与登出、会话吊销**；审计记录应包含用户、操作、日期与时间、变更前/后值、IP 地址或设备信息（可获得时）。

## 3. 验收标准

### 3.1 译文 §5.4 原文验收标准

见 §1.4，共 6 条。

### 3.2 可测试化补充

| # | 验收项 | 可测试描述 |
|---|--------|------------|
| AC-1 | 关闭浏览器后保持登录 | 登录后关闭并重开浏览器，localStorage 中 refresh token 仍有效；首个 401 触发静默刷新成功，无需重新输入密码 |
| AC-2 | 30 天免登录 | 会话 `expires_at` = 登录时刻 + 生效 TTL（Ocean Island = 2592000s）；第 29 天 refresh 成功；第 30 天后 refresh 返回 401 `session_expired`，前端跳转登录页 |
| AC-3 | 登出立即生效 | 调用 `POST /auth/logout` 后：当前会话 `revoked_at` 置位；同会话的 access/refresh token 立即失效（下一次请求 401）；**其它设备会话不受影响**（Q9 方案 A 前提） |
| AC-4 | 重置/修改密码吊销全部会话 | 重置密码成功后，该用户全部 `user_session.revoked_at` 置位（reason=`PASSWORD_CHANGE`）；所有设备下一次 API 请求返回 401 `session_expired`；已吊销 refresh token 重放返回 401 `token_already_revoked` |
| AC-5 | 管理员踢出 | 平台管理员调用踢出端点后，目标会话立即失效（下一次请求即 401，无缓存窗口期>60s）；踢全部时 `revoked_count` 与活跃会话数一致；操作写入审计（FR-B8） |
| AC-6 | 会话到期强制重登 | `expires_at` 已过的会话，access 校验与 refresh 均返回 `session_expired`；前端全局处理并跳转 `/auth` |
| AC-7 | 多设备并发（Q9-A） | 设备 A、B 先后登录同一账号，A 不被 B 挤下线；设置页会话列表显示 2 条且当前会话有 `is_current` 标记 |
| AC-8 | 防重放 | 已被轮换（revoked）的旧 refresh token 再次使用时，返回 401 且该用户该设备 token 全部吊销（现有 `update_tokens` 行为保留） |
| AC-9 | 实体级 TTL | 未配置 `session_ttl_seconds` 的公司用户，会话 TTL = 全局默认；配置后新登录立即生效，存量会话不受影响 |
| AC-10 | 无 Kafka 时登录可用（FR-B9） | Kafka 不可达时 `POST /auth/sign-in` 不再 500（短信验证码类功能可降级报错，登录主链路可用） |

## 5. 关联开放问题

### 5.1 Q9 — 30 天登录是否允许多设备同时在线（直接决定本模块架构）

- **建议 A**：允许多设备并发会话（每设备各自 30 天），提供"会话/设备列表"，管理员和用户本人可踢出指定设备或全部设备（批注 2 即此项）。
- **对本模块影响**：本模块开发方案按 **A** 设计（`user_session` 多行 + 会话列表接口 + 踢出接口）。若客户选 B（维持单设备），`user_session` 表**仍然要建**（为审计与踢出留痕），仅应用层限制每用户一个活跃行（见表结构设计文档 §六）；前端"设备列表"退化为"当前会话信息+踢出"。
- **状态**：未确认前按 A 开发风险可控（B 是 A 的子集）。
