> 1. **Tier A = 默认与回退价（§6.2）**：`price_tier.is_default` 的等级即 **Tier A**；取价四规则——① 该等级显式 `UNAVAILABLE` → 不可下单；② 有所在等级价 → 用之；③ **缺所在等级价 → 回退 Tier A 价**；④ 无 Tier A 价 → 产品不能发布也不能下单。**v1 的"缺价显示'请联系供应商询价'、绝不回退基础价/他 tier 价"已作废。**
> 2. **交付前动态调价（§8.2）**：新增 `order.price_tier_id`（提交时快照客户等级）；目录价变更**自动重算所有未达 `Delivered` 状态的订单**（含已提交、已确认），到 `Delivered` 才锁价、发票定格。**v1 的"提交即快照锁价、历史订单不受改价影响"已作废**（改为"交付即锁价"）。
> 3. **移出首期（§2.2/§10.1）**：定价审计**日志界面**（原 §3.6 接口与前端审计页删除；`product_price.changed_by_user_id` 仍保留可追溯）、tier/价格变更**通知**。仅"客户 tier 分配变更"审计**记录**必须落库（§10.2）。
> 4. **导入以 `Product ID` 为主键**（§7.2，产品名/SKU 不作主键）；客户导入缺 tier → 自动 Tier A；**不含导出**。

## 1. 方案概述

**数据模型**：新增 `price_tier` 表（store/vendor 维度，照抄 `payment_method` 字典表范式：name 唯一、created_by、删除受限 409），等级集合是 vendor 级统一维度。**每个 store 必须有且仅有一个 `is_default=true` 的等级，它承担 §6.2 的 Tier A（默认与回退）角色**（唯一部分索引 `uq_price_tier_store_default` 保证）。定价不另建价格表，而是给现有 append-only 的 `product_price` 表加 `tier_id` 维度（`NULL` = 未启用 tier 的普通 vendor 全局价，向后兼容存量行），改价 = 追加新行、当前价 = 该 `(product_id, tier_id)` 最新一行；补 `changed_by_user_id` / `import_job_id` 两列供追溯。可购性由 `store_product_tier_availability` 承载（仅记"显式不可购"）。客户分配为 `client.price_tier_id` 单值外键（`ON DELETE RESTRICT` 兜底防误删）。**动态调价新增 `order.price_tier_id`**：订单提交时快照客户等级，供未达 Delivered 时按随单等级重算（§6.3/§8.2）。

**读写路径**：管理侧新建 `core/price_tiers/` 领域五件套 + `main_app/vendor/price_tiers/` 传输层，提供等级 CRUD、客户分配（单个/批量）、产品×等级定价矩阵（产品维度与等级维度双入口）。客户侧改造现有读价链路：产品列表/详情按请求方 `client.price_tier_id` 取价，**缺该等级价时回退该 store 的 Tier A（默认等级）价；Tier A 也缺失则产品不可发布/不可下单（`PRICE_NOT_CONFIGURED`）；该等级显式 `UNAVAILABLE` 则不可下单**（§6.2 四规则）。客户响应**不得携带**他等级价、Tier A 原值或等级名称（§6.3/§10.2）。两条下单链路（餐厅端 `POST /restaurants/{restaurant_id}/orders`、供应商代下 `POST /vendors/{vendor_id}/orders`）落 `OrderProduct.price` 快照时取价源改为"客户 tier 当前价 + Tier A 回退"，并写入 `order.price_tier_id`。

**交付前动态调价（v2 核心新增）**：目录价（`product_price` 当前价）变更后，对所有**未达 `Delivered`** 的活跃 liquor vendor 订单按 `order.price_tier_id` + Tier A 回退重算行价、行小计、小计、订单总额及依赖金额，交付前向客户展示更新后价格；订单到 `Delivered` 后锁价，已交付订单与最终发票保留交付时价格；部分交付按行处理（已交付行锁定，未交付行继续随价）。触发方式见 §3.4.5。

**订购流程（§8.1）**：liquor vendor 走"选择产品 → 订单审核 → 提交订单 → 订单确认"四步，提交前一次最终审核、**未完成最终提交前不创建/传输订单**，成功后展示订单号；术语用"订单/采购订单"，**不得称"发票"**；**不得改动其他 Vendor 类型的订购流程**（前端按 vendor 类型分支，见 §4）。

**导入**：新建 `store_import_job`（kind = `CLIENT` / `TIER_PRICE`），仿厂商域 `manufacturer_catalog_import_job` 的 **prepare→commit 两阶段**（幂等、重复提交 409、逐行错误报告）。**产品导入以 `Product ID` 为主匹配键**（命中即更新、新值即建品；产品名/SKU 不得作主键，§7.2），校验重复 Product ID、类目值、**Tier A 价必填**、等级值与货币格式；客户导入承载 §7.1 字段（含执照四列透传执照模块），**缺/无效 tier → 自动分配 Tier A**。导出不在首期范围（§2.2）。

**风险控制**：① `StoreProduct.price` column_property（`core/products/models.py:191-200`）当前取「最新一条」，`product_price` 加 tier 维度后**必须补 `tier_id IS NULL` 过滤**，否则非 tier vendor 的全局价静默取到 tier 价——代码评审必查项。② `_build_calc_input`（`core/orders/services.py:379`）是发票/月结/报表共同上游，**动态调价改造反转了"提交即锁价"语义**，是全项目最高回归风险项，必须带订单→发票→月结全量回归测试。

## 2. 表结构设计

以下 DDL 逐字摘自[《开发方案-表结构设计》v2](../开发方案-表结构设计.md) §3.4（权威版本，不得改动；发现问题以「⚠️ 待确认」标注）。本模块共 **3 张新表 + 3 张表加列**（v2 增 `order.price_tier_id`），对应迁移 **M5**（`add_price_tier_and_order_tier`，含 DDL）与 **M6**（存量客户默认/Tier A 等级回填），基于 `3bdd9e1f06c8` 续写。

### 2.1 新表 `price_tier`（照抄 payment_method 范式 + store 维度 + 管理属性）

```sql
CREATE TABLE price_tier (
    id                 uuid PRIMARY KEY,
    store_id           uuid NOT NULL REFERENCES store(id) ON DELETE CASCADE,  -- vendor 维度
    name               varchar(100) NOT NULL,
    description        varchar(500),
    is_active          boolean NOT NULL DEFAULT true,
    is_default         boolean NOT NULL DEFAULT false,   -- 新客户自动落入的默认等级
    sort_order         integer NOT NULL DEFAULT 0,
    archived_at        timestamptz,                      -- 归档（区别于删除）
    created_by_user_id uuid REFERENCES "user"(id) ON DELETE SET NULL,
    created_at         timestamptz NOT NULL DEFAULT now(),
    updated_at         timestamptz NOT NULL,
    deleted_at         timestamptz
);
CREATE UNIQUE INDEX uq_price_tier_store_name ON price_tier(store_id, name)
    WHERE deleted_at IS NULL;
CREATE UNIQUE INDEX uq_price_tier_store_default ON price_tier(store_id)
    WHERE is_default AND deleted_at IS NULL;             -- 每 store 至多一个默认等级
```

**设计说明**：
- 等级集合是 **store（vendor）级统一维度**（Q2-A）；数量与命名完全自由（§7.1「A/B/C/D、Level 1-5、Gold/Silver 或任意名称」）。
- 两个 partial unique index 分别保证「同 store 等级名唯一（忽略软删行）」与「每 store 至多一个默认等级」；设新默认时服务层在同事务内先清旧默认。
- `archived_at` 归档态：不可再分配新客户、不出现在分配下拉；存量客户价格照常生效直至重分配。`is_active=false` 停用态：语义同归档但可一键恢复，用于临时下线。
- SQLAlchemy 模型放 `core/price_tiers/models.py`，继承 `APIModel`（自带 created_at/updated_at/deleted_at 约定）。

### 2.2 修改 `product_price` —— 加 tier 维度 + 审计（复用 append-only）

```sql
ALTER TABLE product_price
    ADD COLUMN tier_id            uuid REFERENCES price_tier(id) ON DELETE RESTRICT,
                                       -- NULL = 未启用 tier 的普通 vendor 全局价（向后兼容：存量行全部为 NULL）
    ADD COLUMN changed_by_user_id uuid REFERENCES "user"(id) ON DELETE SET NULL,
    ADD COLUMN import_job_id      uuid;                  -- 关联 store_import_job，手工改价为 NULL

CREATE INDEX ix_product_price_product_tier_created
    ON product_price(product_id, tier_id, created_at DESC);
```

**设计说明**：
- 现有 `product_price` 是 append-only 历史表（改价 = 插新行，当前价 = 最新一行），这正是 §7.8「价格审计历史」要的语义，因此在原表加维度而非另建价格表。tier 当前价 = 按 `(product_id, tier_id)` 取 `created_at` 最新一行（与现有查询同构）。
- **必须同步的代码点**：`StoreProduct.price` column_property（`core/products/models.py:191-200`）当前取「最新一条」，加 tier 后必须补 `tier_id IS NULL` 过滤，否则**未启用 tier 的普通 vendor 全局价**会错误地取到 tier 价——本方案唯一「不改会静默出错」的点，代码评审必查。
- `import_job_id` 无外键（表结构设计原文如此，避免跨模块硬依赖）；追溯时按值 join `store_import_job`。
- **v2 取价约束**：对启用 tier 的 liquor vendor，客户取价只走 `tier_id` 非空的行（等级价 + Tier A 回退），`tier_id IS NULL` 行不参与客户取价；**每个活跃产品必须有指向该 store 默认等级（Tier A）的价格行**，否则不可发布（§6.2 规则 4）。
- 大表加索引：`CREATE INDEX CONCURRENTLY` 或维护窗口（迁移 M5 风险项，CONCURRENTLY 需 alembic `autocommit_block()`）。

### 2.3 新表 `store_product_tier_availability`（可购性）+ ⭐ Tier A 回退取价规则

```sql
CREATE TABLE store_product_tier_availability (
    id                 uuid PRIMARY KEY,
    store_product_id   bigint NOT NULL REFERENCES store_product(id) ON DELETE CASCADE,
    tier_id            uuid   NOT NULL REFERENCES price_tier(id)    ON DELETE CASCADE,
    availability       varchar(16) NOT NULL DEFAULT 'AVAILABLE',    -- AVAILABLE / UNAVAILABLE
    updated_by_user_id uuid REFERENCES "user"(id) ON DELETE SET NULL,
    created_at         timestamptz NOT NULL DEFAULT now(),
    updated_at         timestamptz NOT NULL,
    deleted_at         timestamptz,
    CONSTRAINT uq_sptavail UNIQUE (store_product_id, tier_id)
);
```

**⭐ 取价与可购性判定规则（应用层，正式版 §6.2 四规则 + 判定表）——v2 已反转 v1"绝不回退"**：

| 客户等级（`client.price_tier_id`） | 该 (产品×客户等级) 价 | Tier A（默认等级）价 | 客户看到 / 结果 |
|---|---|---|---|
| 任意 | 该等级标记 `UNAVAILABLE` | — | **产品不可下单**（规则 1，优先级最高） |
| 例：Tier C | 已配置 | 已配置 | 用 **Tier C 价**（规则 2） |
| 例：Tier C | 缺失 | 已配置 | **回退用 Tier A 价**（规则 3，⭐ v2 新语义） |
| 任意 | 缺失 | 缺失 | **产品不能发布，也不能下单**（规则 4） |

举例（§6.2）：产品 1 配了 Tier A/B/C 价，产品 2 只配了 Tier A/B 价 → Tier C 客户查看产品 2 时，因 Tier C 价缺失而显示 **Tier A 价**。该结构允许不同产品配置不同数量的等级价，同时保持"每客户一个等级"的分配语义。

**设计说明**：
- `availability` 用 varchar + 应用层 StrEnum（不建 PG enum，规避 `ADD VALUE` 迁移痛点，表结构设计 §一-9 决策）。缺行等同 `AVAILABLE`，只需为「显式不可购」写行。
- **规则 1 的优先级高于回退**：某等级被显式标记 `UNAVAILABLE` 时，即使 Tier A 有价也不可下单（§6.2 规则 1 措辞"the product is not orderable"）。
- **发布校验（规则 4）**：产品上架/激活时校验该 store 默认等级（Tier A）是否有当前价，缺失则拒绝发布并提示补 Tier A 价；产品导入亦校验 Tier A 价必填（§7.2）。
- **隔离要求**：客户侧响应只返回最终生效价与可购状态，**不得**携带 `base_price`、他等级价、Tier A 原值或等级名称/ID（§6.3/§10.2、开放项 N-Q4）。回退发生时对客户不可见（不提示"这是 Tier A 价"）。

### 2.4 修改 `client` —— 等级分配

```sql
ALTER TABLE client ADD COLUMN price_tier_id uuid
    REFERENCES price_tier(id) ON DELETE RESTRICT;   -- RESTRICT 兜底"已分配等级不可删"（FR-D2）
CREATE INDEX ix_client_price_tier_id ON client(price_tier_id);
```

**设计说明**：应用层规则——新建/导入客户未指定或指定无效 tier 时**自动落入该 store 的 `is_default` 等级（即 Tier A）**（§6.1"When a new or imported client does not have a valid price tier, the system must automatically assign Tier A"）；「每个活跃客户必须有等级」由服务层校验（存量 client 由数据迁移 M6 统一赋默认等级，仅对启用 tier 的 store，可空跑）。**客户不得查看或更改自己的等级分配**（§6.1），客户侧无任何等级相关端点与字段。tier 分配变更**必须写审计**（`company_audit_log`，entity_type=`CLIENT_TIER`；§10.2 明确要求记录 client price-tier assignment changes）。归档/删除等级的 409 校验在服务层先行（§6.1"仍分配给客户的等级在重新分配前不得归档"），DB `RESTRICT` 仅兜底。

### 2.4b 修改 `order` —— ⭐ 动态调价随单等级快照（v2 新增）

```sql
ALTER TABLE "order" ADD COLUMN price_tier_id uuid REFERENCES price_tier(id) ON DELETE SET NULL;
    -- 提交时快照 client.price_tier_id（§6.3"订单提交时客户所处的等级必须随订单存储"）
```

**设计说明**：
- 写入时机：两条下单链路创建订单时由客户当时的 `client.price_tier_id` 快照写入；此后**更改客户等级只影响未来订单，不改变既有订单**（§6.3）。
- 读取用途：交付前动态调价重算（§3.4.5）一律按 `order.price_tier_id` + Tier A 回退取当前目录价，而**不是**按客户当前等级——保证客户换等级不会改动在途订单的计价基准。
- `ON DELETE SET NULL`：等级被硬删的极端情况下订单不被级联删除；重算逻辑遇 `price_tier_id IS NULL` 时按该 store 的 Tier A 兜底并记警告。
- 非 liquor vendor 的订单该列为 `NULL`，重算引擎跳过（普通 vendor 维持"提交即锁价"现状，零回归）。

### 2.5 新表 `store_import_job`（客户/价格导入，FR-E7）

```sql
CREATE TABLE store_import_job (
    id                   uuid PRIMARY KEY,
    store_id             uuid NOT NULL REFERENCES store(id) ON DELETE CASCADE,
    kind                 varchar(20) NOT NULL,     -- CLIENT / TIER_PRICE
    source               varchar(16) NOT NULL DEFAULT 'FILE',   -- FILE / PASTE
    file_id              uuid REFERENCES file(id) ON DELETE SET NULL,
    status               varchar(20) NOT NULL DEFAULT 'CREATED',
                         -- CREATED/PARSED/VALIDATED/COMMITTING/COMPLETED/FAILED
    column_mapping       json,
    total_rows           integer NOT NULL DEFAULT 0,
    imported_rows        integer NOT NULL DEFAULT 0,
    skipped_rows         integer NOT NULL DEFAULT 0,
    error_report         json,                     -- 逐行错误 [{row, field, error}]
    requested_by_user_id uuid NOT NULL REFERENCES "user"(id) ON DELETE RESTRICT,
    committed_at         timestamptz,
    created_at           timestamptz NOT NULL DEFAULT now(),
    updated_at           timestamptz NOT NULL,
    deleted_at           timestamptz
);
CREATE INDEX ix_store_import_job_store ON store_import_job(store_id, created_at DESC);
```

**设计说明**：
- 仿厂商域 `manufacturer_catalog_import_job`（`core/manufacturer_catalog_imports/`）的 prepare→commit 两阶段：幂等（同 job 重复 commit 返回 409）、防重复提交、逐行错误报告；不学旧 OCR webhook 直写。
- **客户导入列（§7.1）**：客户 ID/客户编码、企业名称、联系信息、企业地址、指定销售员、分配的价格等级、执照编号、执照类型、执照生效日期、执照到期日期——后四列写入执照模块的 `client_license`（表结构设计 §3.5）；执照模块未上线时这几列跳过并在 `error_report` 中以 WARNING 级提示。**规则**：价格等级为空或无效 → 分配 Tier A；**执照文件不随导入携带，必须从客户档案手动上传**（§7.1）；校验必填字段、重复客户、等级取值与日期格式；对无法导入的记录提供行级错误报告。
- **产品与等级价格导入列（§7.2）**：Product ID、产品名称、类目、品牌、计量单位、**Tier A 价格**、其他等级价格、产品状态。**`Product ID` 是主匹配标识**——命中已有产品则更新，为新值则在通过校验后建品；**产品名称或 SKU 不得作为主匹配键**。校验：重复 Product ID、类目取值、**必填的 Tier A 价格**、等级取值、数字与货币格式；等级名不匹配 → 逐行报错进 `error_report`。
- ⚠️ **待确认 N4**：`Product ID` 应为 Ocean Island 侧的产品编码（CSS 内部产品 id 是系统生成的），需为产品新增"外部产品编码"字段（vendor 内唯一）作为导入主键；最终模板与字段映射须在开发定稿前与 Ocean Island 确认（§7.1 明确要求）。
- **导出不在首期范围**（§2.2"Client or product export"），本模块不实现任何导出端点。
- 状态机：`CREATED`（已建 job）→ `PARSED`（解析出表头与行）→ `VALIDATED`（校验完成，错误报告就绪）→ `COMMITTING`（大文件经 arq worker 异步执行）→ `COMPLETED` / `FAILED`。行数 ≤ 500 时 commit 同步执行直接到 `COMPLETED`。

### 2.6 审计与迁移序列（本模块相关部分）

- **审计范围（v2 收窄）**：§10.2 明确要求落库的只有**客户价格等级分配变更**——写 `company_audit_log`，应用层 `AuditEntityTypeEnum` 追加 `CLIENT_TIER`，`AuditActionEnum` 追加 `TIER_ASSIGNED`（表结构设计 §3.5.5；`details` 列放宽为 text 属迁移 M11，跨模块共用）。
- ⚠️ **v2 移出首期**：**产品价格变更历史 / 定价审计日志界面**（§2.2"Price-change history or a pricing audit-log interface"）——因此**不做** `PRICE_TIER`/`TIER_PRICE` 审计实体、不做审计查询端点与前端审计页。`product_price` 的 append-only 行 + `changed_by_user_id`/`import_job_id` 仍保留（改价天然可追溯，供未来二期开界面时零成本启用），但首期不对外暴露查询界面。
- 迁移排期（表结构设计 §四）：**M5** `add_price_tier_and_order_tier`（本节全部 DDL，**含 `order.price_tier_id`**；风险中：product_price 大表索引用 `CONCURRENTLY`）→ **M6** `backfill_default_tier_for_existing_clients`（数据迁移，低风险，可空跑）。M5/M6 全部向后兼容，老代码可与新 schema 共存，支持先 `alembic upgrade` 再滚动发版。

### 3.4 客户侧读价与下单（改造接口）

#### 3.4.1 R1 改造 POST `/vendors/{vendor_id}/products`（产品列表）

- **行为变化**（对请求方身份分流，服务层依据 `user_id → restaurant → client(store_id=vendor_id)` 解析）：

| 请求方 | price 字段 | 新增字段 | 过滤 |
|--------|-----------|----------|------|
| vendor 自家成员 | 未启用 tier：全局价（`tier_id IS NULL` 最新行，现状不变）；启用 tier：可按 query 指定等级预览 | `purchase_status` 恒 `"AVAILABLE"` | 无变化 |
| 该 vendor 的餐厅客户 | **该客户等级当前价；缺则回退该 store 的 Tier A（默认等级）价**（§6.2 规则 2/3） | `purchase_status`: `AVAILABLE` / `UNAVAILABLE` / `PRICE_NOT_CONFIGURED` | 该等级显式 `UNAVAILABLE` → 不可购（规则 1）；连 Tier A 都缺价 → 产品不可发布，不返回（规则 4） |

- **客户视角响应体节选**（items 内单品）：

```json
{
  "id": 1024,
  "name_en": "Moutai Flying Fairy 53% 500ml",
  "unit": "BOTTLE",
  "price": 95.00,
  "purchase_status": "AVAILABLE"
}
```

  **v2 取价语义**：`price` 是"该客户等级价，缺则 Tier A 价"的**最终生效价**，客户无从判断是否发生了回退（回退对客户透明）。`purchase_status="UNAVAILABLE"` 表示该等级被显式标记不可购（规则 1）；`PRICE_NOT_CONFIGURED` 在 v2 下**仅**出现于"该等级与 Tier A 均缺价"的异常态——正常流程中此类产品已被发布校验拦在上架之前（规则 4），前端仍保留该分支作为防御性提示且禁用加购。
- **硬性约束（§6.3 / §10.2）**：客户视角响应**不携带** `base_price`、不携带其他等级价格、不携带 Tier A 原值、不携带 tier 名称/ID。
- **性能**：列表取价从 column_property 单价改为"按客户等级取价 + Tier A 回退"的相关子查询/JOIN lateral（`COALESCE(tier_price, tier_a_price)` 形态），必须走 `ix_product_price_product_tier_created`；验收 AC-13（5 等级×5,000 产品 P95 ≤ 改造前基线 120%）。

#### 3.4.2 R2 改造 GET `/vendors/{vendor_id}/products/{vendor_product_id}`（产品详情）

同 R1 分流规则，单品详情增加 `purchase_status`；客户请求 `UNAVAILABLE` 产品返回 404（等同不存在，避免探测）。⚠️ 待确认：返回 404 还是带标记的 200（影响前端直链场景文案）。

#### 3.4.3 R3/R4 改造下单链路（餐厅端 / 供应商代下）

- **位置**：`POST /restaurants/{restaurant_id}/orders`（`add_restaurant_order` → `RestaurantsOrdersService`）与 `POST /vendors/{vendor_id}/orders`（`create_order` → `StoresOrdersService`），两者共享 `OrdersService` 底座；落价快照点 `core/stores/orders/services.py:217` → `create_order_products_price_history`（`core/orders/services.py:1636`）。
- **行为变化**：
  1. 逐行取价源改为「该 client 等级当前价，缺则该 store 的 Tier A 价」（vendor 未启用 tier——即无任何 price_tier 行——时维持全局价，普通供应商零影响）；
  2. **写入 `order.price_tier_id = client.price_tier_id` 快照**（§6.3"订单提交时客户所处的等级必须随订单存储"），供后续动态调价重算使用；
  3. 校验：该等级 `availability=UNAVAILABLE` → 400 `{"type": "PRODUCT_UNAVAILABLE_FOR_TIER"}`；该等级与 Tier A 均缺价 → 400 `ErrorOut {"type": "TIER_PRICE_NOT_CONFIGURED", "message": "..."}`（服务端强制，不依赖前端拦截；正常流程下已被发布校验前置拦截）；
  4. `OrderProduct.price` 快照与 `order_product_price_history` 机制保留，但**语义由"提交即终价"变为"当前生效价，未达 Delivered 时会被重算刷新"**（§8.2）——重算即向 `order_product_price_history` 追加新行，保留完整改价轨迹，到 `Delivered` 后不再变动；
  5. `_build_calc_input`（`core/orders/services.py:391-396`）的兜底分支：改为「按 `order.price_tier_id` 当前价 + Tier A 回退」，取不到则 `Decimal('0.00')` 并打 ERROR 日志（防御分支）。
- **请求/响应体**：结构不变（`RestaurantOrderIn` / `VendorOrderIn` → `RestaurantOrderOut` / `OrderIDOut`），仅新增上述两个 400 错误类型。
- **订购流程（§8.1）**：本接口即"提交订单"步骤——**在用户完成最终提交之前不得创建或传输订单**（前端订单审核步骤纯本地态，见 §4.3）；成功响应须含订单号供确认页展示；术语一律"订单/采购订单"，禁用"发票"。

#### 3.4.4 R5 改造 POST `/restaurants/{restaurant_id}/vendors/{vendor_id}/products/price-history`

价格历史（前端 `api/vendors.ts:75` 调用，NewOrder 页展示）改为只查该客户**当前生效价来源**的行——客户等级有价时查该 `tier_id`，回退态则查 Tier A 的 `tier_id`；客户无 tier 或 vendor 未启用 tier 时维持现状（全局价历史）。响应结构不变，杜绝他等级价泄露。

#### 3.4.5 ⭐ R6 交付前动态调价与锁价（v2 新增，§8.2）

**规则**：目录价变更必须更新处于活跃状态的 liquor vendor 订单，**直至订单到达 `Delivered`**；适用于「已提交未确认」「已确认未交付」「其他任何未达 Delivered 的活跃订单」三类。到 `Delivered` 即价格锁定，此后目录价变更不得修改该订单与最终发票，已交付订单/发票保留**交付时记录的最终价格**。

**重算的七项动作（§8.2 逐条实现）**：
1. 更新活跃订单上对应的产品价格（`order_product.price` ← 新生效价，并追加 `order_product_price_history` 行）；
2. 重新计算受影响的行项目小计；
3. 重新计算小计；
4. 重新计算订单总额及其他依赖价格的金额（税/折扣等经 `_build_calc_input` 统一重算）；
5. **使用随订单存储的客户等级**（`order.price_tier_id`，而非客户当前等级）；
6. 所分配等级价缺失时**应用 Tier A 回退规则**；
7. 交付前向客户展示更新后的价格与订单总额。

**触发方式（三选一，建议 A）**：

| 方案 | 机制 | 优点 | 缺点 |
|------|------|------|------|
| **A（建议）改价即扇出** | 写价接口（#11/#13）与价格导入 commit 成功后，在同事务外按 `(store_id, product_id)` 查出受影响的未达 Delivered 订单并逐单重算（大批量转 arq 异步任务） | 客户任何时候读到的都是已定稿金额；发票/月结上游无需改读逻辑 | 改价高峰有写放大；需幂等与并发保护 |
| B 读时惰性重算 | 订单详情/列表读取时若发现目录价已变则即时重算并落库 | 无写放大 | 读路径变重；未被读到的订单金额滞后，报表口径不一致 |
| C 事件驱动 | 改价发领域事件 → worker 消费重算 | 解耦、可重放 | 需新事件通道，最终一致性窗口 |

**方案 A 实现要点**：
- 幂等与并发：按 `order_id` 加行级锁（`SELECT ... FOR UPDATE`）后重算；同一订单并发重算串行化；重算结果与当前值相同时不写历史行（避免噪声）。
- 范围过滤：仅 `order.price_tier_id IS NOT NULL`（即 liquor vendor 订单）且状态未达 `Delivered` 且未软删；**普通 vendor 订单一律跳过**（零回归硬约束）。
- 按行锁价（部分交付）：已交付行不参与重算（依赖 N2 的行级交付标记），未交付行继续随价；与 License Hold 的行级处理保持一致（模块 05 §9.7）。
- 通知：§10.1 明确价格变更**不单独通知**，重算仅在客户查看订单时体现。
- 审计：重算写 `order_product_price_history`（含来源标记 `REPRICED_BY_CATALOG`）即可满足追溯；不做定价审计界面（§2.2）。

**⚠️ 开放项（未确认前不进入开发）**：
- **N1**：重算后是否需要客户重新确认订单？本方案按"**无需重新确认**，仅在客户查看时展示更新后价格"实现（§8.2 措辞"Display the updated price and order total to the client before delivery"）。若客户要求"需重新确认"，则需增加订单"待客户确认新价"标记与相应流程。
- **N1**：交付前已生成的发票是否随目录价变动？本方案按"**发票在 `Delivered` 后才终审/定格**，交付前视为草稿金额"实现。
- **N2**：`Delivered` 在 CSS 订单状态机中的确切映射与**行级交付标记**是否存在（若无需新增）。

**最高回归风险**：本节改造使 `_build_calc_input` 的取价来源与时机双双变化，是发票/月结/报表的共同上游。**必须**带订单→发票→月结全链路金额回归（见 §6.4）。

  - 部分交付：已交付行金额锁定、未交付行随价变动（依赖 N2 行级交付标记）；
  - **普通 vendor（未启用 tier）订单在任何改价下金额都不变**——维持"提交即锁价"现状，零回归。
- **下单快照链路**：tier 价下单 → `OrderProduct.price`/`order_product_price_history` 快照正确 + `order.price_tier_id` 写入正确；不可购/无 Tier A 价提交 400 且错误 type 正确；vendor 未启用 tier 的存量店铺全流程行为与改造前完全一致。
- **导入全流程**：upload→mapping→validate→commit 状态机逐步断言；重复 commit 409；未 validate 直接 commit 409；>500 行走 arq 异步（mock worker）状态 COMMITTING→COMPLETED；**产品导入按 Product ID 命中更新/新建**；客户导入缺 tier 落 Tier A + CLIENT_TIER 审计落库。
- **权限矩阵**：`view__/create__/edit__/delete__price_tier` 四权限 × 各角色（CEO/CFO/Manager/Salesman/Compliance Manager）对 19 个新接口的允许/拒绝矩阵抽样。

### 6.3 E2E（Playwright，关键用户流）

1. vendor CEO：建 4 个等级（A/B/C/D，A 为默认）→ 产品页配等级价 → 客户档案分配 Tier C → 以该客户身份登录 → 列表/详情见 Tier C 价 → 四步流下单（选品→审核→提交→确认）→ vendor 确认订单价格一致。
2. **Tier A 回退链路**：产品只配 Tier A/B 价 → Tier C 客户登录看到 **Tier A 价**（无任何"回退"提示）→ 正常加购下单成功（中英双语各跑一遍）。
3. **⭐ 交付前动态调价**：客户下单（未确认）→ vendor 改目录价 → 客户刷新订单看到**新价与新总额** → vendor 确认 → 再改价 → 金额再次更新 → 标记 **Delivered** → 再改价 → 订单与发票金额**保持交付时价格不变**。
4. 不可购链路：产品对客户所在等级标 `UNAVAILABLE` → 客户端不可加购 → 直接调接口提交被 400 → 页面按 type 显示文案。
5. 批量导入：上传 200 行价格文件（含错行、含缺 Tier A 价行）→ 映射 → 校验错误报告可见 → commit → 矩阵页价格生效、错误行可下载；同文件重复 commit 提示已提交。
6. 防误删/防归档：归档或删除有客户的等级 → 409 弹窗 → 批量重分配客户 → 操作成功。
7. 权限：以 Salesman（未授权 tier 权限）登录 → Sidebar 无入口、直达 `/price-tiers` 显示 NotFound（AllowedTo no 分支）。

### 6.4 回归与性能

- **订单-发票回归（最高风险，v2 加严）**：`_build_calc_input` 是发票/月结/报表共同上游，且 v2 **反转了"提交即锁价"语义**。B7 与 **B11 合入前**各跑一次全量订单-发票测试套件 + 对 preprod 快照数据抽样比对改造前后订单总额；**普通 vendor 订单必须金额零差异**（零回归门禁），liquor vendor 订单按新语义断言（未达 Delivered 随价、Delivered 后锁定）。
- **性能**：5 等级 × 5,000 产品 × 500 客户数据集下，R1 列表 P95 ≤ 改造前 120%（AC-13）；`EXPLAIN` 确认"客户等级价 + Tier A 回退"取价（COALESCE/LATERAL 形态）命中 `ix_product_price_product_tier_created`；#12 分页查询无 N+1。**重算扇出性能**：单次改价影响 N 张未达 Delivered 订单时的耗时与锁竞争（大批量转 arq 的阈值需实测定）。
- **迁移演练**：在 preprod dump 副本上跑 M5（含 `order.price_tier_id` 与 CONCURRENTLY 索引）+ M6，验证向后兼容（老镜像 + 新 schema 冒烟）与 downgrade。
- **前端**：新增代码先清障相关 tsc 类型错误（现存 16 个，构建走 `Dockerfile.novalidate` 的已知债务），至少保证本模块文件零新增错误；视觉回归覆盖矩阵页 320/768/1440 断点。
