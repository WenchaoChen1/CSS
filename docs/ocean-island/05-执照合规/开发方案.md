## 1. 方案概述

**技术路线**：按项目分层规范新建 `internal/core/licenses/` 领域五件套（`domains.py`/`dto.py`/`models.py`/`repositories.py`/`services.py`/`errors.py` + `transport/di.py`），承载执照档案（`client_license`，挂 `restaurant_id`，1:N 多执照）、文件（`client_license_document`，复用 `file` 表）、8 态状态机（varchar + 应用层 StrEnum，规避 PG enum 迁移痛点）、提醒规则/防重发日志、订单合规审查与 Override 六个子域。HTTP 层拆两侧：vendor 侧新增 `internal/main_app/vendor/licenses/`（路由前缀 `/vendors/{vendor_id}/...`，仿 `vendor/clients/transport/handlers.py` 的 `Security(check_access_token)` + `check_permissions(required_permissions=[...], required_roles=[...])` 写法）；餐厅侧在 `internal/main_app/restaurants/` 下新增自助执照端点（前缀 `/restaurants/{restaurant_id}/...`）。权限落 RBAC 四表种子：新 `api_entity` 行 `customer_license`/`license_review`/`compliance_override`（见表结构设计 §3.1，属实体权限模块 M2 迁移）。

**到期与提醒**：`EXPIRING_SOON`/`EXPIRED` 不在读路径现算，由 arq 每日 cron（照抄 `internal/worker/app.py:108` `cron_jobs` + `internal/main_app/clients/tasks.py:87` `check_unregistered_clients` 范式）从 `expiration_date` 派生写回，同一任务按 `license_reminder_rule` 档位（默认 60/30/14/7/1/0）触发三通道通知——站内（`internal/notifications/` RabbitMQ+WS）、邮件（`internal/core/emails/producers.py` Kafka→SMTP）、短信（`internal/core/phone/producers.py` Kafka→Twilio），以 `license_reminder_log` 唯一约束防重发。收件人 = 执照合规联系人 + 按 `notification_event_preference`（新表）解析出的 vendor 合规用户。

**订单阻断**：四个校验时点中，「打开订购流程」「加购」两个时点由前端调用新增的**只读合规状态接口**实现（购物车为纯前端表单态）；「提交订单」在 `internal/core/orders/services.py:756` `OrdersService.create_order` 头部插入合规校验（该服务是餐厅端 POST `/restaurants/{restaurant_id}/orders` 与识别单据建单两条链路的共享底座）；「vendor 确认」在 `internal/core/stores/orders/services.py:141` `confirm_vendor_order` 插入（仿其现有 `check_order_status_for_confirm` 前置校验模式）。阻断返回新错误类型（仿 `internal/core/orders/errors.py` 的 StrEnum + ErrorFactory + `translation_key` 三件套，前端按 key 映射中英文案），同时落 `order_history` 新事件、写审计、发通知。校验采用 **fail-closed**（FR-I3）：合规数据读取失败时拒绝下单而非放行。Override（`license_restriction_override`）在校验处放行并全程审计。已提交订单遇过期由每日扫描落 `order_compliance_review`（仿 OrderClaim 范式，不动 `orderstatus` 枚举），人工处置。

**横切与前置**：审计不建新表，扩展 `company_audit_log`（`internal/core/companies/domains.py` 的 `AuditEntityTypeEnum`/`AuditActionEnum` 加值 + `details` 放宽为 text 存结构化前值/后值 JSON），写入复用 `internal/core/master_database/services.py` 的 `create_audit_log*` 范式；仪表盘为聚合查询 + 导出（导出路径风格仿 `main_app/reports` 的 `.../export`）。**硬前置 FR-E0**：`config/s3_settings.py:27` 现为 `default_acl='public-read'`，执照文件必须走私有前缀（`licenses/`）+ 预签名 URL 下载，属阶段 0 独立工作包（开发计划 0.2），本模块所有文件接口按"private + 预签名"设计。

### 2.1 `client_license`（核心档案 + 状态机，FR-E1/E3/E10）

```sql
CREATE TABLE client_license (
    id                    uuid PRIMARY KEY,
    restaurant_id         uuid NOT NULL REFERENCES restaurant(id) ON DELETE CASCADE,
    license_holder_name   varchar(255),               -- 执照持有人法定名称
    business_name         varchar(255),
    license_number        varchar(100) NOT NULL,
    license_type          varchar(100) NOT NULL,      -- 可配置字典（varchar，不用 PG enum）
    issuing_authority     varchar(255),
    issuing_region        varchar(64),                -- 州/司法辖区（varchar 以兼容非美辖区）
    effective_date        date,
    expiration_date       date,                       -- 审核通过前允许为空
    status                varchar(32) NOT NULL DEFAULT 'NOT_SUBMITTED',
        -- NOT_SUBMITTED / PENDING_REVIEW / VERIFIED / EXPIRING_SOON /
        -- EXPIRED / REJECTED / SUSPENDED / MANUAL_REVIEW_REQUIRED   （8 态，应用层 StrEnum）
    verified_at           timestamptz,
    verified_by_user_id   uuid REFERENCES "user"(id) ON DELETE SET NULL,
    review_notes          text,                       -- 驳回/复核内部备注（客户不可见）
    compliance_contact_name  varchar(255),
    compliance_contact_email varchar(255),
    compliance_contact_phone varchar(50),
    created_by_user_id    uuid REFERENCES "user"(id) ON DELETE SET NULL,
    created_at            timestamptz NOT NULL DEFAULT now(),
    updated_at            timestamptz NOT NULL,
    deleted_at            timestamptz
);
CREATE INDEX ix_client_license_restaurant ON client_license(restaurant_id) WHERE deleted_at IS NULL;
CREATE INDEX ix_client_license_status     ON client_license(status) WHERE deleted_at IS NULL;
CREATE INDEX ix_client_license_expiration ON client_license(expiration_date)
    WHERE status IN ('VERIFIED','EXPIRING_SOON') AND deleted_at IS NULL;   -- 到期扫描专用
```

**设计说明**：
- 挂 `restaurant_id`（餐厅主体，确认单 Q5 建议 A）：一家餐厅一套执照，对多个 vendor 复用；若 Q5 客户选 B（含 vendor 自身执照），按表结构设计文档 §六改多态挂载（restaurant_id/store_id XOR）。
- **1:N**：一餐厅可持多张执照（多州/多类型，FR-E10）。首期"下单需哪张执照有效"规则：**任一 `VERIFIED`（含未过期的 `EXPIRING_SOON`）即可**，规则留应用层可配置点。
- 状态机（应用层 `LicenseStatus` StrEnum）合法流转：`NOT_SUBMITTED → PENDING_REVIEW`（提交送审）；`PENDING_REVIEW → VERIFIED | REJECTED | MANUAL_REVIEW_REQUIRED`（审核）；`MANUAL_REVIEW_REQUIRED → VERIFIED | REJECTED`；`REJECTED → PENDING_REVIEW`（重新提交）；`VERIFIED → EXPIRING_SOON → EXPIRED`（cron 派生）；`VERIFIED | EXPIRING_SOON → SUSPENDED`（吊扣）与 `SUSPENDED → VERIFIED`（恢复=重新 approve）；`EXPIRED → PENDING_REVIEW`（换证重审）。approve 前 `expiration_date` 必填（否则 422）。
- `review_notes` 仅 vendor 侧接口返回，餐厅侧响应模型不含此字段（FR-I2）。
- ⚠️ 待确认：`updated_at` 无 DEFAULT（与库内多数表一致，由 ORM 维护），实现时沿用项目 `APIModel` 基类即可，非问题，仅提示勿手写 DDL 直插。

### 2.3 `license_reminder_rule` + `license_reminder_log`（提醒配置与防重发，FR-E5）

```sql
CREATE TABLE license_reminder_rule (
    id          uuid PRIMARY KEY,
    store_id    uuid NOT NULL REFERENCES store(id) ON DELETE CASCADE,
    days_before integer NOT NULL,                  -- 60/30/14/7/1/0（种子默认 6 档，可增删）
    is_on       boolean NOT NULL DEFAULT true,
    created_at  timestamptz NOT NULL DEFAULT now(),
    updated_at  timestamptz NOT NULL,
    deleted_at  timestamptz,
    CONSTRAINT uq_lrr UNIQUE (store_id, days_before)
);

CREATE TABLE license_reminder_log (
    id          uuid PRIMARY KEY,
    license_id  uuid NOT NULL REFERENCES client_license(id) ON DELETE CASCADE,
    days_before integer NOT NULL,
    expiration_date date NOT NULL,   -- 快照：换证改期后同档位可重新提醒
    channel     varchar(16) NOT NULL,             -- IN_APP / EMAIL / SMS
    sent_at     timestamptz NOT NULL DEFAULT now(),
    CONSTRAINT uq_lrl UNIQUE (license_id, expiration_date, days_before, channel)
);
```

**设计说明**：规则挂 **store（vendor）维度**，Ocean Island 与未来其他酒类 vendor 各自配置；M7 迁移为启用合规的 store 种入默认 6 档。每日 cron 流程：扫 `ix_client_license_expiration` → 计算距到期天数命中启用档位 → 查 `uq_lrl` 无记录才发 → 三通道分发 → 落 log。`expiration_date` 入唯一键保证换证改期后同档位可重新提醒。执照挂 restaurant 而规则挂 store：扫描时经 `client` 表（restaurant×store 关联）联出对应 vendor 的档位与收件人。

- 所有路由挂 `/api` 网关（X-API-KEY 守卫）之下；鉴权 `Security(check_access_token)`（Bearer access token）；权限 `Depends(check_permissions(required_permissions=[...], required_roles=[...]))`，与 `internal/main_app/vendor/clients/transport/handlers.py:91` 现行写法一致。路径参数为 snake_case（`{vendor_id}`），与现有 handlers 一致。

### 3.3 组②：审核工作流

四个动作端点共享状态机校验：非法流转一律 409 `license_invalid_status_transition`，成功后统一写审计 + 触发对应通知事件 + 记录 `verified_at`/`verified_by_user_id`（approve）——满足 §8.5 全部动作。

#### 3.3.1 POST `.../licenses/{license_id}/approve` — 批准

- **用途**：`PENDING_REVIEW`/`MANUAL_REVIEW_REQUIRED`/`SUSPENDED` → `VERIFIED`，记录核验人与核验时间，触发 `LICENSE_APPROVED` 通知。
- **请求体**：`{"notes": "与扫描件比对一致"}`（可选，追加进 `review_notes`）。
- **响应 200**：`{"success": true}`。
- **错误**：409 `license_invalid_status_transition`（当前态不允许）；422 `license_expiration_date_required`（无到期日不得批准）；403（无 `edit__license_review` 或角色不符）；404。

#### 3.3.2 POST `.../licenses/{license_id}/reject` — 驳回

- **用途**：`PENDING_REVIEW`/`MANUAL_REVIEW_REQUIRED` → `REJECTED`，驳回原因必填，触发 `LICENSE_REJECTED` 通知（含客户可见原因）。
- **请求体**：`{"reason": "上传件与录入的执照编号不一致", "notes": "内部备注：疑似旧证"}`（`reason` 必填、客户可见；`notes` 内部）。
- **响应 200**：`{"success": true}`。**错误**：409/403/404/422（reason 缺失）。

#### 3.3.3 POST `.../licenses/{license_id}/request-update` — 要求更新

- **用途**：要求客户补充/修正信息（状态回可编辑态），触发 `LICENSE_UPDATE_REQUESTED` 通知并附说明。
- **请求体**：`{"message": "请补充到期日期并上传新版扫描件"}`（必填，客户可见）。
- **响应 200**：`{"success": true}`。**错误**：409/403/404/422。

#### 3.3.4 POST `.../licenses/{license_id}/suspend` — 吊扣

- **用途**：`VERIFIED`/`EXPIRING_SOON` → `SUSPENDED`（获知官方吊扣时人工标记），立即使该客户酒类下单被阻断。
- **请求体**：`{"reason": "州执照局通报吊扣"}`（必填）。
- **响应 200**：`{"success": true}`。**错误**：409/403/404。恢复走 approve（§2.1 状态机）。

#### 3.3.5 GET `/vendors/{vendor_id}/licenses` — 跨客户执照总览/审核队列

- **用途**：一个接口同时服务"待审核队列"与"全部即将到期执照"（验收 §8.11 第 10 条）。
- **请求**：查询 `status?: LicenseStatus`、`expiring_within_days?: int`、`search?: str`（客户名/执照号）、`limit/offset`、`sort?: expiration_date|updated_at`。
- **响应 200**：`PaginatedListResponse`，items 在 §3.2.1 摘要字段基础上外加：

```json
{
  "client_id": 1024,
  "restaurant_name": "Golden Dragon Restaurant",
  "days_to_expiration": 21
}
```

- **错误**：403。

- **用途**：人工处置审查项——继续履约 / 取消订单 / 走覆盖，处置人、结论与备注落库并审计（绝不自动取消，Q6 建议方案）。

## 6. 测试要点

> 项目规则：TDD、新增领域单元+集成覆盖 ≥80%；后端 `make dev_test k=<name>` 增量、合入前 `make test` + `make lint`。测试目录随 handlers 放 `internal/main_app/vendor/licenses/tests/` 等（仿 `vendor/clients/tests/`）。

### 6.1 单元测试（core/licenses）

- **状态机**：8 态全矩阵合法/非法流转（如 `VERIFIED→VERIFIED` 拒绝、`REJECTED→PENDING_REVIEW` 允许、approve 无 `expiration_date` 拒绝）；`EXPIRING_SOON` 判定的窗口边界（到期日 = 今日、今日+60、今日+61）。
- **提醒计算**：档位命中（60/30/14/7/1/0）；`license_reminder_log` 幂等（同键第二次不发）；换证改期后（`expiration_date` 变化）同档位可重发；`is_on=false` 档位不发。
- **合规判定**：多执照场景（一张 EXPIRED + 一张 VERIFIED → 放行）；Override 生效边界（`expires_at` 已过 / `order_id` 不匹配 → 不放行）；未启用合规的 vendor 恒放行。
- **审计**：PATCH 逐字段 diff 生成 `{"field","old","new"}`；敏感动作全部产出审计条目。

### 6.2 集成测试（API + DB）

- **CRUD/文件**：创建→详情→PATCH→软删全链路；上传 21MB → 413；伪造扩展名 exe → 422；`download-url` 返回可用预签名 URL 且过期后 403（S3 侧）。
- **权限/越权（FR-I2，安全用例）**：无 `view__customer_license` 用户 GET → 403；vendor X 访问 vendor Y 客户执照 → 403；餐厅 A 用户访问餐厅 B 执照 → 403；**餐厅侧响应断言不含 `review_notes` 字段**；approve 用非 CEO/CFO（无 required_roles）→ 403；Override 用无 `create__compliance_override` 用户 → 403。
- **订单阻断（四时点）**：8 种执照状态 × POST `/restaurants/{restaurant_id}/orders` 期望矩阵（仅 VERIFIED/未过期 EXPIRING_SOON 放行）；confirm 端点同矩阵；阻断响应 `type` 与 `translation_key` 断言；阻断触发通知与审计断言；Override 后同一请求放行且落 `COMPLIANCE_OVERRIDDEN`；合规查询抛异常时下单返回 `compliance_check_unavailable` 而非成功（fail-closed）。
- **cron 任务**：构造到期数据跑任务两遍——状态派生正确、第二遍零新增通知（幂等）；跨 vendor 隔离（A 的档位不影响 B）。
- **仪表盘/导出**：9 项统计与种子数据核对；6 维筛选组合；CSV/Excel 内容与筛选结果一致、中文不乱码（UTF-8 BOM）。
- **回归（关键）**：非酒类 vendor 全量下单→确认→发票链路不受执照校验波及（合规开关关闭路径）；现有 `/restaurants/{restaurant_id}/orders` 既有测试全绿。

### 6.3 E2E（Playwright，对齐 web 测试规则）

- **主流程 1（阻断-恢复闭环）**：餐厅用户（中文界面）下单被阻→看到 §8.8 中文文案与「上传执照」引导→自助上传提交→vendor 审核通过→恢复下单成功。
- **主流程 2（审核工作流）**：vendor 在 Client License tab 查看文件与字段比对→reject（原因）→餐厅收到站内通知→修改重提→approve。
- **主流程 3（仪表盘）**：筛选"30 天内到期"→列表与统计一致→导出下载成功。
- 断点 320/768/1440 截屏验证 License tab 与阻断横幅中文排版不溢出；键盘可达性（审核动作弹窗焦点管理）。

### 6.4 性能与可靠性

- 产品列表/下单路径上合规查询的额外耗时 <50ms（走 `ix_client_license_expiration`/状态索引，需求 §12.1）；到期扫描在预期客户量（数千执照）下单次执行 <1min。
