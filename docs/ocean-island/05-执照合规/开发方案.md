> 🔴 **v2 修订摘要（2026-07-27 正式版需求，相较 v1 草稿的范围与建模变化）**
> 1. **两套独立状态（§9.2）**：`client_license` 由 v1 的单一 8 态 `status` 拆为 **`verification_status`**（NOT_SUBMITTED / PENDING_REVIEW / VERIFIED / REJECTED，由工作流或审核人更新）+ **`expiration_status`**（ACTIVE / EXPIRING_SOON / EXPIRED / NOT_AVAILABLE，由到期日自动计算、**用户不得手改**）两列；两者正交，可同时 `VERIFIED` + `EXPIRING_SOON`。Expiring Soon 天数可配置，**建议默认 7 天**。
> 2. **移出首期（§2.2，本文已删除相关章节）**：**合规仪表盘（9 项统计 / 6 维筛选）与 CSV/Excel 导出**、**管理员越权解除执照限制（override）**——连带删除 `license_restriction_override` 表、`compliance_override` 权限实体、`orderevent` 的 `COMPLIANCE_OVERRIDDEN` 值、Override 端点与前端弹窗；OCR 自动批准执照亦明确出局（§2.2/§9.4，人工核验）。
> 3. **通知收敛为仅 6 类执照事件（§10.1）**：新执照/替换执照上传待审、批准、驳回、要求更新信息、即将到期、已过期。**产品价格变更 / 客户等级变更 / 被阻断的订购尝试均不需要单独通知**；导入错误只体现在导入结果中。
> 4. **License Hold（§9.7）= 合规标记，不新增订单状态**：已提交订单遇执照过期**不得自动取消**，将**未交付部分**（`order_compliance_review.order_product_id` 支持**行级**）置于 Hold；已交付条目保持完成不变；续期核验通过后解除并允许订单继续；执照过期**不得阻止**退货 / 冲抵 / 退款。
> 5. **提醒按 vendor 时区（§9.5）**：新增 `company.timezone` 与 `license_reminder_setting`（是否启用、提醒间隔、发送时间、是否到期日当天发、启用通道）。
> 6. **恶意软件扫描属首期要求**（§9.3，不得降级为二期；实现方式见开放项 N8）；续期**另存为新记录**而非覆盖、留存历史、标准 UI **不提供永久删除**。

## 1. 方案概述

**技术路线**：按项目分层规范新建 `internal/core/licenses/` 领域五件套（`domains.py`/`dto.py`/`models.py`/`repositories.py`/`services.py`/`errors.py` + `transport/di.py`），承载执照档案（`client_license`，挂 `restaurant_id`，1:N 多执照）、文件（`client_license_document`，复用 `file` 表）、**两套独立状态**（varchar + 应用层 StrEnum，规避 PG enum 迁移痛点）、提醒规则/设置/防重发日志、订单合规审查（License Hold）五个子域。HTTP 层拆两侧：vendor 侧新增 `internal/main_app/vendor/licenses/`（路由前缀 `/vendors/{vendor_id}/...`，仿 `vendor/clients/transport/handlers.py` 的 `Security(check_access_token)` + `check_permissions(...)` 写法）；餐厅侧在 `internal/main_app/restaurants/` 下新增自助执照端点。权限落 RBAC 四表种子：新 `api_entity` 行 `customer_license`/`license_review`（表结构设计 §3.1 迁移 M2；**v2 不再种 `compliance_override`**）。

**两套状态与到期派生（§9.2）**：`verification_status` 由上传/审核工作流驱动——上传新执照或替换执照 → `PENDING_REVIEW`；获授权用户可 verify / reject / request-update。`expiration_status` **不在读路径现算**，由 arq 每日 cron（照抄 `internal/worker/app.py:108` `cron_jobs` + `internal/main_app/clients/tasks.py:87` `check_unregistered_clients` 范式）从 `expiration_date` 派生写回（`ACTIVE` / `EXPIRING_SOON` / `EXPIRED`；无到期日为 `NOT_AVAILABLE`），**用户不得手动编辑**。Expiring Soon 阈值可配（默认 7 天）。

**到期提醒（§9.5）**：同一 cron 按 `license_reminder_setting`（总开关 / 发送时间 / 是否到期日当天发 / 通道）与 `license_reminder_rule` 档位（默认 60/30/14/7/1/0）触发三通道通知——站内（`internal/notifications/` RabbitMQ+WS）、邮件（`internal/core/emails/producers.py` Kafka→SMTP）、短信（`internal/core/phone/producers.py` Kafka→Twilio），**按该 vendor 配置的时区（`company.timezone`）计算发送时刻**，以 `license_reminder_log` 唯一约束防重发（续期/替换后重算提醒计划、同档位可因新到期日重新提醒）。收件人 = 客户档案中配置的通知联系人 + 指定的 Ocean Island 管理员/审核人（按 `notification_event_preference` 解析）。

**订购资格与阻断（§9.6）**：客户可下单的条件是**至少一张执照同时满足 `verification_status = VERIFIED` 且 `expiration_status ∈ {ACTIVE, EXPIRING_SOON}`**。`EXPIRING_SOON` 时显示可见警告 + 到期日/剩余天数 + 请求更新执照，但**继续允许浏览与下单**。无有效已核验执照时（Not Submitted / 无其他有效执照的 Pending Review / Rejected / Expired）**阻断**：禁用加入订单、禁用结算、禁用最终提交，并说明原因与指引（推荐文案见译文 §9.6）。四个校验时点中，「打开订购流程」「加购」由前端调用新增的**只读合规状态接口**实现（购物车为纯前端表单态）；「提交订单」在 `internal/core/orders/services.py:756` `OrdersService.create_order` 头部插入；「vendor 确认」在 `internal/core/stores/orders/services.py:141` `confirm_vendor_order` 插入（仿现有 `check_order_status_for_confirm` 模式）。阻断返回新错误类型（仿 `internal/core/orders/errors.py` 的 StrEnum + ErrorFactory + `translation_key` 三件套，前端按 key 映射中英文案），落 `order_history` 新事件并写审计。校验 **fail-closed**（§11 可靠性）：合规数据读取失败时拒绝下单而非放行。**替换执照处于 Pending Review 而既有已核验执照仍有效时，客户可继续凭既有执照订购**。**执照限制仅适用于 Liquor Vendor 订购**——非酒类 vendor 的合规接口恒返回放行，链路零影响。

**License Hold（§9.7）**：执照在提交后、完全交付前过期时，由每日扫描（或状态变更钩子）对该客户未交付部分落 `order_compliance_review`（**合规标记，不动 `orderstatus` 枚举**；支持 `order_product_id` 行级）。Hold 期间：订单对客户与 vendor 均可见、展示保留原因、阻止未交付条目的确认/发货/交付、请客户提供更新执照、通知相应 Ocean Island 用户。续期核验通过后解除 Hold、订单继续。已交付条目保持完成不变；已完全交付订单不受后续过期影响；**退货 / 冲抵 / 退款不受执照过期限制**。

**横切与前置**：审计不建新表，扩展 `company_audit_log`（`AuditEntityTypeEnum`/`AuditActionEnum` 加值 + `details` 放宽为 text 存结构化前值/后值 JSON，§10.2 要求记录执照上传替换、状态变更、审核人/日期/原因），写入复用 `internal/core/master_database/services.py` 的 `create_audit_log*` 范式。**硬前置**：`config/s3_settings.py:27` 现为 `default_acl='public-read'`，执照文件必须走私有前缀（`licenses/`）+ 预签名 URL 下载 + **恶意软件扫描**（§9.3 首期要求），属阶段 0 独立工作包，本模块所有文件接口按"private + 预签名 + 扫描"设计。

## 2. 表结构设计

> 以下 DDL **逐字摘录**自[开发方案-表结构设计 v2](../开发方案-表结构设计.md) §3.5–3.6（含 §3.5.4 的 `orderevent` 加值与 §3.5.5 的 `company_audit_log` 改造）。发现的疑点以「⚠️ 待确认」标注，**不擅自修改 DDL**。对应 Alembic 迁移：**M8**（执照相关表 + `company.timezone` + 种子提醒档位）、**M9**（合规审查 + orderevent 加值，**v2 无 Override 表**）、**M10**（通知偏好）、**M11**（审计扩展），全部基于 `3bdd9e1f06c8` 续写。

### 2.1 `client_license`（核心档案 + ⭐ 两套独立状态，§9.1/§9.2）

```sql
CREATE TABLE client_license (
    id                    uuid PRIMARY KEY,
    restaurant_id         uuid NOT NULL REFERENCES restaurant(id) ON DELETE CASCADE,
    license_holder_name   varchar(255),               -- 执照持有人法定名称
    business_name         varchar(255),
    license_number        varchar(100) NOT NULL,
    license_type          varchar(100) NOT NULL,      -- 可配置字典（varchar，不用 PG enum）
    issuing_authority     varchar(255),
    issuing_region        varchar(64),                -- 州/司法辖区（varchar 以兼容非美辖区）
    effective_date        date,
    expiration_date       date,                       -- 审核通过前允许为空
    -- ⭐ v2: 两套独立状态（§9.2），不再用单一 8 态 status
    verification_status   varchar(24) NOT NULL DEFAULT 'NOT_SUBMITTED',
        -- NOT_SUBMITTED / PENDING_REVIEW / VERIFIED / REJECTED（由工作流或获授权审核人更新）
    expiration_status     varchar(16) NOT NULL DEFAULT 'NOT_AVAILABLE',
        -- ACTIVE / EXPIRING_SOON / EXPIRED / NOT_AVAILABLE（由到期日自动计算，用户不可手改）
    verified_at           timestamptz,
    verified_by_user_id   uuid REFERENCES "user"(id) ON DELETE SET NULL,
    review_notes          text,                       -- 驳回/复核内部备注（客户不可见）
    compliance_contact_name  varchar(255),
    compliance_contact_email varchar(255),
    compliance_contact_phone varchar(50),
    created_by_user_id    uuid REFERENCES "user"(id) ON DELETE SET NULL,
    created_at            timestamptz NOT NULL DEFAULT now(),
    updated_at            timestamptz NOT NULL,
    deleted_at            timestamptz
);
CREATE INDEX ix_client_license_restaurant ON client_license(restaurant_id) WHERE deleted_at IS NULL;
CREATE INDEX ix_client_license_verif  ON client_license(verification_status) WHERE deleted_at IS NULL;
CREATE INDEX ix_client_license_expiration ON client_license(expiration_date)
    WHERE verification_status = 'VERIFIED' AND deleted_at IS NULL;   -- 到期扫描专用
```

**设计说明（v2）**：
- 挂 `restaurant_id`（餐厅主体，确认单 Q5 建议 A）：一家餐厅一套执照，对多个 vendor 复用；若 Q5 客户选 B（含 vendor 自身执照），按表结构设计文档 §六改多态挂载（restaurant_id/store_id XOR）。
- **1:N**：一餐厅可持多张执照（多州/多类型，§11 可扩展性）。
- **⭐ 两套状态正交（§9.2）**，各自独立流转，**不合并为单一状态**：

| 状态类型 | 取值 | 更新方 |
|---|---|---|
| `verification_status` | `NOT_SUBMITTED` / `PENDING_REVIEW` / `VERIFIED` / `REJECTED` | 工作流或获授权审核人 |
| `expiration_status` | `ACTIVE` / `EXPIRING_SOON` / `EXPIRED` / `NOT_AVAILABLE` | 由 `expiration_date` 自动计算（cron），**用户不可手改** |

- **核验流转**（应用层 `VerificationStatus` StrEnum）：`NOT_SUBMITTED → PENDING_REVIEW`（上传新/替换执照即置此态，§9.2）；`PENDING_REVIEW → VERIFIED | REJECTED`（审核）；`REJECTED → PENDING_REVIEW`（重新提交）；`VERIFIED → PENDING_REVIEW`（上传替换执照）。**approve 前 `expiration_date` 必填（否则 422）**。
- **到期派生**：`expiration_date` 为空 → `NOT_AVAILABLE`；`> today + N 天` → `ACTIVE`；`≤ today + N 天且 ≥ today` → `EXPIRING_SOON`（N 可配，**默认 7 天**，§9.2）；`< today` → `EXPIRED`。系统必须**定期重新计算**（每日 cron）。
- **可同时 Verified 且 Expiring Soon**（§9.2 明确）——这正是两套状态拆分的目的：`verification_status=VERIFIED` + `expiration_status=EXPIRING_SOON` 的执照**仍可下单**（§9.6）。
- **订购资格判定（§9.6）**：`EXISTS(执照 WHERE verification_status='VERIFIED' AND expiration_status IN ('ACTIVE','EXPIRING_SOON'))`。
- `review_notes` 仅 vendor 侧接口返回，餐厅侧响应模型不含此字段（§10.2 RBAC）。
- ⚠️ v1 的 `SUSPENDED` / `MANUAL_REVIEW_REQUIRED` 两态在正式版 §9.2 的取值表中**不存在**，已移除（吊扣场景用 `REJECTED` + `review_notes` 表达；外部核验的 MANUAL_REVIEW 属未来增强 §9.4）。
- ⚠️ 待确认：`updated_at` 无 DEFAULT（与库内多数表一致，由 ORM 维护），实现时沿用项目 `APIModel` 基类即可。

### 2.2 `client_license_document`（文件，FR-E2）

```sql
CREATE TABLE client_license_document (
    id                  uuid PRIMARY KEY,
    license_id          uuid NOT NULL REFERENCES client_license(id) ON DELETE CASCADE,
    file_id             uuid NOT NULL REFERENCES file(id) ON DELETE RESTRICT,
    is_current          boolean NOT NULL DEFAULT true,   -- 换证后旧文件保留但标非当前
    uploaded_by_user_id uuid REFERENCES "user"(id) ON DELETE SET NULL,
    created_at          timestamptz NOT NULL DEFAULT now(),
    updated_at          timestamptz NOT NULL,
    deleted_at          timestamptz
);
CREATE INDEX ix_cld_license ON client_license_document(license_id);
```

**设计说明**：复用 `file` 表与 `pkg/files_uploading/` 上传管道；**硬前置（无 DDL）**——上传走新的 S3 私有前缀 `licenses/`，`BotocoreUploader` 对该前缀改 `private` ACL + 预签名 URL 下载；允许类型 `[application/pdf, image/jpeg, image/png]`（JPG/JPEG 同为 `image/jpeg`，§9.3 明确 PDF/JPG/JPEG/PNG）、上限建议 20MB，用 `pkg/files_uploading/validators.py:86` `parse_file` 魔术字节校验。

**v2 补充（§9.3 逐条）**：
- **恶意软件扫描是首期要求**（"Apply file-size limits and malware scanning"）——CSS 现无该能力，需引入（云端扫描服务 / 自托管 ClamAV / 云存储对象扫描三选一，见开放项 **N8**）。设计上在"上传落 S3 → 标记待扫描 → 扫描回调置可用/隔离"之间插入一个 `scan_status` 处理（首期可用文件表既有字段或在 `client_license_document` 增列，取决于 N8 选型，**不得省略该要求**）。
- **续期另存为新记录**：`Save a renewed license as a new record rather than overwriting the previous record`——续期时**新建 `client_license` 行**（而非改旧行的到期日），旧行保留并可标记 `Replaced` / `Archived`；旧文档行置 `is_current=false`。执照编号、日期、状态、备注与审核历史全部留存。
- **标准 UI 不提供永久删除**（"Permanent deletion must not be available through the standard user interface in the initial release"）——软删/归档可以，硬删端点不对外暴露。
- 基于角色的访问控制：文档下载须校验请求方对该客户的可见性（vendor 侧成员或该餐厅自身），预签名 URL 短时效。

### 2.3 `license_reminder_rule` + `license_reminder_setting` + `license_reminder_log`（提醒配置与防重发，§9.5）

```sql
CREATE TABLE license_reminder_rule (
    id          uuid PRIMARY KEY,
    store_id    uuid NOT NULL REFERENCES store(id) ON DELETE CASCADE,
    days_before integer NOT NULL,                  -- 60/30/14/7/1/0（种子默认 6 档，可增删）
    is_on       boolean NOT NULL DEFAULT true,
    created_at  timestamptz NOT NULL DEFAULT now(),
    updated_at  timestamptz NOT NULL,
    deleted_at  timestamptz,
    CONSTRAINT uq_lrr UNIQUE (store_id, days_before)
);

-- ⭐ v2 新增：store 级提醒总开关/发送时间/通道（§9.5 的 Vendor Settings 配置项）
CREATE TABLE license_reminder_setting (
    id                    uuid PRIMARY KEY,
    store_id              uuid NOT NULL UNIQUE REFERENCES store(id) ON DELETE CASCADE,
    is_enabled            boolean NOT NULL DEFAULT true,      -- 是否启用到期提醒
    send_time_local       time NOT NULL DEFAULT '09:00',      -- 发送时间（按 company.timezone）
    remind_on_expiration  boolean NOT NULL DEFAULT true,      -- 是否在到期日当天也发
    channels              varchar(16)[] NOT NULL DEFAULT '{IN_APP,EMAIL}',  -- IN_APP/EMAIL/SMS
    created_at            timestamptz NOT NULL DEFAULT now(),
    updated_at            timestamptz NOT NULL,
    deleted_at            timestamptz
);

CREATE TABLE license_reminder_log (
    id          uuid PRIMARY KEY,
    license_id  uuid NOT NULL REFERENCES client_license(id) ON DELETE CASCADE,
    days_before integer NOT NULL,
    expiration_date date NOT NULL,   -- 快照：换证改期后同档位可重新提醒
    channel     varchar(16) NOT NULL,             -- IN_APP / EMAIL / SMS
    sent_at     timestamptz NOT NULL DEFAULT now(),
    CONSTRAINT uq_lrl UNIQUE (license_id, expiration_date, days_before, channel)
);
```

```sql
-- ⭐ v2 新增：提醒计划须遵循该 Liquor Vendor 配置的时区（§9.5，开放项 N9）
ALTER TABLE company ADD COLUMN timezone varchar(64);   -- IANA tz，NULL=平台默认
```

**设计说明**：规则挂 **store（vendor）维度**，Ocean Island 与未来其他酒类 vendor 各自配置；M8 迁移为启用合规的 store 种入默认 6 档 + 一行默认 `license_reminder_setting`。

**每日 cron 流程（v2）**：
1. 按 `company.timezone` 判断该 vendor 本地时间是否到达 `license_reminder_setting.send_time_local`（**提醒计划必须遵循 vendor 配置的时区**，§9.5）；
2. 重新计算 `expiration_status`（`ACTIVE`/`EXPIRING_SOON`/`EXPIRED`/`NOT_AVAILABLE`，阈值默认 7 天）并写回；
3. 扫 `ix_client_license_expiration` → 计算距到期天数命中启用档位（`is_enabled` 为假则跳过；`days_before=0` 受 `remind_on_expiration` 控制）；
4. 查 `uq_lrl` 无记录才发 → 按 `license_reminder_setting.channels` 三通道分发 → 落 log。

`expiration_date` 入唯一键保证**续期改期后同档位可重新提醒**（§9.5"当执照续期或被替换时重新计算提醒计划、避免同一执照/收件人/档位重复通知"）。执照挂 restaurant 而规则挂 store：扫描时经 `client` 表（restaurant×store 关联）联出对应 vendor 的档位与收件人；收件人 = 客户档案配置的通知联系人 + 指定的 Ocean Island 管理员/审核人。

### 2.4 `order_compliance_review`（已提交订单遇过期，FR-F5）+ `orderevent` 加值

```sql
CREATE TABLE order_compliance_review (
```

### 3.3 组②：审核工作流

**三个**动作端点（v2 无 suspend）共享**核验状态**流转校验：非法流转一律 409 `license_invalid_status_transition`，成功后统一写审计 + 触发对应通知事件 + 记录 `verified_at`/`verified_by_user_id`（approve）——满足 §9.4 全部动作（审阅文档、与录入信息比对、批准、驳回、要求更新信息、添加审核备注）。

#### 3.3.1 POST `.../licenses/{license_id}/approve` — 批准

- **用途**：`verification_status`: `PENDING_REVIEW` → `VERIFIED`，记录核验人与核验时间，触发 `LICENSE_APPROVED` 通知；**若该客户存在 `ON_HOLD` 的 License Hold 行则自动解除**（§9.7）。
- **请求体**：`{"notes": "与扫描件比对一致"}`（可选，追加进 `review_notes`）。
- **响应 200**：`{"success": true}`。
- **错误**：409 `license_invalid_status_transition`（当前态不允许）；422 `license_expiration_date_required`（无到期日不得批准）；403（无 `edit__license_review` 或角色不符）；404。

#### 3.3.2 POST `.../licenses/{license_id}/reject` — 驳回

- **用途**：`verification_status`: `PENDING_REVIEW` → `REJECTED`，驳回原因必填，触发 `LICENSE_REJECTED` 通知（含客户可见原因）。**亦用于表达官方吊扣**（v2 无独立 suspend 动作）。
- **请求体**：`{"reason": "上传件与录入的执照编号不一致", "notes": "内部备注：疑似旧证"}`（`reason` 必填、客户可见；`notes` 内部）。
- **响应 200**：`{"success": true}`。**错误**：409/403/404/422（reason 缺失）。

#### 3.3.3 POST `.../licenses/{license_id}/request-update` — 要求更新

- **用途**：要求客户补充/修正信息（状态回可编辑态），触发 `LICENSE_UPDATE_REQUESTED` 通知并附说明。
- **请求体**：`{"message": "请补充到期日期并上传新版扫描件"}`（必填，客户可见）。
- **响应 200**：`{"success": true}`。**错误**：409/403/404/422。

#### 3.3.4 ~~POST `.../licenses/{license_id}/suspend` — 吊扣~~（v2 删除）

> ⛔ 正式版 §9.2 的核验状态取值仅 `Not Submitted / Pending Review / Verified / Rejected`，**不含 `SUSPENDED`**。获知官方吊扣时用 **reject + `review_notes`** 表达（同样立即使该客户酒类下单被阻断，因 `verification_status` 不再是 `VERIFIED`）。

#### 3.3.5 GET `/vendors/{vendor_id}/licenses` — 跨客户执照总览/审核队列

- **用途**：一个接口同时服务"待审核队列"与"全部即将到期执照"（§9.8 验收）。**v2 起还承担原仪表盘的轻量替代职责**（仪表盘出局，见 §3.8）。
- **请求**：查询 **`verification_status?`**、**`expiration_status?`**（两套状态各自筛选）、`expiring_within_days?: int`、`search?: str`（客户名/执照号）、`limit/offset`、`sort?: expiration_date|updated_at`。
- **响应 200**：`PaginatedListResponse`，items 在 §3.2.1 摘要字段基础上外加：

```json
{
  "client_id": 1024,
  "restaurant_name": "Golden Dragon Restaurant",
  "days_to_expiration": 21
}
```

- **错误**：403。

### 4.3 关键组件与交互说明

- **审核交互（vendor）**：仿 `RecognizedInvoice`——左侧文件预览（预签名 URL 加载 PDF/图片），右侧录入字段表单，**支持"将文档与录入信息比对"**（§9.4）；顶部动作条 **Approve / Reject / Request update**（**v2 无 Suspend、无 Override**），每个动作弹备注 modal（reject/request-update 的说明必填），approve 前校验 `expiration_date` 已填；动作成功后 invalidate `CLIENT_LICENSES`/`CLIENT_LICENSE` 并 toast。
- **续期交互（§9.3）**：续期是**新建一条执照记录**（不是编辑旧记录）；详情页提供"历史记录"区展示既往执照（`Replaced`/`Archived` 标记）与其文档，**界面不提供永久删除**。
- **文件下载**：列表点击文件 → 调 `download-url` 接口 → `window.open(url)`（预签名短时效，有效期内直连 S3）；不落地长期 URL。
- **餐厅自助**：`verification_status` 为 `REJECTED`/`NOT_SUBMITTED` 或被要求更新、或 `expiration_status` 为 `EXPIRED` 时展示引导卡（原因 + 需补内容）；**`EXPIRING_SOON` 时展示警告 + 到期日/剩余天数 + "请提供更新后的执照"，但不阻止浏览与下单**（§9.6）；上传+字段完整后「提交审核」激活；`PENDING_REVIEW` 态字段只读。
- **下单阻断**：进入 NewOrder（选定 vendor 后）即以 `LICENSE_COMPLIANCE_STATUS` query 预取；`is_ordering_allowed=false` 时**禁用加入订单 / 结算 / 最终提交**并常驻横幅（说明原因 + 指引联系 Ocean Island 或提交更新执照，§9.6）；`EXPIRING_SOON` 时展示**警告横幅但不禁用**；提交接口返回阻断错误时同样落横幅（双保险，服务端为准）。
- **站内通知**：`useNotificationsWebSocket` 收到执照事件（**仅 6 类**）→ invalidate 执照 queries + notificationsStore 计数；点击通知跳 `Paths.CLIENT` License tab（vendor）或 `Paths.LICENSES`（餐厅）。

## 6. 测试要点

> 项目规则：TDD、新增领域单元+集成覆盖 ≥80%；后端 `make dev_test k=<name>` 增量、合入前 `make test` + `make lint`。测试目录随 handlers 放 `internal/main_app/vendor/licenses/tests/` 等（仿 `vendor/clients/tests/`）。

### 6.1 单元测试（core/licenses）

- **⭐ 两套状态独立性（§9.2）**：`verification_status` 流转全矩阵（`REJECTED→PENDING_REVIEW` 允许、approve 无 `expiration_date` 拒绝、上传替换执照→`PENDING_REVIEW`）；`expiration_status` 由到期日派生的边界（到期日 = 今日 / 今日+7 / 今日+8 / 昨日 / 空 → `EXPIRING_SOON`/`EXPIRING_SOON`/`ACTIVE`/`EXPIRED`/`NOT_AVAILABLE`，阈值默认 7 天可配）；**断言两者可同时为 `VERIFIED` + `EXPIRING_SOON`**；**断言用户无法手改 `expiration_status`**（PATCH 该字段被忽略或 422）。
- **提醒计算**：档位命中（60/30/14/7/1/0）；`license_reminder_log` 幂等（同键第二次不发）；续期改期后（`expiration_date` 变化）同档位可重发；`is_on=false` 档位不发；**`is_enabled=false` 时整体不发**；**`remind_on_expiration=false` 时 0 档不发**；**按 `company.timezone` 计算发送时刻**（同一 UTC 时刻下不同时区 vendor 的触发行为不同）。
- **合规判定（§9.6）**：多执照场景（一张 EXPIRED + 一张 VERIFIED+ACTIVE → **放行**）；`VERIFIED`+`EXPIRING_SOON` → **放行**；`PENDING_REVIEW` 且无其他有效执照 → **阻断**；**替换执照 `PENDING_REVIEW` 但既有 `VERIFIED`+`ACTIVE` 仍在 → 放行**；`REJECTED`/`NOT_SUBMITTED`/`EXPIRED` → 阻断；未启用合规的 vendor 恒放行。**v2 无 Override 分支测试**。
- **License Hold（§9.7）**：过期时对未交付行置 Hold（已交付行不置）；approve 续期后**自动解除**；`PROCEED`/`CANCEL` 处置；**退货/冲抵/退款链路不受 Hold 影响**。
- **审计**：PATCH 逐字段 diff 生成 `{"field","old","new"}`；§10.2 要求的四类记录（上传替换/状态变更/审核人与原因/客户等级分配）全部产出审计条目。

### 6.2 集成测试（API + DB）

- **CRUD/文件**：创建→详情→PATCH→软删全链路；上传 21MB → 413；伪造扩展名 exe → 422；`download-url` 返回可用预签名 URL 且过期后 403（S3 侧）；**恶意软件扫描：模拟命中样本（EICAR）→ 文件被隔离/拒绝，不进入可用状态**；**续期上传 → 新建记录且旧记录仍可查、旧文档 `is_current=false`**；**无永久删除端点对外暴露**。
- **权限/越权（§10.2，安全用例）**：无 `view__customer_license` 用户 GET → 403；vendor X 访问 vendor Y 客户执照 → 403；餐厅 A 用户访问餐厅 B 执照 → 403；**餐厅侧响应断言不含 `review_notes` 字段**；approve 用非 CEO/CFO（无 required_roles）→ 403。
- **订单阻断（§9.6 四时点）**：**核验状态 4 值 × 到期状态 4 值全组合** × POST `/restaurants/{restaurant_id}/orders` 期望矩阵（**仅 `VERIFIED` 且 `ACTIVE`/`EXPIRING_SOON` 放行**）；confirm 端点同矩阵 + **Hold 拦截**；阻断响应 `type` 与 `translation_key` 断言；阻断写审计但**不发通知**（§10.1）；合规查询抛异常时下单返回 `compliance_check_unavailable` 而非成功（fail-closed）；**无任何 Override 绕过路径**。
- **cron 任务**：构造到期数据跑任务两遍——`expiration_status` 派生正确、第二遍零新增通知（幂等）；跨 vendor 隔离（A 的档位/时区/设置不影响 B）；**不同 `company.timezone` 的调度时刻正确**。
- **回归（关键）**：非酒类 vendor 全量下单→确认→发票链路不受执照校验波及（合规关闭路径）；现有 `/restaurants/{restaurant_id}/orders` 既有测试全绿；**退货/冲抵/退款在执照过期与 Hold 状态下仍可执行**。

### 6.3 E2E（Playwright，对齐 web 测试规则）

- **主流程 1（阻断-恢复闭环）**：餐厅用户（中文界面）下单被阻→看到 §9.6 推荐文案的中文版与「上传执照」引导→自助上传提交→vendor 审核通过→恢复下单成功。
- **主流程 2（审核工作流）**：vendor 在 Client License tab 查看文件与字段比对→reject（原因）→餐厅收到站内通知→修改重提→approve（**三动作，无 Override**）。
- **主流程 3（Expiring Soon 不阻断）**：执照进入 `EXPIRING_SOON` → 餐厅端看到警告 + 剩余天数 + 更新提示，但**仍可正常浏览与下单成功**（§9.6）。
- **主流程 4（License Hold）**：下单后执照过期 → 未交付部分进入 Hold（订单不取消、双方可见、原因可见）→ vendor 确认/发货被拦 → 客户续期上传 → vendor 核验通过 → **Hold 自动解除、订单继续**。
- **主流程 5（审核/Hold 队列）**：`/licenses-review` 筛选"30 天内到期"/"待审核"/"Hold 中" → 列表数据正确（**无统计卡、无导出**）。
- 断点 320/768/1440 截屏验证 License tab 与阻断横幅中文排版不溢出；键盘可达性（审核动作弹窗焦点管理）。

### 6.4 性能与可靠性

- 产品列表/下单路径上合规查询的额外耗时 <50ms（走 `ix_client_license_expiration`/状态索引，§11 性能：不得显著拖慢目录或结算体验）；到期扫描在预期客户量（数千执照）下单次执行 <1min。
- 通知通道故障演练：邮件 Kafka 不可达时提醒任务不中断（记录并依赖 email_sender 重试/DLQ），站内通知仍达（§11 可靠性：失败的通知必须被记录并重试）。
- **fail-closed 演练**：合规数据源不可用时下单被拒而非放行（§11"未来的外部核验服务故障不得导致执照限制被绕过"）。
