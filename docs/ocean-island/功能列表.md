## 一、总体业务约束（所有功能项共同遵守）

1. **Liquor Vendor 只是公司类型层面的新增，业务走现有 Vendor 业务线。** 它是 `company_type` 表中 `category='VENDOR'` 下的第 7 行种子数据，不是独立业务分类；vendor 侧的产品管理、订单管理、发票/月结、团队、报表等能力全部直接继承现有 Vendor 链路，**零改动生效**。
2. **不影响现有 Vendor / Restaurant。** 全部迁移为向后兼容的新表/加列/种子数据；既有 6 类实体的 onboarding、下单、发票链路必须回归通过（各模块测试要点均已列入）。
3. **价格等级（Price Tier）仅 Liquor Vendor 使用。** 未启用 tier 的普通 vendor 无任何 `price_tier` 行，读价与下单维持现有默认价（基础价）行为，集成测试要求"普通供应商全流程与改造前完全一致（零回归）"。
4. **执照合规仅 Liquor Vendor 启用。** 非酒类 vendor 的合规状态接口恒返回 `is_ordering_allowed=true`，下单→确认→发票链路不受执照校验波及，其余 vendor 保持原样。
5. **多语言设置（原"中文本地化"）是全站语言能力**，不按 vendor 类型限定：本期交付简体中文（zh），架构按多语言可扩展设计（西班牙语等为后续追加翻译资源即可）。
6. **餐厅（采购侧）的订单管理、产品管理需同时兼容 Vendor 与 Liquor Vendor 两种业务线**：面向普通 vendor 照常显示默认价、无执照概念；面向 liquor vendor 按客户 tier 展示价格与三态可购性、受执照合规阻断（含中文提示与上传引导），且客户侧永远不可见 tier 概念、base price、他客执照。

```
                    ┌────────────── 全站横切 ──────────────┐
                    │  02 持久会话（实体级 TTL 配置）        │
                    │  03 多语言设置（全站，本期 zh）        │
                    └──────────────────────────────────────┘
  现有 Vendor 业务线（产品/订单/发票/团队/报表 —— 不动）
        │
        ├── 普通 Vendor ──────────── 默认价格，无执照校验（保持原样）
        │
        └── 01 Liquor Vendor（新 company_type，继承全部 Vendor 能力）
                ├── 04 价格等级（仅 liquor vendor 启用）
                └── 05 执照合规（仅 liquor vendor 启用）

  餐厅采购侧（订单/产品）：同一套页面兼容两种业务线（按 vendor 是否启用 tier/合规自动分支）
```

### 1. 新实体类型（Liquor Vendor）

> 📁 [01-新实体类型/](01-新实体类型/) · [需求](01-新实体类型/需求.md) · [开发方案](01-新实体类型/开发方案.md)

在现有 6 种实体类型上新增第 7 种 **Liquor Vendor（酒类供应商）**，采用纯种子数据轻量路线（无 DDL、无新端点）：种一行 `category='VENDOR'` 的 `company_type`，自动继承标准 Vendor 全部能力（订单/产品/发票/月结/团队/报表/通知）；同时预种 4 个酒类权限实体（`price_tier` / `customer_license` / `license_review` / `compliance_override`）与 Compliance Manager 角色，作为模块 04/05 的权限载体。

**业务约束**：只在公司类型上加一个类型，**业务仍走 Vendor 线**——继承链路经代码逐点核实为零改动生效；餐厅采购侧无任何改动；不同 category 混选建企会被 400 拒绝。存量 vendor 如需开通酒类能力须另补按 company 维度的权限数据迁移。

### 2. 持久会话（30 天）

> 📁 [02-持久会话/](02-持久会话/) · [需求](02-持久会话/需求.md) · [开发方案](02-持久会话/开发方案.md)

把现有"Redis 单值单会话"升级为"**DB 权威（`user_session` 表）+ Redis 缓存**"的多设备会话体系：最长 30 天绝对期保活、短 access token（8h→15min）+ refresh 轮换、改密/重置密码吊销全部会话、管理员强制踢出、用户自助设备列表，以及前端会话失效全局登出处理。

**业务约束**：30 天 TTL 通过**实体级配置**（`company.session_ttl_seconds`）实现，首期仅 Ocean Island 配置 30 天；标准用户沿用现有全局策略，**不影响现有 vendor/restaurant**。6 个改造接口请求/响应结构完全不变（前端零改动兼容），存量已登录用户在首个 refresh 时平滑补建会话行，不会被全员登出。

### 3. 多语言设置（原"中文本地化"）

> 📁 [03-多语言设置/](03-多语言设置/) · [需求](03-多语言设置/需求.md) · [开发方案](03-多语言设置/开发方案.md)
> 功能项由"中文本地化"更名为**多语言设置**：本期交付简体中文资源，但选择器、语言字段、locale 映射、CI key 校验均按多语言架构设计，后续加语种只需追加翻译资源。

新增简体中文为系统支持语言：15 个 namespace 约 2,089 个 key 的 zh 翻译资源；激活语言选择器并打通"选择→持久化→登录初始化"链路（`user.language` / `company.default_language`）；清偿订购全链路硬编码英文文案；货币/日期/数量格式随 locale（计价货币保持 USD）。英语为回退语言，缺 key 不出现空白。

### 4. 客户价格等级

> 📁 [04-价格等级/](04-价格等级/) · [需求](04-价格等级/需求.md) · [开发方案](04-价格等级/开发方案.md)

酒类供应商可自定义客户价格等级（Price Tier）：任意数量与命名的等级、客户分配到等级、按"产品×等级"配置差异化售价与三态可购性；客户只见本等级价格（缺价显示"请联系供应商询价"且不可加购，**绝不回退基础价或他 tier 价**）；下单按 tier 取价并快照锁价；配套定价审计与客户/价格批量导入。五大功能块中体量最大的全新领域。

**业务约束**：**仅 liquor vendor 使用**——等级为 vendor（store）级维度，各 vendor 独立配置；未启用 tier 的存量 vendor 读价/下单维持现有默认价，要求零回归。**餐厅采购侧兼容**：客户界面完全无"等级"概念，响应不携带 base_price / 他 tier 价 / tier 名称；下单链路（餐厅端 + 供应商代下两条）按客户 tier 取价，历史订单/发票/月结金额不受后续改价影响（快照锁价机制不动）。

| 等级管理与客户分配 | tier CRUD/排序/归档/防误删 7 接口 + 客户单个/批量分配 + 前端等级管理页与客户档案/列表接入 | 全栈 | 后端 5d + 前端 6d |

### 5. 酒类执照合规

> 📁 [05-执照合规/](05-执照合规/) · [需求](05-执照合规/需求.md) · [开发方案](05-执照合规/开发方案.md)

收集、审核、跟踪并监控客户（餐厅）酒类执照：`client_license` 执照档案体系（8 态状态机 + 人工审核工作流 + 每日 cron 到期扫描与 60/30/14/7/1/0 档三通道提醒）；在四个时点（开单/加购/提交/vendor 确认）阻断执照过期或无效客户的酒类订单；配套合规审查队列、授权 Override、9 项统计合规仪表盘（6 维筛选 + 导出）、12 类事件通知偏好与全程审计。

**业务约束**：**仅对启用执照合规的酒类 vendor 生效**——非酒类 vendor 合规状态接口恒返回放行，下单→确认→发票链路零影响（回归测试明确覆盖）。**餐厅采购侧兼容**：执照挂餐厅（一家餐厅一套执照对多 vendor 复用）；被阻断时展示中英双语提示与上传引导（文案 key 与模块 03 共用）；客户不可见他客执照与内部审核备注。校验 fail-closed：合规数据读取失败时拒绝下单而非放行；已提交订单遇过期只标记待合规审查，绝不自动取消。
