## 第一部分：新版需求带来的开发确认项（N1~N11）

### N1. 🔴 交付前动态调价 vs 现有"下单锁价"模型（最高优先级）

**背景**：新版 §8.2 要求目录价变更**自动重算所有未达 Delivered 状态的订单**（含已提交、已确认），到 Delivered 才锁价；已交付订单与最终发票保留交付时价格。现有 CSS 是**提交即锁价**（订单行价格快照），发票/月结以快照为源——这是模型反转，牵动订单→发票→月结全链路。

**请确认**：
1. 重算后**无需客户重新确认订单**，仅在客户查看时展示更新后的价格与总额（§8.2"交付前向客户展示"按此理解）？——**建议：是**；
2. 若发票在交付前已生成（如确认时预生成），发票金额是否也随目录价变动、至交付定格？——**建议：发票在 Delivered 后才终审/定格**，交付前仅视为草稿金额；
3. 部分交付的订单：已交付行是否锁定行价、未交付行继续随价变动？（§8.2 只定义整单 Delivered 锁价）——**建议：按行锁定**（与 License Hold 的行级处理一致）。

**客户确认**：① ☐ 同意 ☐ 其他：＿＿＿　② ☐ 同意 ☐ 其他：＿＿＿　③ ☐ 同意 ☐ 其他：＿＿＿

### N2. "Delivered（已交付）"在 CSS 中的定义与标记方式

**背景**：动态调价与锁价均以 Delivered 为界，但现有 CSS 订单状态流转中"交付"节点与操作人需对齐（由 vendor 手动标记？是否存在部分交付的行级状态？）。

**建议**：以现有订单状态机中 vendor 侧"完成交付"动作对应的状态为 Delivered 映射；如无行级交付状态，首期新增行级交付标记（同时服务于 License Hold 的"未交付部分"）。

**客户确认**：☐ 同意建议　☐ 其他：＿＿＿＿＿＿

### N3. 产品类目库的归属与现有数据的关系

**背景**：新版 §3.3 要求 Vendor Settings 下的**共享类目库**（英/中双语、启停、防删）。需确认：① 类目库是**每个 vendor 各自一套**（按"Vendor Settings"理解）还是平台级共享；② 现有产品的既有分类字段如何对接/迁移；③ 餐厅端目录筛选是否按该类目（§5 要求类目中文）。

**建议**：per-vendor 类目库；存量产品分类值一次性导入为类目库初始数据；餐厅端筛选使用该类目。

**客户确认**：☐ 同意建议　☐ 其他：＿＿＿＿＿＿

### N4. 导入主键"Product ID"的语义

**背景**：新版 §7.2 规定 Product ID 为主匹配键（命中即更新、新值即建品），且明确产品名/SKU 不得作为主键。CSS 内部产品 ID 是系统生成的，客户文件中的"Product ID"应为 **Ocean Island 自己的产品编码**。

**建议**：产品新增"外部产品编码"字段（vendor 内唯一），导入以此匹配；最终以 Ocean Island 样例文件为准（§7.1 要求开发定稿前确认模板与字段映射）。

**客户确认**：☐ 同意建议　☐ 其他：＿＿＿＿＿＿

### N5. Expiring Soon 状态阈值与提醒档位的关系

**背景**：新版 §9.2 建议 Expiring Soon **状态**默认为到期前 7 天（可配置）；§9.5 建议**提醒**档位为 60/30/14/7/1/0 天。即"状态切换"与"发提醒"是两套独立配置。

**建议**：按两套独立配置实现——状态阈值影响界面警告与订购提示；提醒档位只影响通知发送。

**客户确认**：☐ 同意建议　☐ 阈值合并为一套：＿＿＿＿＿＿

### N6. 30 天会话的适用用户范围

**背景**：§4 写"Liquor Vendor 用户"，§13 DoD 写"Ocean Island 用户"。Ocean Island 的**餐厅客户**（下单方）是否也享受 30 天会话？

**建议**：会话时长按实体配置（§4 已要求）；Ocean Island vendor 公司配 30 天；**其餐厅客户是否 30 天请明确**（若餐厅用户也要长会话，需对餐厅实体单独配置）。

**客户确认**：☐ 仅 vendor 侧用户　☐ 含餐厅客户　☐ 其他：＿＿＿＿＿＿

### N7. 邮件/短信通知的语言（旧 Q11 后半，仍开放）

**背景**：§5 将"通知"列入必须支持中文的区域（站内通知中文明确）；§9.5/§10.1 的邮件/短信通知模板语言未明说。

**建议**：首期站内通知双语；邮件/短信模板首期英文、中文化二期（X-Language/用户语言字段已在多语言模块打通）。

**客户确认**：☐ 同意建议　☐ 邮件/短信首期必须中文

### N8. 恶意软件扫描的实现范围

**背景**：§9.3 把 **malware scanning 列为首期执照文件上传的明确要求**（§2.2 未将其排除）。CSS 现无杀毒扫描能力，需引入，方式与成本待定：① 云端扫描服务（如上传后触发扫描 API）；② 自托管 ClamAV 容器；③ 云存储自带的对象扫描能力。三者在成本、时延与运维上不同。

**请确认实现方式**（本项在首期范围内，非可延后项）：
- ☐ 云端扫描服务（最省运维，按量计费）
- ☐ 自托管 ClamAV 容器（无外部依赖，占资源）
- ☐ 云存储对象扫描
- ☐ 其他 / 若客户接受可先只做"魔术字节校验+大小限制+私有隔离"、AV 扫描随后补：＿＿＿＿＿＿

### N9. Vendor 时区配置

**背景**：§9.5 要求提醒计划遵循 Liquor Vendor 配置的时区；系统 company 档案当前无时区字段。

**建议**：company 新增 timezone 字段（Vendor Settings 可改），到期扫描与提醒发送按该时区计算；未配置时默认 UTC 或平台默认时区。

**客户确认**：☐ 同意建议　☐ 其他：＿＿＿＿＿＿

### N10. 简化下单流与现有餐厅下单向导的关系

**背景**：§8.1 规定 Liquor Vendor 订购流为"选品 → 订单审核 → 提交 → 确认"，且**不得改变其他 Vendor 类型的订购流程**。现有餐厅端下单为多步向导。

**建议**：对 liquor vendor 的订单渲染该四步流（在现有向导上按 vendor 类型分支/裁剪），其他 vendor 流程零改动；术语用"订单/采购订单"，不出现"发票"。

**客户确认**：☐ 同意建议　☐ 其他：＿＿＿＿＿＿

### N11. 等级价格维护 UI（旧 Q3 遗留，设计细节）

**背景**：新版定义了数据规则（§6.2）与导入（§7.2），未指定日常改价 UI。沿用 v1 双入口设计：产品编辑页"每等级一行"价格区 + 等级维度批量编辑表格。

## 第二部分：仍然开放的旧问题（沿用 v1 编号）

### Q7. 需要哪些管理角色？"合规经理"是否为独立角色？

新版仅要求"执照批准/驳回限于获授权的 Vendor 角色"（§3.2），未点名角色。**建议维持 v1 方案 A**：新增 Compliance Manager 一个角色；不再新增 Administrator（职能由 CEO 承担）。（新版已砍掉 override，故无需划分 override 权限。）

**客户确认**：☐ 同意建议 A　☐ 其他：＿＿＿＿＿＿

### Q8. 现有执照数据如何处置？

系统现有餐厅执照记录只有"类型+编号+州"（海鲜品类）。**建议**：老数据自动迁入新体系，核验状态 Not Submitted、到期状态 Not Available，由客户补录到期日并上传文件后进入审核流。

**客户确认**：☐ 同意建议　☐ 老数据不迁移、从零录入　☐ 其他：＿＿＿＿＿＿

### Q9. 30 天登录是否允许多设备同时在线？

新版确认了服务端吊销与管理员终止（§4），但未明说多设备并发。**建议维持 v1 方案 A**：允许多设备并发会话（每设备各自计时），提供设备/会话列表与踢出。
