## 一、总体判断

新版需求共 **6 大功能块**：新实体类型、**产品类目管理（v2 新增）**、30 天持久会话、多语言设置（简体中文）、客户价格等级（**Tier A 默认/回退模型**）+ 订购与**交付前动态调价（v2 反转）**、酒类执照合规（**范围缩减**）。对照代码库现状：

| 功能块 | v2 需求要点 | 代码库现状 | 真实工作量 |
|--------|------------|------------|-----------|
| Liquor Vendor 实体 | 第 7 种实体，继承标准 Vendor，酒类逻辑不得影响现有 F&B Vendor | 多类型体系（company_type 种子 + category）已成型 | **小**：种子迁移路线不变（v1 结论有效） |
| 产品类目管理（🆕 v2） | Vendor Settings 下共享类目库：英/中双语名、启停、防删、产品表单选用、目录筛选 | 无 vendor 自建类目库概念，需新表 + 产品表挂外键 + Settings 页 | **小-中**：全新但规模有限（~8~10d） |
| 30 天会话 | 面向 Liquor Vendor 用户；实体级可配置；短 access+refresh 轮换、服务端吊销、管理员终止 | refresh 30 天已是默认；缺多会话/改密吊销/管理员踢出 | **中**：与 v1 一致，模块 02 方案继续有效 |
| 简体中文 | 英+中，指定用户默认中文，英文回退；集中化翻译文件；产品/类目信息按录入语言 | i18next 全栈就绪但只有 en；约 41% 组件硬编码英文；后端无 language 字段 | **中偏大**：翻译量 + 硬编码改造（西语明确出局，比 v1 略收窄） |
| 价格等级 + 动态调价 | Tier A 默认与回退价；产品×等级价与可购性；**未达 Delivered 的订单随目录价动态重算，Delivered 后锁价** | 零 tier 概念；且现有链路是"提交即快照锁价" | **大（最大）**：全新 tier 领域 + **动态调价反转了现有锁价语义**，订单→发票→月结全链路回归风险最高 |
| 执照合规 | 执照档案 + 两套状态 + 人工审核 + 到期提醒 + 订购阻断 + License Hold；**仪表盘/override/OCR 出局** | restaurant_license 仅 type+number；状态机/审核/提醒/阻断全缺 | **中-大**：较 v1 缩减（去仪表盘/override，通知收敛为 6 类） |

**结论**：4 阶段划分仍适用，但须先补一个"阶段 0"处理安全短板、开放决策，并**回改模块 04/05 的方案文档**（见 [开发计划](开发计划.md) 与 [功能列表 §〇](功能列表.md)）。

> **首期范围外完整清单（译文 §2.2，12 条）**：西班牙语本地化、客户/产品导出、价格变更历史/定价审计日志界面、合规仪表盘/报表导出、仅凭 OCR 自动批准执照、管理员越权解除执照限制、政府/第三方核验集成、面向消费者直销（DTC）、消费者年龄核验、酒类专属税费、酒类配送路线合规、Shipped By 与 Payment Method 共享 Settings 库。下文各模块只对与本项目功能相关的排除项（前 6 项）展开；后 6 项属业务本就不做的自然排除，以译文 §2.2 为准。

## 二、逐模块分析

### 2.1 Liquor Vendor 实体（§3.1/§3.2）

**现状**：后端无 "EntityType" 枚举；6 种实体是 `company_type` 表 6 行种子，归入粗粒度 `CompanyTypeEnum`（VENDOR/MANUFACTURER/CLIENT）。RBAC 是 role/permission/api_entity/company_role_permission 四表矩阵。

**v2 要点**：LIQUOR_VENDOR 作为 VENDOR 类别下第 7 个 `company_type` 行（仿 `seed_company_hierarchy` 迁移），零成本继承标准 Vendor 全套能力（§3.1 列的目录/客户/订单/发票/团队/通知）。酒类专属权限（价格等级、类目管理、执照审核）通过新增 `api_entity` + 授权实现；执照批准/驳回限于获授权 Vendor 角色（§3.2）。**v2 变化**：新版已**取消管理员 override**，故 `compliance_override` 权限实体可不再预种。"Vendor Owner/Administrator/Compliance Manager" 的角色划分仍需确认（Q7）。

### 2.2 产品类目管理（§3.3，🆕 v2 新增）

**现状**：CSS 无 vendor 自建的"共享类目库"概念（产品分类是既有字段，非可管理的库）。

**v2 要点**：Vendor Settings 下的共享类目库——创建/编辑、启用/停用、存英文+简体中文名、建改产品时选用、查看类目是否被产品使用；**已被产品使用的类目不得永久删除**，停用仅阻止分配给新产品、既有产品不变。需新增 category 表（vendor 维度、双语名、防删）+ 产品表挂类目外键 + Settings 管理页 + 餐厅端目录按类目筛选（类目名随语言，接入模块 03）。**待确认**（N3）：类目库 per-vendor 还是平台级、存量产品分类如何迁入、餐厅筛选口径。

### 2.3 30 天持久会话（§4）

**现状与方案与 v1 一致**：JWT 双 token，refresh 默认 30 天；缺多设备会话（现单会话覆盖）、改密吊销（缺失）、管理员踢出（无接口）。**v2 要点**：会话时长**按实体可配置**（便于复用于未来酒类供应商）；短 access + refresh 轮换、服务端吊销、管理员终止活跃会话——均与模块 02 方案吻合，**无需返工**。待确认：多设备并发（Q9）、30 天是否含餐厅客户（N6）。

### 2.4 多语言设置（§5）

**现状与 v1 一致**：i18next 全栈就绪只有 en；语言选择器死 UI；约 41% 组件硬编码；货币/日期写死 en-US；后端无 language 字段。**v2 要点**：英+中、指定用户默认中文、英文回退、集中化翻译文件、vendor 录入信息按录入语言显示（提供翻译值则按用户语言）。**v2 变化**：西班牙语**明确首期范围外**（§2.2，原 Q10 落定）；§5 明确要求覆盖的区域含**产品类目**、执照状态/到期消息、价格与单位标签。邮件/短信通知语言仍未定（N7）。

### 2.5 客户价格等级 + 订购动态调价（§6/§8，⚠️ v2 模型反转）

**现状**：全库无 tier 概念；价格是"每 StoreProduct 一个全局价"（`ProductPrice` append-only，取最新）；订单锁价链路已存在（`OrderProduct.price` 快照），**现有语义是"提交即锁价"**。

**v2 要点（两处反转，务必回改模块 04 方案）**：
1. **Tier A = 默认与回退价（§6.2）**：每个活跃产品必须配置 Tier A 价；客户所在等级缺价时**回退 Tier A**（而非 v1 的"绝不回退、显示联系供应商"）；无 Tier A 价则产品不能发布/下单。取价规则四条 + 判定表见译文 §6.2。每产品可配不同数量的等级价（缺失走 Tier A 回退），客户到等级为 vendor 级统一维度。
2. **交付前动态调价（§8.2，反转现有锁价）**：目录价变更必须**自动重算所有未达 Delivered 的订单**（含已提交、已确认）——更新行价、重算行小计/小计/订单总额，用随订单存储的客户等级取价、缺价走 Tier A 回退，交付前向客户展示更新后价格；订单 **Delivered 后才锁价**，已交付订单与最终发票保留交付时价格。这**反转了现有"提交即锁价"**，需新增重算引擎并改动 `_build_calc_input`（发票/月结/报表共同上游），是全项目**最高回归风险项**。
3. 订购流四步（选品→审核→提交→确认，§8.1），术语用"订单/采购订单"非"发票"，**不得改动其他 Vendor 类型订购流**。
4. 客户不可见/不可改自己等级（§6.1/§6.3）；等级分配在订单提交时随单存储，改等级只影响未来订单。
5. 导入（§7）：客户导入含 tier/执照列（缺 tier 自动 Tier A）；产品导入以 **Product ID 为主键**（命中更新/新值建品，名称/SKU 不作主键），校验 Tier A 必填/等级/货币格式；**不含导出**。

**可复用地基**：tier 表可仿 `payment_method`；`Client` 是 tier_id 天然挂载点；导入仿 `manufacturer_catalog_import` 两阶段管道；`ProductPrice` 无 changed_by 需补审计**记录**（界面出局）。

### 2.6 酒类执照合规（§9，v2 范围缩减）

**现状**：`restaurant_license` 仅 type+number（海鲜品类），无到期/状态/文件/审核。**v2 要点**：执照档案挂餐厅客户档案（§9.1 的 ~14 字段，1:N 多执照）；**两套独立状态**（核验：Not Submitted/Pending Review/Verified/Rejected；到期：Active/Expiring Soon/Expired/Not Available 自动计算，Expiring Soon 天数可配默认 7 天，可同时 Verified 且 Expiring Soon）；人工审核（批准/驳回/要求更新/备注）；到期提醒（Vendor Settings 配置开关/间隔/发送时间/是否到期日发/通道，默认 60/30/14/7/1/0 档，按 vendor 时区，防重发）；订购资格（§9.6：Verified 且 Active/Expiring Soon 才可下单，Expiring Soon 警告但放行，其余阻断加购/结算/提交）；**License Hold（§9.7）= 合规标记（非新订单状态）**，已提交订单遇过期不自动取消、未交付部分置 Hold、按行处理部分交付、续期核验后解除、退货/冲抵/退款不受限。

**v2 变化（缩减）**：**合规仪表盘 + 报表导出、管理员 override、OCR 自动批准均明确首期范围外（§2.2）**；政府/第三方核验为未来增强（§9.4）。文件上传要求安全存储 + RBAC + 大小限制 + **恶意软件扫描（N8 待确认实现范围）**；续期另存新记录、留存历史、标准 UI 无永久删除。

### 2.7 横切：通知/访问/审计/非功能（§10/§11）

- **通知（§10.1，收敛）**：首期**仅 6 类执照通知**（上传待审/批准/驳回/要求更新/即将到期/已过期）+ 导入错误进导入结果；**产品价格变更、客户等级变更、被阻断的订购尝试均不单独通知**（与 v1 的 12 类事件相比大幅收敛）。三通道（站内/邮件/短信）现成，收件人=客户联系人 + 指定 Ocean Island 用户。
- **访问与审计（§10.2）**：RBAC 保护执照文档/等级分配/定价/内部备注；阻止客户访问他客数据；**记录**执照上传替换/状态变更/审核人与原因/客户等级分配变更。⚠️ 专门的**价格历史日志与管理员 override 工作流首期出局**（但上述审计**记录**必须落库）。
- **非功能（§11）**：性能（tier 定价与执照校验不拖慢目录/结算；导入显进度与行级错误）、可靠性（通知失败记录并重试；外部核验故障不得绕过限制）、可扩展性（多 vendor/各自 tier 集合/多辖区/每客户多执照/多语言）、可用性（中文用户不依赖英文完成核心下单；执照警告清楚说明所需操作）、安全（安全会话、受保护文档存储、最小权限、**服务端强制执行**定价与执照规则）。
