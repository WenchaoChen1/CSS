# Ocean Island 需求分析与功能需求列表

> 配套文档：[中文译文](Ocean-Island-酒类供应商系统增强需求-中文版.md) · [开发计划](开发计划.md)

## 一、总体判断

需求文档共 5 大功能块：**新实体类型、30 天持久会话、多语言设置（原"简体中文本地化"）、客户价格等级、酒类执照合规**。对照代码库现状，各块的真实工作量与文档预期差异很大：

| 功能块 | 文档预期 | 代码库现状 | 真实工作量 |
|--------|----------|------------|-----------|
| Liquor Vendor 实体 | 新增第 7 种实体类型 | "6 种实体" = `company_type` 表 6 行种子数据（非枚举）；多类型体系（`company_company_type` 关联 + `category`）已成型 | **小**：最轻路线只需种一行 `category='VENDOR'` 的 company_type + 前端第 7 张 onboarding 卡 |
| 30 天会话 | 延长会话 + 安全机制 | JWT 双 token + refresh 轮换 + `issued_token` 吊销表已存在，`refresh_token_ttl` 本来就是 30 天 | **中**：TTL 不是重点，重点是单会话→多会话重构、改密失效、管理员踢出（均缺失） |
| 多语言设置（首期简体中文） | 新增语言 | i18next 全栈就绪（15 个 namespace），但只有 en；语言选择器是死的；约 41% 组件未走 t()；后端邮件/短信全英文硬编码 | **中偏大**：翻译量 + 硬编码文案改造 + 打通切换链路 |
| 价格等级 | 可配置 tier + 按 tier 定价 | **零 tier 概念**（全仓 grep 无命中）；但价格历史表、订单锁价快照、客户关联表、3 套导入基础设施都可复用 | **大**：是五块中最大的全新领域 |
| 执照合规 | 执照档案+审核+提醒+阻断 | `restaurant_license`/`store_license` 表存在但只有 type+number（无到期日/状态/文件）；8 态状态机、审核流、提醒、阻断全部不存在 | **大**：第二大工作量，且牵出 S3 公开读等安全短板 |

**结论**：文档建议的 4 阶段划分（基础 → 定价 → 合规 → 自动化）与代码库现状匹配，可以采纳；但必须在动工前补一个"阶段 0"处理安全短板与开放决策（见 [开发计划](开发计划.md)）。

## 二、逐模块分析

### 2.1 Liquor Vendor 实体（需求 §4）

**现状**：后端没有 "EntityType" 枚举。所谓 6 种实体是 `company_type` 表的 6 行种子（Food Vendor / E&S Dealer / Broadliner Dealer / E&S Manufacturer / Food Manufacturer / Restaurant），每行归入粗粒度 `CompanyTypeEnum`（VENDOR/MANUFACTURER/CLIENT，`companies/domains.py:17`）。RBAC 是 role/permission/api_entity/company_role_permission 四表矩阵，权限串形如 `view__product`；敏感操作已有 `required_roles=[RoleName.CEO, ...]` 的现成写法。

**方案要点**：
- **推荐轻量路线**：LIQUOR_VENDOR 作为 VENDOR 类别下的第 7 个 `company_type` 行（仿 `seed_company_hierarchy` 迁移），自动继承整套 VENDOR 角色/权限/订单/产品/发票能力——即需求 §4.2 "继承标准 Vendor 能力"零成本满足。
- 酒类专属权限（tier 管理、执照审核、合规覆盖）通过新增 `api_entity` 行 + `company_role_permission` 种子授权实现；"审核/覆盖"动作可复用 `PermissionType.EDIT` 或扩展新动作类型。
- 前端需同步：`CompanyTypes` 枚举、onboarding 第 7 张业务卡、`constants/permissions.ts` 规则、Sidebar 菜单守卫。
- ⚠️ 注意：前端静态 abac rules 里 SALESMAN/PARTNER 等角色缺条目、多处 "TODO: Change permissions"——加新权限时需一并补齐，否则新页面对这些角色静默不可见。
- ⚠️ 需求提到的 "Vendor Owner / Vendor Administrator / Compliance Manager"：后端目前 **Owner 即 CEO，没有独立 Admin 角色行**，Compliance Manager 需新种一个 role。

### 2.2 30 天持久会话（需求 §5）

**现状**：JWT（HS256）双 token 已存在：`access_token_ttl` 默认 8 小时、`refresh_token_ttl` 默认 **30 天**（`config/auth_settings.py`）；刷新时已做轮换（旧 token 全部置 `revoked`）；`issued_token` 表按 jti 吊销。**但**：
- Redis 会话是 `user_session:{user_id}` 存**单个** session_id——新登录覆盖旧会话，**单用户单活跃会话**，无设备列表；
- `change_password` / `reset_password` **只改 hash，不吊销任何会话**——直接违反需求 §5.4 验收标准"重置密码使会话失效"；
- **没有管理员强制踢出接口**（批注 2 明确要求）；
- 会话 TTL 只能全局 env 配置，无实体级配置；
- 前端 token 存 localStorage（非 httpOnly cookie），XSS 暴露面大；`SESSION_EXPIRED`/`TOKEN_REVOKED` 错误类型前端未处理（不触发刷新也不登出）。
- ⚠️ 运行耦合：auth DI 急切启动 Kafka producer，Kafka 不可达则登录整体 500（交接文档已知问题）。

**方案要点**：缩短 access TTL（如 15 分钟）→ 重构 Redis 会话为 per-device 多会话结构（session_id → 设备元数据）→ 补改密/重置吊销 → 新增管理员"踢出单会话/全部会话"接口 → 新增系统级+实体级会话时长配置表 → 前端补 session 失效处理与登出跳转。

### 2.3 多语言设置——首期简体中文（需求 §6）

**现状**：i18next + http-backend + languagedetector 全栈就绪，15 个领域 namespace，`fallbackLng:'en'` 天然满足"缺翻译回退英文"。但 `supportedLngs:['en']` 只有英文；设置页语言选择器是**死的**（硬编码单语言数组 + 空 onSelect）；核心下单链路 t() 覆盖良好，但较新的 Catalog 产品卡片等约 41% 组件硬编码英文；货币/日期写死 `en-US`/`USD`/`MM/dd/yyyy`；后端邮件模板、短信文案全英文硬编码（Jinja i18n 扩展注册了但从未装翻译）；后端无用户 language 字段，axios 的 `X-Language` 头被注释（TODO）。

**方案要点**：新建 `public/locales/zh/` 全量 15 个 namespace 翻译 → `supportedLngs` 加 'zh' → 激活语言选择器（changeLanguage + 持久化）→ 用户/实体默认语言落后端（用户模型 + settings API 加 language 字段，登录后初始化）→ 排查订购全链路硬编码文案改 t()（Catalog 重灾区）→ 货币/日期格式化随 locale → 后端邮件/短信多语言（可后置到二期）。
- ⚠️ **文档不一致**：执行摘要写"简体中文/西班牙语"，正文 §6 只讲中文。框架打通后加 es 边际成本低，但翻译资源需确认——**待与 Ocean Island 澄清**。

### 2.4 客户价格等级（需求 §7）

**现状**：**全库无任何 tier/price list 概念**。价格是"每 StoreProduct 一个全局价"（`ProductPrice` append-only 历史表，当前价取最新一条）；唯一 per-client 差异化是 `ClientFinances.discount_percent`（整单折扣，属结算层）。可复用的地基很好：
- `Client`（restaurant×store 关联表）是 tier_id 外键的天然挂载点；
- 订单锁价链路已存在（`OrderProduct.price` 快照 + `OrderProductPriceHistory`），"历史订单保留原价"只需把落快照时的取价源改为 tier 价；
- 3 套导入基础设施可复用，其中 `master_database/import_` 的会话式管道（upload→映射→预览→校验→冲突解决→ARQ 异步执行→错误统计）是"批量导入+校验+错误报告"的最佳蓝本；
- `ProductPrice` 无 changed_by——**价格变更目前零审计**，需补。

**方案要点**：新增 `price_tier` 表（store 维度，name/description/active/default/sort/archived）+ `Client.tier_id` + `(store_product_id × tier_id)` 价格与三态可购性表 → 改造读路径（产品列表/详情按请求方 tier 过滤价格）→ 改造 `_build_calc_input` 取价逻辑 → 前端 tier 管理页 + 产品×tier 定价矩阵 + 客户分配（单个/批量/导入）。

**对批注的解答建议**：
- **批注 1（是否录入 base price？）**：建议保留现有 `ProductPrice` 作为 base price——用途限于：① 未启用 tier 的普通 vendor 照常使用；② 新建 tier 时的初始化参考价；③ 内部报表。客户侧永远只见 tier 价，缺 tier 价时按 §7.6 显示"联系供应商"，**不回退 base price**（与 §7.6"不得自动暴露其他等级价格"一致，需产品确认 base price 是否算"另一个等级"）。
- **批注 3（一个 tier 下如何改每个商品价格？）**：设计双入口——① 产品维度：产品编辑页的价格区改成"每 tier 一行"的矩阵；② tier 维度：tier 详情页提供该 tier 全部产品的批量编辑表格 + Excel 导入（复用导入管道）。
- **批注 4（产品 A/B 的 tier 数量可否不同？）**：建议 **tier 集合是 vendor 级统一维度**，不做每产品自有 tier 集合；"产品 A 有 4 档、产品 B 有 2 档"通过"B 在其余 tier 上不配价/不可购"表达（§7.5 三态天然支持）。这样数据模型简单且客户分配语义清晰。**需产品确认**。

### 2.5 酒类执照合规（需求 §8-§11）

**现状**：`restaurant_license` / `store_license` 表已存在但**只有 license_type + license_number（+region）**——无到期日、无状态、无文件、无审核概念；`RestaurantLicenseType` 枚举全是海鲜类（SEAFOOD/FISH_DEALER 等），无酒类。8 态状态机、人工审核流、到期提醒、订单阻断、合规仪表盘**全部不存在**。可复用地基：
- S3 上传管道（魔术字节验型+限大小）、`core/files` 领域范式；
- arq worker 已有每日 cron 任务范例（`check_unregistered_clients`）——到期扫描照抄即可；
- 三通道通知（站内 RabbitMQ+WS / 邮件 Kafka→SMTP / 短信 Kafka→Twilio）齐备；通知偏好表（company+role+type 开关）可扩展；
- `CompanyAuditLog` 审计表可扩展 `LICENSE` entity_type；
- `catalog_ocr_service`（Gemini）的"图片→OCR 文本"层通用，可为执照新增字段 schema；前端 `RecognizedInvoice` 是"OCR+人工确认"的现成交互范式；
- 订单阻断插入点已定位：提交时 `OrdersService.create_order`（两条创建链路共享底座）、确认时 `confirm_vendor_order`；"打开流程/加购"两个时点需新增只读合规状态查询接口供前端调用。

**必须先修的安全短板（阻断执照功能上线）**：
1. 🔴 **S3 `default_acl='public-read'`**——所有上传文件都是公开 URL。执照是敏感文件（§8.4 明确要求安全存储+角色访问控制），必须改 private + 预签名 URL 或后端鉴权代理；
2. 🔴 `upload_catalog_pdf` 的鉴权被注释（TODO）、OCR webhook 无鉴权——复用 OCR 通道前必须恢复；
3. 🟡 `FilesService.delete_file` 未删 S3 对象（TODO）；
4. 🟡 现有 client-file/product-file 上传只允许 excel/csv/txt(1MB)，执照需单独配 PDF/JPG/PNG + 更大限额。

**方案要点**：新建 `core/licenses` 领域（约 15 字段 + 文档外键 + 8 态状态机）→ 审核工作流端点（批准/驳回/要求更新/备注，接入审计）→ arq 每日到期扫描 + 可配置提醒档位（60/30/14/7/1/0）× 三通道分发 → 四时点订单校验 + 阻断错误类型（前端按 type 映射中文文案）→ 订单合规标记（参考 `OrderClaim` 范式，不新增 OrderStatus 也可）→ Override 权限 + 审计 → 合规仪表盘 + CSV/Excel 导出。

### 2.6 横切项（报表/通知/审计，需求 §9-§11）

- 仪表盘：纯新增页面 + 聚合查询，复用 reports 模块导出能力。
- 通知 12 类事件全部是新事件类型，但分发通道全部现成。
- 审计：扩展 `CompanyAuditLog`（加 LICENSE/PRICE_TIER/PRICING entity_type）或抽通用 audit 服务；`previous_value/new_value` 字段需求超出现有 `details` 字符串（1000 字符），建议结构化 JSON。
