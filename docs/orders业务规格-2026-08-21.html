0.1 业务定位

Order（订单）是买卖双方之间的采购单据，贯穿「餐厅下单 → 供应商确认 → 打包 → 配送 → 餐厅签收 → 交付完成」全流程。同一套 /orders 路由对餐厅（买方）与供应商（卖方）两类账号呈现两套完全不同的界面与操作集：列表页在「取数端点 + 表格列」层分叉，详情页在「组件层」按前端权限 READ_VENDOR_ORDER 分叉为 VendorLayout / RestaurantLayout。订单与装箱单（packing slip）严格 1:1——供应商确认订单时同一事务创建装箱单，此后配送流转全部由装箱单侧驱动、回写订单状态。

数据关系
order 主表 30 个业务列 + 24 张关联表；与 packing slip / invoice 均 1:1（order_id 唯一）。
orders/models.py:132-243
状态口径差
后端 OrderStatus 定义 11 值、实际只写入 8 个；前端枚举只声明 7 个。PENDING/READY_FOR_PACKING/ISSUES_AT_THE_DRIVER_PICKUP_STAGE 为零写入死状态。
权限真相
三条路由全部无前端权限守卫（仅登录+onboarding）；真正闸门在后端 company_role_permission 表 + 公司级 CEO 无条件绕过。
金额三套口径
order.price（按 ordered、无税折）、tax_amount（按 ordered、含软删）、totals.grand_total（按 shipped、含折扣运费）——同一响应并存且互不相等。

0.3 权限体系（开篇必读）

⚠ 两套独立权限体系 + 一个超级角色

前端：constants/permissions.ts 里 35 行按 role-UUID 硬编码的静态表。order 相关只有 3 个权限，且都不是「访问闸门」：READ_ORDERS_PAGE（仅控侧边栏入口）、READ_VENDOR_ORDER（仅控详情页用哪套 Layout）、CREATE_VENDOR_ORDER（仅控下单走哪套步骤序列）。枚举里根本没有 EDIT_ORDER / DELETE_ORDER。

后端：每公司在 onboarding/设置页自行配置并落库的 company_role_permission 表，权限键形如 view__order / create__order / edit__order。公司级角色名为 CEO（COMPANY_OWNER）且 is_active 的成员，对全部挂 check_permissions 的订单端点无条件放行——这是硬编码字符串比较，不是权限位。middlewares/permissions/middlewares.py:45-51；companies/domains.py:15

两者零联动：后端下发的公司级权限本想 deepmerge 进前端 ABAC，但其键名空间是 <permissionId>_<entityId> 的 UUID 拼串，与 READ_ORDERS_PAGE 这类枚举名永不相碰，且唯一的消费者 useMakeApiPermission 全代码库零引用 → 后端可配置权限对前端 UI 完全无效。useGetUserData.ts:48-56；AccessControlProvider.tsx:18

数据范围（后端 service 层注入，仓储层无兜底租户过滤）：餐厅账号看本餐厅；门店账号看本店；公司账号看整棵公司树下所有门店/餐厅的合并列表（递归 CTE）。订单读链路从不按人收窄（无按 creator/salesperson 过滤，下单人 creator_id 甚至被 DTO 注释掉、前端拿不到）。companies/repositories.py:121-158；orders/dto.py:194-195
