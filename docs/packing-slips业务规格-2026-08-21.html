0.1 业务定位

Packing Slip（装箱单）是供应商（Vendor）侧的订单履约执行单据，与订单严格 1:1（order_id 唯一约束）。餐厅下单后，供应商门店确认订单的那一刻系统自动生成装箱单；此后订单的实物履约全程——打包 → 司机取货 → 在途 → 到店 → 餐厅签收 → 司机确认交付——都以这张单据为载体推进。/packing-slips 页面是这条流水线的工作台：打包员（Packer）和司机（Driver）在这里领活干活，门店经理在这里指派、审批、跟踪。本页也是 Packer / Driver 登录后的落地页兼唯一可用页面。

0.3 权限体系（两层，相互独立）

  • 前端页面级：react-abac 静态矩阵 READ_PACKING_SLIPS_PAGE 控制菜单显隐与详情页可达。可见角色：Vendor 公司 CEO/CFO/CHEF/MANAGER/SHIPPING_MANAGER；Store 门店 CFO/CHEF/MANAGER/SALESMAN/SHIPPING_MANAGER/PACKER/DRIVER。不可见：Restaurant 全系、Third Party Courier、ADMIN 等。Manufacturer 公司 8 角色权限为 true 但菜单被有意注释掉（等 manufacturer 专属端点）。注意列表路由本身没有权限守卫（仅登录守卫），详情路由才有——无权限用户直输 URL 能看到空壳页面，数据被后端拦下。permissions.ts；routes.tsx:941-945 vs :968-972
  • 后端数据级：X-API-KEY（/api 全局）→ JWT（每路由）→ service 层成员关系判定；不做页面/角色 RBAC。数据范围：公司账号看全公司所有门店；门店成员看整店；Driver/Packer 列表只看分配给自己的单（详情不收窄）；餐厅用户 403。

需求描述

流程

订单确认 → 装箱单创建（单事务）
  1. 餐厅
    下单（订单 NEW / PENDING）
    此阶段无装箱单；vendor 收到新订单邮件通知
  2. 门店成员
    在订单页确认订单（confirm）
    前置校验：store 存在、成员归属、订单属于该店、订单状态非 DELIVERED
  3. 系统
    单事务依次执行
    更新订单（notes / delivery_type / salesperson）→ 订单历史 CONFIRMED → INSERT 装箱单（仅 order_id，状态默认 New）→ 装箱单历史 CREATED（记确认人+角色）→ 订单状态 → CONFIRMED；异常整体回滚
  4. 系统
    事务外：向订单群聊推送订单消息
    装箱单出现在列表 New 页签，等待打包（F3）与指派（F5）

需求描述

Canceled 是订单取消的联动结果，装箱单侧没有独立的取消功能。取消窗口很宽：订单从确认后到交付前任意阶段（含在途）都可被 vendor 侧取消，装箱单随之进入 Canceled 终态。订单尚未确认（无装箱单）时取消静默成功——所以 Canceled 页签里只会出现「确认之后被取消」的订单。Canceled 页签与详情页均为纯只读（详见 F1 / F11）。

  2. 系统
    订单置 CANCELED
    订单历史记 CANCELED（含操作人+角色）；推订单群消息

前端：仅经理视角且 status===New 时渲染编辑控件（canEditTable）；Approve 与 Confirm 按钮仅 SHIPPING_MANAGER。后端：成员归属校验（company_member OR store_member），无角色校验——与本模块其余写接口同构。usePackingSlipTable.tsx:110-146；stores/orders/services.py:1487-1533
