Products（商品）模块业务规格

以功能点为单位整理 /products 及其子路由的业务。核心口径：一个 URL、三套实体、三张表——由 company.type 决定展示 restaurant_product / store_product / manufacturer_product。每个功能模块统一含「权限（前端可见 vs 后端强制）→ 需求描述 → 字段与数据 → 流程 → 已知问题」。全部结论逆向自实际代码。

0.1 业务定位：一个 URL、三套实体

/products 是同一个 URL 挂了三套完全不同的实体、三个不同 endpoint、三张不同的表格组件，由登录公司类型 company.type（不是角色）分流。餐厅账号与供应商账号看到的绝对不是同一实体——底层是三张不同的表、三套不同的语义、连主键类型都不同。这是本文档必须拆成三节写的核心原因。

client 公司（餐厅）
restaurant_product 「我要采购的物料 + 采购统计」（含 lastPrice/avgPrice/qtyPurchased）。由订单交付自动生成，无手工新增/删除入口。
restaurants/models.py:167-217
vendor 公司（供应商）
store_product 「我在卖的 SKU + 价格库存」。41 业务列，是订单/发票/报价唯一实际引用的商品实体。
products/models.py:99-210
manufacturer 公司
manufacturer_product ⋈ subdivision（INNER JOIN，某商品在当前分部无叠加行则不出现）。侧边栏叫「MFR Catalog」但页内标题仍写「Products」。
manufacturer_products/repositories.py:262-317
分流判据
取数按 company.type、渲染表格按 ABAC 权限 READ_VENDOR_PRODUCTS、头部按钮按公司类型+!isCompany——三套判据混用，见 0.3。

0.2 三条商品线的实体关系

线层级表作用上屏

0.3 权限体系（开篇必读）

⚠ 三套判据混用 + 无「商品增删改」权限概念

前端 Permissions 枚举根本没有 CREATE_PRODUCT / EDIT_PRODUCT / DELETE_PRODUCT，只有 READ_PRODUCTS_PAGE（仅控侧边栏入口）和 READ_VENDOR_PRODUCTS（仅控渲染哪张表）。全部路由（含三个创建页）无任何 AllowedTo 守卫，任何登录用户敲 URL 都能打开。三套分流判据互不一致：取数按 company.type、渲染表格按 ABAC READ_VENDOR_PRODUCTS、头部按钮按 公司类型+!isCompany（零权限判断）。permissions.ts:9-39；ProductsTable.tsx:230-265；Products.tsx:45-89

后端：每公司自配的 company_role_permission 表（view/create/edit/delete__product）+ 公司级角色名 CEO（COMPANY_OWNER）无条件绕过。与前端两套独立体系。

三分支非互斥的后果：厂商公司里未定义 READ_VENDOR_PRODUCTS 的角色（8 个 MANUFACTURER_SUBDIVISION_* 前端权限表全缺项）会同时渲染 RestaurantTable 与 ManufacturerTable 两张表；vendor 公司里 STORE_PACKER/DRIVER 得到 RestaurantTable 但餐厅查询被 enabled 关掉 → 永久空表且无报错。ProductsTable.tsx:230/245/265；useProductsTable.tsx:147-150

F5新增单个商品

谁能用
前端按公司类型+!isCompany 显示"Create new"（零角色判断）；后端要 create__product
入口
"Create new"→ /products/create-product（厂商建品）；/products/add-product 孤儿路由无入口

存在两个割裂的单条新增页：AddProduct（/products/add-product，落 store_product 链条 Product→VendorProduct→StoreProduct→ProductPrice）是孤儿路由——全站无任何按钮指向它，只能手敲 URL，却是供应商唯一能建单条 store_product 的页；而"Create new"按钮一律去 ManufacturerCreateProduct（厂商建品表单），供应商点它进去因 subdivisionId 为 undefined 无法保存（供应商建品链路是坏的）。公司账号建品被强制跳回 /products。

F6批量导入

谁能用
供应商 → UploadProducts；制造商 → Catalog(OCR)。前端按公司类型显示，无角色判断
入口
/products/upload-products（供应商 4 步）/ /catalog（厂商 OCR）
端点
file-headers → file-to-table → table-to-models / catalog import 系列
结果
批量创建/更新 store_product / manufacturer_product

需求描述

两套完全独立的导入。供应商 UploadProducts（4 步向导）：选方式（上传文件/复制粘贴）→ 上传/粘贴 → 列映射 → 预览提交。固定 5 列模板（name/price/quantity/unit/category），仅完全同名直配、无别名字典、多出任何一列都失败；整批一个事务，任一行异常 rollback 全批、返回一条 500——无逐行报错、无部分成功。制造商 Catalog（OCR）成熟度明显更高：36 系统字段 + 30+ 别名、自动嗅探分隔符、逐行 created/skipped/failed 结果、作业幂等（重复提交 409）、PDF 走独立 OCR 微服务（Gemini）。

流程（供应商 4 步）

  1. 供应商
    选方式 → 上传文件（自动进列映射）或粘贴（前端解析）
    格式前后端三处不一致：前端允许 csv/xls/txt≤20MB，后端 MIME 另一套、解析器只认 csv/xls/xlsx、上限 1MB → .txt 必 500、.xlsx 前端拦
  2. 供应商
    为每列选系统字段（仅完全同名自动预填）→ Save 调 file-to-table
    file-to-table 成功后删临时文件 → step4 一旦进入无法安全回退（重进 step3 报文件未找到 500）
  3. 系统
    预览表格 → Continue 调 table-to-models
    整批事务：Product 按全局 name 复用/新建、VendorProduct 按 (product,vendor) upsert(重复导入把已下架商品静默重新上架)、StoreProduct 按 (store,vendor_product,name) 只更新 in_stock/unit、description 写空串。任一行异常整批 rollback+500

权限

file-to-table 与 table-to-models 的 check_permissions 均被注释掉（因中间件只从 path 取 vendor_id，而这两端点 vendor_id 是 query 参数，开启则全员 403）。后果：file-to-table 既无 RBAC 也无成员校验（任意登录用户可解析并删除他人临时文件）；table-to-models 仅服务层成员校验、不查角色（Packer/Driver 只要是成员就能批量导入）。vendor/handlers.py:644-658, 709-722

已知问题
  • 导入两端点权限被注释（C4）；文件格式三处不一致 .txt 必 500（M9）；固定 5 列无别名、多列即失败、无逐行报错（M9）；step4 无法安全回退（L1）；导入往全局分类表写新分类（L1）。

F7核销（库存报损 write-off）

谁能用
餐厅 / 供应商（!isManufacturer，制造商无此端点）
入口
列表头部 Write off product → WriteOffProductsModal
端点
PATCH /{restaurants|vendors}/{id}/products/write-off
结果
扣减 in_stock + 写核销日志

需求描述

把库存中损坏/腐坏的数量从 in_stock 扣掉并留一条日志（inventory write-off，非财务核销）。弹窗逐行填：商品下拉（已选剔除）+ 数量（max=该商品 in_stock，可"全部库存"）+ 原因（仅 2 项：Damaged / Spoiled）。只有最后一行可编辑、已填行不可改无删除。

字段与数据

方向字段存储逻辑
请求{ products:[{ id, quantity, reason }] }PATCH …/products/write-off；reason ∈ {Spoiled, Damaged}
校验商品属该租户 + in_stock−quantity≥0（否则 OVERSTOCK_WRITE_OFF）+ 整数单位不允许小数后端 edit__product + 成员校验
保存write_off_{restaurant|store}_product_log + UPDATE in_stock−=quantity两个循环各自 commit、无事务包裹（部分成功可能）
成功后invalidate VENDOR_PRODUCTS未 invalidate RESTAURANT_PRODUCTS（餐厅侧核销后列表不刷新）
已知问题
  • 核销非原子（部分成功）、餐厅侧核销后不失效列表缓存（L1）；TS 枚举有 6 值但 UI 只暴露 2 个（后 4 值不可达，待清理）（L1）；库存核销到 0 后该商品任何编辑保存必 422（H3）。
