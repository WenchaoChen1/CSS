## 二、结论

**这批改动不能按现状上 uat/prod。** 阻断项：

1. **部署后不可用**
   - N34：迁移超前于代码，升级后权限全部失效。
   - N73：上线后新建的 vendor 公司一接单，订单列表就 500。
2. **安全**
   - N35：任意已注册用户的账号可被接管。
   - N2：dev admin 对所有公司放行，至今未改。
   - H6′：有 `edit__team` 的成员在界面上就能自升 CEO。
   - N37：带明文临时密码的短信可能整条写进日志。
   - N67：操作日志可以被伪造，失败操作显示成成功。
3. **数据迁移**
   - H6：id 冲突时换成随机 id。
   - M1：硬删除聊天消息。
   - H5：清空母公司层级，原值只在 `company_back` 里，删表后不可恢复。
   - H7 的残留：子部门同产品时会中止升级。
   - N41：prod 上没走完旧 onboarding 的公司，暂存的团队成员会作废。
   - N72：历史团队日志会按分支数复制，在 prod 真实数据上永久生效。
4. **公司停用功能不完整**：不级联到分支（N69）；只在一个中间件里拦截（N70）；邀请码作废逻辑两头都有问题（N71）；批量删除能删掉付费客户（N74）。
5. **删表计划**：删 `company_back` 和 `deprecated_*` 表必须单独发版，先核查、导出、改代码，只删表不删列（三-B）。
6. **测试**：套件仍基本失效。本轮第一次带了测试，但只覆盖通知文案、日志中间件和 IP 解析；停用、Join Company、删公司连带删用户都没有测试，Master Database 的旧测试还在断言已经改掉的接口契约。

## 三-B、删表前提下的复核（2026-11-17 补充）

**前提**（团队确认，见沟通与决策记录 D7）：`company_back` 只是备份，将来会删除；`deprecated_*` 表将来也会删除；这些表都不再使用。

**方法**：对 29 条和备份表、`deprecated_*` 表、回滚、数据恢复有关的已有问题逐条重新判断；再从 4 个方向扫描删表本身的风险：运行时代码引用、数据库对象依赖、只存在于旧表里的数据、测试与运维脚本。34 条候选经对抗式验证，合并为 9 条新问题（N88–N96）。N88、N89、N90、N91 的关键证据已人工对照代码核实。

1. 这些表是多条已知问题唯一的数据来源。不先导出就删，数据就永久丢失（N88）。
