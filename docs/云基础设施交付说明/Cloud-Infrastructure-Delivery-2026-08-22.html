The infrastructure has the following characteristics:

  • Fully codified (IaC): every AWS resource is under unified management; any change is traceable and reproducible; critical production resources (database, load balancer) have deletion protection enabled.
  • Production isolation: production has its own network (VPC), its own database instance (highly available across availability zones) and its own release-approval gate, invisible to all non-production environments.
  • Data protection: automatic database backups kept for 35 days with point-in-time recovery; all storage encrypted; non-production environments use masked data.
  • Automated releases: test and acceptance environments build and deploy automatically on every push; production releases require manual approval, with versioned images and minute-level rollback.

2Architecture

Everything runs in AWS us-east-1 (N. Virginia), split into two fully isolated virtual private networks (VPCs) — one for production, one for everything else. All application servers and databases sit in private subnets with no public IP addresses; the only internet-facing components are the load balancers (ALBs).

Three access rules

  • SSH only via the bastion: application servers expose no public port 22; management access goes through the bastion jump host, reachable from allow-listed IPs only.
  • Web only via the environment's own load balancer: one independent ALB per environment; environments never route through each other.
  • Databases stay on the private network: RDS has no public exposure of any kind and only accepts connections from its own environment's application server and the bastion.

The three legacy environments in the previous team's AWS account (EU region) have been fully migrated: databases, file storage and configuration have all been transferred to the current account. The legacy front-ends and middleware have been stopped, with only a few containers left pending final shutdown; the legacy HTTPS certificate expires on 2026-09-15, at which point the old environments lapse naturally.

4Runtime shape

Each environment runs three independent, individually updatable service stacks in containers on a single application server:

StackServicesResponsibility
Frontend stack Web front-end (single-page app) User interface; same-origin reverse proxy to the backend, avoiding cross-origin issues
Backend stack (11 containers) Main API, chat, notifications, async jobs, SMS sender, e-mail sender, AI assistant, product-catalog recognition (OCR), etc. All business logic, split into single-purpose containers that do not block each other
Middleware stack Redis cache, RabbitMQ message queue, Kafka event stream Caching, notification delivery, verification-code and other event messages

Databases do not live on the server: both tiers use AWS-managed RDS PostgreSQL, with the main business database and the OCR database kept separate (see Section 5).

File storage (S3)

  • One bucket per environment, fully isolated: each environment's invoices, product catalogs and images live in a dedicated bucket, accessed through a dedicated least-privilege identity; environments cannot see each other's files.
  • Uniform protection: default encryption, versioning, lifecycle cleanup (abandoned multipart uploads after 7 days, old versions after 30 days).
  • The production bucket holds about 58,000 files (≈7 GB), verified object-for-object against the source environment.

7Releases & operations

Release flow

  1. Dev
    Push code to the environment's branch
    CI runs automatically: code checks → unit tests → container image build → push to the registry (immutable version number + floating tag)
  2. System
    test / uat: automatic deployment
    Database migration (uat snapshots the database first) → deploy command delivered over the AWS Systems Manager channel (no SSH, no long-term keys) → pull images → rolling update → health-check smoke test
  3. Owner
    prod: deploys after manual approval
    Pushes to the main branch only build images, never deploy; a production release is triggered manually in the pipeline (human gate) and then follows the same automated flow
  4. System
    Release complete, notification delivered
    Deployment results are pushed as messages; to roll back, redeploy the previous versioned image — done in minutes

Failure recovery

ScenarioRecoveryTarget
Bad application releaseRoll back to the previous versioned imageMinutes
Production database failureMulti-AZ standby takes over automaticallyAutomatic, typically 1–2 minutes
Accidental data changeRDS point-in-time recovery (PITR)Any moment within the past 35 days
Server failureInfrastructure is codified — rebuild to the same spec; images and configuration all live in the cloudHours

Day-to-day monitoring

A metric crosses its threshold → the alarm fires → e-mail reaches the operations owner immediately. Key alarms include: service down (zero healthy targets — caught earlier than user reports), application errors (5xx), slow responses (P95 > 3 s), disk / memory / storage watermarks, and database connection counts. A two-tier daily cost budget alarm makes unusual spend visible the same day.

9Known risks & recommendations

All items below are known, temporary arrangements from the migration period and are on the management list, ordered by recommended priority:

LevelItemCurrent state & impactRecommendation
HIGH Publicly readable file links To keep legacy file links working, all storage buckets temporarily allow public object reads; anyone holding a link can fetch the file without signing in Move the application to pre-signed (time-limited) URLs, then switch public read off
HIGH Kafka console reachable from the internet The Kafka console (kafka-ui) used to read verification-code messages — including production's — is currently open to the internet, protected only by its login credentials; the production console touches real data Restrict to an IP allow-list or VPN access; treat as the top-priority security item
MEDIUM Wide-open CORS Bucket CORS allows any origin (migration-period integration convenience) Narrow to the actual product domain list
LOW Leftover snapshots and backup copies 8 manual database snapshots and several in-instance backup copies from the migration still occupy space Clean up in batches once rollback needs are ruled out
LOW Frontend build skips type checking 16 pre-existing type errors; the build temporarily uses a no-check path — no functional impact Fix the errors, then restore the standard build
LOW Legacy environment decommissioning A few containers still run in the original hosting account; its certificate expires 2026-09-15 Shut down completely once the rollback window closes, ending charges in the old account
Overall assessment

The infrastructure meets production standards: network isolation, encryption, backups, monitoring and release controls are all in place and verified. The risks above are known, controlled, migration-period leftovers with clear remediation paths; the two HIGH items should be prioritized in an upcoming iteration.
