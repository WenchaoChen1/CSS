Delivery Line Map · v1 · 本地版

交付线路图

一条主线、三段线路、十三个站点。每段之间设一道门禁，过不了就停车；四条虚线是返工支线——它们才是工期真正流失的地方。

需求线 开发线 交付线 阶段门禁（换乘站，不通过不放行） 返工支线（原路退回）

每站交出什么

站点不是「阶段」，是可交付物的交接点。没有产出物的活动不设站——它属于站内工作。

三道门禁的放行条件

门禁只有两种结果：放行，或者退回上一站。不存在「先过、后面补」——那等于把门禁取消了。

Gate 01 · 需求 → 开发需求基线

  • PRD 与原型通过三方评审，无未决问题
  • 每条需求都有一条可测的验收标准
  • 范围与排期已书面确认
  • 变更通道已约定：走变更单，重估工期

把关人：项目负责人

Gate 02 · 开发 → 交付提测准入

  • CI 流水线全绿，构建产物可部署
  • 单元测试覆盖 ≥ 80%，新增代码无下降
  • 代码审查与安全审查无阻塞项
  • 研发自测冒烟用例全部通过

把关人：研发负责人 · 测试负责人

Gate 03 · 交付 → 收尾交付归档

  • UAT 业务签字，验收标准逐条核对
  • 线上 48 小时无 P0 / P1 故障
  • 文档、配置、运维手册已归档
  • 复盘完成，改进项落到负责人

把关人：项目负责人

四条返工支线的代价

返工不是异常，是流程的一部分。差别只在于它退回多远——越靠后发现，退回的路越长。

支线 退回路径 触发条件 典型代价
驳回补正 需求评审 → 产品设计 验收标准写不成可测的句子；异常流或权限没设计 0.5–2 天
CR 打回 代码审查 → 编码自测 存在阻塞级问题：安全、数据正确性、缺测试 0.5–1 天
缺陷返工 集成测试 → 编码自测 P0 / P1 缺陷，或回归打破了既有功能 1–3 天
回炉重估 UAT 验收 → 需求分析 做出来的东西业务不认：需求理解偏差，或验收标准本身就错了 整段重走
