# 付款方式枚举一致性排查报告（2026-10-27）

2026-10-27 · 在线版：https://claude.ai/artifact/2e3dDPvz5pYNFeMc255S1R（本地底稿，与在线版同步维护）

付款方式（payment method）在这套系统里有四份"事实源"：后端代码枚举、PostgreSQL 枚举类型 `paymentmethod`、数据表 `payment_method`、前端 TypeScript 枚举。四份里**后端代码枚举、表的 `code` 列、前端主枚举三者目前是一致的（13 个 code，表 12 行 + 只给退款用的 STORE_CREDIT 不建行）**，但 **PG 枚举类型多出一个 2024 年遗留的 `INVOICES`**，前端还残留两份 2024 年的 3 值旧枚举，另有报价单、OCR、AI 助手三条"自由文本写进枚举列"的路径，以及月结单 PDF 直接打印机器码的问题。本报告按严重程度列出全部不一致，并给出统一到"一个事实源"的对齐方案。

代码一律以 `origin/main` 为准（origin/test、origin/uat、origin/main 在付款方式相关文件上内容相同，已核实）。本机的两个检出都停在 `test` 分支且落后远程约 100 个提交，排查时没有用它们。数据库实测了 test、uat 两个 RDS 库（alembic 均为 `32e15648b82e`）；**prod 库因自动模式拦截生产读取没有实测**，核查方法见第六节。

## 四、不一致清单

### 高

**H1 · PG 枚举多一个 INVOICES，代码枚举没有**
库 14 个标签，代码 13 个。现在没有数据用它，所以不报错；但只要有一行写进 INVOICES（SQL 直灌、老数据恢复），SQLAlchemy 把它读成 `PaymentMethod` 时会抛 `LookupError`，整条查询失败。这是"数据库枚举与代码枚举不一致"的根问题。

**H2 · 月结单 PDF 打印机器码而不是名字**
四个供应商月结单模板 `core_app/src/templates/monthly_statement_{kabona,kens,four_seasons,international_wholesale}.html` 直接渲染 `invoice.payment_method`，餐厅月结单 `restaurant_monthly_statement.html` 渲染的 `description` 在 `orders/services.py:2991,3014` 被赋成 `dto.order.payment_method`。2026-10-16 枚举改成 value==name 之后，这些 PDF 从打印 "Credit Card" 退化成打印 `CREDIT_CARD`、`MONEY_ORDER`。同一系统的发票 PDF（`invoice_render.py:247` 用 `.label`）和前端页面（i18n）显示的是名字。test / uat 的订单里已有 CREDIT_CARD、MONEY_ORDER、GOOGLE_PAY 数据，会实际出现在月结单上。

**H3 · AI 助手复制订单硬编码旧标签 "Cash"**
`ai_assistant/server.js:544` 复制订单时固定发 `payment_method: "Cash"`，`:120`、`:537` 的提示文案也写 "Cash"；创建订单工具的参数描述（`:80`）举例 `"Cash", "CREDIT_CARD"`。后端 `restaurants/transport/requests.py:193` 的 `payment_method: PaymentMethod` 只接受 code，"Cash" 会被 pydantic 拒绝（422）。复制订单功能在枚举改 code 之后必然失败。

**H4 · 餐厅端查看供应商财务页只画 3 个旧选项**
`src/ui/pages/Vendor/ui/Finance/constants.ts` 用 `vendors/entity.ts` 的 3 值旧枚举渲染 Credit Card / Cash / Invoices 三个禁用复选框。接口 `GET /restaurants/{r}/vendors/{v}/finances` 返回的是供应商设置的全部 code（13 个之内），所以供应商设了 CHECK、ACH、ZELLE 等，餐厅这边一个都看不到；"Invoices" 则永远不会被勾上。

**H5 · STORE_CREDIT "仅退款可用" 只靠前端**
代码注释和前端（`useRecordPayment.ts:155-162` 只在退款方式列表里追加 STORE_CREDIT）都把它限定为退款方式，表里也不建行。但后端所有接受 `PaymentMethod` 的请求模型（下单、订单编辑、客户财务、记录付款、送达收款）都没有排除它。直接调接口就能把 STORE_CREDIT 存成 `order.payment_method`、`client_finances.payment_methods` 或 `type=PAYMENT` 的 `order_payment`，收款汇总会把它当成真实收款，且不会给客户加余额。

### 中

**M1 · 报价单付款方式是第五套取值，且是自由文本**
`src/ui/pages/Quotation/ui/QuotationInfo/EditInfoModal.tsx:48` 硬编码 `['Cash', 'ACH', 'Paypal', 'Stripe']`（"Paypal" 拼写与表里的 "PayPal" 不同）再加 "Add new" 自定义，原样写进 `quotation.payment_method` varchar。转订单时 `parse_payment_method` 按 code 或英文标签不区分大小写匹配，匹配不到一律归 OTHER。test 库已经有 "My method"、"信用卡" 两条，转订单后都会变成 OTHER，用户不会得到提示。

**M2 · OCR 识别建单是第二条自由文本路径**
Eden AI 识别出的 `payment_method` 是任意字符串，用户还能在识别结果表单里改成任意字符串，`invoices/services.py:1568` 用同一个 `parse_payment_method` 转换：票面写 "Visa"、"Net 30" 变 OTHER，票面没写**默认变 CASH**（`payments/domains.py:44-45`），而不是 OTHER 或报错。订单付款方式与原始发票不一致且无提示。

**M3 · 给人看的名字有四套来源，管理端还能改其中一套**
后端 `PAYMENT_METHOD_LABELS`（PDF 用）、表 `payment_method.name`（选择器用）、前端 `public/locales/{en,zh}/common.json` 的 `paymentMethods`（列表 / 详情用，经 `utils/paymentMethods.ts` 按 code 映射）、前端 `vendors.json`（餐厅端供应商财务页用，"Credit card" 小写 c 与其他三套不同）。四套现在碰巧一致。管理端 `PATCH /admin/payment-methods/{id}` 允许给系统行改名（服务层只在删除时检查 `is_system`），把 "Cash" 改成别的名字后，选择器显示新名字，PDF 和其他页面仍显示旧名字。

**M4 · 新增一个付款方式要改五处，管理端"新增"却是死胡同**
一个新方法要同步：后端枚举 + `PAYMENT_METHOD_LABELS`；新迁移 `ADD VALUE` + `INSERT payment_method`；前端 `EditOrderInfoModal.tsx` 的 12 项 `FALLBACK_PAYMENT_METHODS`；前端 `LABEL_KEYS` + en/zh 两份 i18n。没有单一事实源。而管理端 `POST /admin/payment-methods` 只收 `name`，新建的行 `code` 永远为空，`GET /payment-methods` 按 `code IS NOT NULL` 过滤，所以它不会出现在任何付款方式选择器里（test 库的 "Eric payment method 1" 就是例子），只能在主数据库订阅页按 id 选中。

**M5 · 表的 `code` 列没有数据库级约束**
`payment_method.code` 是 `varchar(64)`，不是 `paymentmethod` 枚举类型，没有 CHECK 或外键。表与枚举之间只有迁移脚本手工对齐这一层约定。如果有人用 SQL 把 code 填成枚举外的值或不同大小写（如 "Cash"），接口会原样下发给前端，前端提交后后端 422。

**M6 · 后端测试还在发旧标签，且没有测试守护三方一致**
`main_app/restaurants/tests/add_restaurant_order/tools.py:35` 仍是 `payment_method='Cash'`，该目录 3 个成功用例 + 5 个错误用例在 pydantic 这一层就会 422，一个都过不了；CI 目前不跑 pytest（`cicd.yml` 里是 TODO），所以没暴露。全库没有任何测试断言"代码枚举 = PG 枚举标签 = 表系统行 code"，H1 这类漂移测试发现不了。

### 低

**L1 · 前端旧类型 `PaymentMethodDTO` 仍在用**
`src/models/vendors/api.ts:199` 的 `paymentMethods: PaymentMethodDTO[]`（3 值）是下单、客户信息步骤、订单编辑、记录付款四个选择器的实际取值源，运行时拿到的是 13 个 code；`src/models/orders/api.ts:142,499` 同样。开发者只能用 `String()` / `string[]` 绕开类型检查。

**L2 · 客户财务页残留"自定义付款方式"死代码**
`src/ui/pages/Client/ui/Finance/types.ts:12` 的 `customPaymentMethod` 与 `Finance.tsx` 里的输入框从未进入提交数据；`client_finances.payment_methods` 是枚举数组，本来也存不了自由文本。

**L3 · `paymentTerm` 字段里装的是付款方式**
`orders/services.py:3801` 把 `packing_slip.order.payment_method` 赋给 `payment_term`，前端 `ConfirmModal.tsx:122` 用 `billTo.paymentTerm === PaymentMethods.CASH` 判断现金单。值是一致的，但名字把"付款条件"（cash_on_delivery / net_30）和"付款方式"混在一起，容易被后人按字面改错。

**L4 · `SYSTEM_PAYMENT_METHOD_NAMES` 只有 9 个**
`core/payment_methods/domains.py` 列的是 2026-05 首次种子的 9 个名字，表里系统行是 12 个。只有测试在用，注释也说明了是原始种子，但名字容易让人以为是完整集合。

**L5 · 文档过时**
`docs/orders业务规格-2026-08-21.html` 把 `order.payment_method` 记为 "Enum(11 值)"；`docs/ocean-island/` 下多份方案要求新表"照抄 payment_method 范式（name unique / created_by_user_id / 删除 409）"，而 `created_by_user_id` 列已在 `b8e4c17d2f93` 删除，`code` / `sort_order` 两列文档没提。

**L6 · 本机本地库落后**
见第三节末。

## 五、对齐方案（建议）

**原则**：三个机器码集合必须相等——PG 枚举标签 = 后端 `PaymentMethod` = 表 `payment_method` 的系统行 `code`（STORE_CREDIT 作为唯一例外，只在前两者里）；给人看的名字只保留一个来源。

| 步骤 | 做什么 | 对应 |
| --- | --- | --- |
| 1 | 处理 INVOICES。推荐从 PG 枚举里去掉：PostgreSQL 不能 `DROP VALUE`，要新建类型、6 个枚举列逐个 `ALTER COLUMN ... TYPE` 后删旧类型，期间锁表，放在低峰或停机窗口做；先确认 prod 没有数据用它。不推荐把 INVOICES 加回代码——它没有业务含义。 | H1 |
| 2 | 五个月结单模板改成渲染 `.label`（或表 name），`services.py:2991,3014` 的 `description` 同改。 | H2 |
| 3 | `ai_assistant/server.js` 复制订单改为透传原单的 `payment_method` code（找不到才用 `"CASH"`），三处文案与参数描述同改。 | H3 |
| 4 | 餐厅端供应商财务页改用 `models/clients/entities.PaymentMethods` 渲染全部 13 个（或按接口返回动态渲染），用 `formatPaymentMethod` 取 common i18n；删除 `vendors/entity.ts` 与 `common/api.ts` 的两份旧枚举，`vendors/api.ts`、`orders/api.ts` 的类型改为主枚举；`vendors.json` 的四个付款方式键删掉。 | H4、L1、M3 |
| 5 | 后端在接受 `PaymentMethod` 的请求模型上加校验：只有退款允许 STORE_CREDIT。 | H5 |
| 6 | 报价单选择器改调 `GET /payment-methods`，`quotation.payment_method` 改存 code（迁移回填：按标签匹配，匹配不到的归 OTHER 并记日志）。OCR 路径把"空值默认 CASH"改为 OTHER 或要求用户确认。 | M1、M2 |
| 7 | 显示名统一：以表 `payment_method.name` 为唯一来源，前端选择器与列表都从接口取；PDF 从表取；删除 `PAYMENT_METHOD_LABELS` 和前端 `LABEL_KEYS`（i18n 只保留中文翻译时可保留 zh 一套）。管理端改名接口禁止改 `is_system` 行。 | M3 |
| 8 | 表 `code` 列改为 `paymentmethod` 枚举类型（或加 CHECK），管理端新增方法要么同时要求 `code`、要么下线"新增"。删掉前端 `FALLBACK_PAYMENT_METHODS`，没拿到接口数据就显示空。 | M4、M5 |
| 9 | 加一条测试：`set(PaymentMethod) - {STORE_CREDIT} == 表系统行 code 集合 == PG 枚举标签集合 - {STORE_CREDIT}`；把 `tools.py:35` 的 `'Cash'` 改为 `PaymentMethod.CASH`；CI 接上 pytest。 | M6 |
| 10 | 删 `customPaymentMethod` 死代码；`payment_term` 改名为 `payment_method`；更新两处文档；重拉本地库。 | L2–L6 |
