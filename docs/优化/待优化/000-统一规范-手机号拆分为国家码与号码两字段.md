## 一、现在是什么问题

### 1. 表结构现状

**排查方法**：用三种方式查，互相补漏。① 按列名：`information_schema.columns` 里列名匹配 `phone|fax|mobile|tel|country|dial|contact`。② 按内容：用电话正则扫 public 下所有 `varchar/text` 列，JSON 列则扫键名。③ 按代码：Grep 后端、`sms_sender` 和前端。结论如下：

- 结构化电话列一共 **37 个，分布在 29 张表**。有对应国家列的只有 **2 列**（`quotation_card_contact`、`quotation_vendor_client` 的 `phone_country_code`），而且是 `varchar(16)`，没有 CHECK，存的是拨号码。
- 内容扫描在其它列里命中的数字串都在自由文本里（`chat_message.text`、`order_comment.comment`、`order_packing_slip_issue.details`、商品名等），或者是邮编、单号，都不是结构化电话，不在本专项范围内。**例外（终审补充）**：`company_audit_log.details`（varchar(1000)，存 JSON 文本）由 Master Database 写入公司电话 / 联系人 / 应付账款联系人的变更快照，键 `phone_number`、`accounting_payable.phone_number` 的 from/to 里是号码原值：569 行中 44 行含 E.164（`+99999999999` 37 个、`+9-999-999-9999` 6 个），另有 6 个空串。它是审计日志、只增不改，归 002 处理（规定新写入口径，存量不回写）。`audit_client_log.details`（jsonb）实查无电话键。
- 视图、物化视图、函数、触发器里都没有引用电话列（`pg_views` / `pg_matviews` / `pg_proc` / `pg_trigger` 实查结果为 0）。
- OCR 库 `css-test-ocr` 没有电话列，3 个 JSONB 列（`ocr_job.request_payload`、`ocr_job_result.result_json` / `summary_json`）所在表都是 0 行。
- 地址里的国家列都是自由文本，没法拿来推出电话属于哪国：`manufacturer_profile.country` / `mailing_country` 的取值有 `USA` 和 `United States` 两种写法，`mafsi_area.country` 的取值是 `United States` / `Canada` / `International`。restaurant、store、company 都没有国家列。

**异常值与偏差**

1. **脱敏导致位数多一位**：在 2,145 个 +1 号码里，本国号码是 11 位的有 1,128 个（**52.6%**），而美国号应当是 10 位。+380 的 4,922 个里，10 位（乌克兰应当是 9 位）的有 600 个。这些号码在 test 和 uat 上会被 `phonenumbers.is_valid_number` 判为无效。
2. **17 个单字符 `9`**（`company_billing` 11 个，`company_contact_person` 6 个）是空串被“尾部加 1”脱敏后的结果。它们在 prod 上对应的是空串，加上 `company_billing` 本来就有的 12 个空串，prod 上这两列合计应有约 29 个空串，而这两列都是 NOT NULL。
3. **已有国家列的取值口径不统一**：同样表示美国，既有 `1`（22 行）也有 `+1`（15 行）。`+3741`（2 行）不是任何地区的拨号码（亚美尼亚是 +374）。这两张表 300 个号码里，有 261 个（87%）国家列为空。
4. **示例号被当成真实数据存进库**：代码里 `Field(examples=[...])` 的英国示例号在 10 张表里出现了 32 次。
5. **过短和非号码的值**：8 位纯数字 16 个（报价相关表）、长度 18 的 `9 (999) 999-99-999` 9 个（`quotation.from_phone`）、单字符 17 个。

### 4. 影响与风险

1. **分不出国家**：37 列里只有 2 列有国家列，而且这两列存的是拨号码。+1 号码里有 51 个加拿大区号、4 个加勒比和美属领地区号；+7 由 RU 和 KZ 共用，+44 由 GB、GG、JE、IM 共用。地址里的国家是自由文本（`USA` / `United States` / `Canada`），没法兜底。按国家做报表、展示、短信路由，都得依赖 phonenumbers 按区号临时推断。
2. **不带 `+` 的 301 个值只能靠猜**：后端至少有 4 种处理方式——原样返回、`region='US'`、`region=None`、硬编码 `'+1'`；前端还有一种“两个方向都试”的猜法。同一个值在导入、展示、邀请短信里可能得出不同的结果。
3. **身份唯一性、登录、去重不可靠**（P0）：`user.phone_number` 的唯一约束建在原始字符串上，登录查找是全等比较，而 3 个认证请求字段没做任何归一化。客户导入和发票搜索各用一套“只比数字 + 假设 +1”的逻辑。同一个号码换一种写法，就可能绕过唯一性、被误判为“已是登录账号”，或者登录失败。
4. **短信可能静默失败**：发送前不校验 E.164。带分隔符的公司号码正是 master database 邀请短信的收件来源。Twilio 拒收后只在 sms_sender 日志里有记录，重试 `SMS_SENDER_RETRIES_COUNT` 次就丢弃。**日志里还明文记录了验证码和号码**，属于安全问题，应在阶段 0 一并修掉。
5. **展示不一致**：`convert_phone_number` 把非北美号码格式化成不带国家码的国内写法，而 +380 占全库 64%，对账单、发票 PDF 模板（`CSS_backend-main/core_app/src/templates/monthly_statement_*.html`、`order_invoice_*.html`）直接输出这个字符串。前端的 `formatPhone` 又是另一套规则。
6. **校验口径打架**：后端有的地方用 `is_possible`，有的用 `is_valid`，还有只认美国格式的正则；前端用 `isValidPhoneNumber`。结果是前端能过的号码，后端可能拒；或者导入时校验过了，落库的形态却不一样。
7. **已有的国家列已经开始漂移**：`1`、`+1`、`+3741` 混存，前端两处提交的格式不一样。说明“自由填写拨号码”这种口径守不住。
8. **脱敏数据会放大问题，也会误导结论**：test 和 uat 上 52.6% 的 +1 号码多了一位。用户在 test 上编辑资料时，即使号码没改，也过不了 `PhoneNumber` 的 `is_valid` 校验。迁移在 test 上 dry-run 的“无效号”比例会远高于 prod，不能直接外推。

## 二、怎么处理（方案）

### 1. 目标表结构

#### 1.1 统一规范 S1–S10（正文）

| 编号 | 规范 | 理由 |
|------|------|------|
| **S1 拆分** | 每个电话类字段由两个表字段组成：**国家列 + 号码列**。号码列**保持原列名不变**，只新增国家列 | 改名会牵动大量 ORM、DTO、API 和前端字段，新增一列的影响面最小 |
| **S2 国家列命名** | 号码列名去掉末尾的 `_number`，再加上 `_country_code`。例如：`phone_number`→`phone_country_code`，`fax_number`→`fax_country_code`，`temporary_phone_number`→`temporary_phone_country_code`，`main_phone`→`main_phone_country_code`，`sales_phone`→`sales_phone_country_code`，`accounting_phone`→`accounting_phone_country_code`，`customer_service_phone`→`customer_service_phone_country_code`，`cell_phone`→`cell_phone_country_code`，`office_phone`→`office_phone_country_code`，`contact_phone`→`contact_phone_country_code`，`from_phone`→`from_phone_country_code`，`ship_to_phone`→`ship_to_phone_country_code`，`sales_person_phone`→`sales_person_phone_country_code`。分机列 `*_ext` 不变。认证表的多态列 `contact`（`contact_type` = `EMAIL` 或 `PHONE_NUMBER`）新增 `contact_country_code`，只有 PHONE_NUMBER 行填写 | 规则机械统一，可以直接写进验收 SQL（§二.6 的 A 段就是按这条规则自动推导期望的列名） |
| **S3 国家列取值**（推荐口径，**待你拍板**，见 §二.7 D1） | ISO 3166-1 alpha-2 大写（`US` / `CA` / `UA` / `GB`），`varchar(2)`，`CHECK (x ~ '^[A-Z]{2}$')`。国家列的值必须是**规范国家**：由 `pkg/phone` 按号码本身推出，不是用户选了什么就存什么 | +1 由 US、CA 和加勒比多国共用，+7 由 RU 和 KZ 共用，+44 由 GB、GG、JE、IM 共用，只存拨号码没法还原国家；反过来，存 ISO 可以无损推出拨号码。前端的国家选择器本来就是 ISO。规范国家能保证“国家 + 本国号码”和 E.164 一一对应，唯一约束才能成立 |
| **S4 号码列取值** | 只存**本国有效号码**（national significant number，NSN），而且是纯数字：不含 `+`、国家码、空格、横线、括号，也不含国内长途前缀 0。`CHECK (x ~ '^[0-9]{4,15}$')`。号码列原有的类型（varchar(64)/(50)/(255)）**不改** | 一律用 `phonenumbers.national_significant_number()` 取值：意大利这类本身就带前导 0 的 NSN 会被正确保留，而真正的长途前缀会被去掉。收窄列宽要改写整表，没有必要 |
| **S5 成对约束** | `CHECK ((号码 IS NULL) = (国家 IS NULL))`。空串一律转成 NULL | 杜绝“有号码没国家”和“有国家没号码”的半拆状态 |
| **S6 组合与对外** | E.164 = `'+'` + 国家对应的拨号码 + 本国号码。**只在应用层**用 phonenumbers 组合，用于短信、登录查找、去重和唯一性判断。兼容期内 API 响应同时返回 `*_country_code`、号码列和只读的 `*_e164`；前端全部过渡完成后去掉 `*_e164` | 库里不再存第三份冗余值。兼容期让前后端可以按任意顺序发布 |
| **S7 公共能力** | 后端新建唯一入口 `app/pkg/phone`（基于 phonenumbers）：`parse(raw, default_region) -> (country ISO, national, e164, is_valid)`、`format_e164(country, national)`。**禁止**各处自写正则、硬编码 `'+1'`、到处散落 `parse(..., 'US')`。前端统一用 `react-phone-number-input` 的“国家 + 号码”两个值提交 | 3.2 / 3.5 列出的 N 套实现就是这个问题的根源 |
| **S8 迁移** | alembic 按领域写迁移，**一个领域一组 revision**。步骤：加国家列（可空）→ 用 Python 回填（`+` 开头的按 E.164 解析；不带 `+` 的按业务默认区域 US 解析，并做标记）→ 把号码列改写成本国号码 → 解析失败的行保留原值，并输出清单（禁止静默丢弃）→ 加 CHECK（先 NOT VALID，再 VALIDATE）。downgrade 时还原为 `'+'` + 拨号码 + 号码 | 失败行有据可查，可以回滚；CHECK 分两步加，不会长时间锁表 |
| **S9 优先级** | P0：登录、短信、身份唯一性相关；P1：对外展示与联系的业务主数据，以及会转成用户的数据；P2：快照、低频、已废弃、非结构化数据 | 与台账 README 的口径一致 |
| **S10 已优化判定** | 以下全部满足才算已优化：两列都存在，且类型、约束符合 S2–S5；号码列里没有 `+` 和分隔符；号码非空的行，国家列 100% 合法；写入路径统一经过 `pkg/phone`；前端提交与展示正确 | 对应 §二.6 的 SQL A、B、C 和代码检查 |

#### 1.3 DDL 模板

```sql
-- R1（expand，与兼容版代码同一次发布）：只加列。号码列不动，旧代码完全不受影响
ALTER TABLE <表> ADD COLUMN <前缀>_country_code varchar(2);

-- R3（contract，问题清单清零之后）：先 NOT VALID 再 VALIDATE，不会长时间锁表
ALTER TABLE <表> ADD CONSTRAINT ck_<表>__<前缀>_cc   CHECK (<前缀>_country_code ~ '^[A-Z]{2}$') NOT VALID;
ALTER TABLE <表> ADD CONSTRAINT ck_<表>__<前缀>_nat  CHECK (<号码列> ~ '^[0-9]{4,15}$') NOT VALID;
ALTER TABLE <表> ADD CONSTRAINT ck_<表>__<前缀>_pair CHECK ((<号码列> IS NULL) = (<前缀>_country_code IS NULL)) NOT VALID;
ALTER TABLE <表> VALIDATE CONSTRAINT ck_<表>__<前缀>_cc;
ALTER TABLE <表> VALIDATE CONSTRAINT ck_<表>__<前缀>_nat;
ALTER TABLE <表> VALIDATE CONSTRAINT ck_<表>__<前缀>_pair;

-- 认证流水表（contact 是多态列）：只约束 PHONE_NUMBER 行
ALTER TABLE sign_in_data ADD CONSTRAINT ck_sign_in_data__contact_phone CHECK (
  CASE WHEN contact_type = 'PHONE_NUMBER'
       THEN contact ~ '^[0-9]{4,15}$' AND contact_country_code ~ '^[A-Z]{2}$'
       ELSE contact_country_code IS NULL END) NOT VALID;
```

1. `<前缀>` 指国家列名去掉 `_country_code` 后的部分，例如 `phone`、`fax`、`main_phone`、`temporary_phone`、`contact`。约束名不能超过 63 字节，按上面的命名，最长的一个是 `ck_onboarding_manufacturer_subdivision_member__phone_pair`，57 字节。如果超长，就把表名截短，再加 8 位 hash 后缀。
2. 正则 CHECK 对 NULL 的结果是 NULL，也就是放行；“两列同时为空或同时有值”由 `_pair` 约束来保证。**号码列是 NOT NULL 的表也必须加 `_pair`**（此时它和国家列的 NOT NULL 等价，但 §二.6 的 B 段按“存在成对 CHECK”验收，不能只靠 SET NOT NULL 代替）。约束名一律按本模板 `ck_<表>__<前缀>_cc` / `_nat` / `_pair`（认证流水表为 `ck_<表>__contact_phone`），001–009 的 DDL 已按此统一（终审修订）。
3. 唯一性：只有 `user` 需要唯一约束，改为 `UNIQUE (phone_country_code, phone_number)`。成立的前提是 S3 的“规范国家”：同一个号码不管用户在界面上选的是 US 还是 CA，入库时国家都由号码本身推出，所以不会出现两种写法。
4. 对于 NOT NULL 的号码列，如果遇到空串或无法解析的值，先判断业务上是否真的必填：真必填的，就阻断上线，人工补录；不是必填的，就去掉 NOT NULL，把值置为 NULL。`company_billing` 的空串属于后一种，具体由 002 决定。
5. 模型侧用 `pkg.phone.sqlalchemy.phone_check_constraints(table, number_col, country_col, where=None)` 生成同样的 `CheckConstraint` 放进 `__table_args__`，保证 alembic autogenerate 和模型不会漂移。

### 2. 数据迁移

#### 2.1 每个领域一组 revision（S8 的物理落地方式）

CI 的执行顺序是 `build-push → migrate → deploy`（`CSS_backend-main/.github/workflows/cicd.yml:106-107,134-135`）。从迁移跑完到新容器起来之前，**旧代码还在线上服务**。如果在同一个 revision 里就把号码列改成本国号码，旧代码会拿 E.164 去全等查询，手机号登录、找回密码会在这几分钟里失败（001 §二.5 已经指出这一点）。因此统一按下面的方式拆：

| revision | 内容 | 与代码的关系 |
|----------|------|--------------|
| **R1 expand** | 加国家列（可空）；只回填国家列，**号码列不动**；把预计会解析失败的行写进清单表 | 与“兼容版代码”同一次发布。兼容版代码能读两种形态（号码以 `+` 开头时按 E.164 解析，否则读“国家 + 本国号码”），写入一律用新形态 |
| **R2 rewrite** | 把号码列改写成本国号码（只处理国家列已回填、号码仍以 `+` 开头的行）；补回填 R1 之后旧代码新写进来的行；更新问题清单 | 至少晚 R1 一个发布 |
| **R3 contract** | 加 3 条 CHECK，先 NOT VALID 再 VALIDATE；如果清单里还有未解决的行，迁移直接失败（fail fast）；001 在这里换唯一约束 | 与“去掉兼容分支”的代码同一次发布 |

1. 低流量的 P2 表（例如 008 的快照、`deprecated_*`）可以把 R1、R2 合成一个 revision，同时要接受迁移窗口里的短暂不一致。
2. P0 表（001），以及会发短信的表（002 的 `company_phone_number`、005 的 `client.temporary_phone_number`、006 的酒牌联系人）必须拆开。
3. **不要在问题清单清零之前加 NOT VALID 约束**：NOT VALID 的约束对后续 UPDATE 也会校验。某一行号码不合格时，即使只是更新它的其它列（例如 `user.last_login`），也会被拒。

#### 2.2 冻结的拆分函数（迁移不得 import 应用代码）

新建 `CSS_backend-main/core_app/src/app/migrations/phone_v1.py`。它只依赖 phonenumbers 和 sqlalchemy，**发布后就不再修改**；以后规则要变，就新建 `phone_v2.py`。之所以不复用 `app.pkg.phone`，是因为它会随业务演进而变化，而旧的 revision 必须保证每次重放结果一致。现有 25 个迁移 import 了应用代码（模型、枚举、domains），这种写法不要再沿用。

```python
# app/migrations/phone_v1.py —— 冻结：发布后禁止修改
import re
import phonenumbers
from phonenumbers import NumberParseException

DEFAULT_REGION = 'US'                      # S8：不带 + 的号码按业务默认区域解析
NATIONAL_RE = re.compile(r'^[0-9]{4,15}$')

def _region_of(n):
    # 规范国家：先按号段判断（US/CA、RU/KZ、GB/JE…）；判断不出来（无效号、脱敏号）再退回该拨号码的主国家
    r = phonenumbers.region_code_for_number(n) or phonenumbers.region_code_for_country_code(n.country_code)
    return None if r in (None, 'ZZ', '001') else r

def split(raw, default_region=DEFAULT_REGION):
    """返回 (iso, national, reason)。reason=None 表示正常；其余取值见 2.3。
    default_region 只影响不带 + 的值：007 用地址国家、008 用门店 / 报价客户的国家作提示，其余各篇用默认 US"""
    s = (raw or '').strip()
    if not s:
        return None, None, 'empty'
    region = None if s.startswith('+') else default_region
    try:
        n = phonenumbers.parse(s, region)
    except NumberParseException:
        return None, None, 'unparseable'
    iso = _region_of(n)
    national = phonenumbers.national_significant_number(n)   # 意大利式的前导 0 会保留
    stripped = False
    if region is None:                          # 带 + 的号码做往返校验（004 发现的问题，终审并入）
        digits = re.sub(r'[^0-9]', '', s)
        cc = str(n.country_code)
        rest = digits[len(cc):]
        if digits.startswith(cc) and rest != national and rest.endswith(national) and rest[:-len(national)].strip('0'):
            # 例：+7 后紧跟 8 的号码，phonenumbers 会把 8 当成 RU 国内长途前缀剥掉，'+' + 拨号码 + 本国号码 ≠ 原值。
            # 用原值剩余数字保证无损；只是 '(0)' 这类前导 0 的写法则接受 phonenumbers 的结果（S4 不存长途前缀 0）
            national, stripped = rest, True
    if iso is None or not NATIONAL_RE.fullmatch(national):
        return None, None, 'unparseable'
    if region:                                  # 不带 + 的号码：按默认区域猜的，需要复核
        return iso, national, 'default_region'
    if stripped:
        return iso, national, 'nsn_prefix_stripped'
    if not phonenumbers.is_valid_number(n):     # 能拆开但号码无效（脱敏号属于这一类）
        return iso, national, 'invalid_split'
    return iso, national, None

def shape(raw):
    return re.sub(r'[0-9]', '9', raw or '')     # 清单和日志里只记录形态，不记录原值

def to_legacy(iso, national):                   # downgrade 用：还原成 '+' + 拨号码 + 号码
    return f'+{phonenumbers.country_code_for_region(iso)}{national}'
```

R1 / R2 共用的回填函数（按主键 keyset 分页，每批 1,000 行，用 `executemany` 更新）：

```python
ISSUE_UPSERT = sa.text(
    'INSERT INTO phone_migration_issue (revision, table_name, column_name, row_pk, reason, shape) '
    'VALUES (:rev, :t, :c, :k, :reason, :shape) '
    'ON CONFLICT (table_name, column_name, row_pk) DO UPDATE SET revision = EXCLUDED.revision, '
    'reason = EXCLUDED.reason, shape = EXCLUDED.shape, created_at = now(), resolved_at = NULL, resolution = NULL')

def backfill(conn, *, table, pk, num_col, cc_col, rewrite, revision, where='true'):
    """R1（rewrite=False）只补国家列，号码不动；
    R2（rewrite=True）把号码列改写成本国号码，同时补上 R1 之后旧代码新写进来、还没有国家列的行。"""
    pending = f"({cc_col} IS NULL OR {num_col} !~ '^[0-9]{{4,15}}$')" if rewrite else f'{cc_col} IS NULL'
    set_clause = f'{cc_col} = :cc' + (f', {num_col} = :nat' if rewrite else '')
    stats, last = Counter(), None
    while True:
        page = f'AND {pk} > :last ' if last is not None else ''
        rows = conn.execute(sa.text(
            f'SELECT {pk} AS k, {num_col} AS v FROM {table} '
            f'WHERE ({where}) AND {num_col} IS NOT NULL AND {pending} {page}'
            f'ORDER BY {pk} LIMIT 1000'), {'last': last}).all()
        if not rows:
            break
        updates, issues = [], []
        for r in rows:
            iso, nat, reason = split(r.v)
            stats[reason or 'ok'] += 1
            if iso:
                updates.append({'k': r.k, 'cc': iso, 'nat': nat})
            if reason:
                issues.append({'rev': revision, 't': table, 'c': num_col, 'k': str(r.k),
                               'reason': reason, 'shape': shape(r.v)})
        if updates:
            conn.execute(sa.text(f'UPDATE {table} SET {set_clause} WHERE {pk} = :k'), updates)
        if issues:
            conn.execute(ISSUE_UPSERT, issues)
        last = rows[-1].k
    log.info('phone backfill %s.%s rewrite=%s %s', table, num_col, rewrite, dict(stats))  # 只打印计数，绝不打印号码
```

1. 上面的 SQL 是拼出来的，但表名、列名都来自迁移里写死的常量，不接收任何外部输入。
2. R1 之后，兼容版代码读取时一律调用 `parse(号码, default_region=国家)`。这个调用对 E.164 整串、本国号码、R1 留下的不带 `+` 原值（如 `999-999-9999`）都能给出同一个结果。
3. 空串（`empty`）的处理：可空列直接置为 NULL；NOT NULL 列按 1.3 第 4 条处理。
4. `unparseable` 的行：号码保持原值，国家列为 NULL，必须等人工处理完才能进入 R3。
5. R3 的开头先做两件事：① 源行已经合规的清单行，标记为 `resolution = 'fixed'`；② 统计剩下的 `unparseable` / `empty` 行，只要不为 0，就 `raise`，让迁移失败。

#### 2.3 公共问题清单表（各篇统一用这一张）

```sql
-- 由阶段 0 的 revision 创建，所有领域的 revision 都依赖它；全部 R3 上线 30 天后由收尾 revision 删除
CREATE TABLE phone_migration_issue (
  id                  bigserial    PRIMARY KEY,
  revision            varchar(32)  NOT NULL,      -- 产生这一行的 alembic revision
  table_name          varchar(63)  NOT NULL,
  column_name         varchar(63)  NOT NULL,
  row_pk              text         NOT NULL,
  reason              varchar(32)  NOT NULL,      -- 见下表
  shape               text,                       -- 原值的形态（数字替换成 9）；不保存原值
  legacy_country_code varchar(16),                -- 原有国家列的值（只有 009 用到）
  created_at          timestamptz  NOT NULL DEFAULT now(),
  resolved_at         timestamptz,
  resolution          varchar(32),                -- fixed / accepted / nulled
  CONSTRAINT uq_phone_migration_issue_row UNIQUE (table_name, column_name, row_pk)   -- 同一行重复回填只保留最新结论
);
CREATE INDEX ix_phone_migration_issue_open ON phone_migration_issue (table_name, column_name) WHERE resolved_at IS NULL;
```

| reason | 含义 | 处理 | 各篇里的叫法 |
|--------|------|------|--------------|
| `invalid_split` | 能拆成“国家 + 本国号码”，但 `is_valid_number` 判为无效 | 已经拆分，可以通过 R3（CHECK 只校验格式，不校验有效性）。prod 上应抽样复核；test 和 uat 上基本都是脱敏造成的 | 001 的 `invalid_split`、009 的 `INVALID_KEPT` |
| `nsn_prefix_stripped` | 带 `+`，但 phonenumbers 把本国号码开头的数字当作国内长途前缀剥掉了（实测 phonenumbers 9.0.41：`+7` 后接 `8` + 10 位的 13 位值，本国号码会少掉开头的 8） | 已按原值剩余数字拆分（无损），可以通过 R3；交业务复核这个号码本身是否录错。test 上预期 2 行（004 的 `+78…`），prod 需看 dry-run | 004 的 `nsn_prefix_stripped` |
| `default_region` | 不带 `+`，按 US 解析出来的 | 已经拆分，交业务复核（test 上最多 284 个，即 301 个不带 `+` 的值减去 17 个单字符；实际数以 dry-run 为准） | 001 的 `:default_us`、009 的 `DEFAULT_US` |
| `unparseable` | 解析失败、区域未知或长度不合规 | **保留原值**，国家列为 NULL。必须人工修正或置为 NULL，否则不能进入 R3 | 004 的 `unparseable`、009 的 `FAIL` |
| `empty` | 空串或纯空白 | 可空列置为 NULL；NOT NULL 列按 1.3 第 4 条处理 | 004 的 `empty` |
| `country_conflict` | 旧国家列（拨号码）和号码本身推出的国家冲突，或者旧值根本不是合法拨号码（例如 `+3741`） | 以号码推出的结果为准，同时记录旧值 | 只有 009 有 |

不保存原值的原因：清单表会一直放在 prod 库里（prod 是真实数据）。`unparseable` 的行原值本来就还在源列里；能拆开的行，用 `to_legacy()` 就能可逆还原。

#### 2.4 downgrade

1. R3 的 downgrade 直接删掉 3 条约束；001 还要把唯一约束换回 `user_phone_number_key`。
2. R2 的 downgrade：`UPDATE <表> SET <号码列> = to_legacy(<国家列>, <号码列>) WHERE <国家列> IS NOT NULL`，用 Python 分批执行。这个还原有损：原来的分隔符和“没有 `+`”的写法回不来，但还原出来的 E.164 和原值是同一个号码，这是 S8 允许的。
3. R1 的 downgrade：删除国家列，再删除这个 revision 写进清单表的行。

#### 2.5 在脱敏数据上 dry-run 的偏差

- 在 test 上：1,128 个 +1 号码、600 个 +380 号码会被标成 `invalid_split`（多出的那一位是脱敏加上去的）。17 个单字符值会被标成 `unparseable`（在 prod 上它们是空串，会被标成 `empty`）。32 个 Swagger 示例号会被判为有效的英国号码。

- 在 test 和 uat 上，**不能通过“去掉末尾的 1”来修复**：那等于把脱敏还原回去。要不要调整脱敏口径，见 §二.7 D3。

```python
# core.py（接口草案）
DEFAULT_REGION = 'US'                       # 全后端唯一定义“号码不带国家码时按哪国解析”的地方

@dataclass(frozen=True)
class PhoneParts:
    country: str | None      # 规范的 ISO alpha-2（按号码本身推出，同 phone_v1._region_of）
    national: str | None     # 本国号码 NSN，纯数字
    e164: str | None
    is_valid: bool
    assumed_region: bool     # 原值不带 +，是按 default_region 解析的
    error: str | None        # empty / unparseable / unknown_region

def parse(raw: str | None, default_region: str | None = DEFAULT_REGION) -> PhoneParts: ...
def from_parts(country: str | None, national: str | None) -> PhoneParts: ...   # 读库、或收到新格式的请求时用
def format_e164(country: str, national: str) -> str: ...                       # 短信、登录查找、去重
def format_display(country: str | None, national: str | None) -> str: ...      # +1 用 NATIONAL，其它用 INTERNATIONAL（与前端 formatPhone 一致）
def mask(e164: str | None) -> str: ...                                         # 日志打码：只留拨号码和后 2 位
```

`schemas.py`：

1. 用 `phone_fields_validator(number_field, country_field, *, required)` 生成一个 `model_validator(mode='before')`，并且**返回一个新 dict**，不修改入参。它做三件事：
   - 兼容期：如果请求里只有号码、并且号码以 `+` 开头，就按 E.164 解析。
   - 正常情况：按 `country_field` 解析号码。
   - 写回“规范国家 + 本国号码”；`is_valid` 为 False 时返回 422。
2. `PhoneIn` 是字段名为 `phone_country_code` + `phone_number` 的现成类型，供最常见的命名直接使用（001 里已按这个约定写）。
3. 响应侧用 `computed_field` 输出 `*_e164`。
4. 请求和响应一律用**扁平字段**，与表的列名对齐。报价模块现有的嵌套 `phone: {country_code, number}`（`main_app/quotation/transport/requests.py:82-86`）是否改成扁平，由 009 决定，但它的取值必须改用本规范的 ISO 口径并经过校验。

1. 所有迁移和代码都在 **ops 分支**上、基于主线的 alembic head 编写，然后按 `ops → test`、`ops → uat`、`ops → main` 三条线分别晋级。**绝不能从 test 合并到 uat**：那样会把 uat 的 alembic 头从 `b3d9f1a2c4e5` 换成 support-demo 线的头。

### 7. 待决策（请拍板）与决策记录

#### D1：国家列存 ISO 还是存拨号码（S3）

| 维度 | **ISO 3166-1 alpha-2（推荐）** | 拨号码（例如 `+1`） |
|------|--------------------------------|---------------------|
| 能否还原国家 | 能。ISO → 拨号码是确定的（`country_code_for_region`） | 不能。+1 对应 25 个地区，+7 对应 RU/KZ，+44 对应 GB/GG/JE/IM |
| 本库实证 | +1 号码里有加拿大区号 51 个、加勒比和美属领地 4 个，只存 `+1` 就会丢掉这 55 个号码的国家 | 现有的拨号码列已经漂移：`1` 和 `+1` 混存，还出现了无效值 `+3741` |
| 唯一性 | 规范 ISO + 本国号码 ⇔ E.164，`user` 可以直接建复合唯一约束 | 也能一一对应，但必须先把 `1` / `+1` 的写法统一成一种 |
| 前端 | 国家选择器本来就是 ISO（`getCountries()`），零转换 | 要从 ISO 转成拨号码，回显时又要从拨号码猜回 ISO（+1 默认显示美国旗） |
| 与地址国家口径 | 可以借此建立全库统一的国家口径（目前地址国家是 `USA` / `United States` 这样的自由文本） | 和地址国家是两套口径 |
| 在 SQL 里组 E.164 | 不能直接拼，要靠应用层或参照表（见 D4） | `'+' \|\| 拨号码 \|\| 号码` 可以直接拼 |
| 无效号码（脱敏号） | 退回该拨号码的主国家（+1→US、+7→RU、+44→GB），可接受 | 不受影响 |
| 非地理号码（+800 等） | 没有 ISO，拒收（本库 0 个） | 可以存 |
| 改造量 | 35 列新增 varchar(2)，009 的 2 列从 varchar(16) 改为 varchar(2)，并把 39 个旧值转成 ISO | 35 列新增 varchar(4)；009 只要统一写法 |

**推荐 ISO**。理由：唯一能无损表达“哪个国家”的就是 ISO，与前端组件天然一致，也能顺带统一全库的国家口径。“SQL 里不能直接拼 E.164”这个缺点可以用 D4 的参照表弥补，而且按 S6，E.164 本来就只在应用层组合。
如果你决定改用拨号码：把 §二.1 所有 DDL 里的 `varchar(2)` / `^[A-Z]{2}$` 改为 `varchar(4)` / `^\+[1-9][0-9]{0,2}$`（统一带 `+`），`pkg/phone` 的 `country` 字段改为拨号码，唯一性和展示逻辑不变。各篇文档在拍板后据此同步修改。

#### D2：不带 `+` 的号码按哪国解析

- 推荐：按 **US** 解析，标记为 `default_region`，交业务复核。test 上最多 284 个，绝大多数是 10 位或 11 位的美式写法。
- 备选：一律不猜，全部进清单人工处理。

#### D3：test / uat 的脱敏口径要不要改（005 提出）

- 现状：号码“尾部加 1”，导致 test 上 52.6% 的 +1 号码无效，编辑资料时过不了 `is_valid` 校验，dry-run 的失败率也偏高。
- 005 的建议：保留国家码和区号，本地号改成 555-01XX 这类虚构号段。
- **推荐暂不改**。现在的“故意无效”是一道安全设计，它保证测试环境的短信绝对打不到真人。改成“有效号码”的话：除 NANP 的 555-01XX（每个区号只有 100 个号）之外，大多数国家没有虚构号段，很容易撞上真人或违反 `user` 的唯一性。替代做法：
  1. 迁移里 `invalid_split` 照样拆分、照样能通过 CHECK（CHECK 不校验有效性）。
  2. 写入时的 `is_valid` 校验在 test 和 uat 上可以用一个配置开关放宽到 `is_possible`，默认严格。
  3. 需要真实收短信的测试，用团队登记的测试手机号单独注册账号（注意：`swp*` 只是邮箱不脱敏，手机号同样被加了 1）。

#### D4：要不要建国家参照表

可选做法：建 `ref_phone_country (iso varchar(2) PK, dial_code smallint)`，数据由 phonenumbers 生成，37 个国家列都加外键。

- 好处：库内就能拼 E.164、做报表，并且能挡住 `ZZ` 这类形式上合法但不存在的值。
- 代价：37 个外键，每次升级 phonenumbers 都要同步这张表。

推荐**暂不建**，CHECK 加 `pkg/phone` 已经够用；以后报表确有需要时，再建参照表或视图。

#### D5：兼容期多长

- 推荐：`*_e164` 和“只有 E.164”的请求分支，保留到**三个环境的前端都上了新版本之后的下一次后端发布**为止，至少跨过一个 sprint。
- prod 的前端可能比 test 晚，所以要逐个环境确认后再删。
