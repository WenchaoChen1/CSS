**`user.phone_number` 形态与脱敏**

| 形态 | 行数 | 构成 |
|------|------|------|
| `+99999999999`（12 字符） | 203 | +1 有效长度 201、+7 有效长度 2 |
| `+999999999999`（13 字符） | 401 | +1 脱敏多 1 位 284、+380 有效长度 66、+7 脱敏 47、+374 脱敏 3、+375 有效长度 1 |
| `+9999999999999`（14 字符） | 329 | +380 脱敏 325、+44 脱敏 3、+381 1（2024 年老数据，按口径应已加 1，但 10 位本国号码仍落在塞尔维亚合法长度内，phonenumbers 判有效） |
| `+99999999999999`（15 字符） | 2 | +358 脱敏 2 |

- test 库按 2026-08-22 口径脱敏：**手机号尾部加了一位 1**。按创建时间看：2026-08-22 及以前从老 dev 备份带过来的 776 个号码中，按长度看 **665 个（85.7%）比该国常规长度多 1 位**；用 phonenumbers 9.0.41 实测，**664 个判无效、112 个有效**（差的 1 个是上表的 +381 号码，加 1 后仍有效）；2026-08-23 以后新注册的 159 个全部是 +1、长度 12，全部正常。所以 test 上的“有效率”统计会严重偏低，这是脱敏造成的，不代表 prod。
- **拆分后会撞唯一约束**：把号码去掉国家码后，有 **1 对**号码的本国号码完全相同（一个 +375、一个 +380，都是 9 位）。如果只加国家列、还保留 `UNIQUE (phone_number)`，这一对会冲突，所以唯一约束必须改成 `(国家, 号码)` 组合。

**认证流水表**

- `sign_in_data` 是登录流水：4,155 个 PHONE 行只来自 **71 个用户（72 个不同号码）**，单个用户最多 1,716 行；全表 6,752 行里 5,931 行是 30 天以前的。代码里没有任何清理逻辑，这几张表一直在增长。
- 流水表里的号码长度**全部正常**（+1 都是 12 字符、+380 都是 13、+7 都是 12）——也就是说**流水表没有被脱敏**。流水表 342 个不同号码中，**238 个恰好等于某个用户当前 `phone_number` 去掉末尾 1**；`sign_in_data` 4,155 行里 3,299 行要在 contact 后面补一个 1 才能对上 `user.phone_number`（另 791 行直接相等，41 行对应的用户已没有手机号，24 行是用户后来改过号）。邮箱同理：`sign_in_data` 有 1,088 个 EMAIL 行要在前面补 1 才能对上用户邮箱。
- `additional_sign_in_data` 有 2 行被 phonenumbers 9.0.41 判为无效：1 个 +7 号码（本国号码以 1 开头，RU/KZ 无此号段），1 个 +44 号码只有 9 位本国号码。另有 1 个 +1（多米尼加 DO 区号）号码交换码以 0/1 开头，按 NANP 规则不合法，但 phonenumbers 判为有效，迁移不会把它列入清单。前 2 行的验证码都未激活（`confirmation_code.activated_at` 为空），也没有写进 `user`。它们说明“添加联系方式”这个入口并不校验号码（见下文 W2）。

### 4. 影响与风险

1. **国家只能从前缀猜，+1 有歧义**：+1 被 US / CA / 加勒比共用，`user` 中至少 12 个 +1 号码不是美国号。任何“+1 就是美国”的逻辑（例如 L9c 的 `registration_phone_keys`、各处 `'US'` 默认值）都会把它们判错。按国家做的任何事情（短信通道 / 合规、展示格式、按国家统计）都没有可靠的列可用。
2. **登录 / 找回密码靠字符串精确相等**：4 个认证入口里有 3 个（登录、找回密码、添加联系方式）入参是普通 `str`，后端不做规范化，`get_user` 用 `filter_by` 精确匹配（邮箱却做了 `lower()`）。前端只要提交的不是严格的 E.164，就会返回“账号或密码错误 / 用户不存在”。**F5 是一个现成的 bug**：找回密码页是自由文本框，用户输入 `+9 (999) 999-9999` 能通过前端校验，提交到后端后按原样比较，必然找不到用户。
3. **唯一性口径不一致**：数据库唯一约束是精确字符串，应用层查重有精确 / 只比数字 / 数字加 US 假设三种口径。现在数据 100% 是 E.164，所以还没出事；但 W2 不校验格式，只要验证码短信能送达，写进一个 `(999) 999-9999` 这样的写法就能绕过 `user_phone_number_key`，形成两个账号共用一个号码，后续登录 / 查重的结果取决于走哪条路径。另外，如果只是把号码拆成本国号码，而不改唯一约束，test 上已经有 1 对跨国（+375 / +380）号码会冲突。
4. **短信可能静默发不出去**：验证码直接把 `contact` 原样交给 Twilio，后端不保证 E.164；W2 这类不校验的入口一旦写进格式不对的号码，Twilio 会拒收，sms_sender 只记日志，前端仍然显示“验证码已发送”。`additional_sign_in_data` 里已经有 2 行疑似无效号码。另外 sms_sender 把号码和验证码一起写进日志（安全 / 隐私问题）。
5. **展示不一致**：对账单 PDF 和发票 PDF 都用 NATIONAL 格式，非 +1 号码印出来没有国家码（UA 号码印成以 0 开头的本国格式，读者无法判断国家）；前端 `formatPhone` 对非 +1 号码保留国际格式，和 PDF 口径不一致；`formatPhone` 一旦收到 ISO 国家码会静默忽略。
6. **test / uat 数据的偏差（附带发现）**：`user.phone_number` 被脱敏（尾部加 1），认证流水表却**没有**脱敏。结果是：test 上老用户用原来的号码无法登录；流水表还保留了 238 个脱敏前的号码（邮箱同理）。uat 用同一口径脱敏，推测情况相同，需要核实。这不在本文验收范围内，建议另开一项处理（流水表补脱敏或清理）。注意 `mask-residual-pii.sh` 没有 swp 排除逻辑，**不能直接在这两个库上跑**。
7. **流水表无限增长**：没有清理逻辑，`sign_in_data` 有 88% 的行是 30 天以前的。这些行对业务没有价值，但每次迁移、备份、脱敏都要处理它们。

## 二、怎么处理（方案）

### 1. 目标表结构

| 号码列（名称不变） | 新增国家列（S2） | 国家列类型 | 号码列取值 | 约束 |
|------|------|------|------|------|
| `"user".phone_number` | `phone_country_code` | `VARCHAR(2)` NULL | 本国有效号码（national significant number）纯数字 | ISO 正则、号码正则、成对；唯一约束改为 `(phone_country_code, phone_number)` |
| `sign_up_data.contact` | `contact_country_code` | `VARCHAR(2)` NULL | PHONE_NUMBER 行：本国号码纯数字；EMAIL 行：邮箱不变 | 按 `contact_type` 分支的 CHECK |
| `sign_in_data.contact` | `contact_country_code` | 同上 | 同上 | 同上 |
| `reset_password_data.contact` | `contact_country_code` | 同上 | 同上 | 同上 |
| `additional_sign_in_data.contact` | `contact_country_code` | 同上 | 同上 | 同上 |

**认证流水表要不要拆？结论：要，而且和 `user` 用同一个口径（国家列 + 本国号码），不采用“只补国家列、contact 继续存 E.164”。** 理由：

1. **流水表是 `user` 的直接上游和比对对象**。注册时，`sign_up_data.contact` 原样变成 `user.phone_number`（`CSS_backend-main/core_app/src/app/internal/core/auth/services.py:257-264`）；登录、找回密码在最后一步用 `contact` 回查用户、确认号码没被改过（`CSS_backend-main/core_app/src/app/internal/core/auth/services.py:357-364`、`532-538`）；“安全校验”行直接复制 `user.phone_number`（`CSS_backend-main/core_app/src/app/internal/core/auth/services.py:413-414`）。两边形态一致，`unpack_contact_data` 就能直接展开成 `{'phone_country_code': …, 'phone_number': …}` 交给 `get_user`。如果一边存本国号码、一边存 E.164，每个比对点都要转换一次，这正是 L9 三种口径形成的原因。
2. **只补国家列（contact 保持 E.164）不划算**：`contact` 是 EMAIL / PHONE 多态列，无论哪种做法 CHECK 都要按 `contact_type` 分支写，工作量相同；但 E.164 方案会让 `user` 和流水表有两种号码形态，以后改一处忘一处。它唯一的好处是短信可以直接用 `contact`，而改成 `pkg.phone.format_e164(contact_country_code, contact)` 只是一行代码。
3. **完全不改（只当日志）也不行**：注册时建用户需要国家，国家只能来自 `sign_up_data`。不改的话，就要在 `sign_up` 里再解析一遍 E.164，等于在流水表外面又加了一个解析入口，违反 S7。
4. **成本低**：test 上一共 4,531 个 PHONE 行，全部是 `+` 开头、长度有效（流水表没有脱敏），解析成功率预计接近 100%。

**国家列的取值规则（本文特别要求）**：写入的 ISO 必须是 `pkg.phone.parse` 推出来的**规范国家**（`region_code_for_number`，推不出时退到该拨号码的主国家），不能直接用前端选择器里的值。例如用户选了 US，输入的却是加拿大区号的号码，入库应是 `CA`。这样 `(国家, 本国号码)` 和 E.164 一一对应，组合唯一约束才等价于“E.164 唯一”，不会出现 `(US, X)` 和 `(CA, X)` 两行指向同一个 +1 号码、绕过唯一约束的情况（验收 V7 专门检查这一点）。

DDL 草案（约束命名按 000 §二.1.3：`ck_<表>__<前缀>_cc` / `_nat` / `_pair`，流水表为 `ck_<表>__contact_phone`；DDL 放在迁移最后执行）：

```sql
-- 1) 加列
ALTER TABLE "user" ADD COLUMN phone_country_code VARCHAR(2);
COMMENT ON COLUMN "user".phone_country_code IS 'ISO 3166-1 alpha-2 of phone_number (canonical region from phonenumbers)';
ALTER TABLE sign_up_data            ADD COLUMN contact_country_code VARCHAR(2);
ALTER TABLE sign_in_data            ADD COLUMN contact_country_code VARCHAR(2);
ALTER TABLE reset_password_data     ADD COLUMN contact_country_code VARCHAR(2);
ALTER TABLE additional_sign_in_data ADD COLUMN contact_country_code VARCHAR(2);

-- 2) （Python 回填之后）空串归一为 NULL（当前 0 行，保留以防 uat/prod 有）
UPDATE "user" SET phone_number = NULL WHERE btrim(phone_number) = '';

-- 3) 唯一约束：旧的按字符串，换成 (国家, 本国号码)
ALTER TABLE "user" DROP CONSTRAINT user_phone_number_key;
ALTER TABLE "user" ADD CONSTRAINT uq_user_phone_country_code_number UNIQUE (phone_country_code, phone_number);

-- 4) user 的 CHECK（先 NOT VALID）
ALTER TABLE "user" ADD CONSTRAINT ck_user__phone_cc
    CHECK (phone_country_code ~ '^[A-Z]{2}$') NOT VALID;
ALTER TABLE "user" ADD CONSTRAINT ck_user__phone_nat
    CHECK (phone_number ~ '^[0-9]{4,15}$') NOT VALID;
ALTER TABLE "user" ADD CONSTRAINT ck_user__phone_pair
    CHECK ((phone_number IS NULL) = (phone_country_code IS NULL)) NOT VALID;

-- 5) 流水表的 CHECK（四张表同构，以 sign_in_data 为例）
ALTER TABLE sign_in_data ADD CONSTRAINT ck_sign_in_data__contact_phone CHECK (
       (contact_type = 'EMAIL'        AND contact_country_code IS NULL)
    OR (contact_type = 'PHONE_NUMBER' AND contact_country_code ~ '^[A-Z]{2}$' AND contact ~ '^[0-9]{4,15}$')
) NOT VALID;
-- sign_up_data / reset_password_data / additional_sign_in_data 同样各加一条：
--   ck_sign_up_data__contact_phone / ck_reset_password_data__contact_phone / ck_additional_sign_in_data__contact_phone

-- 6) VALIDATE（第 3-6 步都在 R3 执行；R3 开头若清单里还有 unparseable / empty 就直接失败，不先挂 NOT VALID，见“数据迁移”第 6 步）
ALTER TABLE "user" VALIDATE CONSTRAINT ck_user__phone_cc;
ALTER TABLE "user" VALIDATE CONSTRAINT ck_user__phone_nat;
ALTER TABLE "user" VALIDATE CONSTRAINT ck_user__phone_pair;
ALTER TABLE sign_up_data            VALIDATE CONSTRAINT ck_sign_up_data__contact_phone;
ALTER TABLE sign_in_data            VALIDATE CONSTRAINT ck_sign_in_data__contact_phone;
```

- 号码列保持 `VARCHAR(64)` / `VARCHAR(255)`，不缩短类型（长度交给 CHECK，降低 downgrade 复杂度）。
- 枚举在库里存的是名字 `'EMAIL'` / `'PHONE_NUMBER'`（SQLAlchemy `Enum` 默认存 name），CHECK 里要写大写。
- 如果 000 号文档最终拍板“国家列存拨号码”（S3 备选口径）：把 `VARCHAR(2)` / `^[A-Z]{2}$` 换成 `VARCHAR(4)` / `^\+[1-9][0-9]{0,2}$`（与 000 §二.7 D1 一致），其余不变。那种口径下 `(拨号码, 本国号码)` 天然等价于 E.164，不需要“规范国家”这条规则，但会丢掉 US/CA 的区分。

### 2. 数据迁移

> **与 000 对齐（终审修订，优先于下文）**：本范围是 P0，按 000 §二.1 **拆成 3 个 revision**，五张表在每一步里同时处理：
> - **R1 expand**：加 5 个国家列；用冻结的 `app/migrations/phone_v1.py` 的 `backfill(rewrite=False)` 只回填国家列，号码列不动；问题行写 `phone_migration_issue`。与“兼容版代码”（按 `parse(号码, default_region=国家)` 同时认 E.164 整串和本国号码）同一次发布。
> - **R2 rewrite**：`backfill(rewrite=True)` 把号码改写成本国号码，并补齐 R1 之后旧代码新写的行。这样“迁移已跑、新代码未起”的窗口里，线上已经是兼容版代码，手机号登录不会失败（下文 §二.5 第 4 条的“失败几分钟”只在不拆分时出现）。
> - **R3 contract**：先查 `(国家, 本国号码)` 重复（有就中止），换唯一约束，再按清单清零与否加 CHECK（先 NOT VALID 再 VALIDATE）。
>
> 下面的代码块保留为**判定口径说明**（状态名对照：`invalid_split` 同 000，`*:default_us` = 000 的 `default_region`），落地时不要在 revision 里再复制一份 `_split`；清单写 000 §二.3 的 `phone_migration_issue`，不再只写 alembic 日志。

原稿写法：一个 alembic revision（users + auth 领域，五张表一起，因为唯一约束和流水表的比对必须同时切换）。迁移脚本只依赖 `phonenumbers` 和 SQL，**不 import 应用代码**（包括 `pkg/phone`），保证以后能重放。

```python
import logging
import re
from collections import Counter

import phonenumbers
import sqlalchemy as sa
from alembic import op
from phonenumbers import NumberParseException

log = logging.getLogger('alembic.runtime.migration')
DEFAULT_REGION = 'US'  # S8：不带 + 的按业务默认区域解析并标记（本范围当前 0 行）
AUTH_TABLES = ('sign_up_data', 'sign_in_data', 'reset_password_data', 'additional_sign_in_data')


def _region_of(n):
    # 规范国家：先按号段判（US/CA、RU/KZ、GB/JE…），判不出（无效号、脱敏号）再退到拨号码的主国家
    r = phonenumbers.region_code_for_number(n) or phonenumbers.region_code_for_country_code(n.country_code)
    return None if r in (None, 'ZZ', '001') else r


def _split(raw):
    """-> (iso, national, status)；status ∈ ok | invalid_split | unparseable，默认区域解析的追加 :default_us"""
    raw = (raw or '').strip()
    region = None if raw.startswith('+') else DEFAULT_REGION
    try:
        n = phonenumbers.parse(raw, region)
    except NumberParseException:
        return None, None, 'unparseable'
    iso = _region_of(n)
    if iso is None:
        return None, None, 'unparseable'
    national = phonenumbers.national_significant_number(n)  # 保留意大利式前导 0
    status = 'ok' if phonenumbers.is_valid_number(n) else 'invalid_split'
    return iso, national, status + (':default_us' if region else '')


def _shape(raw):
    return re.sub(r'[0-9]', '9', raw or '')  # 清单只输出形态，不输出原值（prod 是真实数据）


def upgrade():
    op.add_column('user', sa.Column('phone_country_code', sa.String(2), nullable=True))
    for t in AUTH_TABLES:
        op.add_column(t, sa.Column('contact_country_code', sa.String(2), nullable=True))

    conn = op.get_bind()
    stats, review = Counter(), []

    def backfill(table, key_col, num_col, cc_col, where):
        rows = conn.execute(sa.text(f'SELECT {key_col} AS k, {num_col} AS v FROM {table} WHERE {where}')).all()
        updates = []
        for r in rows:
            iso, nat, status = _split(r.v)
            stats[(table, status)] += 1
            if iso:
                updates.append({'k': r.k, 'cc': iso, 'nat': nat})
            if status != 'ok':
                review.append((table, str(r.k), status, _shape(r.v)))
        if updates:
            conn.execute(sa.text(f'UPDATE {table} SET {cc_col} = :cc, {num_col} = :nat WHERE {key_col} = :k'), updates)

    backfill('"user"', 'id', 'phone_number', 'phone_country_code',
             "phone_number IS NOT NULL AND btrim(phone_number) <> ''")
    for t in AUTH_TABLES:
        backfill(t, 'confirmation_session_id', 'contact', 'contact_country_code', "contact_type = 'PHONE_NUMBER'")

    # 换唯一约束前先确认 (国家, 本国号码) 没有重复（test 预期 0：E.164 去重后无重复）
    dup = conn.execute(sa.text(
        'SELECT count(*) FROM (SELECT 1 FROM "user" WHERE phone_country_code IS NOT NULL '
        'GROUP BY phone_country_code, phone_number HAVING count(*) > 1) d')).scalar()
    if dup:
        raise RuntimeError(f'{dup} duplicated (phone_country_code, phone_number) pairs in "user"; resolve first')

    # ……执行“目标表结构”里的 DDL 第 2-5 步……

    for (table, status), n in sorted(stats.items()):
        log.warning('phone split %s %s = %s', table, status, n)
    for table, key, status, shape in review:
        log.warning('phone split review %s %s %s %s', table, key, status, shape)

    if not any(s.startswith('unparseable') for (_, s) in stats):
        pass  # ……执行 DDL 第 6 步 VALIDATE……
    else:
        log.warning('unparseable rows remain: constraints left NOT VALID, VALIDATE in a follow-up data-fix revision')
```

步骤说明：

1. **加列**：五个国家列都可空。
2. **回填 `user`**：现有 935 行全部 `+` 开头，按 E.164 解析。`ok` / `invalid_split` 都写回（`invalid_split` 表示能判出国家、但号码本身无效，例如脱敏多出来的一位），并进复核清单。
3. **回填流水表**：只处理 `contact_type = 'PHONE_NUMBER'` 的行，规则同上。EMAIL 行不动，`contact_country_code` 保持 NULL。sign_in_data 4,155 行用 executemany 批量更新即可（prod 行数未知，行数过万时按 1,000 行分批）。
4. **换唯一约束**：先查 `(国家, 本国号码)` 重复，有重复就中止迁移（禁止静默合并账号）；没有重复再删 `user_phone_number_key`、建 `uq_user_phone_country_code_number`。
5. **清单**：`unparseable` 的行**保留原值、国家列留 NULL**，和 `invalid_split`、`*:default_us` 一起输出到 alembic 日志。清单只输出表名、主键、状态、形态（数字替换成 9），**不输出号码原值**。
6. **加约束**（R3）：只有该表 `unparseable` / `empty` 为 0 时才加，先 `NOT VALID` 再 `VALIDATE`；不为 0 时 R3 直接失败，先人工处理清单。**不能在清单未清零时先挂 NOT VALID**：NOT VALID 对后续 UPDATE 照样生效，问题行连 `last_login` 都更新不了，等于锁死这些账号的登录（000 §二.1 第 3 条）。

**downgrade**：对国家列非空的行，执行 `号码 = '+' || phonenumbers.country_code_for_region(iso) || 号码`（拨号码在 Python 里计算），即还原成 E.164；然后删除 7 个 CHECK、删除 `uq_user_phone_country_code_number`、重建 `user_phone_number_key UNIQUE (phone_number)`、删除 5 个国家列。本范围的原值全部是 E.164，所以 downgrade **无损**。还原后跨国同号的那一对重新带上国家码，不会冲突。

**dry-run 偏差**（必须写进 PR）：

- **test**：用 phonenumbers 9.0.41 对快照实测，`user` 为 `ok` 271（2026-08-23 以后新建的 159 + 老数据中仍有效的 112），`invalid_split` 664（脱敏多 1 位），`unparseable` 0。脱敏号大多判不出号段，会退到拨号码主国家：+1 的 3 个加拿大区号脱敏号会被判成 US（PR 区号那 1 个因 PR 有专属前导号段，仍判 PR），+7 全部判成 RU——这是脱敏造成的，prod 不受影响。长度正常的 8 个加拿大号码必须判成 CA（验收 V6）。
- **test 流水表**：没有脱敏，预计 4,529 行 `ok`，`additional_sign_in_data` 的 2 个疑似无效号码是 `invalid_split`。
- **uat**：和 prod 同源，用同一口径脱敏。用它演练流程、耗时、锁，以及跑完以后的登录 / 找回密码 / 添加联系方式。
- **prod**：真实数据，真实的有效率和 KZ / CA / JE 等非主国家的数量只能在 prod 上看到。上线前先用只读账号跑一遍本文“数据现状”的统计 SQL（只看计数和形态），记下基线。

```sql
WHERE schemaname = 'public' AND tablename = 'user' AND indexdef ILIKE '%phone%';

-- V4 user：号码只剩本国号码纯数字、国家 100% 合法且成对（期望 bad_number = 0, bad_country = 0, unpaired = 0；
--    nonnull 与迁移前基线一致，test 基线 935）
SELECT count(*) FILTER (WHERE phone_number IS NOT NULL)                                   AS nonnull,
       count(*) FILTER (WHERE phone_number !~ '^[0-9]{4,15}$')                            AS bad_number,
       count(*) FILTER (WHERE phone_number IS NOT NULL
                          AND (phone_country_code IS NULL OR phone_country_code !~ '^[A-Z]{2}$')) AS bad_country,
       count(*) FILTER (WHERE (phone_number IS NULL) <> (phone_country_code IS NULL))      AS unpaired
FROM "user";

-- V5 流水表：PHONE 行全部拆好、EMAIL 行没有国家（期望 bad_phone = 0, email_with_cc = 0；
--    phone_rows ≥ 迁移前基线，test 基线 291 / 4155 / 23 / 62）
SELECT t, phone_rows, bad_phone, email_with_cc FROM (
  SELECT 'sign_up_data' AS t,
         count(*) FILTER (WHERE contact_type = 'PHONE_NUMBER') AS phone_rows,
         count(*) FILTER (WHERE contact_type = 'PHONE_NUMBER' AND (contact !~ '^[0-9]{4,15}$'
                            OR contact_country_code IS NULL OR contact_country_code !~ '^[A-Z]{2}$')) AS bad_phone,
         count(*) FILTER (WHERE contact_type = 'EMAIL' AND contact_country_code IS NOT NULL) AS email_with_cc
  FROM sign_up_data
  UNION ALL
  SELECT 'sign_in_data',
         count(*) FILTER (WHERE contact_type = 'PHONE_NUMBER'),
         count(*) FILTER (WHERE contact_type = 'PHONE_NUMBER' AND (contact !~ '^[0-9]{4,15}$'
                            OR contact_country_code IS NULL OR contact_country_code !~ '^[A-Z]{2}$')),
         count(*) FILTER (WHERE contact_type = 'EMAIL' AND contact_country_code IS NOT NULL)
  FROM sign_in_data
  UNION ALL
  SELECT 'reset_password_data',
         count(*) FILTER (WHERE contact_type = 'PHONE_NUMBER'),
         count(*) FILTER (WHERE contact_type = 'PHONE_NUMBER' AND (contact !~ '^[0-9]{4,15}$'
                            OR contact_country_code IS NULL OR contact_country_code !~ '^[A-Z]{2}$')),
         count(*) FILTER (WHERE contact_type = 'EMAIL' AND contact_country_code IS NOT NULL)
  FROM reset_password_data
  UNION ALL
  SELECT 'additional_sign_in_data',
         count(*) FILTER (WHERE contact_type = 'PHONE_NUMBER'),
         count(*) FILTER (WHERE contact_type = 'PHONE_NUMBER' AND (contact !~ '^[0-9]{4,15}$'
                            OR contact_country_code IS NULL OR contact_country_code !~ '^[A-Z]{2}$')),
         count(*) FILTER (WHERE contact_type = 'EMAIL' AND contact_country_code IS NOT NULL)
  FROM additional_sign_in_data
) x ORDER BY t;

-- V6 国家分布核对（test 期望（按迁移里的 _region_of 对快照实测）：US 476、UA 391、RU 49、CA 8、GB 3、AM 3、FI 2、BY 1、PR 1、RS 1；
--    +1 共 485 = US 476 + CA 8 + PR 1；长度有效的 8 个加拿大号必须是 CA，3 个加拿大区号的脱敏号退回 US 属预期）
SELECT phone_country_code, count(*) FROM "user"
WHERE phone_number IS NOT NULL GROUP BY 1 ORDER BY 2 DESC;

-- V7 规范国家：共用拨号码的国家之间不能出现同一本国号码（期望 0 行；否则说明有写入路径没走 pkg.phone、绕过了组合唯一约束）
SELECT grp, phone_number, count(*) FROM (
  SELECT phone_number,
         CASE WHEN phone_country_code IN ('US','CA','AG','AI','AS','BB','BM','BS','DM','DO','GD','GU','JM','KN','KY',
                                          'LC','MP','MS','PR','SX','TC','TT','VC','VG','VI') THEN '+1'
              WHEN phone_country_code IN ('RU','KZ') THEN '+7'
              WHEN phone_country_code IN ('GB','GG','JE','IM') THEN '+44' END AS grp
  FROM "user" WHERE phone_number IS NOT NULL
) s WHERE grp IS NOT NULL
GROUP BY grp, phone_number HAVING count(*) > 1;

-- V8 上线后新产生的登录流水与用户口径一致（psql 里先执行 \set release_ts '2026-11-01 00:00+00'，换成实际上线时间；
--    期望 total = consistent）
SELECT count(*) AS total,
       count(*) FILTER (WHERE u.phone_country_code = s.contact_country_code AND u.phone_number = s.contact) AS consistent
FROM sign_in_data s JOIN "user" u ON u.id = s.user_id
WHERE s.contact_type = 'PHONE_NUMBER' AND s.created_at >= :'release_ts'::timestamptz;
```
