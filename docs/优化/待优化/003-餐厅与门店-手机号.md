- **脱敏偏差**：位数超过该国正常长度（疑似脱敏多出 1 位）的有 restaurant 183 行、store 86 行，全部创建于 2026-08-22 重建之前。脱敏脚本会给所有不以 1 结尾的 phone 文本列尾部追加 `1`（`docs/环境运维执行脚本/05-数据库运维/anonymize-db.sh:130-134`）。脱敏前创建的行里，restaurant 有 199/200、store 有 123/124 以 1 结尾，和这个规则对得上。2026-08-22 之后新建的行：restaurant 20 行中 19 行是正常长度的 +1 十位号码、1 行不带 `+`（见 2.4）；store 35 行全是正常长度的 +1 十位号码。**所以 test 里号码“长度/有效性”的统计不代表 prod，prod 是未脱敏的真实数据。**
- **+1 歧义**：+1 号码里，区号属于加拿大的 restaurant 1 行、store 4 行，属于加勒比 NANP 地区的 store 1 行。只存 `+1` 分不出 US / CA / 加勒比。+7 的 50 行首位都是 9 或 8（俄罗斯号段），但 +7 同样被 KZ 共用。
- **明显的测试号**：含 7 位以上连续相同数字的 restaurant 10 行、store 2 行；区号为 123（NANP 非法区号）的 store 3 行。
- **区号 / 号段 Top**：+1 区号 restaurant 为 234（20）、334（10）、949（7），其后 235 / 281 / 512 / 713 各 4 行并列；store 为 234（22）、713（14）、949（7）、212（7）、235（6）。+380 号段 65 在 restaurant 中占 85/103，在 store 中占 48/56。

#### 2.4 异常值

- **restaurant 有 1 行 `999-999-9999`**：10 位数字，不带国家码，带横线，结构上是合法的 NANP 号码。这一行 status=`UNREGISTERED_WITH_ORDERS`，company_id 为空，创建于 2026-10-12（快照当天）。关联的 `client.temporary_phone_number` 形态完全一样，说明它是 sprint4“代客下单”路径 `prepare_order_restaurant` 把客户临时号码原样拷进来的（见 3.1 W5）。这是目前唯一会写入非 E.164 值的路径，而且只存在于 test。
- **空串**：目前 0 行。但 W5 在客户没有号码时会写 `''`（`client.temporary_phone_number or ''`），而客户表单只要求“邮箱或手机填一个”，所以以后一定会出现空串。
- **重复号码**：restaurant 有 11 组 / 39 行、store 有 9 组 / 43 行共用同一个号码（连锁店或测试数据）。重复本身不算错，但现有的“按号码数字匹配”逻辑（3.2 R6/R7）会因此多命中。

#### 2.5 下游已经出现的后果（同一个库里的数据）

- `quotation.from_phone`（报价单上的门店号码快照）104 行**全都不带 `+`**。和门店关联起来看：来自 +1 门店的 75 行形如 `(999) 999-9999[9]` 或 11 位纯数字；来自 +380 门店的 20 行形如 `9999 999 9999`；来自 +7 门店的 9 行形如 `9 (999) 999-99-999`。外国门店的号码被印成了“本国格式”，国家码没了，看报价单的人无法拨打。
- `quotation.ship_to_phone` 里有 53 行和 `restaurant.phone_number` 原值完全一样（E.164；带 restaurant_id 的 53 行全部如此，其中 19 行同时带 vendor_client_id），而只带 vendor_client_id 的 51 行中 50 行是纯数字（取自 `quotation_vendor_client.phone_number`，`quotation/services.py:504`）。同一张报价单上 from_phone 与 ship_to_phone 是两种格式，不同报价单之间 ship_to_phone 也是两种格式。
- `quotation_vendor_client` 230 行中，212 行以 `+` 开头但 `phone_country_code` 为空；其中带 restaurant_id 的 110 行（108 行号码与 restaurant 完全一致）国家列全为空：从 restaurant 复制号码时没写国家列（3.2 R5）。

### 4. 影响与风险

1. **分不出国家**：+1 被 US / CA / 加勒比共用（test 的 +1 门店里有 4 行是加拿大区号、1 行是加勒比区号），+7 被 RU / KZ 共用。列里只有拨号码，没有国家，以后按国家做税务、地址或短信路由都没有依据。
2. **单据上外国号码丢了国家码**：`convert_phone_number` 输出 NATIONAL 格式，报价单 `from_phone` 已经有 29 行（UA 20、RU 9）印成了本国格式。发票、对账单上的 ship_to_phone、store_sales_phones 走的是同一个函数，同样会丢。test 中 +1 以外的号码 restaurant 占 149/220（不含那 1 行不带 `+` 的 NANP 形态号码），store 占 78/159。
3. **展示不一致**：同一个门店号码，在设置列表里是 E.164 原串，门店详情里是本国格式，装箱单上是 E.164 原串，发票上是本国格式，前端 `formatPhone` 又是国际格式；两条邀请邮件路径（R15）一条印 E.164、一条印本国格式。
4. **去重和匹配失败**：未注册餐厅去重（R6）按纯数字比较，同一个号码带国家码和不带国家码时不相等；W5 又把不带国家码的原文写进 restaurant。两者叠加，同一家餐厅会被重复建成多个未注册餐厅。发票识别（R7）用子串匹配，号码越短误命中越多。
5. **脏数据入口还开着**：W5 不校验，可以写空串，也可以写任意分隔符。sprint4 一旦合入主线，uat / prod 也会开始积累非 E.164 数据。
6. **规则分散**：`phoneconverter.py` 的三个函数、lv_import 的 `normalise_phone` / `registration_phone_keys`、invoices 里内联的 `normalize_phone`、`clients/services.py` 写死的 `region='US'`、前端 `formatPhone` 自己的 `resolve`，一共 5 套。S7 要求的统一入口还不存在。
7. **拷贝扩散**：号码被复制进 `quotation.from_phone` / `ship_to_phone` 和 `quotation_vendor_client.phone_number`。源头不拆，下游表永远拿不到国家。

### 1. 目标表结构

按统一规范 S1–S5（国家列取值按 S3 推荐口径 ISO alpha-2，最终以 000 号文档的“待决策”为准）。

### 2. 数据迁移

> **与 000 对齐（终审修订，优先于下文）**：本文是 P1 主数据，按 000 §二.1 落地为 **R1 expand**（加列、只回填国家，号码不动）→ **R2 rewrite**（改写本国号码）→ **R3 contract**（清单清零后加约束、`store` 国家列 SET NOT NULL）。下文“迁移 A” = R1 + R2，“迁移 B” = R3；原稿“迁移 A 最后执行 6 条 NOT VALID”作废——NOT VALID 对之后的 UPDATE 照样生效，清单未清零时会把问题行锁死。拆分统一调用 `app/migrations/phone_v1.py`；状态名对照：`FAIL` = `unparseable` / `empty`，`invalid_number` = `invalid_split`，`assumed_region` = `default_region`，`region_fallback` 不单独记录。清单写 000 §二.3 的 `phone_migration_issue`（只存 shape），不只写日志。

restaurant 和 store 号码来源、写入口都相同，同属一个领域，用一对迁移处理：**迁移 A**（加列 + 回填 + NOT VALID 约束）和**迁移 B**（VALIDATE + SET NOT NULL）。

**迁移 A upgrade 回填伪代码**（迁移里直接用 phonenumbers 写，不 import 应用代码，避免以后 `pkg/phone` 演进时影响历史迁移；规则和 `pkg/phone.parse` 保持一致）：

```python
import logging, re
import phonenumbers
from sqlalchemy import text

log = logging.getLogger('alembic.phone_split')
DEFAULT_REGION = 'US'                       # 不带 + 的号码按 US 解析，并记入“假定区域”清单
NSN_RE = re.compile(r'^[0-9]{4,15}$')

def _split(raw: str):
    s = raw.strip()
    assumed = not s.startswith('+')
    pn = phonenumbers.parse(s, DEFAULT_REGION if assumed else None)   # 抛 NumberParseException 视为失败
    exact = phonenumbers.region_code_for_number(pn)                   # 无效号码（如脱敏多 1 位）会返回 None
    iso = exact or phonenumbers.region_code_for_country_code(pn.country_code)  # 退回该拨号码的主国家
    if iso in (None, 'ZZ', '001'):
        raise ValueError('no_region')
    nsn = phonenumbers.national_significant_number(pn)
    if not NSN_RE.match(nsn):
        raise ValueError('nsn_shape')
    flags = [f for f, hit in (('assumed_region', assumed),
                              ('invalid_number', not phonenumbers.is_valid_number(pn)),
                              ('region_fallback', exact is None)) if hit]
    return iso, nsn, flags

def _backfill(conn, table: str) -> int:
    failures = 0
    rows = conn.execute(text(f'SELECT id, phone_number FROM {table} WHERE phone_country_code IS NULL')).all()
    for row_id, raw in rows:
        if raw is None or raw.strip() == '':
            if table == 'restaurant':       # S5：空串一律转 NULL
                conn.execute(text('UPDATE restaurant SET phone_number = NULL WHERE id = :id'), {'id': row_id})
            else:
                failures += 1; log.warning('FAIL %s %s empty', table, row_id)
            continue
        try:
            iso, nsn, flags = _split(raw)
        except (phonenumbers.NumberParseException, ValueError) as exc:
            failures += 1                    # 保留原值，国家列为 NULL；只打印形态，不打印原值
            log.warning('FAIL %s %s %s shape=%s', table, row_id, exc, re.sub(r'\d', '9', raw))
            continue
        conn.execute(text(f'UPDATE {table} SET phone_country_code = :cc, phone_number = :nsn WHERE id = :id'),
                     {'cc': iso, 'nsn': nsn, 'id': row_id})
        if flags:
            log.info('NOTE %s %s %s', table, row_id, ','.join(flags))
    return failures
```

- 解析失败的行**保留原值、国家列为 NULL**，并输出清单（id + 原因 + 形态，不输出原值），禁止静默丢弃。这些行会挡住迁移 B 的 VALIDATE，必须先人工修正（在应用里重新录入号码）。
- `invalid_number` / `region_fallback` / `assumed_region` 只记 NOTE，不阻断：带 `+` 的号码按拨号码拆分是无损的，国家判错的风险只存在于 +1 / +7 / +44 这类共享拨号码，而且只有号码本身无效时才会判错。
- 迁移 A 的 upgrade 最后执行上面 6 条 `ADD CONSTRAINT ... NOT VALID`。

**脱敏数据 dry-run 的偏差（必须知道）**：

- test / uat 的号码尾部都加过 1。这些号码 `is_valid_number` 为 False，`region_code_for_number` 返回 None，会退回拨号码的主国家（+1→US、+7→RU、+44→GB）。所以 test / uat 的 `invalid_number` / `region_fallback` 计数会远高于 prod，CA / KZ 会被低估，这不是迁移缺陷。
- 本国号码会多 1 位（US 11 位、UA 10 位），但仍满足 4–15 位的 CHECK，不会挡住 VALIDATE。
- prod 上线前，用同一个 `_split` 在 prod 只读连接上跑一次“只出报告”（只输出各 flag 的计数和行 id，不输出原值）。`invalid_number` 应该接近 0，不为 0 的行逐条人工核对国家。
