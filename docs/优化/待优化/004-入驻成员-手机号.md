- **脱敏偏差**：162 行全部以 `1` 结尾。`anonymize-db.sh` 的规则是给手机号追加 `1`，但带幂等保护 `NOT LIKE '%1'`，原值以 1 结尾的号码会被跳过（`docs/环境运维执行脚本/05-数据库运维/anonymize-db.sh:125-134`）。所以：
  - **138 行（85%）** 是脱敏后多了一位，`phonenumbers.is_valid_number` 会判为无效；
  - **24 行（15%）** 保持标准长度，可以正常校验。
  - 扣掉脱敏影响后，162 行原值都是"`+` 拨号码 + 标准长度本国号码"的合法 E.164，跟写入口的 `PhoneNumber(E164)` 校验一致。prod 是未脱敏的真实数据，不会出现这种偏差。
- **+1 的国家歧义（有实证）**：33 行 +1 号码里，32 行是美国区号段（其中 2 行是 800 免费号段，属 NANP 共用的非地理号段），**1 行是加拿大区号段**。区分 US/CA 只能靠 libphonenumber 查号段，而且只对有效号码管用。test 里这 1 行长度为 13（`+199999999999`），**正是脱敏多出一位的行**，在 test 上无法判定为 CA。

### 4. 影响与风险

1. **国家只能靠猜**：表里只有拨号码，没有国家。+1 的 33 行中有 1 行是加拿大区号段，+7 的 22 行是 RU/KZ 共用拨号码，只能用 libphonenumber 查号段推出国家，而且只对有效号码管用。test 里有 138 行因脱敏无效，其中 +1/+7 的行**根本判不出国家**。前端 PhoneInput 明明拿到了 ISO 国家，却在 `PhoneInput.tsx:59-61` 把它丢了，信息在源头就丢失了。
2. **与 001 强耦合，转正链路会断**：finish 时把成员的 E.164 字符串原样写进 `user.phone_number`，并按字符串精确匹配已有用户（`users/repositories.py:123`）。001 一旦把 `user.phone_number` 改成"国家列 + 本国号码"：
   - (a) 按号码匹配永远不中，本该归并到老用户的成员会落空；
   - (b) `create_non_independent_users` 会把 E.164 写进 `user.phone_number`，违反 001 的 CHECK `^[0-9]{4,15}$`，**整个公司的 finish_onboarding 报 500**。

   所以 004 只能和 001 同批或晚于 001 上线，绝不能早于 001。
3. **身份归并靠字符串相等**：按 finish 的真实匹配口径模拟，test 里有 **62 个成员行**（company 53 / restaurant 7 / store 2）邮箱没命中任何用户、只因号码字符串相等就会被挂到号码所属用户名下（`services.py:1150-1157`），其中 55 行归到的是无邮箱用户、邀请被静默跳过（`services.py:1213`）；另有 11 行邮箱和号码分别指向两个不同用户。拆列后如果各处比较口径不一致，比如一边存 US、一边存 CA，或一边 E.164、一边本国号码，就会出现两种错：重复建号，或者错绑到别人名下。
4. **唯一性校验全在比原始字符串**：后端 `requests.py:16-28`、`:114-146`、`services.py:247`，前端 `utils.ts:235-254`。只要新旧两种格式并存，同一个号码就会被当成两个，绕过"同一单元内联系方式唯一"的校验。
5. **展示/回填断裂风险**：前端 PhoneInput 只能解析 E.164。如果后端直接把响应里的 `phone_number` 改成本国号码、又不保留兼容字段，表单回填会变空。公司电话已经踩过这个坑，见 `hydrateOnboardingStore.ts:16-19` 的注释。
6. **test 环境假象**：138 行脱敏号码无效。在 test 里重新打开入驻流程时，回填的号码过不了 `BusinessMemberFormFieldset.tsx:46` 和 `usePhoneRule`，必须重新输入才能保存。这是脱敏造成的，不是迁移 bug，prod 不受影响。
7. **残留数据也会转正**：这些行都属于未完成的入驻，最早可追溯到 2024-02。企业主任何时候回来点完成，旧格式号码都会流进 `user`。所以迁移必须覆盖存量，不能只改新写入。

## 二、怎么处理（方案）

### 1. 目标表结构

### 2. 数据迁移

> **与 000 对齐（终审修订，优先于下文）**：① 迁移里**不得 `from app.pkg import phone`**（应用代码会演进，旧 revision 重放结果会变），改为调用冻结的 `app/migrations/phone_v1.py`；本文发现的“往返校验 / `nsn_prefix_stripped`”已并入 000 的 `phone_v1.split`。② 按 000 §二.1 拆成 **R1 expand → R2 rewrite → R3 contract**：`onboarding_*_member` 会在入驻完成时转成 `user`，必须与 001 的同名步骤同批或更晚。③ 约束只在 R3、清单清零后加（下文第 4 步“先挂 NOT VALID、清单不为 0 时保留 NOT VALID”作废）。④ 状态名对照：`invalid_country_by_calling_code` = `invalid_split`，`assumed_region_US` = `default_region`，其余同名。

一个 alembic revision 覆盖入驻成员这个领域的 4 张表（S8：一个领域一个迁移），例如 `xxxx_onboarding_member_phone_country_code`。前置条件：001 的迁移已经在同一条链上更早执行，并且 `app/pkg/phone` 已存在（S7）。

**upgrade**

1. 四张表各自 `ADD COLUMN phone_country_code VARCHAR(2) NULL`。
2. 用 Python 回填，统一调用 `app.pkg.phone.parse`，和运行时用同一套解析口径：

```python
from app.pkg import phone  # S7 唯一入口：parse(raw, default_region) -> ParseResult(country, national, e164, is_valid) | None

TABLES = {
    'onboarding_company_member': 'ck_onboarding_company_member',
    'onboarding_restaurant_member': 'ck_onboarding_restaurant_member',
    'onboarding_store_member': 'ck_onboarding_store_member',
    'onboarding_manufacturer_subdivision_member': 'ck_onboarding_manufacturer_subdivision_member',
}

def _backfill(conn, table: str) -> list[tuple[str, str, str]]:
    issues = []
    rows = conn.execute(sa.text(f'SELECT id, phone_number FROM {table} WHERE phone_country_code IS NULL')).all()
    for row_id, raw in rows:
        value = (raw or '').strip()
        if not value:
            issues.append((table, str(row_id), 'empty'))            # 本域实测 0 行；保留原值
            continue
        res = phone.parse(value, default_region='US')               # '+' 开头按 E.164；否则按 US 解析
        if res is None:                                              # NumberParseException
            issues.append((table, str(row_id), 'unparseable'))      # 保留原值、不回填、进清单
            continue
        if not value.startswith('+'):
            issues.append((table, str(row_id), 'assumed_region_US'))
        if not res.is_valid:
            # 号码无效时国家按拨号码的主国家兜底（1→US、7→RU、380→UA），并进清单复核
            issues.append((table, str(row_id), 'invalid_country_by_calling_code'))
        national = res.national
        if value.startswith('+') and phone.format_e164(res.country, national) != value:
            # 往返校验：libphonenumber 会把超长号码开头的国内前缀剥掉（如 RU 的 8），
            # 导致 '+' + 拨号码 + 本国号码 ≠ 原值。此时改用"原值去掉 '+' 和拨号码后的剩余数字"，保证无损，并进清单
            national = value[1 + len(phone.calling_code(res.country)):]
            issues.append((table, str(row_id), 'nsn_prefix_stripped'))
        conn.execute(
            sa.text(f'UPDATE {table} SET phone_country_code = :cc, phone_number = :nsn WHERE id = :id'),
            {'cc': res.country, 'nsn': national, 'id': row_id},
        )
    return issues
```

   对 `pkg/phone.parse` 的要求（由 000/001 定义，这里列出本域依赖的行为）：
   - `country = region_code_for_number(p) or region_code_for_country_code(p.country_code)`。
   - `national = national_significant_number(p)`，这样意大利这类前导 0 也能保留。
   - 无效号码不抛异常，只把 `is_valid` 置为 False。
   - `format_e164(country, national)` 是纯拼接 `'+' + calling_code(country) + national`，不经 `phonenumbers.format_number`，这样脱敏/无效号码也能无损往返；`calling_code(country)` 即 `country_code_for_region`。

3. **输出清单**：按 `(table, id, reason)` 写进 000 约定的迁移清单（例如 `phone_migration_issue` 表或 alembic 日志），并打印每种原因的计数。**日志里不打印号码原值**。
4. **加约束**：四张表都先 `ADD CONSTRAINT ... NOT VALID`。只有 `unparseable + empty = 0` 时，才在同一个迁移里 `VALIDATE` 三条约束并 `SET NOT NULL`。否则保留 NOT VALID 状态，人工修正清单里的行后，再用后续 revision 做 VALIDATE / SET NOT NULL。在这之前本文保持"待优化"，**禁止删行或清空号码**。

**downgrade**

```python
def downgrade():
    conn = op.get_bind()
    for table, prefix in TABLES.items():
        for suffix in ('pair', 'nat', 'cc'):
            op.execute(f'ALTER TABLE {table} DROP CONSTRAINT IF EXISTS {prefix}__phone_{suffix}')
        rows = conn.execute(sa.text(
            f'SELECT id, phone_country_code, phone_number FROM {table} WHERE phone_country_code IS NOT NULL')).all()
        for row_id, cc, nsn in rows:
            # 还原为 '+' + 拨号码 + 本国号码：format_e164 是纯拼接，不经 phonenumbers 格式化，脱敏/无效号码也能无损往返
            conn.execute(sa.text(f'UPDATE {table} SET phone_number = :v WHERE id = :id'),
                         {'v': phone.format_e164(cc, nsn), 'id': row_id})
        op.drop_column(table, 'phone_country_code')
```

**用 test/uat 脱敏数据 dry-run 时的预期偏差**（以 test 快照为基线，共 162 行）：

| 结果 | 预期 | 说明 |
|------|------|------|
| `phone_country_code` 分布 | UA 107 / US 33 / RU 22 | +380 只对应一个国家，不受有效性影响。+1/+7 的脱敏行无效，按拨号码兜底成 US/RU；那 1 行加拿大号段正是脱敏行（13 位），所以在 test 会被记成 US；prod 用真实数据会判成 CA |
| `unparseable` / `empty` / `assumed_region_US` | 0 / 0 / 0 | 全部以 `+` 开头 |
| `invalid_country_by_calling_code` | 约 138（≥138） | 脱敏多出的一位导致；在 test/uat **不作为阻断条件**。prod 应接近 0，因为写入口一直有 `is_valid_number` 校验 |
| `nsn_prefix_stripped` | 2（预期） | 2 行脱敏后的 `+78…`（本国部分 11 位、以 8 开头）会被 libphonenumber 当作 RU 国内前缀 8 剥掉；靠往返校验改用原值剩余数字。若漏掉这步，这 2 行本国号码少一位，下面的 md5 回滚演练会失败。prod 的真实 10 位 `+78…` 号码不会被剥 |
| 回填后号码长度 | UA 9–10 位、US/RU 10–11 位 | 多出的 1 位是脱敏造成的 |

**回滚演练**：在 uat 副本上依次执行 upgrade → downgrade，比较前后 `SELECT md5(string_agg(id::text || ':' || phone_number, ',' ORDER BY id)) FROM <表>` 必须相同。

### 5. 环境与发布注意

1. **表存在性**：四张表在 test、uat、prod 以及 main/uat/test/ops/support-demo 各条代码线上都存在。成员电话相关的代码在 test 和主线之间一致，所以同一套改动可以同时进两条线。
2. **分支**：在 `ops`（或从 main 拉出的特性分支）上开发，按 `ops → test` / `ops → uat` / `ops → main` 合入。**禁止从 test 合到 uat**。
   - 迁移的 `down_revision` 取落地时主线的 head。
   - test 线 head 是 `d8e2f6b4a1c3`，和主线不同。如果合入后出现两个 head，**只在 test 分支**补一个 merge revision，不回灌主线。
3. **依赖顺序**：000 拍板国家列口径 → 001 落地 `app/pkg/phone` 和 `user` 的两列 → 本项（004）与 001 同一发布批次或更晚。**本项绝不能早于 001**，理由见「一、4 第 2 条」。
4. **同一批次内的发布顺序**：
   1. FE-1：只做兼容读，取值用 `phoneE164 ?? phoneNumber`；
   2. BE：迁移 + 请求同时接受旧 E.164 和新号码对 + 响应三字段（`phone_country_code` / NSN 的 `phone_number` / 只读的 `phone_e164`）；
   3. FE-2：表单提交号码对；
   4. 所有环境都上了 FE-2 之后，BE 收尾：删掉旧 E.164 入参和 `phone_e164`。
5. **演练**：在 uat（preprod 来源，和 prod 同源）的副本上跑 upgrade → 看清单 → downgrade，并做 md5 比对。上 prod 前先只读统计行数：

   ```sql
   SELECT 'onboarding_company_member' t, count(*) n, count(*) FILTER (WHERE phone_number !~ '^\+[0-9]{8,15}$') non_e164 FROM onboarding_company_member
   UNION ALL SELECT 'onboarding_restaurant_member', count(*), count(*) FILTER (WHERE phone_number !~ '^\+[0-9]{8,15}$') FROM onboarding_restaurant_member
   UNION ALL SELECT 'onboarding_store_member', count(*), count(*) FILTER (WHERE phone_number !~ '^\+[0-9]{8,15}$') FROM onboarding_store_member
   UNION ALL SELECT 'onboarding_manufacturer_subdivision_member', count(*), count(*) FILTER (WHERE phone_number !~ '^\+[0-9]{8,15}$') FROM onboarding_manufacturer_subdivision_member;
   ```

6. **脱敏偏差**：test/uat 的号码末尾多了一位 1，导致 test 里 85% 的行被判无效，但这不影响国家回填。prod 是未脱敏的真实数据，以 prod 的清单为准。
7. **进行中的入驻**：成员行是原地迁移的，发布后用户继续入驻并点完成，走的就是新逻辑。CI 的 `migrate` job 先于 `deploy`，保证新代码不会读到未迁移的数据。
8. **部署方式**：
   - test/uat：push 后 CI 自动构建、迁移、部署。
   - prod：在 GitHub Actions 手动 Run workflow（environment=prod，image_tag 留空）。
   - support-* 环境：按各自代码线同步执行迁移。
   - 前端：不涉及 `VITE_*`，只需要正常重建镜像。
