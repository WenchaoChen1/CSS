### 4. 影响与风险

- **分不清国家**：413 个号码都没有国家列。+1 被 US、CA 和加勒比各国共用；前端让用户选国家，但只提交 E.164（`PhoneInput.tsx:59-61`），用户的选择丢了。`ClientTemporaryStoreDTO` 和 `VendorOut` 对外返回去掉国家码的 national 格式，调用方再也拿不回国家。
- **导入只支持北美**：两个文件导入入口都要求 `^\d{3}-\d{3}-\d{4}$`，后端再写死 '+1'（`files/repositories.py:375,507`），非北美的客户和供应商根本导不进来。LV 导入的 `PHONE_RE` 虽然允许 +CC，但号码主体必须是北美形状。
- **同一号码多种格式，去重失效**：现有 2 个号码、9 行以不同写法并存。导入去重用精确字符串比较（`files/repositories.py:156,196`），不带 + 的 24 行和同号的 `+1…` 被当成两个号码，可能重复建客户、重复发邀请。
- **身份匹配和占用判断靠猜**：纯数字比较，加上“10 位补 1、11 位去 1”的规则只对 +1 成立。24 行不带 + 的值里有 4 行和 `user` 号码只差一个国家码 '1'，`_matches_contact_keys` 匹配不上，未注册客户就不能自动关联到已注册餐厅。对非 +1 号码，`registration_phone_keys` 直接返回数字串，理论上不同国家的号码可能撞成同一串数字。
- **短信**：`usable_invitation_contacts` 只看 `is_possible_number`、不看 `is_valid_number`，所以 2 行区号以 1 开头的无效号也会被当成可用号码去发短信。test 里那批脱敏超长号会因为 TOO_LONG 被判 `missing_or_invalid_contact`，在 test 上验证不了短信链路。
- **展示不一致**：E.164 值显示成 `(999) 999-9999`，旧格式值原样显示；前端 `formatPhone` 只能靠两个方向都猜来兜底。
- **脏数据往外扩散**：`temporary_phone_number` 会原样复制进 `restaurant.phone_number`（下单时）和 `quotation_vendor_client.phone_number`（而且不填它的 `phone_country_code`）；迁移 `718644a7510b` 到 uat/prod 时还会把 `client_temporary_restaurant` 的脏格式再搬一次。
- **冗余表**：`deprecated_` 表 147 行和 `client` 完全重复，却仍被 JOINED 加载（`models.py:151`），多一次 join。给它拆国家列纯属白做。
- **维护成本**：四套电话工具函数各自写死 'US' 或 None 作为默认区域，改一处漏一处。

### 1. 目标表结构

**为什么 `deprecated_` 表直接删、不拆**：（1）test 代码从 `f6f025ea` 起已经不写它，`b516e474f920` 明确把它标成废弃；（2）数据 147/147 和 `client.temporary_*` 完全一致，它有而 client 没有的信息是 0 行；（3）剩下的读取方都只用 name/address 做回退，在 client 已有同样数据的前提下是多余的，**phone_number 没有任何读取方**；（4）前端没有引用。删表之后它的号码问题也就没了。

号码列类型保持 `varchar(64)` 不缩，长度交给 CHECK 约束，避免改类型时锁表、回滚变复杂。DDL 草案（约束名仅作示例，以 000 号文档的命名口径为准）：

```sql
-- ① 加列（迁移第 1 步，nullable）
ALTER TABLE client
  ADD COLUMN sales_person_phone_country_code varchar(2),
  ADD COLUMN temporary_phone_country_code   varchar(2);
ALTER TABLE client_temporary_store
  ADD COLUMN phone_country_code varchar(2);

-- ② 回填完成后加约束（先 NOT VALID，再单独 VALIDATE）
--    注意：NOT VALID 只是跳过加约束时对存量的一次性全表扫描；存量行之后只要被 UPDATE（哪怕只改别的列），
--    PostgreSQL 仍会对这一行检查 CHECK。所以某张表还有 FAIL 行（号码非空、国家列为 NULL）时不能加这组约束，
--    否则这些 client 行的确认/拒绝、改价格档、改备注等任何更新都会报 23514。见下文 R2 的“按表门控”。
ALTER TABLE client
  ADD CONSTRAINT ck_client__sales_person_phone_cc CHECK (sales_person_phone_country_code ~ '^[A-Z]{2}$') NOT VALID,
  ADD CONSTRAINT ck_client__sales_person_phone_nat     CHECK (sales_person_phone ~ '^[0-9]{4,15}$') NOT VALID,
  ADD CONSTRAINT ck_client__sales_person_phone_pair         CHECK ((sales_person_phone IS NULL) = (sales_person_phone_country_code IS NULL)) NOT VALID,
  ADD CONSTRAINT ck_client__temporary_phone_cc    CHECK (temporary_phone_country_code ~ '^[A-Z]{2}$') NOT VALID,
  ADD CONSTRAINT ck_client__temporary_phone_nat        CHECK (temporary_phone_number ~ '^[0-9]{4,15}$') NOT VALID,
  ADD CONSTRAINT ck_client__temporary_phone_pair            CHECK ((temporary_phone_number IS NULL) = (temporary_phone_country_code IS NULL)) NOT VALID;
ALTER TABLE client_temporary_store
  ADD CONSTRAINT ck_client_temporary_store__phone_cc CHECK (phone_country_code ~ '^[A-Z]{2}$') NOT VALID,
  ADD CONSTRAINT ck_client_temporary_store__phone_nat     CHECK (phone_number ~ '^[0-9]{4,15}$') NOT VALID,
  ADD CONSTRAINT ck_client_temporary_store__phone_pair         CHECK ((phone_number IS NULL) = (phone_country_code IS NULL)) NOT VALID;

-- ③ 后续单独一个迁移（各环境失败清单清零后）
ALTER TABLE client VALIDATE CONSTRAINT ck_client__sales_person_phone_cc;  -- 其余 8 条同理
ALTER TABLE client_temporary_store ALTER COLUMN phone_country_code SET NOT NULL;   -- phone_number 本来就 NOT NULL，配合成对约束

-- ④ 删除废弃表（单独迁移，排在 ①② 之前）
DROP TABLE deprecated_client_temporary_restaurant;
```
