**数据里的异常和佐证：**

- **形态**：现有值全是 `+` 开头的 E.164，没有空串，没有分隔符，也没有夹带字母。原因是写入时绝大多数经过 `PhoneNumber`（全局配置成 E164 格式）的校验。但"国家"和"号码"挤在同一个字符串里，**库里没有任何一列能直接回答"这是哪国的号码"**。
- **+1 有歧义**：client_restaurant_contact 里有 4 个 +1 号码的区号属于加拿大。只存拨号码 `+1` 区分不出 US 和 CA，存 ISO 码才能区分。
- **不合法的 NANP 号**：用"区号首位和交换码首位都必须是 2–9"粗查：
  - client_restaurant_contact 有 1 行区号以 0/1 开头。
  - client_store_contact 有 4 行（区号或交换码以 0/1 开头），**其中 1 行是 2026-08-22 之后新写入的**，不是脱敏造成的。它所在的那天（2026-09-23）正好批量建了 4 条门店联系人（2026-08-22 之后的门店联系人只有这 4 条），推测来自批量导入路径的 `'+1' + 数字`拼接，这条路径会绕过 `is_valid_number`，见下文"代码现状"写入路径第 4 条。
  - 这个粗查比 phonenumbers 宽松：用 phonenumbers 把末尾脱敏位去掉后再校验，client_restaurant_contact 仍有 3 行、client_store_contact 仍有 7 行无效（见"数据迁移"的 dry-run 预期）。
- **测试数据痕迹**：匹配正则 `1234567|(\d)\1{6}`（含 1234567 或同一数字连续 7 位）的值，client_restaurant_contact 11 行、client_store_contact 1 行、client_liquor_license 4 行。
- **重复**：
  - client_restaurant_contact 有 192 行，分属 156 个 client，只有 116 个不同号码；同一 client 下号码相同的有 8 组。
  - client_store_contact 有 89 行，每个 client 1 条，只有 37 个不同号码。
  - 这些重复都是测试数据，号码列上没有唯一性约束，也没有基于号码的去重逻辑（前端新增联系人时的判重除外，见"代码现状"）。
- **fax_number 全空**：前端联系人表单根本没有传真字段，所以从未写入过；后端对账单却会读它，见下文。
- **client_liquor_license.contact_phone 是独立字段**：
  - 20 张酒牌配了客户侧收件人，其中 16 张填了 contact_phone，这 16 张的 contact_phone 和所选联系人的电话**全都不同**。可见它是牌照上的联系人电话，不是联系人表电话的副本，必须单独拆分。
  - 另有 1 行有 contact_phone 却没有 contact_name。
- **引用面**：
  - `"order"` 共 1697 行，其中 1324 行引用了联系人，涉及 56 个不同联系人。
  - 被酒牌选为短信收件人的联系人有 20 个，全部是 2026-08-22 之后写入的（不是脱敏数据）。

**脱敏偏差（test/uat 专有，写结论时必须扣掉）**：test/uat 的号码在尾部加了一位 `1`。

- 2026-08-22 之前写入、长度比该国正常长度多 1 位的行（+1 共 13 位、+380 共 14 位、+44 共 14 位、+7 共 13 位、+61 共 13 位）：
  - client_restaurant_contact 有 **141/192**
  - client_store_contact 有 **79/89**
- 用 phonenumbers 校验时，这些行在 test/uat 会判成 TOO_LONG，也就是无效。
- client_liquor_license 的 17 行全部是 2026-09-14 之后写入的，没被脱敏，长度正常。
- 另外 client_restaurant_contact 有 6 行、client_store_contact 有 6 行是 2026-08-22 前写入、长度却是 12（+1 加 10 位）。说明脱敏没覆盖全部行，或者原值本来就短一位，dry-run 时要单独列出来看。
- prod 是未脱敏的真实数据，上述"超长"在 prod 不应出现。

### 4. 影响与风险

1. **国家无法结构化查询**：国家只能靠解析字符串前缀才能得到。现在 17 条非 +1 的餐厅联系人和 1 条非 +1 的门店联系人，在 UI 上都被格式化成**不带国家码**的本国格式，用户看不出是哪国号码。
2. **+1 歧义**：4 条加拿大区号的联系人和美国号外观完全一样。批量导入时写死 `'+1'`，非北美联系人只要走表格导入就一定被写错国家。
3. **校验口径不一**：
   - 表单路径用 `PhoneNumber` 做 `is_valid_number` 校验；批量导入路径只做正则加拼接，不做有效性校验。
   - 已有 1 条 2026-08-22 之后写入的不合法 NANP 号，证明脏数据仍在持续产生。
4. **短信耦合**：酒牌到期短信直接拿号码列当 `to`。拆列时只要漏改这一处，会出现两种后果：
   - 短信发到错误号码，比如把本国号码当成国际号码发；
   - 或者全部投递失败。
   - test 里被选为短信收件人的 20 个联系人都是未脱敏的新数据，能直接验证这一点。
5. **展示和编辑不一致**：
   - 订单编辑页 `useClientInfoStep.tsx:169` 把展示串当 E.164 用。
   - 装箱单 PDF 印的是未格式化的 E.164，对账单的传真永远是 `-`。
   - 同一个号码在不同页面、不同单据上的样子都不一样。
6. **传真是"死字段"**：库有列、后端会读，但前端从来不写。fax_number 现在 0 行，拆分本身零风险，但需要产品确认：是把它补进 UI，还是直接废弃。

### 2. 数据迁移

> **与 000 对齐（终审修订，优先于下文）**：① 迁移里**不得 `from app.pkg.phone import parse`**（下文伪代码第一行作废），改为调用冻结的 `app/migrations/phone_v1.py`。② clients 领域与 005 共用一条 revision 链：006 的 4 列并进 005 的 **R1 expand / R2 rewrite / R3 contract**（或紧随 005 的同名 revision 串行），不再另起一个“`split_clients_phone_country_code`”单 revision，也不得出现多头。③ 约束只在 R3、清单清零后加（下文“`add_check_constraints_not_valid()` 在回填后立即执行”作废）。④ 状态名对照：A 类 = 正常，B 类 `invalid_split` 同 000，`assumed_region_US` = `default_region`，`unparsed` = `unparseable`，`empty_not_null` = `empty`。清单写 000 §二.3 的 `phone_migration_issue`（只存 shape）。

**一个领域一个迁移**：这 4 列都属于 clients 领域。迁移应该和同属 clients 领域的其它待优化项合并成同一个 alembic revision，例如 `client.temporary_phone_number`、`client.sales_person_phone`、`client_temporary_store.phone_number`、`deprecated_client_temporary_restaurant.phone_number`，各见对应文档。如果分开做，就按顺序串成连续的 revision，不要并行出多头。

迁移文件建议命名为 `core_app/src/app/migrations/versions/<日期>-<rev>_split_clients_phone_country_code.py`。

**回填规则**（只能用 S7 的 `app/pkg/phone`，不允许在迁移里自己写正则）：

| 分类 | 判定 | 处理 | 是否进清单 |
|------|------|------|------------|
| A 有效 | `parse(raw)` 成功且 `is_valid` | 国家列写 `region_code_for_number`（+1 自动区分 US/CA，+7 区分 RU/KZ，+44 区分 GB/GG/JE/IM），号码列改写成 national significant number | 否；不带 `+`、按默认区域 US 解析出来的行除外，这类要进清单并标 `assumed_region_US` |
| B 可解析但无效 | 能识别出国家码，但 `is_valid=False`（典型情况是脱敏多出 1 位导致 TOO_LONG，或者交换码以 0/1 开头） | 国家列写该国家码的主区域（`region_code_for_country_code`：1→US，7→RU，44→GB），号码列写去掉国家码后的全部数字。这样能满足 CHECK，但**必须**进清单 | 是，标 `invalid_split` |
| C 无法解析 | `parse` 抛异常，或者是空串 | 空串：可空列置 NULL；NOT NULL 列进清单。其它情况保留原值、国家列留 NULL | 是，标 `unparsed` / `empty_not_null`。**VALIDATE 之前必须人工清零** |

> B 类的处理口径如果和 000 号规范的最终约定不一致，以 000 为准。`app/pkg/phone.parse` 需要在 `is_valid=False` 时仍然返回"国家码对应的主区域"，否则迁移就得在本地再写一层兜底。

关键伪代码：

```python
from app.pkg.phone import parse  # S7 唯一入口；必须保证 pkg/phone 不依赖 ORM，迁移才能直接 import

TARGETS = [
    # table,                      number col,      country col,                   number nullable
    ('client_restaurant_contact', 'phone_number',  'phone_country_code',          False),
    ('client_restaurant_contact', 'fax_number',    'fax_country_code',            True),
    ('client_store_contact',      'phone_number',  'phone_country_code',          False),
    ('client_liquor_license',     'contact_phone', 'contact_phone_country_code',  True),
]

def upgrade() -> None:
    for table, _num, cc, _ in TARGETS:
        op.add_column(table, sa.Column(cc, sa.String(2), nullable=True))

    conn, issues = op.get_bind(), []
    for table, num, cc, nullable in TARGETS:
        for row in conn.execute(sa.text(f'SELECT id, {num} AS v FROM {table} WHERE {num} IS NOT NULL')):
            raw = (row.v or '').strip()
            if not raw:
                if nullable:
                    conn.execute(sa.text(f'UPDATE {table} SET {num} = NULL, {cc} = NULL WHERE id = :id'), {'id': row.id})
                else:
                    issues.append((table, row.id, num, 'empty_not_null'))
                continue
            p = parse(raw, default_region='US')          # '+' 开头按 E.164 解析；否则按 US 解析
            if p.country and p.national:                  # A 类 / B 类
                conn.execute(sa.text(f'UPDATE {table} SET {cc} = :cc, {num} = :n WHERE id = :id'),
                             {'cc': p.country, 'n': p.national, 'id': row.id})
                if not p.is_valid:
                    issues.append((table, row.id, num, 'invalid_split'))
                elif not raw.startswith('+'):
                    issues.append((table, row.id, num, 'assumed_region_US'))
            else:                                         # C 类：保留原值
                issues.append((table, row.id, num, 'unparsed'))

    report_phone_issues(issues)   # 按 000 号规范输出：写 alembic 日志 + 清单表/文件；只记 表/id/列/原因，不记原值
    add_check_constraints_not_valid()   # 见上面的 DDL；所有 C 类清零后才执行 VALIDATE 和 SET NOT NULL


def downgrade() -> None:
    drop_check_constraints()
    conn = op.get_bind()
    for table, num, cc, _ in TARGETS:
        for (code,) in conn.execute(sa.text(f'SELECT DISTINCT {cc} FROM {table} WHERE {cc} IS NOT NULL')):
            dial = phonenumbers.country_code_for_region(code)   # US -> 1
            conn.execute(sa.text(f"UPDATE {table} SET {num} = '+' || :dial || {num} WHERE {cc} = :cc"),
                         {'dial': str(dial), 'cc': code})
        op.drop_column(table, cc)
```
