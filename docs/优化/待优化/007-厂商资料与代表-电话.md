## 一、现在是什么问题

### 1. 表结构现状

这 4 张表的 9 个电话列都是**单列**，没有对应的国家列。号码列里存的是带 `+` 的 E.164 整串，没有任何 CHECK 约束。

|----|----|------|------|------|------------------|-----------------------------|

| manufacturer_profile | main_phone_ext | varchar | YES | 10 | —（分机，S2 不变） | 否 |
| manufacturer_profile | accounting_phone | varchar | YES | 50 | 无 | 否 |
| manufacturer_profile | accounting_phone_ext | varchar | YES | 10 | — | 否 |
| manufacturer_profile | customer_service_phone | varchar | YES | 50 | 无 | 否 |
| manufacturer_profile | customer_service_phone_ext | varchar | YES | 10 | — | 否 |
| manufacturer_profile | sales_phone | varchar | YES | 50 | 无 | 否 |
| manufacturer_profile | sales_phone_ext | varchar | YES | 10 | — | 否 |
| manufacturer_representation | cell_phone | varchar | YES | 50 | 无 | 否 |
| manufacturer_representation | office_phone | varchar | YES | 50 | 无 | 否 |
| vendor_manufacturer_representation | cell_phone | varchar | YES | 50 | 无 | 否 |
| vendor_manufacturer_representation | office_phone | varchar | YES | 50 | 无 | 否 |
| manufacturer_subdivision | phone_number | varchar | YES | **64** | 无 | 否 |

各表现有的索引和约束都不涉及电话列（已查 `pg_indexes` 和 `pg_constraint`）：

- `manufacturer_profile`：主键 `id`，唯一约束 `uq_manufacturer_profile_company(company_id)`，`ix_manufacturer_profile_company_id`，`ix_manufacturer_profile_created_at`，FK `company_id → company.id ON DELETE CASCADE`。
- `manufacturer_representation`：主键 `id`，唯一约束 `uq_manufacturer_representation_company(manufacturer_company_id)`，两个普通索引，FK 指向 `company`。
- `vendor_manufacturer_representation`：主键 `id`，唯一约束 `uq_vendor_manufacturer_representation_pair(vendor_company_id, manufacturer_company_id)`，三个普通索引，两个 FK 指向 `company`。
- `manufacturer_subdivision`：主键 `id`，部分唯一索引 `uq_manufacturer_subdivision_company_name_active(manufacturer_company_id, name) WHERE deleted_at IS NULL`，两个普通索引，FK 指向 `company`。
- 全库只有 `quotation_card_contact` 和 `quotation_vendor_client` 有 `phone_country_code` 列，本文涉及的 4 张表都没有。

**长度不一致**：前 8 列是 `VARCHAR(50)`，由迁移 `d554c79187b4` 和 `4c7e7001566b` 建出；`manufacturer_subdivision.phone_number` 是 `VARCHAR(64)`，由迁移 `d1a8250b8ec8` 建出，和库里其它多数 `phone_number` 一致。拆分以后号码列只存不超过 15 位的数字，由 CHECK 约束长度，所以本次**不改列长**，避免无意义的 DDL。

**地址国家列不能当电话国家用**：`manufacturer_profile` 另有 `country` 和 `mailing_country`（`VARCHAR(255)`）。
- 它们是**地址**国家，前端 `MasterDataSection` 用自由文本框录入，test 库里的取值是 `USA` ×2、`United States` ×1，不是 ISO 码。
- 它们描述的是厂商的实体地址和邮寄地址，不代表每条电话线所在的国家。比如美国厂商完全可能有一条加拿大的销售专线。
- 它们只能作为解析**不带 `+` 的号码**时的「默认区域」兜底。使用前要先把文本映射成 ISO（`USA` / `United States` → `US`，`Canada` → `CA`），不能写进电话国家列冒充用户选择。
- `manufacturer_subdivision` 和 `company` 都没有任何国家列。分部的 `address` 是一整串自由文本，17 行非空，其中 5 行文本里出现了国家名。

- **脱敏偏差**：test 库在 2026-08-22 05:50 UTC 跑过 `anonymize-db.sh`（`_css_pii_masked` 第 1 行），规则是「手机号后加 1」。所以 11 个值比正常长 1 位：美国号 +1 后面 11 位，乌克兰号 +380 后面 10 位。这些值全部创建于脱敏之前，去掉尾部 1 后全部合规。

- **脱敏遗漏（只记录，不处理）**：`manufacturer_profile.sales_phone` 有 1 行在脱敏前创建，但仍是正常的 10 位。原因是原值本身就以 1 结尾，被 `anonymize-db.sh` 的幂等保护（`NOT LIKE '%1'`，脚本 125–129 行注释写了这条已知边界）跳过。这一行可能还是老 dev 环境的原始号码。

### 4. 影响与风险

1. **国家只隐含在 `+` 前缀里，无法按国家查询或治理**。26/27 是 +1。NANP 由 US、CA 和多个加勒比国家共用，`mafsi_area` 里加拿大区域有 6 个，所以 +1 号码一定会混有加拿大号。不拆出国家列，就没法回答「这个代表是不是加拿大号」，也没法按国家做数据质量检查。
2. **后端对 9 列里的 8 列零校验**。profile 和两张 representation 表的 PATCH 接受任意 50 字符以内的字符串，现在数据干净只是因为前端是唯一写入方。将来做导入、开放 API 或别的客户端写入，`999-999-9999`、`ext 12`、甚至邮箱都能写进去。onboarding 写分部却校验 E.164，两条入口口径不一致。
3. **默认分部会继承 company 的号码形态**（`onboardings/services.py:806-814` 和回填迁移 `5d68ace011f1`）。test 中有号码的 20 家 MANUFACTURER 公司里，14 家的 `company.phone_number` 是带横线的 `+9-999-999-9999` 形态，而且这 14 家目前**一个分部都还没有**。它们一旦完成 onboarding 触发默认分部创建，就会把带分隔符的形态扩散到分部。前端同样存在回退到 company 号码的地方（`types.ts:158`），遇到非 E.164 会显示为空，逼用户重新录入。
4. **写时复制种子是拆列时的坑**：供应商第一次编辑代表时，`load_manufacturer_values` 只按 `REPRESENTATION_FIELDS` 复制。如果拆列时忘了把国家列加进白名单，副本会只有号码没有国家，成对 CHECK 上线后直接 `IntegrityError`（500）。供应商卡片的 `ManufacturerMasterDataOut` 同理：没声明的新字段会被静默丢弃，前端拿不到国家。
5. **脱敏脚本会撞到新列**：`docs/环境运维执行脚本/05-数据库运维/anonymize-db.sh:134` 用 `column_name ILIKE '%phone%' AND NOT ILIKE '%type%'` 选列。新增的 `*_phone_country_code` 会被选中，执行 `|| '1'`，结果 `'US1'` 超出 `VARCHAR(2)`（同时违反 `^[A-Z]{2}$`），脚本会报错中断。`mask-residual-pii.sh:81, 97` 已经排除了 `%country%`，`anonymize-db.sh` 没有排除。
6. **展示工具口径冲突**：`formatPhone(value, countryCode)` 期望拨号码。`resolve`（`formatPhone.ts:23-36`）先用 `digitsOf` 只取数字，拆列以后如果直接把 ISO 码（`US`/`UA`）传进去，字母会被**静默丢掉**，号码退回按默认国家 `US` 解析：NANP 号碰巧还能显示对，非 +1 号码（如 test 里那条 +380 分部电话）会被当成美国号解析成错误格式，而且不报错。
7. **onboarding 回显闭环会断**：`GET /onboarding` 把分部 `phone_number` 原样回给前端 `PhoneInput`，用户再提交给要求 E.164 的 `BusinessIn.phone_number`。拆列后如果这里直接返回本国号码（不带 `+`），表单会显示为空或错位；用户不改就提交还会 422。`/me/accounts` 的 `businesses[].phone_number` 同理会变成不带国家的裸号码。
8. **dry-run 噪声**：test/uat 是「尾号加 1」的脱敏数据，dry-run 会报出 11/27（test）的无效号码。prod 是真实数据，无效数要单独预检（见 §二.5），不能拿 test 的结果推断 prod。

### 2. 数据迁移

> **与 000 对齐（终审修订，优先于下文）**：① 拆分调用冻结的 `app/migrations/phone_v1.py`；本文特有的“不带 `+` 时用地址国家 `ADDRESS_COUNTRY_TO_ISO` 作默认区域”作为 `split(raw)` 之前的预处理保留（命中时仍记 `default_region`）。② 按 000 §二.1 拆成 R1 expand / R2 rewrite / R3 contract，约束只在 R3、清单清零后加（下文“回填后立即挂 NOT VALID”作废）。③ **更正**：test 的头 `d8e2f6b4a1c3` 虽然是主线头 `9b8e2c7d4f10` 的后代，但以 `9b8e2c7d4f10` 为 `down_revision` 的新迁移合入 test 后会与 `d8e2f6b4a1c3` 并列成两个头，**必须在 test 上补 merge revision**（下文“仍保持单 head”的说法有误）。

- `down_revision` 取实施时**主线**的单一 head。当前 origin/main 是 `9b8e2c7d4f10`。test 的 head `d8e2f6b4a1c3` 是它的后代（经 merge revision），所以这次迁移合入 test 后会与 `d8e2f6b4a1c3` 并列成两个 head，**需要在 test 上补一个 merge revision**（终审更正：原稿“仍保持单 head”有误），不回灌主线。
- 迁移脚本里**直接调用 `phonenumbers`**，不要 import `app.pkg.phone`。迁移要能在将来的代码上原样重放，不能依赖应用代码的版本。
