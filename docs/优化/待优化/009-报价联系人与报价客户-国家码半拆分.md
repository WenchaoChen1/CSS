### 4. 影响与风险

1. **一列三种口径，数据无法直接使用**：300 行号码里只有 39 行有国家码，取值还是 `'1'`、`'+1'`、`'+3741'` 三种写法；212 行把国家塞在号码串里，49 行干脆把国家丢了。任何下游都必须先“猜”才能用。
2. **国家丢失导致展示和拨号出错**：49 行 Ship To 联系人没有国家码，其中 7 个 8 位亚美尼亚号码，后端 PDF（`format_us_phone` 按 US 解析）和前端（`formatPhone` 默认 US）都会当成美国号处理，`tel:` 链接也是错的。
3. **编辑即清空，已是真实的数据丢失风险**：那 49 行一打开编辑，号码框为空，用户只改名字也会把号码清掉；选“全局更新”时还会把 vendor client 的号码一起清掉。号码解析失败时 `toPhoneBody` 返回 null，效果相同。
4. **口径互相覆盖**：“全局更新”会把 vendor client 的 `'+1'` 改成 `'1'`，test 上已经发生了 1 例。
5. **查重失效**：查重用精确等值，前端送本国号码，库里关联客户存的是 E.164 整串，所以 212 行关联客户永远不会因为电话相同被查出（只能靠名称或客户号命中，换个店名就漏）。前端只能靠后缀匹配兜底，`'9999999'` 这种短串还会误报。
6. **同一接口返回两种形态**：`vendor-clients` 和候选客户接口里，关联客户返回“国家码 NULL + 整串（甚至带分隔符）”，独立客户返回“`'+1'` + 本国号码”。调用方无法统一处理。
7. **入参零校验**：`PhoneIn.country_code` 接受任意字符串，脏数据随时可能写进来。
8. **脱敏脚本与国家列冲突**：现在脚本已经把 `'+374'` 改成了 `'+3741'`。如果国家列改成 ISO 之后不改脚本，`'US'` 会被改成 `'US1'`：超出 `VARCHAR(2)` 或违反 CHECK，导致 test/uat 脱敏中断。
9. **+1 有歧义**：拨号码 `'+1'` 无法区分 US、CA 和加勒比各国，PDF 统一输出 NATIONAL 格式，看不出国家。存 ISO 才能无损还原。

### 2. 数据迁移

> **与 000 对齐（终审修订，优先于下文）**：本文的 R1 / R2 / R3 编号与 000 不同：本文 **R1 = 000 的 R1 + R2**（扩列、回填、改写号码；兼容入参两种口径），本文 **R2 = 000 的 R3**（清单清零后加约束），本文 **R3** 是本文独有的“删 `*_legacy` 列”收尾。拆分调用冻结的 `app/migrations/phone_v1.py`，旧国家列与号码推出的国家冲突时记 000 的 `country_conflict`。清单写 000 §二.3 的公共表，**只存 `shape` 和 `legacy_country_code`，不存 `raw_value`**（原值在 R3 之前保留在 `phone_number_legacy` 列里，R3 删列后不再留存）。

一个领域一个迁移链（S8），分 3 个 revision。新迁移写在 main 线上，`down_revision` 取 main 当前 head。

**R1 `quotation_phone_country_split`（扩列 + 回填 + 失败清单，不加约束）**

1. 两张表：把 `phone_country_code` 改名为 `phone_country_code_legacy`；新增 `phone_number_legacy VARCHAR(64)`，填入原号码；新增 `phone_country_code VARCHAR(2)`。
2. **先处理 `quotation_vendor_client`，再处理 `quotation_card_contact`。** 联系人行国家码为空、且号码与报价单所选 vendor client 的**原号码**相同时，继承该 vendor client 的 legacy 国家码。这是为了避免 49 行复制品被统一按 US 处理，其中 7 个亚美尼亚号码就会被错判。
3. 用 Python 和 `phonenumbers` 逐行规范化。迁移里**直接 import `phonenumbers`，不 import `app.*` 的活代码**，与 d284357d8372 “frozen SQL” 的做法一致，保证将来重放不受代码改动影响：

```python
import re
import phonenumbers

FAIL = {'BAD_LEGACY_CC', 'PARSE_ERROR', 'UNKNOWN_COUNTRY', 'BAD_LENGTH'}

def normalize(raw: str | None, legacy_cc: str | None) -> tuple[str | None, str | None, str | None]:
    """-> (iso, national, flag)；flag 属于 FAIL 时整行保持原值、只记清单。"""
    raw = (raw or '').strip()
    if not raw:
        return None, None, 'EMPTY'                        # 空串 → NULL
    digits = re.sub(r'\D', '', raw)
    cc = re.sub(r'\D', '', legacy_cc or '')
    if raw.startswith('+'):
        candidate, region, flag = '+' + digits, None, 'E164'
    elif cc:
        if phonenumbers.region_code_for_country_code(int(cc)) in ('ZZ', '001'):
            return None, None, 'BAD_LEGACY_CC'            # test 的 '+3741'
        candidate, region, flag = '+' + cc + digits, None, 'LEGACY_CC'
    else:
        candidate, region, flag = digits, 'US', 'DEFAULT_US'   # S8：不带 + 的按 US 解析并标记
    try:
        p = phonenumbers.parse(candidate, region)
    except phonenumbers.NumberParseException:
        return None, None, 'PARSE_ERROR'
    national = phonenumbers.national_significant_number(p)
    iso = phonenumbers.region_code_for_number(p)          # 有效号码按号段区分 US/CA/加勒比
    if iso in (None, 'ZZ', '001'):
        iso = phonenumbers.region_code_for_country_code(p.country_code)  # 1→US, 7→RU, 380→UA
        if iso in ('ZZ', '001'):
            return None, None, 'UNKNOWN_COUNTRY'
        flag += '|INVALID_KEPT'                           # 国家能确定、号码无效：照填，同时进清单
    if not re.fullmatch(r'[0-9]{4,15}', national):
        return None, None, 'BAD_LENGTH'
    return iso, national, flag
```

4. 按 flag 落库：
   - flag 不在 `FAIL` 中：写 `phone_country_code = iso`、`phone_number = national`。
   - flag 属于 `FAIL`：这一行保持原值，新国家列留空。
   - flag 为 `FAIL`、`DEFAULT_US` 或带 `INVALID_KEPT` 的行，一律写入失败清单表 000 §二.3 定义的公共清单表 `phone_migration_issue(revision, table_name, column_name, row_pk, reason, shape, legacy_country_code, …)`（终审修订：不存 `raw_value`，只存形态 `shape`；`flag` 写进 `reason`：`FAIL` → `unparseable`，`DEFAULT_US` → `default_region`，`INVALID_KEPT` → `invalid_split`，旧国家列与号码冲突 → `country_conflict`）。同时把这些行的 表/主键/列/flag 打印到迁移日志（**日志不打印号码原值**；prod 是未脱敏真实数据，原值只留在库内清单表，不导出明文）。**禁止静默丢弃。**
5. 规整：号码为空串的置 NULL；有号码但没有 `phone_type` 的补 `'phone'`；没有号码的把 `phone_type` 置 NULL。

**R2 `quotation_phone_country_constraints`（加约束）**

前提：该环境 `phone_migration_issue` 中本域的 `FAIL` 行已经人工处理为 0。按 §二.1 的 DDL 先加 `NOT VALID`，再逐个 `VALIDATE`。之所以不在 R1 里直接加约束：`NOT VALID` 约束对之后的 UPDATE 照样生效，失败行一旦被更新（比如“全局更新”改联系人名字）就会报 500。
