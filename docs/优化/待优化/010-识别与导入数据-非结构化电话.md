> **本文结论先行**（回答“原始识别 JSON 是否应保持原样，只在落库时拆分”）：
> 1. 识别表的 `data` 列**并不是原始 OCR 数据**，理由有三。第一，它已经过 DTO 映射，丢掉了供应商字段（如商户 `country_code`）。第二，人工审核会整段覆盖它：`client_master_invoice_recognition` 30 行中有 21 行、`master_invoice_recognition` 81 行中有 17 行是 MODERATED。第三，生成单张发票识别时，会被主发票或所选客户的数据覆盖。它实际上是“识别 + 人工校正后的表单数据”：前端直接编辑它，匹配逻辑也直接读它。所以**应在 JSON 内部按规范成对存“国家 + 本国号码”**。电话的识别原文另存到一个只写一次的 `raw_phones` 子对象，用于审计和回溯。
> 2. 识别出的电话**目前没有任何代码落到结构化表**（已逐条核对写入路径，见 §一.3）。唯一会写结构化列的是 `customer_number → client.custom_id`，和电话无关。以后如果要做“从识别结果建或更新客户”，必须直接读 JSON 里的成对键，经 `pkg/phone` 校验后写目标表的两列。
> 3. `import_session.column_mapping` 只是“表头→系统字段”的元数据。`raw_paste_data` 和 S3 文件是管理员提交的源数据。这三者都**保持原样、不迁移**。拆分只发生在 importer 落库那一刻，落库时一律经 `pkg/phone` 写成“国家 + 本国号码”两列。

### 4. 影响与风险

1. **国家无法判定，信息还被主动丢弃**：
   - 160 个识别号码中带 `+` 的为 0；`country` 只有 `USA` 或 null（还有 2 行乱码）。
   - 供应商给出的商户 `country_code` 在 DTO 层被丢掉（`dto.py:66-96`）。
   - 5 个 `0` 开头的 5+5 号码不可能是 US 号码，但系统照常保存、照常展示，没人知道它们属于哪个国家。
2. **客户匹配误命中（有数据佐证）**：
   - 匹配逻辑先切片段再做子串匹配。号码里只要有空格（`(999) 999-9999`、`99999 99999`、`999 999-9999` 共 41 个），就会被切成 3–5 位的短片段。
   - 在 test 上模拟 `services.py:527-570` 的逻辑：**3 条 `client_master_invoice_recognition`（都是 MODERATED）因为带空格，产生了短片段，每条在 219 家有效餐厅中误命中 4~16 家**。这 3 张主发票下挂了 39 张客户发票，打开它们时“businesses”候选列表都会被这些误命中污染。
   - 只有一条号码是完整 10 位、不会被切碎，它命中 0 家。原因是 test 的餐厅号码脱敏了，prod 上会正常命中。
   - 另外，任何不含数字的值（如 `-`）规范化后是 `''`，而 `'' in rest_phone` 恒为真，**会命中全部餐厅**。目前 `-` 只出现在 `invoice_recognition` / `master_invoice_recognition` 中，暂时没触发，属于潜在缺陷。
3. **同一键里格式混杂**：OCR 写入的是 7 种本国写法，而选了客户之后，`prepare_client_invoice_recognition_from_master` 写入的是 E.164（:741-743），还附带一个非 schema 的 `customer_data.phone_number` 键。下游只能靠“只留数字 + 子串”来猜。
4. **门店分支 KeyError 是潜伏缺陷**（:498 / :1172）。一旦出现 CLIENT 类型公司的主发票，门店匹配会整体失效，而且只会留下一行 error 日志。
5. **导入的国家推断太粗，规则也不一致，而且直接影响短信**：
   - 不带 `+` 的号码一律按 US 解析（importer.py:36）。
   - 同一条导入流程里，校验用 `is_valid`（row_report），落库用 `is_possible` 并在失败时回写原文（phoneconverter），两套标准。
   - 导入后立即按该号码发邀请短信（tasks.py:84-136）。一个没写 `+` 的外国号码，如果恰好也能按 US 规则解析通过，就会**被当成美国号码收到短信**。
   - 联系人电话为空时写 `''` 而不是 NULL（§2.3 有 6 条佐证）。
   - 客户文件导入的 `'+1' +` 硬编码会留下 `+1(999) …` 这种既不是 E.164、也不是本国格式的值。
6. **旧映射会静默丢号**：9 个 MAPPED/VALIDATED 会话的映射含当前不认识的目标字段（其中 8 个是旧版电话字段，如 `Phone → phone`）。现在如果继续 validate 或 execute，电话列会被静默忽略，也就是 `row.get('phone_number')` 读到 None。
7. **个人信息卫生**：6 个会话的 `row_errors` 以明文回显了电话原值。这和规范化无关，但属于同一批非结构化电话数据。
8. **审计假设不成立**：`data` 列已经被映射、覆盖、复制过，算不上“原始识别结果”。真正的原始件只有发票文件本身。因此“为了审计，JSON 一个字都不能动”这个理由不成立。反过来，如果在 JSON 里直接把 OCR 原文改写成本国号码，又确实会丢失“OCR 到底读到了什么”。所以需要 `raw_phones` 来保留这部分原文。

## 二、怎么处理（方案）

### 1. 目标表结构

**原则**（对应结论 1–3）：

- 4 张识别表**不加表列**。在 `data` JSON 内按 S1/S2 成对存储“国家 + 本国号码”，号码键名保持不变，新增 `*_country_code` 键。校验放在 DTO 层，因为 JSON 只由唯一的 DTO 写入。不加 DB 级 JSON CHECK：维护成本高，而且对 `json` 类型要写函数。
- 电话识别原文存进只写一次的 `raw_phones`。它只由识别 worker 或迁移写入，之后任何人工修改都必须原样保留它。
- `import_session` 的三个字段（`column_mapping`、`raw_paste_data`、S3 原文件）都**保持原样**。拆分只在落库时做，目标列由各表文档负责新增。

**JSON v2 电话键**（S2：号码键去掉末尾 `_number` 再加 `_country_code`）：

| 对象 | 号码键（保持不变） | 新增国家键 | 号码键取值 | 国家键取值 |
|------|-------------------|-----------|-----------|-----------|
| `customer_data` | `first_phone_number` | `first_phone_country_code` | 本国号码纯数字 `^[0-9]{4,15}$` 或 null | ISO 3166-1 alpha-2 `^[A-Z]{2}$` 或 null |
| `customer_data` | `second_phone_number` | `second_phone_country_code` | 同上 | 同上 |
| `customer_data` | `sales_person_phone_number` | `sales_person_phone_country_code` | 同上 | 同上 |
| `customer_data` | `fax_number` | `fax_country_code` | 同上 | 同上 |
| `merchant_data` | `phone_number` | `phone_country_code` | 同上 | 同上 |
| `merchant_data` | `fax`（不改名，S1） | `fax_country_code` | 同上 | 同上 |

规则（S4/S5）：
- 号码和国家要么都为 null，要么都非 null。
- 空串一律转为 null。
- 号码中不得含 `+`、空格、横线或括号。
- 删除非 schema 的 `customer_data.phone_number` 键。

**顶层新增键**：

```jsonc
{
  "customer_data": { "first_phone_country_code": "US", "first_phone_number": "9999999999", "...": "..." },
  "merchant_data": { "phone_country_code": "US", "phone_number": "9999999999", "fax_country_code": null, "fax": null },
  "phone_schema": 2,                       // v2 标记，便于验收和兼容判断
  "raw_phones": {                          // 只写一次：识别/迁移时的电话原文，人工修改不得改动
    "source": "ocr",                       // ocr | migration
    "default_region": { "customer_data": "US", "merchant_data": "US" },
    "customer_data": { "first_phone_number": "(999) 999-9999", "second_phone_number": null,
                       "sales_person_phone_number": null, "fax_number": null },
    "merchant_data": { "phone_number": "999-999-9999", "fax": null },
    "unparsed": ["customer_data.second_phone_number"]   // 解析失败的键：号码对置 null，原文保留在本对象
  }
}
```

**API 兼容期**（S6）：响应在每对键旁边增加只读的 `*_e164` 字段，例如 `customer_data.first_phone_e164`、`merchant_data.fax_e164`。这些字段由 `pkg/phone.format_e164` 计算，**不落库**。前端完成过渡后删除。

**DDL**：本文范围内**没有表结构 DDL**，4 张识别表和 `import_session` 的列都不变。导入落库的目标列 DDL 由各自文档给出，本文只依赖它们：

| 落库目标 | 依赖的新列 | 负责文档 |
|----------|-----------|----------|
| `company.phone_number` | `company.phone_country_code` | company 系列文档 |
| `company_phone_number.phone_number` | `company_phone_number.phone_country_code` | company 系列文档 |
| `company_contact_person.phone_number` | `company_contact_person.phone_country_code` | company 系列文档 |
| `client.temporary_phone_number` | `client.temporary_phone_country_code` | 005 |

### 2. 数据迁移

**A. 识别 JSON v1 → v2**：新增一个纯数据的 alembic 迁移（如 `<rev>_recognition_json_phone_pairs.py`），不做 DDL。

迁移内需要内嵌一份**冻结的**转换函数，直接 `import phonenumbers`，不引用 `app.pkg.phone`。这样以后应用代码怎么改，都不会影响这次迁移的结果。

```python
TABLES = [('client_invoice_recognition', 'client_invoice_id'),
          ('client_master_invoice_recognition', 'id'),
          ('invoice_recognition', 'invoice_id'),
          ('master_invoice_recognition', 'id')]
PAIRS = {'customer_data': [('first_phone_number', 'first_phone_country_code'),
                           ('second_phone_number', 'second_phone_country_code'),
                           ('sales_person_phone_number', 'sales_person_phone_country_code'),
                           ('fax_number', 'fax_country_code')],
         'merchant_data': [('phone_number', 'phone_country_code'),
                           ('fax', 'fax_country_code')]}
COUNTRY_TEXT = {'USA': 'US', 'US': 'US', 'U.S.A.': 'US', 'UNITED STATES': 'US'}  # 只认明确写法

def region_of(obj):                        # 地址国家文本 -> 默认解析区域；认不出就用业务默认 US
    return COUNTRY_TEXT.get((obj.get('country') or '').strip().upper(), 'US')

def split(raw, region):                    # -> (iso2, national) | None；口径同 000 号文档的 split()
    try:
        p = phonenumbers.parse(raw, None if raw.startswith('+') else region)
    except phonenumbers.NumberParseException:
        return None
    # JSON 中的号码未脱敏，且原文会留在 raw_phones，所以这里比 000 更严格：
    # 只接受 is_valid_number。is_possible 会放过 0 开头和不存在的区号（如 898），
    # 而 region_code_for_number 对无效号返回 None，会被错误地兜底成默认区域。
    if not phonenumbers.is_valid_number(p):
        return None
    iso = phonenumbers.region_code_for_number(p)              # +1 等共用码按号段推回国家
    national = phonenumbers.national_significant_number(p)    # 保留意大利式前导 0；不要用 str(p.national_number)
    if not iso or not re.fullmatch(r'[0-9]{4,15}', national):
        return None
    return iso, national

def to_v2(data, source, report, ref):
    d = copy.deepcopy(data)
    raw = {'source': source, 'default_region': {}, 'unparsed': []}
    for obj, pairs in PAIRS.items():
        o = d.get(obj) or {}
        d[obj] = o
        region = region_of(o)
        raw['default_region'][obj] = region
        raw[obj] = {}
        for num_key, cc_key in pairs:
            v = (o.get(num_key) or '').strip()
            raw[obj][num_key] = o.get(num_key)                # 原文（含空串）原样留档
            if not v:
                o[num_key] = o[cc_key] = None; continue
            res = split(v, region)
            if res is None:
                o[num_key] = o[cc_key] = None
                raw['unparsed'].append(f'{obj}.{num_key}')
                report.append((*ref, f'{obj}.{num_key}', mask(v)))   # 清单只记形态（数字→9），不记原值
            else:
                o[cc_key], o[num_key] = res
    d.get('customer_data', {}).pop('phone_number', None)       # 清理 prepare_* 写入的非 schema 键
    d['raw_phones'], d['phone_schema'] = raw, 2
    return d

def upgrade():
    conn, report = op.get_bind(), []
    for table, pk in TABLES:
        for r in conn.execute(sa.text(f'SELECT {pk} AS id, data FROM {table}')).mappings():
            data = r['data']
            if not isinstance(data, dict) or 'customer_data' not in data or data.get('phone_schema') == 2:
                continue                                       # FAILED 行（{} 或只有 selected_client_id）跳过
            conn.execute(sa.text(f'UPDATE {table} SET data = CAST(:d AS json) WHERE {pk} = :id'),
                         {'d': json.dumps(to_v2(data, 'migration', report, (table, str(r['id'])))), 'id': r['id']})
    log_unparsed(report)   # 输出解析失败清单（表、主键、JSON 路径、形态），禁止静默丢弃；
                           # 同时写入 000 号文档的 phone_migration_issue（column_name 写 data.<obj>.<key>）
```

**downgrade**：对 `phone_schema = 2` 的行逐键处理：
- 如果当前号码对仍等于“原文按当时规则解析的结果”，说明迁移后没人改过，就还原 `raw_phones` 中的原文。
- 否则按 S8 写回 `'+' + 拨号码(国家) + 号码`。

处理完后删除全部 `*_country_code`、`raw_phones` 和 `phone_schema` 键。

**test 快照 dry-run 预期**（JSON 未脱敏，可以直接参考）：
- 共改写 255 行；涉及 160 个非空值，分布在 51 行中。
- 28 个空串转为 null。
- 已用 phonenumbers 在 test 快照上实测（只统计、不输出原值）：**147 个值成功拆成 `US + 10 位`**。
