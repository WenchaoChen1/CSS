## 一、现在是什么问题

### 1. 表结构现状

| 表 | 电话 / 邮箱所在列 | 类型 | 说明 |
|----|------------------|------|------|
| `sign_in_data` | `contact` + `contact_type`（EMAIL / PHONE_NUMBER） | varchar(255) + enum | 多态列：同一列既存邮箱也存手机号；另有 `password_hash`、`confirmation_session_id` |
| `sign_up_data` | 同上 | 同上 | 同上 |
| `reset_password_data` | 同上 | 同上 | 另有 `user_id` |
| `additional_sign_in_data` | 同上 | 同上 | 另有 `main_confirmation_session_id` |
| `company_audit_log` | `details` | varchar(1000)（JSON 文本） | Master DB 改公司电话 / 联系人 / 应付账款时写入号码与邮箱快照（详见 [002](002-公司-手机号.md)） |

四张认证表的行只在验证码会话期间被读取（按 `confirmation_session_id` 取，`CSS_backend-main/core_app/src/app/internal/core/auth/repositories.py:202-215`），验证码有效期 30 分钟（`CSS_backend-main/core_app/src/config/auth_settings.py:21` `confirmation_code_ttl = 60 * 30`）。但代码里没有任何清理逻辑，`deleted_at` 全为空，记录从 2024-02 起一直累积。

### 2. 数据现状

判定方法：`user` 表是按规则脱敏的（手机号尾部加 `1`、邮箱前加 `1`），认证流水里的值如果**与 user 的脱敏值不相等、但等于 user 脱敏值去掉脱敏标记**，就可以确定它是脱敏前的原值。这是保守口径——与任何用户都对不上的行（下表最后一列）同样可能是真实值，没有计入。

| 表 | 类型 | 行数 | 去重值 | 确认为原值（行） | 确认为原值（去重） | 对不上任何用户（行） |
|----|------|------|--------|------------------|--------------------|----------------------|
| sign_in_data | PHONE | 4,155 | 72 | 3,299 | 58 | 65 |
| sign_in_data | EMAIL | 2,597 | 285 | 1,084 | 142 | 73 |
| sign_up_data | PHONE | 291 | 286 | 208 | 205 | 31 |
| sign_up_data | EMAIL | 454 | 407 | 291 | 261 | 80 |
| reset_password_data | PHONE | 23 | 15 | 19 | 11 | 0 |
| reset_password_data | EMAIL | 100 | 89 | 53 | 48 | 4 |
| additional_sign_in_data | PHONE | 62 | 58 | 33 | 29 | 14 |
| additional_sign_in_data | EMAIL | 62 | 53 | 40 | 34 | 15 |

- 时间分布：四张表最早记录 2024-02，`created_at < 2026-08-22`（test 库重建、脱敏之日）的行占 sign_in 5,303 / 6,752、sign_up 639 / 745、reset 83 / 123、additional 106 / 124；确认为原值的手机号最晚一条创建于 2026-08-12，即**全部来自重建时导入的老环境数据**，脱敏时被漏掉。
- `company_audit_log.details`：共 626 行（569 行是 JSON 文本），44 行含 `+99999999999` 形态号码、42 行含邮箱，其中 38 行的邮箱没有 `1` 前缀（排除按约定保留的 swp* 邮箱后 36 行）。
- uat 库用同一个脚本、同一口径脱敏（数据来自 preprod），**预计同样存在**，本次未连 uat 核实。

### 3. 代码现状（脱敏脚本）

1. `docs/环境运维执行脚本/05-数据库运维/anonymize-db.sh:118-135`：只按**列名**选列——`column_name ILIKE '%email%'` 加前缀、`column_name ILIKE '%phone%'` 加后缀。认证表的列叫 `contact`，两条都不命中；JSON / 文本快照列（`company_audit_log.details`、`*_invoice_recognition.data`、`import_session.raw_paste_data` 等）也不在范围内。
2. `docs/环境运维执行脚本/05-数据库运维/mask-residual-pii.sh:61-97`：“残留复扫”脚本沿用同一个按列名选列的口径，所以复扫也查不出 `contact` 列的残留。
3. **与本专项的冲突**：`anonymize-db.sh` 的 phone 选列条件只排除了 `%type%`，没有排除 `%country%`。按 [000](000-统一规范-手机号拆分为国家码与号码两字段.md) 新增 `phone_country_code` 等列后，下次脱敏会把 `US` 改成 `US1`，直接违反新加的 CHECK 约束、导致脚本中途失败（`mask-residual-pii.sh:97` 已排除 `%country%`，两份脚本口径不一致）。
4. 业务代码：认证流水行在会话结束后没有任何清理（见 一.1），生产库同样会无限累积所有登录尝试的联系方式。

### 4. 影响与风险

- 非生产库存有约 300 个真实手机号、约 480 个真实邮箱（各表去重合计，跨表可能重叠），任何持有 `css_dev` 只读账号或堡垒机开发者钥的人都能读到，和“test / uat 已脱敏”的对外口径不符。
- 脱敏后自检（`anonymize-db.sh:111-116`、`:161-162` 只抽查一张带 `email` 列的表，优先 `user`）给出“已脱敏”的假象。
- 拆分国家列上线后，现有脱敏脚本会在新列上失败（一.3 第 3 条），阻断后续 test / uat 重建流程。
- 生产库：认证流水无保留期限，超出业务需要长期保存个人联系方式（数据最小化问题）。

## 二、怎么处理（方案）

### 1. 目标结构

不改表结构。目标是：
- 非生产库的认证流水表只保留脱敏后的值（或直接只保留近期行）；
- 脱敏脚本按“**列名 + 多态列 + JSON / 文本快照列**”三种口径覆盖，并排除国家列；
- 认证流水行有明确保留期限（验证码 TTL 30 分钟，建议保留 7 天用于排障）。

### 2. 数据处理

1. **非生产库一次性清理（test，先跑；uat 复核后同样处理）**——推荐直接删历史行，因为这些行在会话结束后已无业务用途：
   ```sql
   -- 在 test / uat 执行（需写权限账号，如 css_ops）；prod 不执行本段
   BEGIN;
   DELETE FROM additional_sign_in_data WHERE created_at < now() - interval '7 days';
   DELETE FROM reset_password_data     WHERE created_at < now() - interval '7 days';
   DELETE FROM sign_in_data            WHERE created_at < now() - interval '7 days';
   DELETE FROM sign_up_data            WHERE created_at < now() - interval '7 days';
   -- 剩下的近期行按脱敏口径补齐（swp* 邮箱按既有约定不加前缀）
   UPDATE sign_in_data SET contact = contact || '1' WHERE contact_type = 'PHONE_NUMBER' AND contact NOT LIKE '%1';
   UPDATE sign_in_data SET contact = '1' || contact WHERE contact_type = 'EMAIL' AND contact NOT LIKE '1%' AND contact NOT ILIKE 'swp%';
   -- sign_up_data / reset_password_data / additional_sign_in_data 同上
   COMMIT;
   ```
   注意 `confirmation_session` 与这四张表是 `ON DELETE CASCADE`（`CSS_backend-main/core_app/src/app/internal/core/auth/models.py:24-26`），删除方向是从会话删到流水；只删流水不影响会话表，若要一并清理会话表可按同样时间条件删除 `confirmation_session`。
2. **`company_audit_log.details`**：非生产库按正则替换 JSON 文本里的号码与邮箱（号码尾部加 `1`、邮箱前加 `1`），或在重建时整表清空（审计日志在非生产无保留价值）。由 [002](002-公司-手机号.md) 规定的新快照格式上线后同样适用。
3. **生产库**：不做脱敏；只上“保留期限”清理任务（见 二.3 第 3 条），先在 uat 演练。

### 3. 脚本与后端改动

1. `anonymize-db.sh`：
   - phone 选列条件增加 `AND column_name NOT ILIKE '%country%'`（与 `mask-residual-pii.sh:97` 对齐，**必须在任何 `*_country_code` 列上线前合入**）；
   - 新增多态列处理：对 `information_schema` 中同时有 `contact` 与 `contact_type` 列的表，按 `contact_type` 分别套用邮箱 / 手机号规则；
   - 新增“已知快照列”清单（`company_audit_log.details` 等）的处理或清空；
   - 末尾自检从只看 `user` 扩展为跑本文 二.6 的残留查询。
2. `mask-residual-pii.sh`：同样补多态列与快照列，否则复扫永远查不到这类残留。
3. 后端（P1，可单独排期）：worker 增加定时任务，删除 `created_at < now() - 7 天` 的四张认证流水行（及其已结束的 `confirmation_session`），prod 一并生效。

### 4. 前端改动

无。

### 5. 环境与发布注意

- 脚本改动在工作区仓库（`WenchaoChen1/CSS`），不涉及前后端分支；清理 SQL 只在 test / uat / support-* 执行，**prod 只上保留期限任务，不跑脱敏**。
- 清理前用 `backup-env-db.sh <env>` 先备份；`swp*` 邮箱按既有约定保留可收信。
- 与本专项的顺序：二.3 第 1 条的 `%country%` 排除必须先于 001–010 任何迁移上线，否则下一次 test / uat 重建脱敏会失败。

### 6. 验收标准

```sql
-- V1 认证流水表中不再有“可确认的脱敏前原值”（每行都应为 0）
SELECT 'sign_in_data', count(*) FROM sign_in_data s
WHERE (s.contact_type = 'PHONE_NUMBER'
       AND NOT EXISTS (SELECT 1 FROM "user" u WHERE u.phone_number = s.contact)
       AND EXISTS (SELECT 1 FROM "user" u WHERE u.phone_number = s.contact || '1'))
   OR (s.contact_type = 'EMAIL'
       AND NOT EXISTS (SELECT 1 FROM "user" u WHERE lower(u.email) = lower(s.contact))
       AND EXISTS (SELECT 1 FROM "user" u WHERE lower(u.email) = '1' || lower(s.contact)));
-- sign_up_data / reset_password_data / additional_sign_in_data 同样查询，均应为 0
-- （当前快照：sign_in_data 4,383 行，未通过）

-- V2 非生产库认证流水无超期历史行（应为 0）
SELECT count(*) FROM sign_in_data WHERE created_at < now() - interval '8 days';

-- V3 审计日志快照中无未加前缀的邮箱（应为 0；当前 36）
SELECT count(*) FROM company_audit_log
WHERE details ~ '"(?!1)[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\.[A-Za-z]{2,}"' AND details !~* '"swp';
```

脚本检查点：
- `grep -n "NOT ILIKE '%country%'" docs/环境运维执行脚本/05-数据库运维/anonymize-db.sh` 有命中；
- 两个脚本都处理 `contact` + `contact_type` 多态列；
- 在 test 重建演练中，脚本跑完后 V1–V3 全部为 0，且新增的 `*_country_code` 列取值未被改动。
