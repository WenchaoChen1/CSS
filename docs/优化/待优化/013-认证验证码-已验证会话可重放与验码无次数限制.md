## 一、现在是什么问题

### 1. 验证码框架现状

所有需要验证码的流程共用一套「确认会话」：

```
POST /api/auth/<场景>/pre           → 新建 system_confirmation_session(id, scenario) + 一行流水（contact 等）→ 返回会话 id
POST /api/auth/verify/contact       → 生成 6 位码，写 system_confirmation_code(code, expired_at = now + 30min)，发短信 / 邮件
POST /api/auth/verify/contact/code  → 码对上 → 把本会话"最近一批"未激活码的 activated_at 置为 now
POST /api/auth/<最后一步>            → 只查"本会话有没有 activated_at 非空的码" → 执行登录 / 改密码 / 加联系方式 / 注册
```

| 场景 | 第一步（谁能发起） | 最后一步 | 最后一步另外核对什么 | 代码 |
|------|------------------|----------|----------------------|------|
| 登录 `SIGN_IN` | `/auth/sign-in/pre`：邮箱或手机 + 正确密码 | `/auth/sign-in` → 签发 token | 用户 id + 密码哈希 + 联系方式都没变 | `services.py:318-345`、`:347-401` |
| 重置密码 `RESET_PASSWORD` | `/auth/reset-password/pre`：**只要邮箱或手机号** | `/auth/reset-password` → 改密码、吊销该用户全部 token | 用户 id + 联系方式没变（**不核对密码哈希**） | `services.py:519-537`、`:539-565` |
| 注册 `SIGN_UP` | `/auth/sign-up/pre`：任意未注册的邮箱 / 手机 + 密码 | `/auth/sign-up` → 建用户 | 邀请码未使用（一次性） | `services.py:89-108`、`:220-316` |
| 加联系方式 `ADDITIONAL_SIGN_IN` + `ADDITIONAL_SIGN_IN_SECURITY_CHECK` | `/auth/additional/contact/pre`：需登录 | `/auth/additional/contact` → 改写用户邮箱 / 手机 | 三个会话都存在，其中 contact、security_check 两个有已激活码（main 会话不发码、不查激活），main 会话对得上（见 R7） | `services.py:403-446`、`:448-517` |

两张表：

| 表 | 列 | 说明 |
|----|----|------|
| `confirmation_session` | `id`、`scenario`、`created_at`、`updated_at`、`deleted_at` | **没有过期时间、没有"已验证 / 已使用"标记、没有失败次数**（`models.py:14-18`；建表 `CSS_backend-main/core_app/src/app/migrations/versions/2024_01_22_0654-55ce4a3bbce6_auth_and_users.py:53-64`） |
| `confirmation_code` | `id`、`confirmation_session_id`、`code varchar(32)`（明文）、`expired_at`、`activated_at`、`created_at`… | `models.py:64-71`；建表同一迁移 `:108-122`；`confirmation_session_id` 上没有索引（报告 P3-3：8,514 行） |

配置（`auth_settings.py:20-22`）：重发间隔代码默认 5 s，验证码有效期 1800 s，`confirmation_code_verification_enabled` 默认 `True`。各环境底稿只配了重发间隔和校验开关（见 一.2 R6），有效期都用默认值。

### 2. 根因（代码）

**R1（主因）已验证的确认会话可以无限次重放。**

- 最后一步只判断"本会话**曾经**有过一个已激活的码"：`check_activated_codes_exists`（`repositories.py:79-86`）的条件只有 `activated_at != NULL`，**没有时间窗口**。登录（`services.py:354-368`）、重置密码（经 `_get_verified_confirmation_session`，`services.py:567-590`）、注册（`services.py:223-238`）、加联系方式（`services.py:472-491`）都是这一个判断。
- 会话本身不过期：`get_confirmation_session`（`repositories.py:105-117`）只按 `id` + `scenario` 查，不看 `created_at`，也不看 `deleted_at`。成功之后没有任何代码把会话标成已用或删掉（后端没有删 / 改 `confirmation_session` 的代码，worker 也没有清理任务——与 [011](011-测试库脱敏-认证流水与快照列残留真实联系方式.md) 一.1、报告 P3-4 结论一致）。
- 结果：
  - **登录**：同一个 `confirmation_session_id` 反复 `POST /api/auth/sign-in`，每次都签发一套新 token（`CSS_backend-main/core_app/src/app/internal/core/auth/tokens/services.py:34-72`），带 `keep_me_signed_in=true` 就是 30 天 token（`auth_settings.py:17`、`:41-43`）。失效条件只有用户改了密码或联系方式、或被删除（`services.py:374-381`；软删除用户按联系方式查不到），sprint6 另加公司被停用（`:383-385`）。
  - **重置密码**：最后一步回查用户只用 `id` + 联系方式（`services.py:554-560`），**不看密码哈希**。同一个 `RESET_PASSWORD` 会话在用户改过密码之后**仍能再把密码改成任意值**，直到用户换掉邮箱 / 手机号或被删除。团队改密（`CSS_backend-main/core_app/src/app/internal/core/users/services.py:103-116`，只改 hash）也不会让它失效。
  - 注册：重放会被邀请码一次性校验挡住（`services.py:243-245` → `CSS_backend-main/core_app/src/app/internal/core/master_database/services.py:676-677`），影响小。
- **sprint6 会把会话 id 写进操作日志**：操作日志中间件记录 `POST /auth/sign-in/pre` 和 `POST /auth/sign-in` 的请求参数（`CSS_backend-main/core_app/src/app/internal/main_app/middlewares/action_log.py:73-74`、`:128-141`、`:283`），屏蔽规则只匹配键名含 `password|token|secret` 的字段（`action_log.py:33`），所以 `confirmation_session_id` 会原样写进 `system_user_action_log.params`（推断，未实测；与 015 一.3 第 6 条结论一致）。叠加 R1，**能读 `system_user_action_log` 表或数据库备份的人，就能拿里面的会话 id 直接登录成该用户**。（2026-11-19 更正：原文写的是「能看操作日志的人」，不对——日志接口 `admin_users/dto.py:93-109` 和 team `responses.py:61-75` 从来不返回 `params`，`8ce6cdca` 只改了 Logs 页的显示范围，写入没变。）test 已于 2026-11-18 随 sprint6 上了这个中间件、没有带 A11；`origin/main` / `uat` 上还没有，所以必须在 sprint6 上 uat / prod 之前处理（A11）。
- 现在是单会话：每次签发都覆盖 Redis 键 `user_session:{user_id}`（`CSS_backend-main/core_app/src/app/internal/core/auth/sessions/services.py:18-29`），重放一次会把真用户挤下线，多少能被察觉。[持久会话开发方案](../../ocean-island/02-持久会话/开发方案.md) §3.5.1 第 4 条改为多会话并存（Q9-A）后，重放将**完全静默**。

**R2 没有任何尝试次数限制、锁定或频控。**

- `verify_contact_code`（`services.py:175-203`）码不对就返回 `incorrect_confirmation_code`，没有失败计数，会话不会因为猜错而作废；两张表上也没有可计数的列（一.1）。
- `pre_sign_in`（`services.py:318-326`）密码错只记一条操作日志，没有失败计数、锁定或退避。
- 发码只限制"同一会话两次发码间隔 ≥ N 秒"（`services.py:142-153`）。但会话可以无限新建：`pre_reset_password` 只要一个已注册的邮箱或手机号（`services.py:519-537`），`pre_sign_up` 只要一个格式合法、未注册的号码（`requests.py:30-37`）——**对同一个联系人、同一个 IP 都没有发送上限**（短信轰炸、短信刷量费用、发件域名信誉）。
- 仓库里没有频控：后端代码与依赖中未检索到 `slowapi` / `ratelimit` / `rate_limit` / `limit_req`（排除 `.venv`），`CSS_backend-main/core_app/nginx/nginx.conf` 没有 `limit_req`；`css-terraform` 中未检索到 `wafv2` / `rate_based` / `aws_waf`，即**未在代码仓库中发现** WAF 限速规则。
- `/api` 唯一的门槛 `X-API-KEY`（`CSS_backend-main/core_app/src/app/internal/main_app/app.py:66`）是前端构建期烤进 JS 的（`CSS_frontend-main/src/constants/appConfig.ts:4`、`CSS_frontend-main/src/config/axios/http.ts:9`），等于公开，挡不住脚本。

**R3 发新码时旧码不作废，同时有效的码可多达数百个。**

- 每次 `verify_contact` 都插入一行新码（`services.py:155-161`），旧码原样保留。
- 验码时的候选集 = 本会话"未过期、且晚于最近一次激活"的**全部**码（`repositories.py:44-65`），输入命中其中任意一个就通过（`services.py:197-203`）。
- 有效期 1800 s，重发间隔代码默认 5 s、各环境底稿 10 s → 一个会话最多约 **360 / 180 个**同时有效的 6 位码：

| 同时有效码个数 k | 单次猜中概率 | 平均需要猜的次数（不重复猜）≈ (10⁶+1)/(k+1) |
|---:|---:|---:|
| 1 | 1 / 1,000,000 | 约 500,000 |
| 180（间隔 10 s，攒满 30 分钟） | 约 1 / 5,556 | 约 5,525 |
| 360（代码默认 5 s） | 约 1 / 2,778 | 约 2,770 |

  按每秒 50 次请求估算，k = 180 时约 2 分钟可猜中（推断，未实测）。
- 发码间隔检查是"先查最后一条、再插入"（`services.py:142-161`），没有加锁，并发请求可以同时通过、一次产生多个码（推断，未实测）。
- `activate_all_recent_codes`（`repositories.py:67-77`）的 UPDATE 只按会话 + 码值匹配、**没有过期条件**，会把同会话里码值相同的旧行（含已过期的）一起改 `activated_at`。现在影响不大，但"按值批量激活"本身就是 R3 的写法。

**R4 验证码用非密码学随机数生成、明文存库。**

- `CSS_backend-main/core_app/src/app/pkg/utils.py:1`、`:16-17`：`random.choice(string.digits)`（Mersenne Twister，不是密码学安全的随机数）。
- 码明文存在 `confirmation_code.code`（`models.py:69`）。能读库的人（只读账号、备份文件、运维）可以：用目标邮箱调 `pre_reset_password` → 触发发码 → 从库里读到码 → 验码 → 改密码。也就是**读库权限 = 可接管任意账号**。prod 库现为未脱敏真实数据。
- 同类泄露面：短信文本经 Kafka `sms_send` 主题传递（`本地运行指南.md:87`），`sms_sender` 日志同时记号码和验证码（[001](001-用户与登录认证-手机号.md) 一.4 第 4 条）。
- 本地开发依赖读明文码：`CSS_backend-main/deploy/windows/README.md:84`、`本地运行指南.md:87`、[012](012-WebSocket鉴权-数据库会话泄漏卡死迁移.md) 附「本机复现脚本要点」第 1 步。方案必须保住 dev 的这条路。

**R5 账号枚举。**

- `pre_sign_up` 遇到已注册的联系方式返回 400 `contact_already_use`（`services.py:90-93`、`handlers.py:92-98`）；`pre_reset_password` 找不到用户返回 400 `user_not_found`（`services.py:520-522`、`handlers.py:346-352`）。前端原样展示（`CSS_frontend-main/src/models/errors.ts:13`、`:15`）。配合 R2，可以批量探测哪些邮箱 / 手机号是本平台用户。
- `pre_sign_in` 统一返回 `invalid_credentials`（`CSS_backend-main/core_app/src/app/internal/core/auth/errors.py:58-60`），这一步本身没问题。

**R7（指向 014）加联系方式链路。**

### 3. 影响与风险

1. **重置密码是接管任意账号的捷径**：只需目标邮箱 / 手机号（R5 可先确认是否注册）→ 反复 `verify/contact` 攒码（R3）→ 不限次猜码（R2）→ 改密码。代价只是受害人会收到大量验证码短信 / 邮件。prod 代码相同。
2. **已验证的会话 = 长期有效、免二次验证的凭证**（R1）：会话 id 只要在 sprint6 的操作日志、浏览器开发者工具、HAR 排障材料、代理日志里出现过一次，就能在之后任意时间登录（直到改密码）或改密码（直到换联系方式）。前端只把它放在内存里（`CSS_frontend-main/src/ui/pages/Auth/ui/AuthForm/AuthFormStore.ts:42-48`，没有持久化），所以泄露面主要是服务端日志、网络层与排障材料（推断）。
3. **第二因素名存实亡**：R2 + R3 下，登录的验证码只剩几千次猜测量级；`pre_sign_in` 无锁定，密码本身也能在线爆破（每次尝试都算一次 PBKDF2，大量请求同时也是 CPU 压力，推断）。
4. **费用与信誉**：发码对联系人 / IP 没有上限 → 短信轰炸、短信刷量费用、发件域名被拉黑。
5. **读库即接管**（R4）：凡有库读权限的人都能接管任意账号。
6. **与持久会话方案的交互**：多会话并存上线后，R1 的重放不再挤掉真用户，更难发现 → A1 必须先于或随同持久会话上线。

```sql
-- 表名按 sprint6（31731a571e02 之后，test 已是）；在 uat / prod 的旧代码线上执行要换回 confirmation_session / confirmation_code
-- system_confirmation_session：A1 / A3
ALTER TABLE system_confirmation_session
  ADD COLUMN expires_at      timestamptz DEFAULT (now() + interval '30 minutes'),  -- 见 二.5「迁移窗口」

      FROM system_confirmation_code WHERE activated_at IS NOT NULL GROUP BY 1) c
```

### 3. 后端改动

**A1 会话一次性 + 有效期。**

- `ConfirmationSession` 模型加上述列；`create_confirmation_session`（`repositories.py:93-103`）写入 `expires_at = now + confirmation_session_ttl`（新配置，默认 1800 s）。
- 新增仓储方法，用一条 UPDATE 原子地"校验 + 消费"，取代四个最后一步里的 `check_activated_codes_exists`：

  ```python
  async def consume(self, id: UUID, scenario: Scenario, require_verified: bool) -> bool:
      now = datetime.now(tz=timezone.utc)
      conditions = [
          models.ConfirmationSession.id == id,
          models.ConfirmationSession.scenario == scenario,
          models.ConfirmationSession.consumed_at.is_(None),
          models.ConfirmationSession.expires_at > now,
      ]
      if require_verified:   # = auth_settings.confirmation_code_verification_enabled
          conditions.append(models.ConfirmationSession.verified_at > now - auth_settings.confirmation_verified_window_timedelta)
      query = (
          update(models.ConfirmationSession).where(*conditions)
          .values(consumed_at=now).returning(models.ConfirmationSession.id)
      )
      consumed = (await self._session.execute(query)).scalar_one_or_none()
      await self._session.commit()
      return consumed is not None
  ```

  - `confirmation_verified_window`：验证后多久内必须完成最后一步，建议 10 分钟。
  - **校验开关关闭时也要消费**（只是不要求 `verified_at`），保证 test 上同样一次性。
  - 先消费、再做业务（失败即关闭）：登录、重置密码在回查用户之前消费；注册在邀请码预检（`services.py:243-245`）通过之后、建用户之前消费；加联系方式三个会话一起消费（与 014 B6 是同一件事，按 014 的事务写法实现）。并发两个相同请求时只有一个 UPDATE 能命中。
  - **注册另有一种写法，待二选一**：[016](016-注册-普通邀请码路径非原子留下孤儿用户.md) D5 建议把消费放进注册的同一个事务（`consume` 加 `commit=False`，在建用户之前执行、与建用户和激活一起提交）。这样失败时整体回滚，会话仍可用，用户改正后可以用原会话重试；双击或重放的第二个请求会在行锁上等待，第一个提交后返回 `invalid_confirmation_session`。两种写法都能保证一次性，实现时选定一种，并在本项和 016 的「三、处理记录」里写明。
- `verify_contact` 与 `verify_contact_code` 开头也要拒绝已消费 / 已过期的会话（返回 `invalid_confirmation_session`）。
- 验码成功时写 `confirmation_session.verified_at = now`。

**A3 只认最新码 + 次数上限 + 发码加锁。**

- `verify_contact`（`services.py:110-173`）：
  1. `SELECT ... FROM system_confirmation_session WHERE id = :id FOR UPDATE` 锁住会话，再做间隔检查和插入，消除并发多发码；

### 6. 验收标准

接口级（在 uat 执行，校验开启）：

1. **登录不可重放**：完成一次登录后，用同一个 `confirmation_session_id` 再 `POST /api/auth/sign-in` → 400 `invalid_confirmation_session`。同时发 2 个相同的 sign-in 请求 → 恰好 1 个 200。
2. **重置密码不可重放**：完成一次重置后，同一会话再 `POST /api/auth/reset-password` → 400。另开一个已验码、未使用的 `RESET_PASSWORD` 会话，期间先用另一会话完成一次重置（或团队改密），再用它 → 400（A2）。
3. **会话有效期**：用 SQL 把某会话 `expires_at` 改到过去，`verify/contact`、`verify/contact/code`、最后一步都返回 400。验码成功后超过 10 分钟才调最后一步 → 400。
4. **旧码作废**：发码 A，等过间隔后发码 B；提交 A → `incorrect_confirmation_code`；提交 B → 200。
5. **次数上限**：连续 5 次错码后，第 6 次即使提交正确的码也返回 `too_many_attempts`，最后一步 400；同一会话第 6 次发码被拒。
6. **频控**：同一联系方式连续输错密码超过阈值 → 429 且带 `Retry-After`；同一联系方式 1 小时内发码超过阈值 → 429；换 IP 后对同一联系方式仍生效。
7. **随机数**：`grep -n "random.choice" CSS_backend-main/core_app/src/app/pkg/utils.py` 无命中，验证码生成用 `secrets`。
8. **枚举**（若 A7 采纳）：对不存在的邮箱调 `pre_reset_password`，状态码与响应结构和存在时相同。
9. **test**：SSM `/css/test/backend.env` 中 `CONFIRMATION_CODE_VERIFICATION_ENABLED=true`，或「三、处理记录」已写明例外与拍板人；uat / prod 的 SSM 值已核对为 `true`。
10. **自动化测试**：二.3 列出的新用例在校验开启下全部通过（`make dev_test k=confirmation` 或对应目录）。
