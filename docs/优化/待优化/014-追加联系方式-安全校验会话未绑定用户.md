## 一、现在是什么问题

### 1. 流程与表结构现状

### 2. 问题清单

**F1（主因）三个会话不绑定用户，最后一步不核对安全校验发给了谁。**

- 第 4 步的用户 id 只来自调用者的 token（`CSS_backend-main/core_app/src/app/internal/main_app/middlewares/jwt/services.py:48` → `handlers.py:247-250`），会话和数据行里都没有用户信息（见 一.1），`add_additional_sign_in` 也从不比对 security_check 数据行的联系方式是不是**这个用户**的当前联系方式（`services.py:448-517` 全段没有读用户）。
- 安全校验（向旧联系方式发码）本来就是为了防“只拿到 token 的人改联系方式”，现在可以拿**别的账号**的安全校验顶替。
- 攻击路径（推断，未实测）。条件：攻击者拿到受害者 V 的 access token（前端把 token 存在 `localStorage`，`CSS_frontend-main/src/utils/storageManager.ts:7-16`，任何注入页面的脚本都能读；勾“保持登录”时 access token 有效期 30 天，`CSS_backend-main/core_app/src/config/auth_settings.py:16-17,41-43` + `services.py:387-391` + `core/auth/tokens/services.py:45-61`；但当前代码每个用户只保留一个活动会话，V 在别处重新登录后旧 token 即失效，`core/auth/tokens/services.py:89-98`，所以窗口是“V 下次登录之前”），另有一个自己能登录的账号 A。

  | 步 | 攻击者操作 | 为什么能过 |
  |----|-----------|-----------|
  | 1 | 用 **A 的 token** 调 `pre`，新联系方式填自己能收信的新邮箱 E_x | E_x 没人用；security_check 行写的是 **A 自己的**邮箱（`services.py:435-436`） |
  | 2 | 调 `verify/contact`、`verify/contact/code` 激活两个会话 | 两个码分别发到 E_x 和 A 的邮箱，都在攻击者手里；这两个接口不要 token |
  | 3 | 用 **V 的 token** + 第 1 步的 3 个 id 调 `/auth/additional/contact` | 会话存在、场景对、码已激活、数据行都指向 main —— 没有任何一项和用户有关；写入 `user_id = V`（`services.py:511-515`） |
  | 4 | 用 E_x 走找回密码，再用 E_x + 新密码登录 | `pre_reset_password` 按联系方式找人（`services.py:519-537`），码发到 E_x；重置后 `revoke_all_tokens` 把 V 踢下线（`:564-565`） |

  结果：V 的邮箱被换成 E_x、密码被改、V 所有会话失效。V 如果还有手机号，攻击者把第 1–3 步用手机号再跑一次即可把两种联系方式都换掉 → **整号接管**。
- test 环境的验证码开关是关的（`deploy-env/test/backend.env:71` `CONFIRMATION_CODE_VERIFICATION_ENABLED=false`），第 4 步的两个“码已激活”判断整段跳过（`services.py:472-491`），**只凭 V 的 token、不需要 A 账号**就能改（推断，未实测；test 是脱敏数据，但同样说明这个接口唯一的保护就是那两个码）。

**F2 主会话关联校验用了 `and`，一边对上就放行。**

```python
# services.py:492-507（prod：origin/main services.py:470-485，and 在 :478）
or (
    contact_data.main_confirmation_session_id != main_confirmation_session.id
    and security_check_data.main_confirmation_session_id != main_confirmation_session.id
)
```

只有两行**都**不属于 main 才拒绝。也就是说 security_check 可以取自**另一次** `pre`。即使将来只给 main / contact 加了用户绑定，安全校验仍可从攻击者自己的那次流程里借过来，所以 F1 的修复必须同时覆盖三个会话，并把这里改成 `or`。

现有测试没有覆盖到这一支：两个“未关联”用例传的都是随机 `main_confirmation_session_id`（`CSS_backend-main/core_app/src/app/internal/main_app/auth/tests/additional_contact/test_additional_contact_error.py:132-136`、`:170-174`），在第一道“main 会话不存在”就返回 400 了，根本走不到 `and` 这一行。

**F3 “追加”实为覆盖。**

- 写入是按列直接 `UPDATE`：`values({contact_type: contact})`（`CSS_backend-main/core_app/src/app/internal/core/users/repositories.py:99-102`），这是后端唯一一处调用（`services.py:511`）。
- `pre` 不限制联系方式类型（入参 `email` / `phone_number` 二选一、都是自由字符串，`CSS_backend-main/core_app/src/app/internal/main_app/auth/transport/requests.py:88-92`），而 `system_user` 只有一个邮箱列、一个手机号列。已有邮箱的用户再“追加”一个邮箱 = **把原邮箱换掉**，手机号同理。
- 前端只给缺的那种类型显示入口（`AdditionalAuthStep.tsx:58-71`：`{!email && ...}`、`{!phoneNumber && ...}`），产品语义是“补第二种”，后端没有守住；直接调接口就能“换”。
- 换掉的时候不通知原联系方式、不写用户日志（`LogEvent` 没有对应事件，`CSS_backend-main/core_app/src/app/internal/core/users/domains.py:85-99`）、不吊销其他会话。

**F4 用 main 会话 id 调 `verify/contact` → 500，且先落了一条验证码。**

main 会话的场景也是 `ADDITIONAL_SIGN_IN`（`services.py:414-416`），`verify_contact` 按场景去 `additional_sign_in_data` 取数据行（`:127-129`、`:137`），main 没有数据行 → `contact_data` 为 `None`；随后先建码并提交（`:157-161`，仓储里直接 `commit`，`CSS_backend-main/core_app/src/app/internal/core/auth/repositories.py:39-40`），再在 `:163` `contact_data.contact_type` 抛 `AttributeError` → 全局 500（`CSS_backend-main/core_app/src/app/internal/main.py:51-63`、`CSS_backend-main/core_app/src/app/pkg/global_exception_handler.py`）。前端不会这样调（`useAdditionalAuthStep.ts:50-53`、`:116-118` 只用 contact / security_check 的 id），但任何人都能触发，并留下孤儿 `confirmation_code` 行。第 4 步把 main 的 id 当 contact id 传时，验证码开关关闭的环境（如 test）同理：`services.py:495-498` 对 `None` 取属性 → 500；开关打开时 main 会话没有已激活的码（`verify/contact` 建的码在发送前就 500 了，没人收到），会先在 `:472-481` 返回 400。

**F5 最后一步不复查唯一性。**

唯一性只在 `pre` 查一次（`services.py:408-410`），第 4 步直接写（`:511-515`）。两次之间别人注册或追加了同一联系方式（验证码有效期 30 分钟，会话本身不过期，见 F6），写入就撞部分唯一索引（`users/models.py:38-39`），`IntegrityError` 没人接 → 500 而不是“联系方式已被占用”。号码不规范化时（例如带空格括号）唯一索引还拦不住，见 001 一.4 第 3 条。

**F6 会话用后不作废、激活不看时效（全场景通病，由 [013](013-认证验证码-已验证会话可重放与验码无次数限制.md) 统一处理；原记在 015 一.3 第 6 条）。**

`check_activated_codes_exists` 只看“有没有激活过的码”，不看过期时间（`repositories.py:79-86`）；第 4 步成功后三个会话原样保留。所以一组准备好的会话 id 可以隔几天再用；配合 F1，攻击者可以提前备好多组（每组一个新邮箱）。

**F7 两个 handler 的错误分支没有兜底。**

`add_additional_contact` 只把 `INVALID_CONFIRMATION_SESSION` 映射成 400，其他错误类型会**掉到 `return SuccessOut()` 返回 200**（`handlers.py:251-258`）；`pre_additional_contact` 只处理 `CONTACT_ALREADY_USE`，其他错误会在 `:227` 对 `None` 取 `model_dump()` → 500。修 F3 / F5 时新增的错误类型如果不改 handler，会出现“后端拒绝了、前端显示成功”。

**附带（前端）：**窄屏不渲染“旧联系方式验证码”输入框（`AdditionalAuthStep.tsx:168-207` 包在 `isDesktop &&` 里），提交时 `oldLayerCode` 为空，`verify/contact/code` 必然 422，手机上走不完这个流程（推断，未实测）；`pre` 失败（如联系方式已被占用）没有 `onError`，界面无提示（`useAdditionalAuthStep.ts:45-61`）。

### 4. 影响与风险

- **账号接管**：任何一次 access token 泄露（页面脚本注入、日志、共享设备）都能被升级为改联系方式 → 找回密码 → 永久占有账号；受害者原联系方式收不到任何提示，找回密码也找不回（联系方式已不是他的）。prod 当前真实数据未脱敏（2026-08-22 起），影响的是真实客户账号。
- **数据被静默覆盖**：F3 让“追加”变成“替换”，用户自己误操作或被利用都会把唯一的邮箱 / 手机号换掉，没有日志可查。
- **可用性**：F4、F5 在边界情况下返回 500；F7 可能把后端拒绝显示成成功。
- 是否已发生过：本次未查库。二.2 给出只读核查 SQL，在 uat / prod 跑过后把结果记入“三、处理记录”。

```sql

WITH runs AS (
    SELECT c.created_at,
           c.contact_type AS new_type,   c.contact AS new_contact,
           s.contact_type AS check_type, s.contact AS check_contact
    FROM additional_sign_in_data c
    JOIN confirmation_session cs ON cs.id = c.confirmation_session_id
                                AND cs.scenario = 'ADDITIONAL_SIGN_IN'
    JOIN additional_sign_in_data s ON s.main_confirmation_session_id = c.main_confirmation_session_id
    JOIN confirmation_session ss ON ss.id = s.confirmation_session_id
                                AND ss.scenario = 'ADDITIONAL_SIGN_IN_SECURITY_CHECK'
)
SELECT r.created_at::date            AS day,
       r.new_type, r.check_type,
       u.id                          AS holder_user_id,      -- 现在持有新联系方式的用户
       o.id                          AS check_owner_user_id  -- 非空 = 安全校验联系方式属于另一个用户，重点复核
FROM runs r
JOIN "user" u ON (r.new_type = 'EMAIL'        AND lower(u.email) = lower(r.new_contact))
             OR (r.new_type = 'PHONE_NUMBER' AND u.phone_number = r.new_contact)
LEFT JOIN "user" o ON o.id <> u.id
                  AND (lower(o.email) = lower(r.check_contact) OR o.phone_number = r.check_contact)
WHERE lower(coalesce(u.email, '')) <> lower(r.check_contact)
  AND coalesce(u.phone_number, '')  <> r.check_contact
ORDER BY 1;
```

判读：`new_type = check_type` 且 `check_owner_user_id` 为空 → 多半是用户自己把原联系方式“追加”覆盖了（F3）；`check_owner_user_id` 非空 → 疑似 F1，逐条人工复核（也可能是没走完的流程，新联系方式后来被别人注册了）。结果只记计数到“三、处理记录”。

注意：test / uat 的 `"user"` 已脱敏（邮箱前加 1、手机号后加 1），认证流水表没有脱敏（[001](001-用户与登录认证-手机号.md) 一.4 第 6 条、[011](011-测试库脱敏-认证流水与快照列残留真实联系方式.md)），2026-08-22 重建前的历史行在这两个库上对不上，会被 JOIN 丢掉。所以 uat 只用来确认 SQL 能跑，结论以 prod 为准。
