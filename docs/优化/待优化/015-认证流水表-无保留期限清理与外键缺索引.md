### 3. 代码现状

1. **只有增、查、改，没有删。** `ConfirmationCodeRepository`（`CSS_backend-main/core_app/src/app/internal/core/auth/repositories.py:11-86`）、`ConfirmationSessionRepository`（`:89-117`）、`ContactDataRepository`（`:150-235`）只有 `create_*` / `get_*` / `activate_all_recent_codes`，没有任何 delete；整个 `core/auth/` 里没有写 `deleted_at` 的地方（搜索无结果）。除 auth 模块外，没有其他代码碰这六张表。
2. **没有定时清理。** worker 的 `cron_jobs` 只有 8 个任务，没有一个与认证有关（`CSS_backend-main/core_app/src/app/internal/worker/app.py:127-140`）；prod 所在的 `origin/main` 同样没有（`origin/main:core_app/src/app/internal/worker/app.py:122-133`）。
3. **从用户方向的级联删除永远不会触发。** `system_sign_in_data.user_id`、`reset_password_data.user_id` 都是 `ON DELETE CASCADE`（`models.py:47`、`:61`），但用户只做软删除：sprint6 的 `soft_delete_user` 只写 `deleted_at`（`CSS_backend-main/core_app/src/app/internal/core/users/services.py:118-121`）；`origin/main` 的 `core/users`、`core/auth` 里根本没有删除用户的函数。（应用代码之外，只有一次性迁移硬删过用户：`dd574833f1bd` 删导入占位用户、`4b52dd3297e5` 的 downgrade 删 dev 管理员，都不是运行时路径。）所以用户「删除」后，他的登录 / 重置流水和联系方式都还在。
4. **每次口令校验通过都留一份口令哈希副本。** `pre_sign_in` 先算哈希、按 `(联系方式, password_hash)` 等值查用户，通过后把同一个哈希写进 `system_sign_in_data`（`services.py:318-345`）。这份副本只在第二步 `sign_in` 里用来判断「这期间口令有没有改过」（`services.py:374-381`）。改口令（`core/users/services.py:103-116`）和重置口令（`services.py:562-564`）只更新用户表，**旧副本不会随之删除**。放弃的注册在 `system_sign_up_data` 里同样留着联系方式加口令哈希，而这些人从来没有成为用户。
5. **全局固定盐放大了副本的风险。** 口令哈希是 `pbkdf2_hmac(算法, 口令, 全局 salt, 迭代次数)`（`CSS_backend-main/core_app/src/app/pkg/auth/password.py:11-17`），盐来自环境变量 `PASSWORD_SALT`，全站共用一个（`CSS_backend-main/core_app/src/config/password_settings.py:4-9`）。同一个口令在不同用户、不同时间算出的哈希完全相同，`pre_sign_in` 的等值查找也依赖这一点（`services.py:321-322`）。哈希方案本身不在本项范围（截至本文，台账里还没有专门的口令哈希条目；[013](013-认证验证码-已验证会话可重放与验码无次数限制.md) 管的是确认会话与验证码，不改哈希方案），本项只把它当成风险放大因素记录。
6. **验证会话不过期，也不会在用完后作废（附带发现，推断，未实测；已由 [013](013-认证验证码-已验证会话可重放与验码无次数限制.md) R1 跟踪，修复见其 A1 / A11）。** `check_activated_codes_exists` 只看「有没有被激活过的码」，不看时间（`repositories.py:79-86`）；`sign_in`（`services.py:347-401`）、`reset_password`（`:539-565`）、`_get_verified_confirmation_session`（`:567-590`）成功后都不删会话、不做标记。照代码推断：一个验证过的 SIGN_IN 会话 id，只要用户口令和联系方式没变，可以反复 `POST /auth/sign-in` 换新 token；一个验证过的 RESET_PASSWORD 会话 id 可以反复重置口令（重置时只核对用户 id + 联系方式，`services.py:554-560`）。除了用户自己改口令 / 联系方式，目前**唯一能限制这个时间窗口的就是删除旧行**，而现在从来不删。

### 4. 影响与风险

- **数据最小化**：验证码只有 30 分钟有效，流水在会话结束后没有任何业务用途，却一直保留：放弃注册的人的联系方式加口令哈希；每次成功登录的联系方式；重置口令和添加联系方式填过的号码 / 邮箱；被软删除的用户的全部流水。prod 是真实数据，这是这几张表最主要的问题。
- **口令哈希副本（prod）**：用户每成功登录一次，`system_sign_in_data` 就多一份当时口令的哈希；改口令以后，旧口令的哈希还在。加上全局固定盐，这张表一旦泄露，可以直接按哈希值分组，看出哪些用户用的是同一个口令，或者谁又改回了旧口令；离线猜口令时算一次就能同时比对所有用户。
- **会话重放窗口无上限**（一.3 第 6 条，推断；根治在 [013](013-认证验证码-已验证会话可重放与验码无次数限制.md) A1）：旧的已验证会话从不删除，所以理论上的重放窗口是「永久」。sprint6 上线后，会话 id 还会出现在操作日志里（013 A11）。本项的 C3 只是把窗口缩到保留期以内。
- **性能**：`confirmation_code` 按会话查全表扫描，成本随行数线性增长；test 目前约 8,500 行，影响还不明显。真正要紧的是**清理任务**：没有索引时，删除 N 个会话要扫 N 遍 `confirmation_code`，第一次清理（test 约 7,600 个过期会话）会很慢。所以必须**先建索引、再上清理**。
- **运维负担**：每次备份、脱敏、迁移都要处理这些没用的行（[001](001-用户与登录认证-手机号.md) 第 161 行）；001 的手机号拆分也要为四张流水表回填，其中有 2 行无效号码（001 第 84 行），而它们本可以直接被清掉。

### 2. 数据 / 迁移

**C1 补外键索引（单独一个迁移，只放这 4 条）。**

这几张表每次登录都会写入。按 [012](012-WebSocket鉴权-数据库会话泄漏卡死迁移.md) 二.3 B5，热表上的 DDL 单独成迁移。普通 `CREATE INDEX` 会拿 `ShareLock`，建索引期间挡住写入（也就是挡住登录），所以用 `CONCURRENTLY`。它不能在事务里执行，而本仓库的 `env.py` 是 `transaction_per_migration=True`（`CSS_backend-main/core_app/src/app/migrations/env.py:60-68`），所以要放进 `autocommit_block`。仓库里已有先例：`2026_10_17_1200-6949627542f7_sprint5_refund_adjustment_refunds_and_invoice_adjustments.py:30`。

```python
"""index the foreign keys of the auth flow tables

Revision ID: <new>
Revises: <写迁移时 sprint6 线的 head>
"""
from alembic import op

INDEXES = {
    'ix_system_confirmation_code_confirmation_session_id': ('system_confirmation_code', 'confirmation_session_id'),
    'ix_system_sign_in_data_user_id': ('system_sign_in_data', 'user_id'),
    'ix_reset_password_data_user_id': ('reset_password_data', 'user_id'),
    'ix_additional_sign_in_data_main_confirmation_session_id': ('additional_sign_in_data', 'main_confirmation_session_id'),
}


def upgrade() -> None:
    # CONCURRENTLY 不能在事务里跑；本迁移只放这 4 条（012 B5）
    with op.get_context().autocommit_block():
        op.execute("SET lock_timeout = '10s'")
        for name, (table, column) in INDEXES.items():
            op.execute(f'CREATE INDEX CONCURRENTLY IF NOT EXISTS "{name}" ON "{table}" ("{column}")')


def downgrade() -> None:
    with op.get_context().autocommit_block():
        for name in INDEXES:
            op.execute(f'DROP INDEX CONCURRENTLY IF EXISTS "{name}"')
```

- 索引名用 SQLAlchemy 默认的 `ix_<表>_<列>`，与模型上加 `index=True` 后的名字一致（`pkg/databases.py` 的 `Base` 没有设置命名约定，`CSS_backend-main/core_app/src/app/pkg/databases.py:9`）。模型同步修改：`models.py:47`、`:61`、`:68`（同时把 `Mapped[int]` 改成 `Mapped[uuid.UUID]`）、`:53-55`（加 `index=True`；`primary_key=True` 是否去掉需要先跑一遍测试确认）。
- **手写这个 revision，不要用 autogenerate**：`31731a571e02` 改名的两张 confirmation 表保留了旧索引名（`ix_confirmation_code_created_at`、`ix_confirmation_session_created_at`），autogenerate 会把它们当成「要删的旧索引 + 要建的新索引」（推断，未实测）。`system_sign_*` 的旧索引名已由 `049461d68471`（2026-11-18）改成新表名，不再有这个问题。
- 写死的是 sprint6 的表名 `system_confirmation_code`、`system_sign_in_data`，所以本迁移只能接在 `da8ba148ea59`、`3d9e6b1c7a52`、`31731a571e02` 之后，随 sprint6 或在 sprint6 之后上线（test 已于 2026-11-18 上 sprint6）。如果要在 sprint6 之前单独上 uat / prod，就得另写一版用旧表名 `confirmation_code` / `sign_in_data` 的迁移，两版不能都合进来。
- `CONCURRENTLY` 中途失败会留下 `INVALID` 索引，`IF NOT EXISTS` 不会重建它。处理方法：手工 `DROP INDEX CONCURRENTLY`，然后重跑（见 二.6 V1 的 `indisvalid` 检查）。`CONCURRENTLY` 还要等表上已有的写事务（以及持有旧快照的事务）结束；本迁移设了 `lock_timeout = '10s'`，等不到时会报错并留下 `INVALID` 索引，而不是一直等（推断，未实测）。如果 [012](012-WebSocket鉴权-数据库会话泄漏卡死迁移.md) 的泄漏会话还在，就可能撞上这种情况。建议在 012 的 B1–B3 上线后、低峰时执行，并用 `pg_stat_progress_create_index` 观察进度。
- 本迁移是 [013](013-认证验证码-已验证会话可重放与验码无次数限制.md) A10 与 [014](014-追加联系方式-安全校验会话未绑定用户.md) 共用的索引来源：013 写明不再单独建索引，014 写明不重复建 `main_confirmation_session_id` 的索引。若以后仍有别的迁移建同名索引，须同样带 `IF NOT EXISTS`。
- 数据量只有几千到几万行，建索引本身是秒级（推断，未实测）。

### 3. 后端改动

**C2 仓储：按时间分批删除会话。** 在 `ConfirmationSessionRepository`（`CSS_backend-main/core_app/src/app/internal/core/auth/repositories.py:89-117`）中增加：

```python
async def delete_sessions_created_before(self, cutoff: datetime, batch_size: int) -> int:
    """删除 cutoff 之前创建的一批会话；子表（验证码与四张流水）由 ON DELETE CASCADE 连带删除。"""
    doomed = (
        select(models.ConfirmationSession.id)
        .where(models.ConfirmationSession.created_at < cutoff)
        .order_by(models.ConfirmationSession.created_at)
        .limit(batch_size)
    )
    result = await self._session.execute(
        delete(models.ConfirmationSession).where(models.ConfirmationSession.id.in_(doomed))
    )
    await self._session.commit()
    return result.rowcount
```

- 只需要删 `confirmation_session`。5 张子表的外键都是 `ON DELETE CASCADE`，其中 `additional_sign_in_data` 的**两个**外键也都是（`b6b5aac6eccf...py:33-34`）。添加联系方式时 3 个会话在同一次请求里创建（`services.py:414-430`），按时间删除会一起删掉；就算只删到其中一个，流水行也会被级联删除。
- PG 的 `DELETE` 没有 `LIMIT`，所以用子查询取一批；每批单独提交，避免一个大事务长时间持锁。子查询走 `ix_confirmation_session_created_at`。
- 只删「创建时间早于保留期」的会话。验证码有效期 30 分钟，前端也不持久化会话 id（见 二.4），所以 7 天前的会话不可能还在流程里。
- [013](013-认证验证码-已验证会话可重放与验码无次数限制.md) A1 给 `confirmation_session` 加上 `expires_at` 以后，删除条件可以改成按 `expires_at` 判断（013 二.3 A10 的建议），语义更准确；在那之前按 `created_at`。

**C3 定时任务。**

   ```python
   PURGE_BATCH_SIZE = 1000

   async def purge_auth_flow_data(ctx: dict) -> None:
       """每日：删除超过保留期的验证会话，连带验证码与登录 / 注册 / 重置 / 追加流水。"""
       async with ctx['deps']() as deps:
           repository: ConfirmationSessionRepository = deps['confirmation_session_repository']
           cutoff = datetime.now(tz=timezone.utc) - timedelta(days=auth_settings.auth_flow_retention_days)
           total = 0
           while (deleted := await repository.delete_sessions_created_before(cutoff, PURGE_BATCH_SIZE)) > 0:
               total += deleted
               if deleted < PURGE_BATCH_SIZE:
                   break
               await asyncio.sleep(0.2)   # 批间让出，避免长时间占用 IO
           ctx['logger'].info('purge_auth_flow_data: deleted %d confirmation session(s) before %s', total, cutoff)
   ```

### 5. 环境与发布注意

- **prod 的时机**：建议随 sprint6 或在 sprint6 之后上。原因：sprint6 之前，`sign_in_data` 是 prod 上**唯一的登录痕迹**；sprint6 的操作日志会单独记录 LOGIN 事件（`action_log.py:73-74`），之后再删流水，就不会丢登录审计。如果需要更长的登录审计期，应该在操作日志那边定保留期，而不是保留流水表。是否需要先对 prod 历史流水做一次导出归档，需要业务方拍板。
