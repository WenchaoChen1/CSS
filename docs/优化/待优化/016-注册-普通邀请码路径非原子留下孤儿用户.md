## 一、现在是什么问题

### 1. 注册链路与事务边界（POST `/api/auth/sign-up`）

`sign_up` 位于 `CSS_backend-main/core_app/src/app/internal/core/auth/services.py:220-316`。所有仓储共用同一个请求级会话（`CSS_backend-main/core_app/src/app/internal/core/auth/transport/di.py:27-57`，`get_session` 见 `CSS_backend-main/core_app/src/app/pkg/databases.py:18-20`），所以"能不能一次提交"只取决于各步是否自己 `commit`。

| 步骤 | 代码 | 普通邀请码路径 | 手工 Client 路径 |
|------|------|----------------|------------------|
| 1 校验会话、验证码已激活 | `.../auth/services.py:223-238` | 只读 | 只读 |
| 2 预校验邀请码 | `.../auth/services.py:243-245` → `.../master_database/services.py:671-691` | 只读 | 只读 |
| 3 预留身份 | `.../auth/services.py:247-253` → `.../master_database/services.py:431-476` | **不加锁**，直接返回 `False`（`:442-456`） | 锁 Client / 订阅行 / 餐厅身份（`:441`、`:464`、`:468`） |
| 4 建用户 | `.../auth/services.py:266-276` → `CSS_backend-main/core_app/src/app/internal/core/users/repositories.py:16-38`、`:40-62` | **立即 commit**（`users/repositories.py:57-58`） | `commit=False` → flush |
| 5 写密保答案 | `.../auth/services.py:278-285` → `CSS_backend-main/core_app/src/app/internal/core/auth/repositories.py:129-144` | **再 commit**（`auth/repositories.py:141-142`） | flush |
| 6 激活订阅 | `.../auth/services.py:287-297` → `.../master_database/services.py:725-830` | 再查一遍、`SELECT … FOR UPDATE`（`:753`），写订阅 / 公司 / owner 账号 / 审计（`:777-817`），**第三次 commit**（`:819-820`），紧接着在函数里直接 `send_task`（`:824-828`，**无 try**） | flush；回到 auth 后**单次 commit**（`auth/services.py:298-299`） |
| 7 通知管理员 | — | 已在第 6 步里发了 | commit 之后 `try/except` + 日志（`auth/services.py:305-309`） |
| 8 发 token | `.../auth/services.py:311` → `CSS_backend-main/core_app/src/app/internal/core/auth/tokens/services.py:34-72`（Redis `set_user_session` 在 `:48`） | commit 之后 | commit 之后 |

- 代码自己承认这一点：`CSS_backend-main/core_app/src/app/internal/core/master_database/services.py:443-445` 注释写着普通路径 "whose User creation commits before activation"。
- 现有测试**把普通路径的非原子行为固化了**：`CSS_backend-main/core_app/src/app/internal/main_app/auth/tests/sign_up/test_manual_client_signup_atomic.py:18-64` 证明手工路径失败会回滚；同文件 `:71-140` 的 `(False, False)` 参数断言普通路径**不传** `commit` 参数、`session.commit` 未被调用（`:134-140`）。邀请码错误测试（`CSS_backend-main/core_app/src/app/internal/main_app/auth/tests/sign_up/test_sign_up_with_invitation_code__error.py:19-52` 等）只覆盖"预校验阶段就拒绝"，没有覆盖"建完用户之后才失败"。
- `activate_subscription_by_code` 唯一的调用方就是 `sign_up`（全仓 grep），所以它内部的 `commit` / `send_task` 分支只服务于普通注册路径。

### 2. 失败触发点（普通邀请码路径）

| 编号 | 触发 | 在哪一步失败 | 已提交 | 接口返回 | 结果 |
|------|------|--------------|--------|----------|------|
| T1 | 密保问题 id 不存在 | 第 5 步：`question_id` 外键（`CSS_backend-main/core_app/src/app/internal/core/auth/models.py:85-87`）在 `auth/repositories.py:142` commit 时报 `IntegrityError` | 用户行 | 500 | **孤儿**（无答案、无公司） |
| T2 | 同一问题 id 出现两次 | 第 5 步：主键 `(user_id, question_id)`（`auth/models.py:84-87`）冲突（报 `IntegrityError` 或 SQLAlchemy `FlushError`，推断，未实测） | 用户行 | 500 | **孤儿** |
| T3 | 邀请码在第 2 步与第 6 步之间被用掉 / 作废 / 过期：两人并发使用同一个普通邀请码（两边预校验都通过、都建了用户，后到的在第 6 步发现码已用：`:733-735`，或在 `:753` 的行锁上等前者提交后拿不到行）；管理员同时停用公司（未注册公司会作废有效码，`.../master_database/services.py:952-953`）或改码（`update_subscription`，`:1888` 起）；恰好跨过过期边界 | 第 6 步返回 `Result.fail`，auth 直接 `return`（`auth/services.py:294-297`） | 用户行 + 答案 | 400 `invitation_code_invalid_or_used` / `invitation_code_expired` | **孤儿** |
| T4 | Redis / arq 不可用 | 第 6 步 commit 之后的 `send_task`（`.../master_database/services.py:824-828` → `CSS_backend-main/core_app/src/app/internal/worker/services.py:19-22`，每次新建 arq 连接池） | 用户、答案、订阅、公司、owner 账号**全部** | 500，不发 token | 不是孤儿，但用户看到失败；重试注册只会得到 `invitation_code_invalid_or_used`；"公司已激活"管理员通知丢失。main 线上还会跳过 `init_onboarding`，留下"有公司、无 onboarding 行"的用户 |
| T5 | 第 4–6 步之间任何其他异常（连接中断、语句超时、部署重启杀进程） | 同 T1 | 已走完的步骤 | 500 | 与 T1 同类（推断，未实测） |

- T1 / T2 的入口：请求模型 `SignUpIn.questions` 只限 1–2 条，不去重（`CSS_backend-main/core_app/src/app/internal/main_app/auth/transport/requests.py:52-58`），服务层也不校验 id 是否存在（`auth/services.py:278` 的 TODO）。正常前端会把已选问题从下拉里过滤掉（`CSS_frontend-main/src/ui/pages/Registration/ui/RegistrationForm/ui/SecurityQuestionStep/ui/SecurityQuestionModal/useSecurityQuestionModal.ts:43-45`），所以 T1 / T2 主要来自直接调 API、问题表变动或前端缺陷（推断）。
- 500 的原因：主应用只注册了 `JsonHTTPException` 与 `RequestValidationError` 两个异常处理器（`CSS_backend-main/core_app/src/app/internal/main.py:51-54`，实现见 `CSS_backend-main/core_app/src/app/pkg/errors.py:134`、`:144`），其余异常由 `ServerErrorMiddleware` + `global_execution_handler` 统一返回纯文本 500（`main.py:61-64`、`CSS_backend-main/core_app/src/app/pkg/global_exception_handler.py:10-18`），所以 `IntegrityError` 一律变 500，响应体里也没有错误 `type`。

### 3. 孤儿用户的后果

- **联系方式被占**：重新注册时 `pre_sign_up` 先按联系方式查用户（`CSS_backend-main/core_app/src/app/internal/core/auth/services.py:89-93`），返回 400 `contact_already_use`。
- **sprint6 上登录不了**：`can_sign_in` 要求用户在 ACTIVE 公司有账号，或拥有一家 INVITED 公司（`CSS_backend-main/core_app/src/app/internal/core/onboardings/services.py:569-577`，查询见 `.../onboardings/repositories.py:22-51`）；孤儿两样都没有 → 输完密码就返回 `company_account_disabled`（`auth/services.py:327-330`）。
- **现网（main）上能登录但进去是空壳**：main 没有 `can_sign_in`，孤儿能拿到 token；但没有 `onboarding` 行，`onboarding_step` 为空（main:`.../onboardings/repositories.py:304-311`），所有 onboarding 接口经 `check_onboarding_is_available_to_user`（main:`.../onboardings/services.py:75-122`）返回 `onboarding_is_not_inited`，用户卡住（前端表现推断，未实测）。
- **用户无法自助恢复**：现网没有管理员删用户的入口（main 的 `main_app/admin/` 下没有 `users`），只能直接改库。sprint6 新增 All Users 软删（`CSS_backend-main/core_app/src/app/internal/main_app/admin/users/transport/handlers.py:98-104`），配合部分唯一索引理论上能释放联系方式（推断，未实测）。
- **前端放大**：
  - 注册提交用的 mutation 没关重试，走全局默认 `retry: 2`、间隔 200 ms（`CSS_frontend-main/src/app/providers/queryProvider.tsx:43-46`；`CSS_frontend-main/src/ui/pages/Registration/ui/RegistrationForm/ui/SecurityQuestionStep/useSecurityQuestionStep.ts:52-62` 未覆盖，也没有 `onError`）。同一页面对邀请码查询已经显式 `retry: false`（`CSS_frontend-main/src/ui/pages/Registration/ui/RegistrationForm/ui/RegistrationStep/useRegistrationStep.tsx:89`、`:239`），注册 POST 反而没有。
  - 失败时没有提示：全局拦截器只给 `/admin/` 接口弹 toast（`CSS_frontend-main/src/config/axios/interseptors.ts:65-77`、`:147-157`），`queryClientErrorHandler` 默认分支只 `console.error`（`CSS_frontend-main/src/app/utils/queryClientErrorHandler.ts:42-44`）。
  - 合起来：T1 一次点击 = 第一次 500 留下孤儿 → 自动重试两次都撞联系方式唯一索引再 500 → 页面无提示；T4 一次点击 = 第一次 500（实际已注册成功）→ 重试得到 400 `invitation_code_invalid_or_used`（推断，未实测）。

### 4. 同一接口的相关问题

**R1 SIGN_UP 会话用完不作废。** `get_confirmation_session` 只按 id + 场景查（`CSS_backend-main/core_app/src/app/internal/core/auth/repositories.py:105-117`），`check_activated_codes_exists` 不看时间（`:79-86`），`sign_up` 成功后也不改会话——一个 SIGN_UP 会话永久可用。这是 [013](013-认证验证码-已验证会话可重放与验码无次数限制.md) R1「已验证会话可重放」在注册场景的表现（013 认为注册重放会被邀请码一次性校验挡住、影响小）；下面只记注册特有的后果。

- 成功注册后，拿同一会话 + 另一个有效邀请码再调：前三步都通过，建用户撞联系方式唯一索引（`CSS_backend-main/core_app/src/app/internal/core/users/models.py:38-39`）→ `IntegrityError` → 500（普通路径在 `users/repositories.py:58` 的 commit 处，手工路径在 `:60` 的 flush 处）。不留数据，但是 500。
- sprint6 的唯一索引只管未删除用户：若第一个用户已被软删，旧会话（带旧口令 hash）可以不经重新验证再建一个同联系方式的新用户（推断，未实测）。main 上是全量 unique，仍是 500。
- 本地底稿 `deploy-env/test/backend.env:71` 为 `CONFIRMATION_CODE_VERIFICATION_ENABLED=false`（dev / uat / prod 底稿为 `true`：`deploy-env/dev/backend.env:38`、`deploy-env/uat/backend.env:71`、`deploy-env/prod/backend.env:63`；运行时以 SSM 为准，本次未核对）。关闭时 `sign_up` 跳过"验证码已激活"检查（`auth/services.py:229-237`），test 上只要拿到会话 id 就能注册。

**R2 `sign_up` 不复查联系方式。** 唯一检查在 `pre_sign_up`（`auth/services.py:90`）。从 `pre_sign_up` 到 `sign_up` 之间，同一联系方式可能被另一笔注册或"添加第二联系方式"入口（[001](001-用户与登录认证-手机号.md) 一.3 的 W2）占走，此时返回 500 而不是 400 `contact_already_use`。

**R3 接口文档与代码不符。** `CSS_backend-main/core_app/src/app/internal/main_app/auth/transport/docs.py:72-80` 写着 `invitation_code` "currently disabled… optional and ignored"，`:7-8` 的注释也说邀请码错误已不会出现；实际 `requests.py:59` 必填（`min_length=1`），`auth/services.py:243-297` 会校验并激活。错误列表只写了 `invalid_confirmation_session`，缺 `invitation_code_invalid_or_used`、`invitation_code_expired`（`CSS_backend-main/core_app/src/app/internal/core/master_database/errors.py:8-9`）。main:`docs.py:71` 同样过时。

### 5. 影响与风险

- 单次触发概率不高：T1 / T2 需要非常规请求；T3 的窗口在同一请求内（毫秒到秒级）；T4 / T5 依赖基础设施故障。但一旦触发，**用户自己无法恢复**（注册提示联系方式已占用，登录进不去或进去是空壳），只能找客服改库。
- 普通邀请码是 Admin 给公司发码的主路径，受影响面是全部新入驻公司的 owner。
- prod 是未脱敏的真实用户数据，清理孤儿要动生产库。
- T4 会丢"公司已激活"的管理员通知；日志 / Sentry 里只有一条 Redis 连接异常导致的 500，看不出注册其实已经成功（推断）。
- 未消费的 SIGN_UP 会话让认证流水继续累积（参见 [001](001-用户与登录认证-手机号.md) 一.4 第 7 条"流水表无限增长"、[015](015-认证流水表-无保留期限清理与外键缺索引.md)、[数据库表结构优化分析报告 P3-4](../../数据库表结构优化分析报告-2026-11-05.md)）。

### 2. 后端改动

**D1 一个事务。** 去掉 `auth/services.py:274-303` 里所有 `if manual_client_invitation:` 的分支，两条路径同一写法；`:254-260` 的"必须共用一个会话"检查改为无条件执行。结构示意：

```python
session = self._users_repository._session        # 全部仓储共用这一个会话（auth/transport/di.py:36-39）
try:
    if not await self._confirmation_session_repository.consume(..., commit=False):     # D5：013 A1 的原子消费，不单独提交
        await session.rollback()
        return Result.fail(error=AuthErrorFactory.get_invalid_confirmation_session_error())
    ...                                          # D2：校验密保问题；validate_invitation_code；reserve（D4）
    user = await self._users_repository.create_user(**user_fields, commit=False)        # D6 见下
    await self._security_question_repository.create_answers_to_security_questions(..., commit=False)
    activation = await self._master_database_service.activate_subscription_by_code(
        invitation_code=..., new_user_id=user.id, identity_reserved=True,                # 不再有 commit 参数
    )
    if activation.is_fail():
        await session.rollback()
        return Result.fail(error=activation.error)
    await session.commit()                       # 唯一一次提交（会话消费、用户、答案、激活一起生效）
except Exception:
    await session.rollback()
    raise
# 以下都在 commit 之后，失败不影响已完成的注册
try:
    await self._master_database_service.notify_activation_by_code(sign_up_dto.invitation_code)   # D3
except Exception:
    logger.exception('Activation notification failed after sign-up commit')
tokens = await self._tokens_service.issue_tokens(user_id=user.id, device_id=uuid4())
```
