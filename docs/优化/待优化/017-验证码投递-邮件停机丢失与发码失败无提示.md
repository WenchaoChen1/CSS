### 2. 代码现状（问题清单）

**L1（主因）email_sender 每次启动都是一个新消费组、从“最新”开始读，停机期间写入的邮件永远不会被消费。**

```python
# CSS_backend-main/email_sender/app/main.py
117            group_id=self._generate_group_id(),  #'email_send_consumer_group',
119            auto_offset_reset='latest',
...
343    def _generate_group_id(self, base='email_send_consumer_group') -> str:
344        timestamp = datetime.utcnow().strftime('%Y%m%d_%H%M%S')
345        return f"{base}_{timestamp}"
```

- 新组没有已提交位点，`latest` 让它从拿到分区那一刻的末尾开始读。旧容器停下到新容器拿到分区之间写进 `email_send` 的消息，留在 topic 里，但不会再有任何组读它们——**消息没丢在 Kafka，是被跳过了**。
- 来历：老团队 2025-05-30（任务 CSS 3194，提交 `c1003be0`、`8c4e774c`）把原来的“固定组 `email_send_consumer_group` + `earliest`”改成了“按时间戳生成组名 + `latest`”，提交信息没写原因；推测是为了避免重启时重放积压（推断）。正确的解法是固定组 + 逐条提交位点（已处理的不会重放），而不是每次换组。
- 触发场景：部署时重建 email_sender 容器（`CSS_backend-main/deploy/bin/deploy.sh:163-165` 的 `pull` + `up -d`，镜像有变化时重建）；`restart: always` 的崩溃重启（如启动时 Kafka 未就绪，`wait_for_kafka` 重试 15 次后抛错退出，`main.py:469-509`；SMTP 变量缺失会崩溃循环，见 `css-terraform/环境实况/aws服务-服务技术文档.md:53`）；EC2 重启；手动 `restart`。每重启一次就有一个空窗。
- 影响不止验证码：走 `email_send` 的所有邮件（邀请、发票、通知）都会在空窗期丢失。
- 对照：仓库里已有正确写法——定时任务管道用固定组名 + `earliest` + 处理完手动提交（`CSS_backend-main/core_app/src/app/internal/scheduler/bus.py:117-131`，组名定义 `CSS_backend-main/core_app/src/config/scheduler_settings.py:35-41`）；sms_sender 也是固定组（`sms_sender/app/main.py:34-36`）。
- 本地开发文档把它当已知行为记过一笔（“消费组 latest 不重放历史”，`CSS_backend-main/deploy/windows/README.md:82-83`），但 AWS 环境上没有任何补偿。

**L2 投递失败没人知道：DLQ 只写不读，也没有告警。**

- 按 `app_settings.sender_retries_count` 共尝试 3 次（默认值，`email_sender/config/app_settings.py:12`；循环见 `email_sender/app/main.py:274-293`）仍失败、或处理时抛异常。注意环境底稿里的 `EMAIL_SENDER_RETRIES_COUNT=3` 其实读不到——该配置类没有前缀，字段对应的环境变量是 `SENDER_RETRIES_COUNT`，只是默认值碰巧也是 3。失败后，消息写进 `email_send_dlq`（`main.py:184-190`、`:209-228`）。全后端 grep `_dlq`，除 email_sender 自己和定时任务管道自己的 `scheduler_task_dlq` 外**没有任何消费者**；`css-terraform` 里没有任何日志指标过滤器（grep `metric_filter` 无命中），现有告警只覆盖机器 / RDS / ALB 指标；email_sender 和 sms_sender 都没接 Sentry（grep `sentry` 无命中，主应用是接了的，`CSS_backend-main/core_app/src/app/pkg/sentry.py:11-39`）。
- 写 DLQ 本身也不可靠：`_send_to_dlq` 用的是 `send`（不等确认），`finally` 里紧接着提交原消息位点（`main.py:218-228`）。只有同步异常会进 `_log_failed_message`，异步写失败无人知晓，原位点却已经提交。
- 反序列化失败的消息连 DLQ 都不进：`value_deserializer` 失败时返回 `None`（`main.py:295-341`），主循环把它当“空消息”跳过并提交（`main.py:160-164`）。
- 处理时长可能超过 `max_poll_interval_ms`：它被设成 `producer_timeout_seconds * 1000` = 30 秒（`main.py:122`），而 SMTP 客户端没用配置里的 `smtp_timeout = 10`（`email_sender/config/app_settings.py:24` 定义了，`email_sender/app/smtp/smtp.py:16` 的 `SMTP(**self._settings.model_dump())` 只传了 `smtp_settings` 的 hostname / port / username / password 四个字段），走的是 aiosmtplib（`email_sender/poetry.lock` 锁定 2.0.2）的默认超时（库常量 `DEFAULT_TIMEOUT = 60` 秒，未在本机核对源码）。一条 SMTP 不通的消息，3 次尝试加退避很容易超过 30 秒，消费者可能被踢出组再加入；新组在提交第一条位点之前被踢出，重新加入时又会落到 `latest`，同样会跳过消息（推断，未实测）。

**L3 发码接口：邮件投递失败 = 500 且验证码已落库；短信投递失败感知不到。**

- 邮件：`verify_contact` 先 `create_confirmation_code`（内部 commit），再 `await send_email_method(...)`（`services.py:157-165`）。Kafka 写入失败或超时，`produce_request_to_send_email` 重新抛出（`emails/producers.py:62-85`），接口 500。验证码行已经提交：用户 10 秒内重试会得到 `TIME_INTERVAL…` 错误；库里多了一条永远收不到的码。
- 短信：`PhoneProducer` 调的是 `send`（`phone/producers.py:10-11`）。aiokafka 的 `send` 只等主题元数据、把消息放进缓冲就返回一个 future（aiokafka 0.10.0 源码 `producer/producer.py:419-421`、`:440`；`send_and_wait` 才 `await` 这个 future，`:470-477`）。broker 拒收或缓冲发不出去时，异常只落在这个没人 await 的 future 上，接口照样 200（推断，未实测）。实际发送由生产者的后台任务异步完成，最晚在依赖清理 `producer.stop()` 时冲刷缓冲（`pkg/brokers.py:43-47`）；`stop()` 只等缓冲清空，不会把某条消息的投递失败抛给调用方（aiokafka 0.10.0 `producer/producer.py:328-344`）。
- Kafka 整个不可达时，`get_auth_service` 的 `Depends(get_producer)`（`core/auth/transport/di.py:29`）在建生产者时就失败，所有认证接口 500——已作为持久会话 G10 / AC-10 登记，由 B-11 处理。
- 发码接口的 `match` 没有兜底分支（`handlers.py:119-127`）。现在 `verify_contact` 只会返回那两种错误，所以没出事；**以后给它加任何新错误类型而不改这里，接口会返回 200**（E3 必须同时改）。

- 登录是“密码 + 验证码”两步，能读日志的人在 30 分钟有效期内就拿到了第二因素。（test / uat 的 kafka-ui 本来就被当作“2FA 看码工具”，`infra.yml:95`，那是有意为之且有登录认证；日志属于无意泄露，范围更大。）

**L6 邮件消息被序列化了两次，消费者靠 `ast.literal_eval` 还原（脆弱）。**

- 生产者先把 DTO 转成 bytes（`emails/producers.py:25`），再交给生产者的 `value_serializer=universal_serializer`（`pkg/brokers.py:35`）。`universal_serializer` 没有 bytes 分支，落到兜底的 `str(data).encode('utf-8')`（`pkg/brokers.py:24-25`），Kafka 里存的是 `b'{"subject": ...}'` 这样的 Python 字面量字符串。
- email_sender 识别 `b'` 前缀后用 `ast.literal_eval` 还原（`email_sender/app/main.py:310-318`）。本机复现：含中文与引号的样例往返结果一致，但消息体积变成原来的 1.44 倍（非 ASCII 字节被转成 `\xNN`）；生产者的大小检查（`emails/producers.py:26-35`）量的是包装前的大小。
- 两头任何一边改动（换 JSON 库、改 serializer）都会让**所有**邮件反序列化失败，而失败的消息按 L2 会被静默跳过。

**L7 邮件里的有效期分钟数在 TTL ≥ 1 小时时会算错。**

`confirmation_code_ttl=auth_settings.confirmation_code_ttl_timedelta.seconds // 60 % 60`（`CSS_backend-main/core_app/src/app/internal/core/emails/services.py:40`），模板写的是 “within the next {{ confirmation_code_ttl }} minutes”（`CSS_backend-main/core_app/src/templates/sign-in-verification.html:581`，另 4 个验证码模板同用此变量）。默认 TTL 1800 秒（`config/auth_settings.py:21`），四个环境底稿都没覆盖 `CONFIRMATION_CODE_TTL`，所以现在显示 30，是对的。本机计算：60 分钟 → 0、90 分钟 → 30、1440 分钟 → 0。潜在缺陷，改 TTL 时才会暴露。

**L8 测试替身缺 `send_and_wait`，邮件路径的用例应当已经失败，但 CI 不跑测试。**

- `CSS_backend-main/core_app/src/app/internal/conftest.py:143-145` 用 `MockedProducer` 顶替 `AIOKafkaProducer`，而 `MockedProducer` 只有 `start / stop / send`（`CSS_backend-main/core_app/src/app/internal/tools.py:11-22`）。自 `c20b2c8d` 起邮件生产者调 `send_and_wait`，凡走邮件发送的用例——例如 `CSS_backend-main/core_app/src/app/internal/main_app/auth/tests/verify_contact/test_verify_contact_success.py:11-29`，用的是邮箱联系人（fixture 见 `main_app/auth/tests/conftest.py:21-30`）——会因 `AttributeError` 失败（推断，未运行）。
- CI 没有单测 job（`CSS_backend-main/.github/workflows/cicd.yml:79` 是 TODO），所以没人发现。

**L9 sms_sender：位点“提交”是空操作，失败只记日志，异常会让进程退出。**

- `await self._consumer.committed(partition=partition)`（`sms_sender/app/main.py:61-63`）是**读取**已提交位点，不是提交。实际提交靠 aiokafka 默认的 `enable_auto_commit=True`、每 5 秒自动提交（aiokafka 0.10.0 `consumer/consumer.py:243-244`），不管成没成功都会提交。
- 3 次尝试之间没有等待（`main.py:49-59`），全部失败只 `logger.error`，没有 DLQ、没有告警。
- 只捕获 `HTTPStatusError`（`main.py:75-76`）；网络错误（`httpx.ConnectError` 等）或消息缺字段会冲出 `consume()`，进程退出后由 `restart: always` 拉起；那条消息会不会重放，取决于自动提交是否已经提交了它（推断，未实测）。
- 固定组 + `earliest` 让 sms_sender 停机后会补发积压——但积压里超过 30 分钟的验证码已经失效，补发只会让用户困惑并产生 Twilio 费用。

### 3. 影响与风险

- **用户**：email_sender 每重启一次（部署、崩溃、重启机器），空窗期内触发的登录 / 注册 / 找回密码 / 添加联系方式验证码邮件全部丢失；页面显示“已发送”，邮件等不来，只能 10 秒后重发。登录页即使后端 500 也没有任何提示，重发失败也照样倒计时。邀请、发票等业务邮件同样会丢，且没人知道丢了哪些。
- **运维**：SMTP 账号失效、Twilio 拒收、DLQ 堆积都没有告警，只能等用户反馈后翻 CloudWatch。
- **安全 / 隐私**：验证码与完整手机号 / 邮箱进了 CloudWatch（prod 保留 30 天），削弱了登录第二因素。
- **test 上看不到问题**：test 关闭了验证码校验（`deploy-env/test/backend.env:71` `CONFIRMATION_CODE_VERIFICATION_ENABLED=false`，校验逻辑见 `services.py:189-195`），任意码都能过，投递问题被掩盖；uat / prod 是 `true`（`deploy-env/uat/backend.env:71`、`deploy-env/prod/backend.env:63`）。
- **范围**：test / uat / prod 代码相同，全部受影响。

### 3. 后端改动

**E1 email_sender 固定消费组。**

- 删除 `_generate_group_id`（`main.py:343-345`）；`main()` 里授权失败提示的组名（`main.py:539-549`）本来就写的是固定组名，保持一致。
- 处理成功后已有逐条提交（`main.py:175-178`），组固定后重启会从上次提交处继续，空窗期的消息不再被跳过，已处理的也不会重放。
- `_processed_offsets`（`main.py:106`、`:166-169`、`:177`）是进程内去重集合，无上限增长；固定组 + 逐条提交后可删除。
- **首次上线的坑**：新组没有位点，`earliest` 会从 topic 保留期内最早的消息读起，把过去几天（infra 未覆盖 `log.retention`，按 Kafka 默认 7 天，推断）的邮件**全部重发给真实用户**。所以部署前必须先把新组的位点设到末尾（见 二.5）。

**E2 投递失败可见。**

- `_send_to_dlq` 改用 `send_and_wait`，确认写入后再提交原位点；写 DLQ 失败时不提交、打 CRITICAL，让这条消息在重启后重新处理。
- 去掉 `value_deserializer`，在主循环里手动反序列化，失败的消息带原始字节进 DLQ，不再按“空消息”跳过（`main.py:160-164`）。
- 告警（`css-terraform/modules/monitoring/main.tf`，经各环境 `<env>/monitoring` stack 生效）：对日志组 `/css/<env>`（模块里的 `aws_cloudwatch_log_group`，`:243-245`）加 `aws_cloudwatch_log_metric_filter`，匹配 email_sender 的 `"Sent to DLQ"`、`"DLQ unavailable"`、`"Critical error at"` 和 sms_sender 新增的固定文案 `"SMS permanently failed"`（E7），5 分钟内 ≥ 1 次即告警，发往模块已有的 SNS 主题 `css-${var.env}-alarms`（`:110-111`）。
- Sentry：两个发送器加 `sentry-sdk`，用与主应用相同的 `SENTRY_DSN`（两个容器与主应用共用同一份 env 文件，`deploy/compose/backend.yml:145-152` 的 `<<: *env-file`），`send_default_pii=False`。
- DLQ **不做自动重放**：验证码 30 分钟就过期，重放没有意义；发票等业务邮件是否重放，由人看到告警后决定（可补一个只读查看 / 手动重放脚本，非必须）。

**E3 发码失败时撤销验证码并返回明确错误。**

```python
# CSS_backend-main/core_app/src/app/internal/core/auth/services.py  verify_contact()

    match contact_data.contact_type:

                message=AuthTexts.get_phone_verification_sms_text(confirmation_code.code),
                to=contact_data.contact,
            )
except Exception:  # KafkaError / asyncio.TimeoutError / ValueError（消息超大）
    logger.exception(
        'Confirmation code delivery failed',
        extra={'confirmation_session_id': str(confirmation_session_id),
               'contact_type': contact_data.contact_type.value},     # 不记联系方式和码

    await self._confirmation_code_repository.delete_confirmation_code(id=confirmation_code.id)  # 新增
```

- 新错误类型 `CONFIRMATION_CODE_DELIVERY_FAILED = 'confirmation_code_delivery_failed'`（`core/auth/errors.py`）；`handlers.py:120-125` 增加对应分支，`general_error_type=BasicErrorTypes.SERVICE_UNAVAILABLE`（503，已有，`CSS_backend-main/core_app/src/app/pkg/errors.py:26`）。**必须同时改 handler**，否则按 L3 最后一条会返回 200。顺手给 `match` 加兜底分支（未知错误返回 500），以后不再静默。
- 用“先提交、失败再删除”的补偿写法，**不要**把写验证码和 Kafka 发送放进同一个未提交事务：`send_and_wait` 最长等 30 秒（`config/kafka_settings.py:13`），期间挂着事务就是 [012](012-WebSocket鉴权-数据库会话泄漏卡死迁移.md) 那类 `idle in transaction`。
- `PhoneProducer.produce_request_to_send_sms_code` 改成和邮件一样 `await asyncio.wait_for(self._producer.send_and_wait(...), timeout=...)`。发码是交互接口，超时建议单独配成 10 秒左右，不沿用 30 秒。
- 与持久会话 B-11 同批：B-11 把 `get_producer` 改为懒获取后，Kafka 不可达时只有发码接口返回 503，登录其他步骤不受影响（AC-10）。

**E6 过期验证码不再投递。**

- 兼容性：email_sender 的 `EmailDTO`（`email_sender/app/main.py:91-95`）是 pydantic 默认忽略多余字段，sms_sender 按 key 取值，老消费者收到带新字段的消息不受影响，两边部署顺序无要求。

**E7 小修。**

1. `universal_serializer` 加 bytes 直通：`elif isinstance(data, (bytes, bytearray)): return bytes(data)`（`pkg/brokers.py:15-29`）。全后端 Kafka 发送点只有 `emails/producers.py:56`、`phone/producers.py:11`、`internal/scheduler/bus.py:114` 三处，只有第一处发 bytes，后两处发 dict，不受影响。email_sender 对普通 JSON 本来就走 `else` 分支（`main.py:317-318`），兼容；`b'` 分支保留到 topic 里旧格式消息过期后再删。
2. TTL 分钟数：`int(auth_settings.confirmation_code_ttl_timedelta.total_seconds() // 60)`（`core/emails/services.py:40`）。
3. sms_sender：`enable_auto_commit=False`，处理完（成功，或确认永久失败）后 `await self._consumer.commit()`，删除 `committed()` 空操作（`main.py:61-63`）；重试之间加退避；捕获 `httpx.HTTPError` 及其他异常，单条失败不让进程退出；永久失败记固定文案 `SMS permanently failed`（供 E2 告警匹配），可选写 `sms_send_dlq`。
4. email_sender：`SMTP(...)` 传入 `timeout=app_settings.smtp_timeout`（`smtp/smtp.py:16`）；`max_poll_interval_ms` 提到 300 秒，并保证“重试次数 × SMTP 超时 + 退避”小于它；重试次数的环境变量名对齐（给 `sender_retries_count` 加 `EMAIL_` 前缀或 alias，让底稿里的 `EMAIL_SENDER_RETRIES_COUNT` 生效）。

新增用例：

**E9（可选）发件箱。**

验证码和待发消息在同一事务里写库，worker 定时（或经现有 scheduler 管道）把待发消息推到 Kafka（或直接调 SMTP / Twilio），成功后标记已发，失败按 `next_attempt_at` 退避重试，超过 `expires_at` 放弃。好处：请求路径完全不依赖 Kafka（AC-10 的彻底解法），每条消息“至少投递一次”且有落库记录可查。代价：多一张表和一个中继任务，验证码到达会多出中继轮询间隔的延迟。E1–E3 上线后若仍有丢失再评估。

### 6. 验收标准

1. **停机不丢（E1，uat）**：停掉 email_sender 容器 → 用 `swp*` 账号在登录页触发验证码（接口 200）→ 2 分钟后启动 email_sender → 1 分钟内收到邮件。再重启一次 email_sender，不重复发送。`kafka-consumer-groups.sh --describe --group email_send_consumer_group` 显示 `LAG = 0`。
2. **首次上线不重放（E1）**：上线后 email_sender 日志里处理的第一个 offset ≥ 上线前记下的 `email_send` 末尾 offset；`swp*` 邮箱没有收到旧邮件。

   - `grep -n "_generate_group_id\|auto_offset_reset='latest'" CSS_backend-main/email_sender/app/main.py` 无命中；

5. **发码失败有明确响应（E3，本地 dev 或 uat）**：Kafka 写入失败时，`POST /api/auth/verify/contact` 对邮箱会话、手机号会话都返回 **503**，`type = confirmation_code_delivery_failed`；该会话在 `confirmation_code` 表没有新行；恢复后立即重发返回 200。（B-11 上线前，Kafka 完全不可达会在依赖注入阶段直接 500；这一条可用“Kafka 可连、写 topic 失败”的场景验收——如本地临时把 `KAFKA_EMAIL_SEND_TOPIC` / `KAFKA_SMS_SEND_TOPIC` 指向非法 topic 名，或用单测 mock 生产者抛错（前者能否稳定触发写入失败为推断，未实测）——或在 B-11 后验收。）
