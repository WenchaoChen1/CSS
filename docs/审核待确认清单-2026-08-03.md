## P0 必修 —— 已实测确认，当前就是坏的

### 1. ⛔ 开发者 SSH 钥全部失效（发出去的 dev1l/dev2f 现在登不上）**[实测]**

- **现象**：`ssh -i dev-keys/nonprod-dev1l.pem ec2-user@3.225.148.166` → `Permission denied (publickey)`。
- **根因**：`06-服务器密钥与访问/grant-dev-ssh.sh:40` 生成的到期时间是 `20260830T0808Z`，**中间的 `T` 是非法的**——OpenSSH（堡垒机为 8.7p1）只认 `YYYYMMDD[Z]` 或 `YYYYMMDDHHMM[SS][Z]`，解析失败即整条 key 被拒。堡垒机 authorized_keys 已实查确认写的就是这个格式。
- **影响**：这个脚本从写出来到现在**发的每一把开发者钥都是废的**（包括我 07-31 发的两把，台账里记的"到期 2026-08-30"实际是"从未生效"）。
- **建议修**：`date -u -d "+${DAYS} days" +%Y%m%dT%H%M` → 去掉 `T`（`+%Y%m%d%H%M`）；改完对 dev1l/dev2f 各重跑一次脚本刷新条目，然后我实测登录验证。

### 2. ⛔ `restore-dump-via-gw.sh` 对 test/uat 已不可用 **[确定]**

- `05-数据库运维/restore-dump-via-gw.sh:20` 仍写 `GW_NAME=css-non-prod-gw`，堡垒机 07-30 已改名 `css-non-prod-bastion`；第 40 行按 Name 标签查实例会查不到，直接报"网关机未运行"退出。同文件 prod 分支已是新名，两分支自相矛盾。

### 3. ⛔ test/uat 的 CloudWatch Dashboard 是瞎的 **[确定]**

### 4. ⛔ 两个数据脚本"失败了也报成功" **[确定]**

- `anonymize-db.sh:125`：SSM 返回 Failed/TimedOut 时只打印 stderr，接着照样打印"脱敏完成"并 exit 0 → **脱敏失败但你以为成功，库里真实 PII 还在**。
- `restore-dump-via-gw.sh:90-100`：同样，SSM Failed 也 exit 0；且 72-73 行两条 `pg_restore ... || true` 把硬失败（连不上、版本不兼容、恢复中断）一起吞了。
- **建议修**：两处都加 `[ "$ST" = "Success" ] || { echo 失败...; exit 1; }`，成功横幅只在成功分支打印；pg_restore 改为捕获退出码后判断。
