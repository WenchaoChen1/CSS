# 数据库表结构优化分析报告（2026-11-05）

2026-11-05 · 本地底稿

**依据**：本机 `postgres-latest-5432` 里的 `css-test-main`（test RDS 整库恢复，今天 09:10 UTC 在本机跑完 sprint5 迁移，alembic 头 `b76f719b477b`）+ 后端分支 `sprint/sprint5_merge_member`（`73875be4`）的代码。所有行数、冲突数都是这个库的实测值；uat / prod 的数据来源不同（preprod），上线前要用附录的 SQL 在 uat 上再跑一遍。代码路径以 `CSS_backend-main/core_app/src/app/internal/` 为根。

## 结论摘要

sprint5 已经完成了 account / company 归一的**第一步**：四张成员表的数据进了 `account`，门店 / 餐厅 / 制造分部的行按原 id 复制进了 `company`，10 张旧表改名为 `deprecated_*`。但第二步还没做：**代码新建、修改、删除门店 / 餐厅 / 分部时仍然只写 `deprecated_*` 表，`company` 里的副本从迁移那一刻起就不再更新**；业务表的外键和 ORM 也仍然挂在 deprecated 实体表上。所以这三张"废弃表"实际上还是主表，而 company 里的副本会越来越旧。

需要优先处理的（P0）：

| 编号 | 问题 | 规模 / 后果 |
| --- | --- | --- |
| P0-1 | 新建门店 / 餐厅 / 分部不写 company，修改、删除也不同步到 company | 新实体建不了聊天、改不了门店设置（报错），新账号在 `/me` 里看不到 |
| P0-2 | 27 张业务表的 33 个外键仍指向三张 deprecated 实体表；ORM 的 `Store` / `Restaurant` / `ManufacturerSubdivision` 也仍映射到它们 | 33 个外键 |
| P0-3 | 门店 FoodFitness 的 id 与其所属公司 Super Vendor 的 id 相同，复制进 company 时换了新 id；61 行业务数据还指向旧 id，外键一改指 company 就会错挂到父公司 | 61 行 |
| P0-4 | `account.company_id` 没有外键 | 1,627 行，当前 0 孤儿 |
| P0-5 | 迁移清空了公司之间原有的父子关系，旧值只在 `company_back` 里；`parent_company_id` 同时被两套功能用作不同含义 | 8 条，其中 1 对互为父子 |

**P0-1 是这个分支合入 test 之前必须解决的**：本地库今天刚迁移，副本还没开始漂移（实测 0 条），但只要有人在这个分支上建 / 改门店就会出问题。其余问题按 P1（account 模型）→ P2（company 统一、同构表合并、废弃列清理）→ P3（权限表、索引、数据卫生）排列，第九节给出建议的执行顺序。

## 二、P0：数据正确性与阻塞项

### P0-1 company 副本不再同步

**写入路径**（全部只写 deprecated 表，没有双写，也没有数据库触发器）：

| 实体 | 创建 | 修改 / 删除 |

| 餐厅 | `core/restaurants/repositories.py:406-446`（入口：onboarding `core/onboardings/services.py:582-619`、设置页 `core/settings/services.py:549-570`）；下单时建未注册餐厅 `core/clients/repositories.py:547-560` | `update_restaurant` `:324-379`；状态变更 `core/clients/repositories.py:562-590`；合并 `:1020-1028`；硬删 `:381-388`、`:32-36` |
| 分部 | `core/manufacturer_subdivisions/repositories.py:26-48`（入口：`core/onboardings/services.py:663-705`、`:811-821`） | 只软删 deprecated 表 `:98-108` |

**后果**：

报错类：
1. **聊天**：`chat_party.company_id` 已是 NOT NULL 且外键到 company。新门店 / 餐厅发起普通聊天返回 404（`core/chats/services.py:166-172`），装箱单聊天外键冲突返回 500（`core/chats/repositories.py:592-597`），餐厅合并时改 chat party 也会外键冲突、整个合并回滚（`core/clients/repositories.py:1063-1067`）。
2. **门店设置**：门店的 terms / remit-to、打包审批、打包员 / 司机开关存在 `company_info`，代码拿 store_id 当 company_id upsert（`core/stores/repositories.py:571-578`，经 `core/companies/repositories.py:380-389`）。新门店在 company 里没有行，外键冲突报错。另外建门店时 terms / remit-to 只写进 deprecated_store 的列（`core/stores/repositories.py:266-269`），读取却走 company_info，所以创建时填的值读不出来。

静默出错类：
3. **账号切换**：`Account.business_type` 靠 company 行判断（`core/accounts/models.py:22-38`），新实体的账号得到 None，`/me` 账号列表会把它过滤掉（`main_app/me/services.py:124`）。只有这一个账号的用户直接得到 404。
4. **聊天候选**：新门店 / 餐厅永远不出现在新建聊天的候选列表里（`core/chats/repositories.py:284-333`）。
5. **报表**：发票短信 / 邮件按 `order.store_id` 查 company 查不到（`core/reports/services.py:96-98`、`:130-131`）；报表 SQL 用 inner join company，新实体的数据从报表里消失。
6. **旧值**：改名、改地址、餐厅状态、合并、删除都不进 company。聊天里显示的 party 名称、聊天搜索、`/me` 的公司名、报表名称都会读到旧值；被硬删的门店，company 副本和账号还留着，`/me` 里仍能看到。
7. **Master DB 后台**：`transfer_stores` / `transfer_restaurants` 只改 deprecated 表（`core/master_database/repositories.py:472-488`）；`bulk_detach_subsidiaries_no_commit` 会把门店 / 餐厅副本的 parent 清空，这些行随即被当成"公司"（`:395-420`）；导入器按名称 UPDATE company 不过滤 parent，可能改到同名副本（`core/master_database/import_/importer.py:470-491`）。

**建议**（二选一，需要你决定）：
- 方案 A（先止血）：给门店 / 餐厅 / 分部的创建、修改、删除加上对 company（和 company_info）的同步写，再补一个迁移把迁移之后的差异补齐。这样 sprint5 可以先合入，P0-2 以后再做。
- 方案 B（一步到位）：直接做 P0-2，让 company 成为唯一写入目标，deprecated 表只读。改动面大，但不会出现两份数据。

### P0-4 `account.company_id` 没有外键

迁移 `8c6f5e1a90b1` 的注释写明当时 company_id 可能指向四张不同的表，所以没建外键。现在四类实体都已在 company 里，实测 1,627 行全部能对上 company。也正因为没有外键，P0-1 里新实体的账号能插进去，只是在 `/me` 里看不到。

**建议**：先解决 P0-1，再补 `account.company_id → company.id` 外键。ON DELETE 建议用 RESTRICT（公司是软删除，不应级联删账号）。另有 2 个未删除的 account 挂在已软删除的公司下，补约束前先决定这两条怎么处理。

### P0-5 旧公司层级被清空，`parent_company_id` 有两种含义

迁移 `d8aaccb9a900` 把所有原有公司的 `parent_company_id` 清空了，从此这一列表示"门店 / 餐厅 / 分部属于哪家公司"。原来的 8 条公司→子公司关系只剩在 `company_back` 里，其中 Alpha Supplies Co 与 Beta Foods Ltd **互为父子**（现有的 CHECK 只能拦住指向自己，拦不住环）。这 8 条看上去都是测试数据，但方案里的需求 R5（父公司管辖子公司）要用到这层关系。

代码里的冲突：Master DB 后台的子公司功能仍用 `parent_company_id` 表示"子公司"（`core/master_database/services.py:839-867`、`repositories.py:681-704`）。admin 给一家真实公司设了上级，它就会被 `business_type_case` 当成门店 / 餐厅，并被权限中间件拒绝（`main_app/middlewares/permissions/middlewares.py:111-114`）。admin 的公司列表 `get_companies_list`（`core/master_database/services.py:113-169`）也不过滤 parent，门店 / 餐厅副本会混进去。

**建议**：先确认 R5 的公司层级还要不要用 `parent_company_id` 表达。如果要，就必须有一个字段区分"子公司"和"门店 / 餐厅"（见 P2-1 的 `kind`），并加防环校验（触发器或写入时递归检查）。在这之前不要删 `company_back`。

## 三、P1：account 模型

### P1-1 公司账号被复制到每个下级实体

迁移 `9d18fcda7ab1` 把每个公司级 account 复制到该公司下的每家门店 / 餐厅 / 分部，本库今天因此新增了 668 个 account。结果：

- 一个用户最多有 26 个 account（4 个用户各 26 个）；523 个用户只有 1 个。
- 姓名、职位、安全码在副本之间各存一份。已经有 34 个用户的多个 account 姓名不一致、39 个用户安全码不一致。
- 以后公司新开一家门店、公司账号被停用或删除时，副本不会自动跟着变，要靠代码逐条同步。

这和方案第 7.1 节"档案不再重复"的目标相反。

**建议**（需要你拍板）：
- 方案 A：保留副本，但把 `first_name`、`last_name`、`security_code` 移到 user 级（或单独一张 `user_profile`），account 只留"在哪个实体、什么角色、是否启用"；并写清楚新开门店、停用、删除时的同步规则。
- 方案 B：不复制，公司级 account 通过数据范围（方案里的"本公司含下级"档位）直接管辖下级实体，登录后的 account 清单里再按需展开下级实体。

### P1-2 `account_role_m2m` 实际是一对一

1,627 个 account 每个恰好 1 个角色。如果近期不打算支持一个 account 多个角色，可以改成 `account.role_id` 一列，少一次 JOIN、少一张表；如果要支持，就保留现状。

### P1-3 软删除与唯一约束

`account` 的唯一约束 `(user_id, company_id)` 不区分是否已删除。现在有 41 个已删除的 account：同一用户被重新邀请进同一实体时，要么代码恢复旧行，要么插入失败。`chat_member (chat_id, account_id)`、`user.email`、`user.phone_number` 也是这样。建议统一规则：要么改成 `WHERE deleted_at IS NULL` 的部分唯一索引，要么明确"重新邀请 = 恢复旧行"。

### P1-4 操作记录还用 user_id + role_id

多 account 之后，"哪个用户"已经不足以说明"以哪个身份、在哪个实体做的"。以下表还没有 account_id：

| 表 | 行数 | 现有列 |
| --- | --- | --- |
| `order_history` | 19,110 | `user_id`、`role_id` |
| `order_packing_slip_history` | 2,349 | `user_id`、`role_id` |
| `order_invoice_history` | 837 | `user_id`、`role_id` |
| `user_action_log` | 746 | `user_id`、`team_member_id`（外键指向 user，列名有误导） |
| `store_product_stock_movement` | 2,213 | `user_id` |
| `price_tier_version`、`order_payment`、`quotation`、`quotation_comment` 等 | — | `created_by` / `changed_by_user_id` |

**建议**：先给三张订单历史表和 `user_action_log` 加 `account_id`（可空，新数据写入），`role_id` 可以从 account 推出，保留作为当时角色的快照。

### P1-5 `chat_member.user_id` 与 `account_id` 重复

两列都是 NOT NULL，`user_id` 可以由 `account.user_id` 得出，实测 2,103 行一致。保留的话要保证一起写；不需要按 user 直接查的话可以删掉 `user_id`。

### P1-6 四张 onboarding 成员表

`onboarding_company_member`（133）、`onboarding_restaurant_member`（25）、`onboarding_store_member`（5）、`onboarding_manufacturer_subdivision_member`（0）是旧成员表模式的翻版，**仍在使用**：onboarding 过程中按"实体 id + role_id"写入（`core/onboardings/repositories.py:43-202`），`finish_onboarding` 时才转成 account 并删除这些行（`core/onboardings/services.py:777-835`、`:887-1131`）。后三张还外键到 deprecated 实体表。另有一个小问题：分部软删除后，对应的 onboarding 行会残留。

**建议**：合成一张 `onboarding_account`，用 `company_id`（实体的 company id）+ `role_id`，和 P0-2 一起做。

### P1-7 多个顶层公司 account 时查询报错

`get_company_for_user` 按 account 联表、只取顶层公司，结尾用 `scalar_one_or_none()`（`core/companies/repositories.py:266-286`）。本库有 12 个用户在两家以上顶层公司有 account（9 人 2 家、2 人 3 家、1 人 6 家），他们调到这里会抛 `MultipleResultsFound`。目前的调用方是 `get_categories_for_user_company_types`（`core/companies/services.py:176`）。这是"一人一公司"旧假设的残留，应改成按当前 account 取公司。

### P1-8 公司 owner 没有 account（不是这次迁移造成的）

`company.user_id` 记的是公司的 owner，也就是在 onboarding 里创建这家公司的用户。本地库和 test RDS（迁移前状态，alembic `731ddff784cc`）实测结果一致：563 家有 owner 的未删除公司里，293 家的 owner 是本公司成员；另有 262 家的 owner 不是任何实体的成员，迁移后也就一个 account 都没有。

这 262 家**全部是母公司**：迁移前 260 家没有父 id，另外 2 家是 `company_back` 里那 8 条子公司关系中的子公司（迁移清空父 id 后，262 家都没有父 id）。按 owner 的 onboarding 进度分：

| 情况 | CLIENT | VENDOR | MANUFACTURER | 合计 | 近 180 天登录过 |
| --- | --- | --- | --- | --- | --- |
| onboarding 没走完（停在 company / places / company_account / company_team 这几步） | 155 | 72 | 4 | 231 | 24 |
| onboarding 已完成 | 26 | 5 | 0 | 31 | 0 |

- **231 家是注册后没走完 onboarding。** account（迁移前是成员行）要等 `finish_onboarding` 才创建（`core/onboardings/services.py:777-835`），所以没有 account 是正常状态。这些用户登录后，`/me` 返回 onboarding 进度，`/me/accounts` 返回 404；迁移前同样是按成员表找、找不到也返回 404，行为没有变。可以考虑定期清理长期没走完的注册，最早的停在 2024 年。
- **31 家走完了 onboarding，但 owner 不是成员。** 都是 2024-02 到 2025-11 的老数据，近 180 天没人登录过，其中 23 家公司里有其他成员。从数据看不出 owner 为什么不在成员里（可能被移出过团队，或早期流程没给 owner 建成员）。要不要给这 31 个 owner 补 account，按业务定。

另外，onboarding 建公司仍以 `company.user_id` 为冲突键 upsert（`core/companies/repositories.py:290-300`），靠的是"一个用户最多拥有一家公司"的部分唯一索引。这不影响一人多 account，但一个用户没法自助注册第二家公司；需要支持时再改。

## 四、代码侧核对小结

第二、三节已经引用了具体位置，这里只汇总判断规则和可以放心删的部分。

**怎么判断一行 company 是什么**，代码里有三套不一致的规则：

| 位置 | 规则 | 问题 |
| --- | --- | --- |
| `business_type_case`（`core/accounts/models.py:22-38`），用于 `Account.business_type` | `parent_company_id` 为空 → 公司；否则看 `company_type` 的 category：CLIENT → 餐厅、VENDOR → 门店、MANUFACTURER → 分部 | 依赖 `parent_company_id` 的单一含义，和 P0-5 冲突 |
| 权限中间件、vendor / manufacturer 的 DI、`COMPANY_IDS` 等（`main_app/middlewares/permissions/middlewares.py:111-114`、`core/companies/repositories.py:37`） | 只认 `parent_company_id IS NULL` 的为公司 | 同上 |
| 聊天（`core/companies/domains.py:136-138`、`core/chats/models.py:32-55`） | `company_type` 在 `STORE_TYPE_CODES` / `RESTAURANT_TYPE_CODES` 里就当门店 / 餐厅，**不看 parent** | 顶层供应商公司和它的门店 code 相同，分不开 |

另外 `find_active_by_id_and_type`、`list_active_by_ids`（`core/companies/repositories.py:174-202`）只按 `company.type` 过滤，门店副本也能通过 manufacturer_relationships、terms、profile 等服务的 VENDOR 校验。这三套规则是 P2-1 建议加 `kind` 列的直接原因。

**已确认业务代码不再读写、可以放心清理的**：
- 四张 deprecated 成员表和 `deprecated_company_company_type` 的 ORM 类（`CompanyMember`、`StoreMember`、`RestaurantMember`、`ManufacturerSubdivisionMember`、`CompanyCompanyTypeModel`）。业务代码里同名的 `*Member` 是由 account 生成的领域对象（`core/accounts/members.py:29-44`）。
- 第七节列出的所有 `deprecated_*` 列：ORM 没映射，也没有原生 SQL 引用。vendor 接口里的 `packer_store_member_id` 等只是 API 字段名，实际映射到 `*_account_id` 列。
- `company_back`：只在迁移里出现。

**待验证**：一些老迁移直接 import 了现行 ORM 类（例如 `migrations/versions/2024_06_12_0919-d2cfa5cf0e97`、`2026_05_18_1827-5d68ace011f1`），而测试库是从零跑 alembic 建的（`conftest.py:70-94`）。这些类现在指向 `deprecated_*` 或 `company_type_role`，在老 revision 下这些表还不存在，从零迁移可能会失败。这一条没有实际跑过，建议在 CI 里跑一次空库 `alembic upgrade head` 确认。

## 五、P2：company 表本身

### P2-1 `type` 与 `company_type` 两套类型并存

`company.type`（枚举 CLIENT / VENDOR / MANUFACTURER / ADMIN）和 `company.company_type`（varchar，存 `company_type.code`）同时存在，没有约束保证二者一致。实测 16 行不一致：

| company.type | company_type 所属 category | 行数 | 原因 |
| --- | --- | --- | --- |
| VENDOR | MANUFACTURER（E&S_Manufacturer / Food_Manufacturer） | 12 | 门店复制时一律 VENDOR，company_type 继承父公司 |
| CLIENT | VENDOR（Food_Vendor） | 1 | 餐厅挂在供应商公司下 |
| VENDOR | CLIENT（Restaurant） | 1 | 门店挂在餐厅公司下 |
| MANUFACTURER | VENDOR（Broadliner_Dealer） | 1 | 分部挂在经销商公司下 |
| ADMIN | 无（`dev_admin` 不在 `company_type` 表里） | 1 | 迁移 `4b52dd3297e5` 只加了角色没加类型行 |

此外：
- `company_type` 列没有外键到 `company_type.code`。
- **没有字段说明一行是"公司"还是"门店 / 餐厅 / 分部"**，代码只能靠 `parent_company_id` 是否为空或 `company_type` 推断，三套规则互不一致（见第四节）。10 家不属于任何公司的餐厅 `parent_company_id` 为空，看上去就和顶层 CLIENT 公司一样。
- `company_status` 用的枚举类型名还是 `restaurant_status`；`merge_company_id` 没有外键（目前 4 行，都能对上）。

**建议**：加一列 `kind`（company / store / restaurant / subdivision / admin），作为判断实体形态的唯一依据，三套规则统一改成看它；`type` 如果保留，加 CHECK 或由 `company_type` 推出；给 `company_type` 补外键并补上 `dev_admin` 的类型行。

### P2-2 `company` 与 `company_info` 字段重复

`date_founded`、`subscriber_status`、`number_of_licences` 两张表都有。441 行两边不同：company 是 `NONE / 0`，company_info 是 NULL（门店 / 餐厅 / 分部的副本）。devAdmin 公司没有 company_info 行。建议这三列只留一处，并定一条规则：每个 company 必须有一行 company_info，或者代码允许它不存在。

`company_info` 里 opening_time、打包 / 司机开关、terms、remit_to 等列实际只对门店有值（171 行门店全部有 opening_time，其余 995 行只有 229 行有）。而 `allow_backorder`、opening_time 等在 deprecated_store 里也还有一份，`update_store_toggles` 一半写 deprecated_store、一半写 company_info（`core/stores/repositories.py:758-778`）。P0-2 做完后应以 company_info 为唯一来源，并在模型上注明哪些列只对哪种 kind 有意义。

## 八、P3：权限表、索引与数据卫生

### P3-1 权限矩阵全量展开

`company_role_permission` 有 96,108 行、20 MB，是全库最大的表：390 家公司每家平均 246 行（最多 644 行），即"公司 × 角色 × 权限 × 实体"全部展开存储。另有 1 家门店也有 384 行。新加一个角色或权限就要给每家公司补行。

**建议**：默认矩阵挂在 `company_type_role` 上，`company_role_permission` 只存公司对默认值的改动；改造前至少给 `role_id`、`permission_id`、`entity_id` 补索引（现在删一个角色会全表扫描）。

### P3-2 权限相关表缺唯一约束

- `permission.type` 没有唯一约束（6 行：view / create / edit / delete / category / write_off）。
- `company_type_role` 没有唯一约束，`(type, code, belongs_to_company)` 理论上可以重复；`type` 也没有外键到 `company_type.code`。
- 枚举 `permissiontype`、`type` 没有任何列使用；`businesstype` 只有 `deprecated_role` 在用，可以随旧表一起删。

## 附录：复查 SQL

在 uat 或 prod 上执行迁移前，用这几条确认本报告的数字。

```sql
-- A1 门店 / 餐厅 / 分部 id 冲突：deprecated 表的 id 在 company 里对应的不是它自己的副本
SELECT 'store', s.id FROM deprecated_store s JOIN company c ON c.id = s.id
 WHERE c.parent_company_id IS DISTINCT FROM s.company_id
UNION ALL
SELECT 'restaurant', r.id FROM deprecated_restaurant r JOIN company c ON c.id = r.id
 WHERE c.parent_company_id IS DISTINCT FROM r.company_id
UNION ALL
SELECT 'subdivision', m.id FROM deprecated_manufacturer_subdivision m JOIN company c ON c.id = m.id
 WHERE c.parent_company_id IS DISTINCT FROM m.manufacturer_company_id;

-- A2 仍指向 deprecated 表的外键
SELECT conrelid::regclass, confrelid::regclass, conname
  FROM pg_constraint
 WHERE contype = 'f' AND confrelid::regclass::text LIKE 'deprecated%'
   AND conrelid::regclass::text NOT LIKE 'deprecated%';

-- A3 account 孤儿（补外键前必须为 0）
SELECT count(*) FROM account a WHERE NOT EXISTS (SELECT 1 FROM company c WHERE c.id = a.company_id);

-- A4 owner 没有任何 account 的未删除公司
SELECT c.type, count(*) FROM company c
 WHERE c.user_id IS NOT NULL AND c.deleted_at IS NULL
   AND NOT EXISTS (SELECT 1 FROM account a WHERE a.user_id = c.user_id)
 GROUP BY 1;

-- A5 type 与 company_type 不一致
SELECT c.type, ct.category, count(*) FROM company c
  LEFT JOIN company_type ct ON ct.code = c.company_type
 WHERE c.type::text <> coalesce(ct.category::text, '?')
 GROUP BY 1, 2;

-- A6 同一用户多个 account 档案不一致
SELECT count(*) FILTER (WHERE nf > 1) AS names_differ, count(*) FILTER (WHERE ns > 1) AS seccode_differ
  FROM (SELECT user_id,
               count(DISTINCT coalesce(first_name, '') || '|' || coalesce(last_name, '')) AS nf,
               count(DISTINCT coalesce(security_code, '')) AS ns
          FROM account WHERE deleted_at IS NULL GROUP BY user_id HAVING count(*) > 1) x;

-- A7 company 副本与 deprecated 表的漂移（P0-1 修好之前定期看）
SELECT 'store' AS kind, count(*) FROM deprecated_store s
  LEFT JOIN company c ON c.id = s.id
 WHERE c.id IS NULL OR s.name IS DISTINCT FROM c.name OR s.deleted_at IS DISTINCT FROM c.deleted_at
UNION ALL
SELECT 'restaurant', count(*) FROM deprecated_restaurant r
  LEFT JOIN company c ON c.id = r.id
 WHERE c.id IS NULL OR r.name IS DISTINCT FROM c.name OR r.deleted_at IS DISTINCT FROM c.deleted_at
    OR r.status::text IS DISTINCT FROM c.company_status::text;
```
