## 二、PASSWORD_SALT 专项（重要：与预期相反）

### 实测事实

| 环境 | PASSWORD_SALT（打码） | 相互关系 |
|---|---|---|
| 新 test | `f09d****`（=你给定的值） | 与新 uat 相同 ✓ |
| 新 uat | `f09d****` | 同上 |
| 新 prod | 尚无配置（SSM 为占位符） | — |
| 老 dev | `sDad****` | 与老 stage 相同 |
| 老 stage | `sDad****` | 同上 |
| 老 preprod | `s73u****` | **独立一组** |

- **没有任何老环境的 salt 等于 `f09d****`**；该值在整个 `备份/` 目录全文检索零出现——它来自更早的原团队 GitLab CI/.env 时代（7 月初处理老 test 机数据时采用），不是现存三个老环境的运行时值。
- 老环境自身分两组：dev=stage 一组、preprod 独立。

### 为什么新环境现在【不能】改成老环境的 salt

salt 必须匹配的是**库里 password_hash 是用什么 salt 算出来的**，而不是"对应老环境 env 写了什么"：

- test 库数据 = preprod 备份 → **2026-08-03 脱敏时用 `f09d****` 重算了全部 188 个账号的哈希**（口令统一 `Test1234!`）；
- uat 库 = test 副本（同一批哈希）。
- 因此新 test/uat 的 `f09d****` 与库内数据**自洽**，现在改成 `sDad****`（对齐老环境）会让所有账号立刻登不进，还得重跑 `anonymize-db.sh`。

### 什么时候才需要对齐老环境的 salt（决策表）

| 场景 | salt 应取值 |
|---|---|
| 非生产导入老数据 → **必脱敏**（铁律） | 无需对齐——脱敏用当前 salt 重算哈希，现状即正确 |
| **prod 上线直接导 preprod 真实数据（不脱敏）** | **prod 的 salt 必须 = 老 preprod 的 `s73u****`**（否则全体真实用户登录挂）——⭐ 制作 prod 底稿时的第一关键项 |

## 四、prod 底稿制作 checklist（基线 = 老 preprod，116 键）

prod 的 SSM 参数当前仍是占位壳，制作底稿时按本表逐项决策：

1. ⭐ **`PASSWORD_SALT` = 老 preprod 的 `s73u****`**（prod 直接承接 preprod 真实数据、不脱敏——salt 不对全体用户登录挂）；`PASSWORD_HASH_ALGORITHM`/`ITERATIONS` 同样照抄 preprod。

3. `API_KEY`/`JWT_SECRET`/`SPRING_SECURITY_USER_PASSWORD` → 重新生成（环境隔离）。
4. SMTP 五键 → 照抄老 preprod（沿用口径）。
5. `OPENAI_API_KEY`/`GEMINI_API_KEY` → 自建新 key（08-03 拍板；老 key 已撤销不可用）。
6. Twilio → prod 要发真短信：用自建 Twilio 真凭证（非生产的占位策略不适用）。
7. `EDEN_API_TOKEN` → prod 专属 token；`VITE_GOOGLE_MAPS_API_KEY` → 自建 key。
