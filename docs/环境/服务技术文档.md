## 1. 总体形态：一台应用机上的三个 compose 栈

每个环境（test/uat/prod）在一台 EC2 上跑三个**独立 compose 项目**，通过外部共享网络 `css-<env>-net` 互通，可**独立部署**：

```
frontend 栈 css-<env>-frontend          backend 栈 css-<env>-backend               infra 栈 css-<env>-infra
┌─────────────────────────┐   /api /ws  ┌──────────────────────────────────┐      ┌──────────────────┐
│ frontend                │────────────▶│ nginx :80（宿主 ${PORT:-8080}）    │      │ redis 7.2        │
│ (nginx+SPA静态, 宿主:80) │ /notifications│  ├─ app（FastAPI 主 API, gunicorn│─────▶│ rabbitmq 3       │
└─────────────────────────┘             │  │   --preload, 复用镜像×4）       │      │ kafka 3.7(KRaft) │
                                        │  ├─ messenger-app（/ws 聊天）      │      │ kafka-ui(tools)  │
                                        │  └─ notifications-app :8002       │      │ ocr-redis        │
                                        │ worker（arq 任务+cron, Redis）     │      └──────────────────┘
                                        │ sms_sender / email_sender（Kafka） │      RDS（栈外，AWS 托管）
                                        │ ai_assistant（Node, :2025）        │      css-<env>-main / css-<env>-ocr
                                        │ ocr-migrator→ocr-api :8088→worker │
                                        └──────────────────────────────────┘
```

**入口链路（2026-07-31 现状）**：
`用户 → ALB css-<env>（每环境一个，:80）→ 前端容器 :80 → 同源反代 /api·/ws·/notifications → 后端 nginx`。
✅ 堡垒机 `css-non-prod-bastion`（原 `css-non-prod-gw`，2026-07-30 改名）的 nginx 反代早已退役，
它**只剩堡垒 SSH + NAT 出网**两件事；共享 ALB `css-nonprod-alb` 与"按 Host 头分流 uat"的旧设计已作废。
kafka-ui（无认证且能读到 2FA 验证码 topic）**只走开发入口 ALB** `css-non-prod-entry`
（test `:8085` / uat `:8086`，仅白名单 IP `221.214.0.190/32` + `134.195.101.194/32`）；
业务 ALB 上的 8085 监听器已全部撤除。

### 3.2 对象存储（S3）

**一环境一个桶，桶与桶之间完全不可见**。后端从 `S3_STORAGE_BUCKET_NAME` 读桶名（运行时变量，改桶名不用重建镜像）。

| 桶 | 用途 | 访问主体 |
|----|------|----------|
| `css-test-582797602427` ✅ | test 的发票/目录/图片 | IAM 用户 `css-app-test` |
| `css-uat-582797602427` ✅ | uat 同上（空） | `css-app-uat` |
| `css-prod-582797602427` ✅ | prod 同上（空，等上线） | `css-app-prod` |
| **`css-dev-582797602427`** ✅ | **本地开发直传真实 S3**（2026-07-29 新增） | `css-app-dev`（**唯一已生成 key** 的一个，写在 `deploy-env/dev/backend.env`） |
| `css-dbsync-582797602427` | 运维：数据库 dump 中转（`05-数据库运维/restore-dump-via-gw.sh`），标签 `Environment=css-shared` | 堡垒机实例角色 `css-gw-non-prod`（只读） |

**为什么桶名都带账号 ID 后缀**：S3 桶名是**全球唯一命名空间**，跨账号跨区域共用。
纯名 `css-test` / `css-prod` 早被别的 AWS 账号占了（`css-test` 实际在 ap-northeast-1、属于别人）。
只有 `css-uat` 当时侥幸能建，但"三个环境两种写法"比"都带后缀"更容易出错，所以 uat 也重建成带后缀的名字。
⚠️ 判断桶归属**只能用 `list-buckets`**：`head-bucket` 对**别人的公开桶**也返回成功，用它判断会误以为"我们已有"，
后续所有 `put-*` 全部 AccessDenied。

**为什么用 IAM 用户而不是实例角色**：后端代码要求**显式 AK/SK 环境变量**，读不了实例角色的临时凭证。
折中办法是每个桶配一个专属用户，权限只覆盖本桶：

| 层级 | 授予的动作 |
|------|-----------|
| 桶级（`arn:aws:s3:::css-<env>-<账号>`） | `ListBucket`、`GetBucketLocation`、`ListBucketMultipartUploads` |
| 对象级（`.../*`） | `PutObject`、`GetObject`、`DeleteObject`、`AbortMultipartUpload`、`ListMultipartUploadParts` |

脚本 `07-应用s3密钥/issue-app-s3-key.sh <env> [--new-key]`。
✅ **隔离已实测**：用 dev 的 key 对 dev 桶上传/列举/下载/删除全通过，访问 test 桶与 prod 桶均被拒。
test/uat/prod 三个用户的策略也已挂上，但**刻意不生成 key**——闲置的长期凭证本身就是风险，要用时再发。

每个桶统一配置（现由 css-terraform 各环境 `s3` stack 管理）：SSE-S3 默认加密 + 版本控制 + 生命周期
（未完成分段上传 7 天、历史版本 30 天）+ 双标签 + 最小 CORS。
⚠️ 两笔临时债：① test/uat/prod 三桶**开了对象公有读**（桶策略型 GetObject，2026-07-30 决策，
代码接入 presigned URL 后置回 false 回收）；② CORS 现为 `AllowedOrigins: ["*"]`（方便联调），**上生产前必须收成真实域名**。

> 已退役：旧桶 `css-test-storage-582797602427`（2026-07-29）。它的 102 个对象早已 `s3 sync` 进新桶，
> 退役前又做了逐对象内容指纹比对确认无遗漏才删除。

### 5.1 告警清单与为什么选它们

| 告警 | 触发条件 | 为什么盯这个 |
|------|---------|-------------|
| `ec2-cpu-high` | CPU 连续 15 分钟 > 80% | 死循环、负载过大 |
| `ec2-status-check` | 状态检查失败 2 个周期 | 实例或底层宿主机故障；**缺数据也算告警**——机器没了指标就断了，"没数据"本身就是坏消息 |
| `ec2-cpu-credit-low` | CPU 积分 < 20（仅 t 系列） | 突发型实例积分耗尽会被限速到基线，症状是"莫名其妙全站变慢"，没这条根本猜不到 |
| `rds-cpu-high` | 数据库 CPU > 80% 持续 15 分钟 | 慢查询、缺索引 |
| **`rds-memory-low`** | 可用内存 < 100 MB | ⭐ **本实例最紧的资源**：t4g.micro 实测只剩约 146 MB，再低就开始换页、查询雪崩。这条实际上是"升配倒计时" |
| `rds-storage-low` | 剩余存储 < 2 GB | 写满会让数据库直接进入 **storage-full 只读**状态，业务全线写失败 |
| `rds-connections-high` | 连接数 > 80 | t4g.micro 连接上限约 100，打满后新连接全被拒（表现和"数据库挂了"一样） |
| **`alb-no-healthy-target`** | 健康目标数 < 1 持续 3 分钟 | ⭐ **最有价值的一条**：它比 5xx 更早、更确定地说明"服务已经不可用"。5xx 需要有人来访问才会产生，健康检查是 ALB 主动打的——半夜没人访问时服务挂了，只有这条能发现 |
| `alb-5xx` | 5 分钟内后端 5xx > 10 次 | 应用报错（有人在用且报错） |
| `alb-latency-high` | 后端响应 P95 > 3 秒 | 性能劣化，早于"彻底挂掉" |

> 挑选原则：**每条告警都要能对应一个明确的处置动作**。只报"有点异常"而无人知道该干什么的指标不配告警，
> 那种放 Dashboard 就够了——告警疲劳比没有告警更糟。

### 5.2 ⚠️ EC2 的内存和磁盘为什么不在里面

因为**它们不是 AWS 的基础指标**。CloudWatch 的 EC2 指标是从**宿主机侧（hypervisor）**采集的：
CPU、网络、磁盘 IO 这些宿主机看得见；而"客户机内部还剩多少内存、根分区用了百分之几"，
宿主机根本看不到——那是操作系统内部的事。

要监控就必须在机器**里面**装 CloudWatch Agent 主动上报（⏳ 暂未开）：
自定义指标 $0.30/个/月，两个指标约 +$0.6/月/机，届时配套加
`ec2-mem-high`（>85%）与 `ec2-disk-high`（>85%）两条告警。生产建议开，非生产暂不开。

⚠️ 磁盘这块非生产尤其要留神：容器日志走 json-file 落本地盘（见下一节），**磁盘写满是真实风险**，
现在只能靠人上机 `df -h` 看。

## 6. 日志

### 6.1 现状：日志只在机器本地

所有服务跑在 Docker 里，compose 用默认的 `json-file` 驱动，日志落在应用机本地磁盘
（`/var/lib/docker/containers/<id>/*-json.log`），`infra.yml` 里配了 `max-size: 50m` / `max-file: 3` 轮转。

**这带来三个后果**：

| 后果 | 说明 |
|------|------|
| ① 机器一挂日志就没了 | 恰恰是最需要日志的时候（实例故障、被重建）日志跟着消失 |
| ② 查日志必须上机 | 得走 SSM/堡垒机 `docker logs`，非生产还好，生产等于把排障权限和登录权限绑死 |
| ③ 交叉排查靠手拼 | 一个请求横跨 nginx → app → worker → ocr 四个容器，只能各看各的、人工对时间线 |

轮转配置本身是**必须保留**的——没有它日志会把根盘写满，那是真正的生产事故（见 §5.2）。

### 6.2 目标方案（⏳ 已出方案，按要求暂不执行）

一句话：**主用 Docker 的 `awslogs` 驱动把 stdout 直送 CloudWatch Logs，生产额外加 CloudWatch Agent 收系统日志。**

| 要点 | 取值 |
|------|------|
| 为什么选 awslogs 驱动 | 改动最小（只动 compose 的 `x-logging` 锚点）、无额外常驻进程；代价是 `docker logs` 失效，必须配 `mode: non-blocking` 防止网络抖动阻塞容器 |
| 日志组划分 | 按服务分 9 组：`/css/<env>/backend/{app,nginx,worker,messenger,notifications,senders,ocr}`、`/css/<env>/frontend`、`/css/<env>/system`（仅 prod） |
| 保留期 | test **7 天** / uat **14 天** / prod **30 天**（审计相关 90 天）——⚠️ 日志组**默认永不过期**，不显式设保留期费用会一直累积，这是 Logs 最常见的踩坑 |
| 成本 | test ≈ $0.5、uat ≈ $0.5、prod ≈ $5.3，合计 **≈ $6.3/月**（摄入 $0.50/GB 为主） |
| 落地耗时 | 5 步、约 30 分钟；回滚就是把 `driver` 改回 `json-file` 重新部署 |

📖 日志组（`/css/test`、`/css/uat`）已由 css-terraform 的 monitoring stack 纳管；
监控/日志组件说明见 `css-terraform/使用说明/10-监控与账单.md`。原详细方案文档（14-cloudwatch）
已随脚本目录迁移退役，落地时以上表要点 + compose 的 `x-logging` 锚点改 `awslogs` 驱动为准。

## 7. 高可用与扩容

### 7.1 现状：单节点运行，多 AZ 就绪

| 层 | 现状 | 跨几个 AZ |
|----|------|-----------|
| VPC 子网（两套 VPC 同构） | 公有 ×2 + 私有 ×2，分列 us-east-1a / us-east-1b | **2** |
| ALB `css-test` / `css-uat` | 各绑两个公有子网 | **2** |
| RDS 子网组 | 覆盖两个私有子网 | **2** |
| 应用机 | test 在 **1a**、uat 在 **1b** | **各 1 台**（当前 1 个节点即可） |
| RDS 实例 | 非生产**单 AZ**（省钱）；生产规划 **Multi-AZ** | — |

**网络铺满、机器按需**：子网、路由表这些结构性资源不收费，建的时候就按最终形态铺好；
ALB 和 RDS 子网组本来也**强制要求至少 2 个 AZ** 才能创建。真正花钱的是 EC2 实例，
所以实例只放当前需要的数量，不为"以后可能扩容"提前买机器。

### 7.2 将来加节点：两步，不动网络

1. 在**另一个 AZ 的私有子网**建第二台机器（css-terraform 的 `<env>/ec2` stack 加一个模块实例）；
2. 目标组注册随 ec2 stack 的 TG attachment 一起声明，加进**同一个目标组**。

之后 ALB 自动在两个 AZ 之间负载均衡、自动剔除不健康节点。
**VPC / 子网 / 路由表 / 安全组 / NAT / RDS 全部不用改**——这是当初把子网铺成 2 AZ 换来的。

⚠️ 但**加节点前必须先处理三件有状态的事**（现在都是"每台机器自己跑一份"）：

| 组件 | 多节点时的问题 | 解法 |
|------|---------------|------|
| redis / rabbitmq / kafka（infra 栈） | 两台机器各跑一份、**数据互不相通**，用户请求打到哪台就看到哪台的状态 | 抽成共享服务（ElastiCache / Amazon MQ / MSK），或指定一台为主、另一台连过来 |
| arq worker + cron | **cron 任务会被重复执行**（两个 worker 各跑一遍定时发票 OCR） | 只在一个节点起 worker，或引入分布式锁 |
| messenger 的 WebSocket | 连接状态在单机内存里，第二个节点看不到 | ALB 开 stickiness，或让 messenger 走 redis pub/sub 广播 |

**数据库的高可用不是"加节点"**，而是 RDS 开 **Multi-AZ**（自动同步备机 + 故障时自动切换）；
生产规划里已经是 Multi-AZ，非生产为省钱保持单 AZ。

## 8. 已知运行特性 / 坑

- app 用 gunicorn `--preload --timeout 120`：2 vCPU 机器上多 worker 冷启动曾致 CPU 崩溃循环；
- 跨栈无 `depends_on`，靠 `restart: always` 收敛——首次全量 up 顺序必须 infra → backend → frontend；
- `PASSWORD_SALT` 决定所有存量密码有效性，环境间不可互换、迁移须原样搬运；
- 前端 `VITE_WS_BASE_URL` 烤死在镜像里——**2026-07-29 起三个环境一律指向本环境 ALB 的 DNS**
  （test 实际值 `ws://css-test-524317374.us-east-1.elb.amazonaws.com`），不再指向网关机 EIP 或服务器 IP：
  ALB DNS 是稳定的，换机器、加节点都不用重建前端镜像；
- 前端现存 16 个 tsc 类型错误 → 构建走 `Dockerfile.novalidate`（`npx vite build` 跳过 tsc），修完后应恢复 `npm run build`；

  `css-non-prod-entry-1482605872.us-east-1.elb.amazonaws.com`（test `:8085` / uat `:8086`，仅白名单 IP）。
