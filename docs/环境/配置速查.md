### 3.1 `css-shared` 标签到底哪里用到

`CssEnv` **不是装饰性标签**——它被三处实际逻辑消费。`css-shared` 的作用正是：既满足"每个资源都有标签"，又**不会被任何环境的部署逻辑命中**。

| 消费方 | 怎么用 `CssEnv` | 共享资源打成 `css-<env>` 的后果 |
|--------|----------------|--------------------------------|
| **IAM 部署角色的权限条件** | `css-deploy-<env>` 角色的 `ssm:SendCommand` 权限带条件 `"Condition": {"StringEquals": {"ssm:resourceTag/CssEnv": "css-<env>"}}`——只**有权**对打了本环境标签的 EC2 发命令 | 该环境的部署角色获得了对共享机器发命令的权限，环境隔离被打穿 |
| **部署脚本的目标机过滤** | `docs/新aws账号/09-ssm-run-command/run.sh` 与 `deploy-env.sh` 用 `--filters "Key=tag:CssEnv,Values=css-$ENV_NAME"` 定位要部署的机器 | 共享机器被选进部署目标列表，收到本不该收的部署命令 |
| **Billing 成本分摊** | Cost Allocation Tags：按 `Group` 看 non-prod/prod 两个群组的花费，按 `CssEnv` 看各环境；`css-shared` 那一份 = test/uat 共担的基础设施（VPC、网关机、RDS 实例本身） | 共享成本被错记到单一环境头上，环境成本对比失真 |

**打错会怎样（具体例子）**：网关机 `css-non-prod-gw` 若打成 `CssEnv=css-test`，前两条会同时命中——IAM 允许 + 脚本过滤选中——test 的部署命令就会把它当应用机，`deploy.sh` 跑到网关机上去，**往错误的机器上发部署**（轻则部署失败，重则在堡垒机上拉起一整套应用栈）。打成 `css-shared` 则永远不匹配任何 `css-<env>` 过滤条件，天然免疫。

| 类别 | 资源 |
|------|------|
| 网络 | 两个 VPC、8 个子网、6 个路由表 |
| 安全组 | 8 个安全组 |
| 计算 | 网关机 `css-non-prod-gw` 及其 EIP、其 EBS 根卷 |
| 数据库 | 非生产 RDS 实例 `css-non-prod`、两个 RDS 子网组 |
