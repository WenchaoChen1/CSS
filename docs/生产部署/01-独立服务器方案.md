# 方案一：独立服务器 + ECR CI/CD（生产环境初步方案）

> 定位：**落地最快、改动最小**的生产方案。单台 EC2 承载应用与自托管中间件，**RDS 独立部署**，复用并扩展现有三栈工具链（[Backend 仓库 `deploy/`](../../CSS_backend-main/deploy/README.md)，原 `部署包/` 已并入；test 已跑通），按[审计报告](../../审计报告/)逐条硬化，规避 preprod 暴露的全部安全问题。
> 只出方案，不创建资源。编制日期：2026-07-23。

---

## 1. 方案概述

- **应用编排**：沿用现有 `部署包/` 的三个独立 compose 栈（`infra` / `backend` / `frontend`，compose 项目 `css-prod-{infra,backend,frontend}`，共享 external 网络 `css-prod-net`），跑在**一台 prod EC2** 上。
- **数据库**：**独立 RDS 实例**（PostgreSQL），两个库 `css_prod` + `ocr_prod`，私有子网、Multi-AZ、自动备份、主密码托管于 Secrets Manager。栈内**无 db/ocr-db 容器**（现有 backend 栈已是此假设）。
- **对外入口**：ALB（HTTPS，ACM 证书 + 我方分配子域名）→ 前端栈 nginx（同源反代 `/api` `/ws` `/notifications` 到 backend 栈 nginx）。**不再用 http://IP 裸暴露**。
- **CI/CD**：本机/CI 构建 7 个镜像推 **ECR**（不可变版本 tag）→ EC2 经 **SSM Run Command** 拉取并滚动重启（**CI 不落在业务机、不开 22**）。
- **硬化基线**：不发布 pgadmin/kafka-ui/任何管理端口；`DEBUG=0`/`SQL_ECHO=0`；S3 桶全私有 + 预签名；密钥进 Secrets Manager；EC2 实例角色取代静态 AK/SK；安全组最小化（仅 ALB→EC2、EC2→RDS）；CloudWatch 日志与告警。

## 4. 相对 preprod 的变化（保留 vs 硬化）

**直接复用现有部署包能力（已修好，无需再做）**：三栈拆分、RDS 独立无 db 容器、每环境独立 S3 桶、EC2 只 pull（实例角色拉 ECR）、默认不启 kafka-ui/pgadmin、OCR 独立库由 `ocr-migrator` 自动迁移、同源反代无 CORS。

**必须新增/硬化的生产级 delta**（见 §5 对照表）：ALB+TLS+WAF 入口层、RDS Multi-AZ+备份、Secrets Manager、SSM 免开 22、不可变镜像 tag+回滚、CI 移出业务机、容器资源限额、集中日志监控、`DEBUG/SQL_ECHO=0`、去 `public-read`。

## 6. CI/CD：GitHub Actions 触发（ECR）

> 生产 CI/CD 由 **GitHub Actions** 触发驱动，完整设计（触发策略、OIDC、Environments 审批、密钥分层、workflow 骨架、审计规避）见 **[03-CICD-GitHub-Actions.md](03-CICD-GitHub-Actions.md)**。本方案下 GitHub Actions 只做"远程触发器"，**EC2 上的 `deploy.sh` 与三栈 compose 不变**。

**构建推送（GitHub 托管 runner，不在 prod 业务机）**：
1. push git tag `v*` 或手动 `workflow_dispatch` 触发；托管 runner 经 **OIDC 假设 AWS 角色**（无长期 AK/SK）→ ECR 登录 → `build+push` 后端 6 持有者服务 + 前端（构建逻辑等价现有 `build-push.sh`）。
2. **不可变 tag**：prod 用 `v1.4.0` / git sha，**不用**可变 `IMAGE_TAG=prod` 覆盖式推送；ECR 开镜像扫描 + 生命周期保留最近 N 个版本。
3. 前端 `VITE_*` 由 GitHub Environment secrets 作为 build-arg 注入（**不打印到日志**，规避原前端 CI 泄露 `.env` 问题）；上线前修掉 16 个 tsc 错误恢复 `npm run build`（归 §六技术债）。

**部署到 EC2（不开 22、runner 不上机）**：
4. `deploy` job 用 **GitHub Environment `main` + Required reviewers 审批**（2026-07-29 起 environment 名=分支名 test/uat/main，弃用 `production`；取代 GitLab `when: manual`）；经 **AWS SSM Run Command** 在 prod EC2 执行 `deploy.sh prod deploy`（ECR 登录 + pull + `up -d --remove-orphans`，按 `infra→backend→frontend` 序），**不 SSH、业务机无 runner**。
5. **迁移解耦**：独立 job 先打 **RDS 快照** → 经 SSM 跑 `deploy.sh prod migrate`；生产库源自快照时先 `SELECT version_num FROM alembic_version` 与代码迁移链核对，对不上不 upgrade。
6. **回滚**：保留上一版本 tag，回滚 = 用旧 tag 重新触发 `deploy`（数据库迁移不可逆部分需人工评估）。

## 7. 数据库与迁移

- **独立 RDS**：Multi-AZ + 自动备份（保留 ≥7 天）+ 存储加密 + 删除保护；参数组按需（`log_min_duration_statement` 等）。
- **两库**：`css_prod`（主）+ `ocr_prod`（OCR 微服务，需 `CREATE EXTENSION vector`），RDS 不自动建库，需一次性手动 CREATE。
- **迁移**：主库 `alembic upgrade head`（backend 栈内一次性容器）；OCR 库由 `ocr-migrator` 每次 up 自动迁移。**生产迁移含删表且 `transaction_per_migration=True` 中途失败不整体回滚 → 迁移前必打快照**。
- **备份验证**：定期做恢复演练（审计要求）；Kafka 若保留自托管须挂卷 + 快照（未消费的验证码消息不落盘会丢）。

## 8. 一次性 provisioning 清单（执行阶段用，本方案不执行）

1. VPC + 公有/私有子网 + NAT + 路由（Terraform）。
2. 独立 RDS 实例 → `CREATE DATABASE css_prod; CREATE DATABASE ocr_prod;` + vector 扩展 + 专用低权账号；SG 放行 EC2 SG → 5432。
3. S3 `css-prod-storage`（Block Public Access 全开 + 加密 + 版本化）+ 受限 IAM 策略。
4. ECR：确认 7 仓库 + 镜像扫描 + 生命周期策略；构建机凭据用 OIDC。
5. EC2（私有子网）+ 实例角色（ECR 只读 / S3 / Secrets / CloudWatch）+ 装 docker/compose v2/aws cli + SSM Agent + 建 `/opt/css`。
6. ALB + ACM 证书（我方子域名）+ WAF + Route 53 记录；SG：ALB 仅 443 对外、EC2 仅放行 ALB SG。
7. Secrets Manager 写入全部密钥（**全新生成，不复制 preprod/test**）。
8. 建 `env/prod/`（`backend.env` + `frontend.env`）：`ENV`/`COMPOSE_PROJECT_NAME=css-prod`、RDS 端点、S3、`API_KEY==VITE_X_API_KEY`、`CATALOG_OCR_API_KEY==OCR_API_KEY`、`DEBUG=0`/`SQL_ECHO=0`；必填变量以 `config/*.py` pydantic 类为准（勿信旧 `.env.example`，历史缺 `CATALOG_OCR_*`）。
9. CloudWatch 日志组 + 指标告警 + （可选）Container Insights。

## 10. 风险与限制

- **单点**：单台 EC2 是应用+中间件单点，EC2 故障即中断（RDS 已 Multi-AZ）。真正高可用需方案二（Fargate 多副本）或至少双 EC2 + ALB。
- **自托管 Kafka/RabbitMQ 仍在**：本方案保留自托管中间件（仅挂卷持久化），运维负担与数据可靠性弱于托管队列——彻底解决见方案二（Kafka→SQS、RabbitMQ→Amazon MQ）。
- **实例角色改造**：现 `config/s3_settings.py` 要求显式密钥，若要用实例角色需小改代码；短期可退用 Secrets 托管的受限专用 key。
- **滚动发布有限**：单机 compose 只能"重建变更容器 + 健康检查"，非真正蓝绿/零停机。
- **前端类型检查**：仍走 `Dockerfile.novalidate` 跳过 tsc，需先清 16 个类型错误（§六技术债）。
