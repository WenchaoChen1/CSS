# **1\. 目的与范围**

本文档汇总了 CSS 平台的业务需求，来源于客户访谈与流程工作坊。它描述了市场参与者、当前的工作方式、目标流程，以及平台在业务层面必须满足的需求。

本文档定义业务需要什么以及为什么需要。它不规定实现方式、界面设计或系统架构；这些内容由单独交付的功能规格说明和设计产物覆盖。

**范围内：**

* 制造商产品目录的发布与维护

* 面向餐厅的产品搜索与制造商比较

* 询价单（RFQ）、报价单、采购订单与发票流程

* 定价、折扣层级与价格可见性规则

* 采购集团隶属关系记录

* 组织结构与员工分配

* 报表、导出与通知

**范围外：**

* 支付处理——付款在 CSS 之外结算

* 采购集团的财务结算、佣金与返利

* 制造商与连锁直接协商的净价（推迟至第二阶段之后）

# **2\. 业务背景与目标**

设备与耗材（E\&S）市场目前通过承载制造商产品目录并服务经销商的平台运作。餐厅——最终买家——被排除在这些平台之外。经销商手工编制报价单，通过电子邮件发送，并在平台外结算付款。因此，餐厅对哪些制造商生产其所需产品的可见性有限，也缺乏比较报价的依据。

**业务目标**

| 目标 | 理由 |
| :---- | :---- |
| 让餐厅看到多个制造商，并能按产品而不仅仅按品牌进行比较和选择 | 餐厅搜索某类产品时，应看到生产可比产品的制造商列表，附带规格和价格 |
| 允许餐厅直接与其偏好的经销商和制造商合作，降低中间环节成本 | 对外定位须谨慎处理——见下方说明 |
| 在将餐厅纳入为活跃用户的同时，保持现有经销商工作流程不变 | 经销商仍是商业交易对手方；平台是增加需求而非取代他们 |
| 提供一个统一场所用于搜索、发起询价、比较报价和交换文档 | 被表述为平台相对于现有行业解决方案的独特优势 |

*定位说明（内部）：降低中间环节成本这一目标属于战略层面，不应在与采购集团、销售代表或经销商共享的材料中公开表述，否则会引起这些方的抵触。本段仅供内部使用，应从本文档任何对外流通的版本中删除。*

# **3\. 干系人与角色**

| 角色 | 职责与利益 |
| :---- | :---- |
| 制造商（MFR） | 发布数字化产品目录；设定目录价以及针对特定经销商的折扣和净价；确认来自经销商的采购订单；发货至经销商仓库或直发（drop-ship）至餐厅现场；可能借助制造商代表进行推广并使用自动报价权限。 |
| 制造商代表 | 推广品牌，与连锁及经销商合作，参加行业展会；拥有自动报价权限，可代表工厂为经销商准备报价；偶尔直接向餐厅销售（CSS 不涉及此场景）。 |
| E\&S 经销商（vendor，经销商） | 访问制造商产品目录；编制可混合多个制造商产品的报价单；查看自身净价并加上其加价；向餐厅出具报价单；将已确认的报价单转换为采购订单和发票；库存不足时向制造商发起采购订单；收取货款；可能隶属于某个采购集团。 |
| 餐厅业主 / 采购人 | 将作为活跃买家加入 CSS。按产品名称搜索，编制覆盖所有所需物品的询价单——最多可涵盖新餐厅的整套设备——发送给多家经销商，比较报价，确认所选报价并支付定金或全款。 |
| 采购集团 | 汇总多家经销商的订单，在采购订单上盖章并以单一法律实体身份提交给制造商；协商批量折扣；收取佣金（举例提到 6%）并将其中一部分作为返利返还给经销商；出具季度对账单，并举办年度活动发放累积返利。 |
| 全国连锁客户（NAS） | 可能运营自己的采购部门和独立配送体系；拥有自动报价权限，可直接采购。 |
| CSS 管理员 | 可代表制造商加载和维护其产品目录（符合当前市场惯例）；维护采购集团列表等参考数据。 |

# **4\. 业务对象**

| 对象 | 描述 |
| :---- | :---- |
| 数字化产品目录 | 制造商、产品、规格、类目、目录价、折扣、最小起订量、按地点的可供货情况，以及适用时的库存 |
| 询价单（RFQ） | 餐厅所需物品的清单，发送给选定的经销商 |
| 报价单 | 经销商的报价：所选物品、制造商、价格、货号、所应用的加价 |
| 采购订单（PO） | 由餐厅向经销商开具，以及由经销商向制造商开具 |
| 发票 | 采购订单被接受后由经销商开具 |
| 付款 / 定金 | 在平台外结算；举例提到 50% 的定金是典型做法 |
| 采购集团对账单 | 采购集团向经销商出具的季度对账单 |
| 返利单 | 佣金的部分返还，作为采购激励返给经销商 |

# **5\. 当前流程（现状（As-Is））**

1. 制造商发布数字化产品目录；制造商按字母顺序排列。

2. 经销商浏览产品目录，选择产品并编制报价单，可混合多个制造商的物品，以制造商的目录价为基础。

3. 经销商应用其从制造商获得的折扣和净价——这是内部信息，对餐厅不可见——并加上其加价。

4. 经销商生成报价并以 PDF、Word、Excel 或 CSV 形式发送给餐厅，或打印出来。

5. 餐厅通过电子邮件或电话确认报价；如有需要，经销商对报价进行修改。

6. 付款在平台外安排：餐厅直接向经销商支付定金或全款。

7. 收到付款后，经销商按需发起采购订单并开具发票。

8. 如果经销商没有全部订单货品的库存，则向制造商发起采购订单，由制造商确认。

9. 制造商发货至经销商仓库，或直发（drop-ship）至餐厅现场。

10. 餐厅收到货物，流程闭环。

# **6\. CSS 中的目标流程（目标（To-Be））**

## **6.1 主流程**

11. 制造商通过文件或 API 上传其产品目录，设置价格可见性，并指定接收请求的电子邮件地址。

12. 餐厅在 CSS 中注册，并按产品名称或制造商品牌搜索；系统返回多个制造商及其规格和价格，并按地点过滤。

13. 餐厅将所需物品汇集为一份询价单，可涵盖新门店的整套设备。

14. 餐厅将 RFQ 发送给最多三家经销商，当连锁与本地供应商合作时可包含不同区域的经销商。

15. 经销商收到 RFQ，核对库存，加上其加价并回传报价单。

16. 餐厅比较各份报价单并确认所选报价；双方达成一致前可能经历数轮协商。

17. 确认后报价单转为采购订单；条款要求时经销商收取定金；付款在 CSS 之外进行。

18. 如经销商没有货品，则向制造商发起采购订单，由制造商确认或提出替代品；替代方案须与餐厅商定，否则订单被修改或取消。

19. 制造商发货至经销商仓库或直发（drop-ship）至餐厅；货物经由经销商仓库时，由经销商安排最终配送。

## **6.2 餐厅的进入路径**

| 路径 | 描述 | 权衡 |
| :---- | :---- | :---- |
| 直接向经销商下单 | 餐厅在经销商目录中找到本地经销商，通过链接跳转到经销商自己的网站下单 | 对重复订单快捷方便；交易发生在 CSS 之外 |
| 通过制造商产品目录发起请求 | 餐厅搜索产品，选择制造商并向其经销商发送 RFQ | 可以比较报价；每次请求限三家经销商 |
| 自由文本请求（已否决） | 餐厅输入诸如"40 升炸炉"之类的笼统需求，CSS 将其群发给经销商 | 已否决：存在不相关报价泛滥以及经销商过载的风险 |

# **7\. 业务需求**

## **7.1 产品目录管理**

| ID | 需求 | 备注 |
| :---- | :---- | :---- |
| BR-CAT-01 | 制造商应能在 CSS 中发布和维护产品目录。 |  |
| BR-CAT-02 | 产品目录应支持通过文件（CSV、Excel）上传，制造商有自有系统时亦可通过 API 集成上传。 |  |
| BR-CAT-03 | 一条产品目录条目应包含名称、描述、类目、规格、目录价、折扣、最小起订量、可供货地点（城市、ZIP）以及适用时的库存可用性。 | E\&S 行业的产品明细深度很高；客户提供了参考样例 |
| BR-CAT-04 | 制造商应按制造商名称的字母顺序排列。 |  |
| BR-CAT-05 | 关键词搜索栏应可按公司名称、产品名称或类目，以及城市、州或 ZIP 邮编过滤产品目录。 |  |
| BR-CAT-06 | 制造商特定政策（如运费条款和保修）应与该制造商的目录产品一并发布在平台上。 |  |
| BR-CAT-07 | 制造商应能通过开关隐藏或显示其产品目录的零售（目录）价。 |  |
| BR-CAT-08 | 制造商应能将经销商与产品关联（按城市和 ZIP 邮编过滤），并记录经销商联系方式，包括用于接收 RFQ 的电子邮件地址。 |  |
| BR-CAT-09 | 制造商应能将选定经销商提升至经销商列表顶部作为优选经销商。 | 付费推广；经销商和制造商也可为产品投放广告 |
| BR-CAT-10 | CSS 管理员应能代表制造商加载和维护产品目录。 | 反映当前市场使用主 Excel 模板的惯例 |
| BR-CAT-11 | 制造商应能指定接收订单的电子邮件地址，并接收关于新订单和变更的提醒。 |  |

| ID | 需求 | 备注 |
| :---- | :---- | :---- |
| BR-SEA-01 | 餐厅应能在 CSS 中注册，并可按产品名称以及制造商品牌进行搜索。 | 按产品而不仅按品牌搜索是核心目标 |
| BR-SEA-02 | 搜索结果应列出生产可比产品的各制造商，附带规格和价格，以便比较报价。 |  |
| BR-SEA-03 | 餐厅应能按名称、品牌、城市或 ZIP 邮编搜索经销商，并支持按距离、相关性、价格和可供货情况排序。 |  |
| BR-SEA-04 | 系统应自动检测餐厅所在位置，并允许手动更改。 |  |
| BR-SEA-05 | 当餐厅选择直接下单时，CSS 应外链至经销商自己的网站，而不重复实现经销商的电商功能。 |  |
| BR-SEA-06 | 餐厅应能将来自不同制造商的产品汇集到一个购物篮中，构成 RFQ。 |  |

## **7.3 询价单**

| ID | 需求 | 备注 |
| :---- | :---- | :---- |
| BR-RFQ-01 | 餐厅应能编制覆盖所有所需物品的询价单，最多可涵盖新餐厅的整套设备。 |  |
| BR-RFQ-02 | 每次请求的 RFQ 最多可发送给三家经销商。 | 该限制用于防止滥用和经销商过载 |
| BR-RFQ-03 | 系统应按优先级顺序推荐经销商：所有物品皆有库存的经销商，其次是部分可供货的经销商，再次是与所需制造商合作的经销商。 |  |
| BR-RFQ-04 | 餐厅应能覆盖系统推荐，手动选择其偏好的经销商。 | 连锁可能需要多个区域的经销商 |
| BR-RFQ-05 | 经销商应通过电子邮件及 CSS 站内收到 RFQ 通知。 |  |
| BR-RFQ-06 | RFQ 应包含物品清单、要求的交付日期以及餐厅的联系方式。 |  |
| BR-RFQ-07 | 系统应限制 RFQ 的提交频率，以保护经销商免受骚扰。 | 所举示例：每分钟不超过五份 RFQ |

## **7.4 报价单**

| ID | 需求 | 备注 |
| :---- | :---- | :---- |
| BR-QUO-01 | 经销商应能编制组合多个制造商目录产品的报价单。 |  |
| BR-QUO-02 | 经销商应能在其全部产品范围内全局应用加价，也可按单品或按单份报价应用；加价字段应始终保持可编辑。 | 明确要求保持灵活 |
| BR-QUO-03 | 系统应提供半标准化的报价单模板，报价方可扩展额外的字段、列、行和备注。 | 客户提供了模板样例 |
| BR-QUO-04 | 报价单应由销售方人工审核，可在确认前修改；不得自动转换为采购订单。 |  |
| BR-QUO-05 | 餐厅应能确认报价单或请求调价；流程应支持数轮协商。 |  |
| BR-QUO-06 | 餐厅应能在确认之前比较从不同经销商收到的报价单。 |  |
| BR-QUO-07 | 报价单应可以 PDF、Word、Excel 和 CSV 格式导出和发送，并可打印。 |  |
| BR-QUO-08 | 报价与订单流程应支持协商序列产生的各状态：RFQ 已发出、报价已发送、买方已确认、采购订单已生成、已开票、已发货。 | 在签署及（如要求）支付定金之前，任何内容均无约束力 |

## **7.5 采购订单、发票与履约**

| ID | 需求 | 备注 |
| :---- | :---- | :---- |
| BR-ORD-01 | 报价单一经签署并收到所需定金（如有），即转为采购订单；采购订单随后由卖方转换为发票。 |  |
| BR-ORD-02 | 当经销商没有货品库存时，应生成发往制造商的采购订单。 |  |
| BR-ORD-03 | 制造商应能确认采购订单或提出替代产品；被接受的替代方案须与餐厅商定，否则订单被修改或取消。 |  |
| BR-ORD-04 | 系统应支持两种交付方式：发货至经销商仓库，以及直发（drop-ship）至餐厅现场。 | 当经销商没有仓库时使用直发 |
| BR-ORD-05 | 交付条款应支持预付和赊销条款，以及条款要求时的定金。 | 举例提到 50% 的定金是典型做法 |
| BR-ORD-06 | 单个采购订单可包含多个制造商的产品；按制造商的拆分应在经销商侧完成。 |  |
| BR-ORD-07 | 餐厅不应看到订单在各制造商之间的内部拆分。 |  |
| BR-ORD-08 | 付款应在 CSS 之外结算；平台不处理付款。 | 支付处理可能是后续阶段的内容 |

## **7.6 定价与折扣**

| ID | 需求 | 备注 |
| :---- | :---- | :---- |
| BR-PRC-01 | 系统应区分目录价（制造商发布的参考价）与净价（应用所有折扣后的价格）。 |  |
| BR-PRC-02 | 系统应支持多级折扣层级，每一级都作用于已折扣后的价格。 | 公式：净价 \= 目录价 × (1 − D1) × (1 − D2) × (1 − D3) |
| BR-PRC-03 | 算例：目录价 $100，折扣层级 50/10/5，得 $100 × 0.5 × 0.9 × 0.95 \= $42.75。 | 用作验收示例 |
| BR-PRC-04 | 系统应允许直接配置乘数，例如 50/10/10 层级对应的 0.45。 |  |
| BR-PRC-05 | 目录价应可从制造商以 Excel 和 CSV 格式导入。 |  |
| BR-PRC-06 | 目录价变更时，所有价格层级应自动重算。 |  |
| BR-PRC-07 | 系统应支持零售、批发和分销商等价格层级，各自拥有独立的折扣设置。 |  |
| BR-PRC-08 | 当物品以不足整箱的数量销售时，应额外应用拆箱加价。 |  |
| BR-PRC-09 | 系统应支持价格取整规则，例如将零售价取整到 .99。 |  |
| BR-PRC-10 | 折扣应可按产品类目和按客户配置。 |  |
| BR-PRC-11 | 界面应以"目录价 → 折扣 → 净价"清晰展示价格层次，允许手动录入或修正价格与折扣，并展示计算公式以保持透明。 |  |
| BR-PRC-12 | 制造商授予经销商的折扣应以"目录价 / 折扣 / 结果价"的形式保存在制造商模块中。 |  |

## **7.7 价格可见性与保密性**

| ID | 需求 | 备注 |
| :---- | :---- | :---- |
| BR-CNF-01 | 制造商给其经销商的折扣属于机密信息，不得发布在产品目录中。 |  |
| BR-CNF-02 | 经销商只能看到自己从制造商获得的折扣和净价，不得看到授予任何其他经销商的折扣。 |  |
| BR-CNF-03 | 制造商只能看到自己的产品及其给经销商的净价，不得看到经销商的加价。 |  |
| BR-CNF-04 | 餐厅只能看到制造商的产品信息及目录价；净价对其不可见。 |  |
| BR-CNF-05 | 制造商与大型餐厅连锁直接协商的净价不在第二阶段范围内。 | 由客户推迟 |
| BR-CNF-06 | CSS 不得存储或处理制造商、经销商与采购集团之间的保密协议。 |  |

## **7.8 采购集团**

| ID | 需求 | 备注 |
| :---- | :---- | :---- |
| BR-BGR-01 | 每条经销商记录应包含一个采购集团字段，由经销商从下拉列表中选择填写，并支持手动录入。 |  |
| BR-BGR-02 | 应预加载已知采购集团列表，且该列表应保持可编辑。 | 列表由客户提供 |
| BR-BGR-03 | 一家经销商应可隶属于多个采购集团。 | 罕见但可能 |
| BR-BGR-04 | 采购集团不应作为与经销商和制造商并列的独立业务实体创建；相关信息应保存在经销商记录内。 |  |
| BR-BGR-05 | 系统应允许经销商在报价单、订单或发票上记录采购集团。 |  |
| BR-BGR-06 | CSS 应记录采购集团取值，但不追踪与之相关的合同、佣金、返利、义务或付款。 |  |
| BR-BGR-07 | 采购集团数据准确性和时效性的责任由经销商承担；对于过期条目以及因此错失的折扣与返利，CSS 不承担任何责任。 |  |

*仅作规模背景说明，非需求：采购集团佣金通常约为 6%，其中约一半可能作为返利返还给经销商；部分经销商每年获得的返利超过 $1,000,000。当平台达到临界规模——客户提到大约 5,000 家经销商和 1,000 家制造商——CSS 可考虑充当虚拟采购集团，届时采购集团取值可从参考列表自动填充。*

# **8\. 业务规则**

* 餐厅向经销商采购；经销商向制造商采购。

* 在报价单经签署以及（条款要求时）支付定金予以锁定之前，任何内容均不构成承诺。

* 报价单在确认前始终由销售方人工审核。

* 给餐厅的最终价格由经销商设定，即在净价基础上加上自己的利润。

* 制造商与经销商之间的折扣属于机密，仅对该经销商本身可见。

* 采购集团数据仅作记录，CSS 从不核实、追踪或结算。

* 付款由双方直接进行，从不通过平台。

# **9\. 约束与排除项**

| 领域 | 约束 |
| :---- | :---- |
| 采购集团 | CSS 不将采购集团的记账、佣金计算或付款自动化。仅记录隶属关系。采购集团逻辑不得过度设计；记账工作仍由经销商负责。 |
| 多制造商订单 | 单个采购订单可包含多个制造商的产品，但拆分在经销商侧完成，不向餐厅暴露。 |
| 付款 | 平台不接受也不处理付款。据了解有竞争对手正在做这方面的工作，但目前尚不可用。 |
| 连锁净价 | 大型连锁与制造商直接协商折扣净价的场景不在第二阶段处理。 |
| 自由文本 RFQ | 向经销商发送不明确的自由文本需求的方案曾被考虑并已否决。 |
| 经销商电商 | CSS 链接至经销商网站，而非复制其下单功能。 |
