### 1. check_permissions 授权检查目标可被查询参数 business_id/business_type 篡改，导致跨租户越权 (IDOR)

| 文件 | 类型 | 验证 |
|---|---|---|
| `CSS_backend-main/core_app/src/app/internal/main_app/middlewares/permissions/middlewares.py:242` | authorization-bypass | CONFIRMED |

**问题**：任何持有合法 token 的普通租户用户，只要是自身某个 company/store/restaurant 的成员(或 owner)，即可对他人资源发起越权操作。攻击者请求 `PUT /vendors/{受害者vendor_id}/products/{pid}?business_id={攻击者自己的store_id}&business_type=store`：check_store_permissions 针对攻击者自己的 store 校验通过，而 handler 用 path 中受害者 vendor_id 调用 update_store_product 修改/删除受害者商品。BusinessEntityType 为 StrEnum('store'/'company'/'restaurant'/'manufacturer_subdivision')，查询串字符串可直接匹配 match 分支，无需任何额外权限。该模式覆盖 vendor/invoices/restaurants/companies 等大量带 path 资源 id 的 check_permissions 路由，且服务层普遍不复查成员身份 —— 系统性跨租户读/写/删越权。

**证据**：
```
check() 先从 path 解析资源: store_id = path_params.get('vendor_id')(236 行), company_id = path_params.get('company_id')(237 行)。随后无条件读取查询串并覆盖: business_id = query_params.get('business_id')(242 行); business_type = path_params.get(...) or query_params.get('business_type')(244 行); match 中 `store_id = business_id` / `company_id = business_id`(251/253 行)。权限校验用被覆盖后的 id，但 handler 仍用 path 值。以 vendor/transport/handlers.py:324 `update_vendor_product(vendor_id)` 为例，其 store_id=path vendor_id，而 service stores/products/services.py:324-334 `update_store_product` 只校验 store/product 是否存在，不校验成员身份。
```

**修复建议**：权限中间件必须对 handler 实际操作的同一资源标识做校验，禁止用查询参数覆盖由 path 推导出的资源 id。方案：只有当路由本身以 business_id/business_type 作为业务上下文(即 handler 也读取同一值)时才允许该覆盖，且优先信任 path_params；对存在 path 资源 id 的路由忽略查询串覆盖。更稳妥的做法是由中间件把已鉴权通过的资源 id 注入 request.state 并让 handler/service 只使用该值，或在 service 层对 user 成员身份做二次校验(纵深防御)。


### 2. IDOR: cross-tenant payment/refund on other vendors' order invoices (no order↔store ownership check)

| 文件 | 类型 | 验证 |
|---|---|---|
| `CSS_backend-main/core_app/src/app/internal/core/stores/orders/services.py:1806` | authorization | CONFIRMED |

**问题**：StoreOrderInvoiceService.create_order_invoice_transaction (called by POST /stores/{store_id}/orders/{order_id}/invoice/transactions, which has only Security(check_access_token)) authorizes with `store_member = get_store_member(store_id=store_id, user_id)` OR `company_member = get_company_member(company_id=order.store.company_id)`, but NEVER verifies `order.store.id == store_id`. So any user who is a member of ANY one store can pass their own store_id in the path together with a victim's order_id (belonging to a different store/company) and record PAYMENT/REFUND transactions on that victim invoice. The REFUND branch additionally calls top_up_restaurant_account_credit_balance(restaurant_id=order.restaurant_id, amount=data.amount) (lines 1835-1839), i.e. it grants real store credit to an arbitrary restaurant, and mutates invoice.total_paid/total_refunded/balance_due/is_paid. The sibling read methods get_order_invoice_transactions (line 1787) and get_order_invoice_history (line 1859) perform NO membership check at all, so any authenticated user can read any order's financial transaction/history. Contrast the correct methods in the same file (get_order_invoice line 400, update_order_invoice_payment_record line 441, generate_order_invoice line 321) which all do `if order.store.id != store_id: return Forbidden`.

**证据**：
```
order = await self._orders_service.get_order(order_id=order_id) ... store_member = get_store_member(store_id=store_id, user_id) ; company_member = get_company_member(company_id=order.store.company_id) ; if store_member is None and company_member is None: return not_found('member')  # no `order.store.id == store_id` check; REFUND then tops up order.restaurant_id credit
```

**修复建议**：In create_order_invoice_transaction, get_order_invoice_transactions and get_order_invoice_history, after loading the order add `if order.store.id != store_id: return Result.fail(PermissionsErrorFactory.get_you_have_no_rights_to_work_with_this_resource_error())`, and gate the two read methods behind the same store/company membership check used by the write path. Do not let the store_member(store_id) branch alone authorize actions on an order that belongs to a different store.

### 5. Refund validation operator-precedence bug + mutate-before-validate with no rollback; balance never restored

| 文件 | 类型 | 验证 |
|---|---|---|
| `CSS_backend-main/core_app/src/app/internal/core/orders/repositories.py:1519` | correctness | CONFIRMED |

**问题**：In update_order_invoice_total_refunded: `total_paid = invoice.total_paid or invoice.payment_record.paid_amount if invoice.payment_record else Decimal('0.00')`. Python's conditional expression binds looser than `or`, so this parses as `(invoice.total_paid or invoice.payment_record.paid_amount) if invoice.payment_record else 0`. When there is no payment_record (payments recorded via the PAYMENT transaction path only set invoice.total_paid, they do NOT create a payment_record), total_paid is forced to 0 and every legitimate refund is rejected with 'Refund would exceed total paid'. Also `invoice.total_refunded += amount` is applied before the check and on failure the method returns without session.rollback(), leaving a dirty ORM object; and even on success the refund never decrements balance_due or clears is_paid, so a fully-refunded invoice still reads as paid with a stale balance.

**证据**：
```
invoice.total_refunded += amount
        total_paid = (
            invoice.total_paid or invoice.payment_record.paid_amount if invoice.payment_record else Decimal('0.00')
        )
        if invoice.total_refunded > total_paid:
            return Result.fail(... 'Refund would exceed total paid')
```

**修复建议**：Parenthesize explicitly: `total_paid = invoice.total_paid if invoice.total_paid is not None else (invoice.payment_record.paid_amount if invoice.payment_record else Decimal('0.00'))`. Validate before mutating, rollback on the failure branch, and update balance_due/is_paid to reflect the refund.

### 11. 验证码/安全码使用非加密安全的随机数生成器 (random 而非 secrets)

| 文件 | 类型 | 验证 |
|---|---|---|
| `CSS_backend-main/core_app/src/app/pkg/utils.py:15` | security | CONFIRMED |

**问题**：generate_random_digital_code 用 random.choice(string.digits) 生成数字码。它被用于生成认证确认码(auth/services.py:140,邮箱/短信 OTP)以及 companies/restaurants/onboardings 的 member security_code(如 companies/services.py:506)。Python 的 random 是 Mersenne Twister PRNG(CWE-338),状态可被恢复/预测:观察到若干输出即可推断内部状态并预测后续验证码;配合 6 位仅 10^6 空间,可绕过联系方式验证/接管账户。

**问题**：任何 VITE_* 变量在构建时会被写死进浏览器可下载的 bundle。这意味着守卫全部后端 API 的共享密钥对任意访客都是明文可读的，使 check_api_key 中间件失去安全边界意义（只是形同虚设的门禁）。

**证据**：
```
Dockerfile 注释明示需要 .env 供 Vite 读取，`COPY . .`（L15）后 `npm run build`（L18）把 VITE_X_API_KEY（.env.example L11）内联进静态 JS。CLAUDE.md 说明该值必须等于后端 API_KEY，是所有 /api 路由的 check_api_key 网关。
```

**修复建议**：不要把 API 网关密钥当作前端可见配置分发；后端应改用真正的每用户会话/JWT 鉴权而非全局共享静态 Key，或将该 Key 校验移到只有服务端持有的反向代理层。至少明确该值等同公开信息并据此设计后端授权。


### 67. 后端生产镜像包含 dev 依赖且以 root 运行

| 文件 | 类型 | 验证 |
|---|---|---|
| `CSS_backend-main/core_app/src/Dockerfile:16` | image-hygiene | PLAUSIBLE |

**问题**：生产镜像携带测试/静态分析工具链增大体积与漏洞面；以 root 运行放大容器逃逸/被入侵后的影响。均属可直接消除的部署硬化缺口。

**证据**：
```
`RUN poetry install`（L16）未加 `--only main`/`--no-dev`，会安装 pyproject.toml 的 `[tool.poetry.group.dev.dependencies]`（mypy 等）及 pytest 全套测试依赖；镜像全程无 `USER` 指令，容器以 root 运行。catalog_ocr_service/Dockerfile、ai_assistant/Dockerfile 同样以 root 运行。
```

**修复建议**：改为 `poetry install --only main --no-root`（或多阶段构建仅拷运行期依赖）；创建非特权用户并 `USER appuser`，对三个服务镜像统一处理。
