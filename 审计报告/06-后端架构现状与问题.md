# 06 · 后端架构现状与问题（v20260705）

> FastAPI / Python，约 **1491 个 .py 文件**（不含迁移），Alembic 约 195 个 revision。

## 1. 现在是怎么做的

**分层 + 领域模块化**，代码在 `core_app/src/app`，三个大区：

- **`internal/core/<domain>/`** —— 领域层，可跨 app 复用。33 个域：
  `auth · users · user_management · roles · companies · clients · restaurants · stores · team · invitations · onboardings · subscribers · settings · orders · payments · payment_methods · invoices · products · product_attributes · manufacturer_catalog_imports · manufacturer_products · manufacturer_relationships · manufacturer_subdivisions · manufacturer_subdivision_products · master_database · chats · notifications · emails · phone · files · reports`。
  每个域内部统一切分：`domains.py / dto.py / models.py(SQLAlchemy) / repositories.py / services.py / errors.py / transport/di.py`。
- **`internal/main_app/<feature>/`** —— HTTP/传输层（路由）。24 个 feature：admin/auth/catalog_ocr/chats/clients/companies/entity/files/invoices/manufacturer/me/middlewares/notifications/onboarding/orders/permissions/products/reports/restaurants/settings/team/temporary_files/vendor。`main_app/app.py` 聚合所有 feature 路由到 `/api`。
- **`pkg/`** —— 可复用基础设施：auth、http、websockets、errors、validators、eden_ai、finance、reports、s3_data、files_uploading 等。

**多进程/多服务**：
- 4 个 ASGI/worker 共用同一 `app` 镜像：主 API（gunicorn）、messenger（聊天/ws）、notifications（RabbitMQ）、worker（arq/Redis）。
- 独立服务：`catalog_ocr_service`（自有 alembic/DB/worker，Gemini OCR）、`sms_sender`/`email_sender`（Kafka 消费者）、`ai_assistant`（Node/OpenAI）。
- 所有 `/api` 路由由 `check_api_key` 网关校验；用户态由 `check_access_token`(JWT) 注入 `request.state.user_id`。

**优点**：领域切分清晰、DI 装配规整、职责分层到位，利于按域扩展。

## 2. 系统性问题（按主题归纳，明细见 [04](04-代码审计发现清单.md)）

### 2.1 授权模型是最大的结构性缺陷 🔴
- **鉴权目标可被查询参数篡改**：`main_app/middlewares/permissions/middlewares.py` 用 `business_id/business_type` 覆盖由 path 推导的资源 id，而 handler 仍用 path 值 → 系统性跨租户越权（#1）。
- **服务层普遍不复查成员身份**：`store_member(store_id)` 只证明"你属于你自己选的那个 store"，却未校验 `order.store.id == store_id` → 他人订单可被记账/退款（#2）、他人客户 PII 可被读取（#7）、跨公司报表可被导出（#9）。
- **团队成员可被越权改角色**：仅凭 `member_id` 定位、business 取自请求体 → 提权（#3）。
- **修复方向**：把"已鉴权资源 id"由中间件注入 `request.state`，service 只信任它；并在 service 层对 user↔资源做二次成员校验（纵深防御）。

### 2.2 金额/退款正确性 🟠
- 退款校验存在**运算符优先级 bug + 先改后校验且无回滚** → 余额永不恢复（#5）；`update_order_invoice_total_paid` 同类模式（#40）。
- 支付/退款金额**未校验下界**，接受负数/零（#16）。

### 2.3 数据外泄面 🟠
- **上传对象硬编码 `public-read`**（`config/s3_settings.py`）→ 发票/客户文件/报表永久公开可读（#10）。
- **DEBUG 开启回传完整堆栈**（#51）；生产实测 `DEBUG=1`。
- **报表 CSV/Excel 公式注入**（未中和 `= + - @`，#24）。

### 2.4 SSRF / 外部请求 🟠
- 厂商目录图片导入 worker 未校验目标 URL（#6）；OCR 文件抓取可经重定向 + DNS rebinding 绕过校验打内网/元数据（#12）。

### 2.5 认证健壮性 🟠
- **OTP 无失败次数锁定**，结合"仅凭邮箱发起密码重置"→ 账户接管（#4）。
- 验证码用非加密安全的 `random` 而非 `secrets`（#11）。
- 口令哈希用**全局静态盐**（所有用户共用一个 salt，#15）。

### 2.6 弹性/健壮性（中间件与消费者） 🟡
- `email_sender` 每次启动换新消费组 + `auto_offset_reset=latest` → 重启期间邮件被静默丢弃（#8）。
- `sms_sender` 只捕获 HTTPStatusError，其余异常导致**毒丸崩溃循环**（#21）；offset 提交实为空操作（#46）。
- websocket 在线计数只减不清、并发断开触发 `RuntimeError`（#22/#23）。
- 报表/目录导入**无行数上限**，`limit=-1` 拉全表进内存 → worker OOM/DoS（#18/#25）。
- OCR 任务在 DB 提交前入队（丢任务竞态，#27）；成本上限是有竞态的 check-then-act（#13）。

### 2.7 其他卫生 ⚪
- API-Key 用非恒定时间 `!=` 比较（时序侧信道，#38）；Bearer 解析用子串包含 + 全局 replace（#39）。
- 生产服务代码 import 了 pytest conftest fixture（#42）；生产镜像含 dev 依赖且 root 运行（#67）。
- 已停用但仍在库的 Catalog OCR 路由：鉴权被注释关闭 + webhook 无认证 + IDOR（#43，建议删除死代码）。

## 3. 建议优先级

1. **先修 3 条 CRITICAL 越权 + public-read + DEBUG**（对外风险最高）。
2. 补 OTP 限速/锁定、改 `secrets` 随机、修退款金额校验与回滚。
3. 治理消费者健壮性（毒丸、丢消息）与报表/导入的内存上限。
4. 清理死代码（停用 OCR 路由、conftest 误引用）、统一恒定时间比较。
