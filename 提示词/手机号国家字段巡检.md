# 提示词：手机号「国家字段 + 号码字段」巡检与优化台账维护

> 用途：让 AI（Claude Code 等）定期排查 **test 数据库** 里所有电话类字段，找出「号码和国家没有拆成两个表字段」的地方，
> 并把结果维护进 `docs/优化/` 的「待优化 / 已优化」台账。
> 用法（任选其一）：
> - Claude Code 里输入 `/phone-country-audit`（命令文件 `.claude/commands/phone-country-audit.md` 指向本文）；
> - 或直接对 AI 说：「按 `提示词/手机号国家字段巡检.md` 执行一次巡检」；
> - 或把本文「## 提示词正文」以下的内容整段复制给 AI。
>
> 首次产出：2026-10-12（台账见 [`docs/优化/`](../docs/优化/README.md)）。

---

## 提示词正文

你是 CSS（Chain Serve）项目的数据规范巡检员。请**完整**执行下面的流程，不要跳步，不要只给计划。

### 0. 目标与判定口径

- **要求**：每个电话类字段（手机、座机、传真、联系人电话、快照电话等）必须是**两个表字段**：
  「国家字段」+「号码字段」。国家字段命名为号码列名去掉末尾 `_number` 再加 `_country_code`
  （`phone_number`→`phone_country_code`、`main_phone`→`main_phone_country_code`、`fax_number`→`fax_country_code`）。
- **详细规范以 `docs/优化/待优化/000-统一规范-手机号拆分为国家码与号码两字段.md` 为准**
  （若它已移到 `docs/优化/已优化/`，就读那里）。国家列取值口径（ISO 3166-1 alpha-2 还是拨号码）以该文“待决策/决策记录”小节的最终结论为准。
- **已优化**的判定（全部满足才算）：
  1. 国家列与号码列都存在，类型/约束符合规范；
  2. 号码列不含 `+`、空格、横线、括号等分隔符，只存本国号码；
  3. 号码非空的行，国家列 100% 填充且取值合法；
  4. 后端写入路径统一经公共电话模块（`app/pkg/phone`），不再有散落的正则 / 硬编码 `+1` / `parse(..., 'US')`；
  5. 前端提交与展示按「国家 + 号码」两个值处理。
  任一不满足 → **待优化**。

### 1. 只读与安全约束（必须遵守）

- 对任何数据库**只允许 SELECT**。连接时加只读会话参数：`PGOPTIONS="-c default_transaction_read_only=on"`。
- 不修改前后端代码、不切换用户当前分支、不 commit / push（除非用户明确要求）。看代码用**只读 worktree**：
  ```bash
  # 在会话 scratchpad 里建（不要建在仓库内），用完 git worktree remove
  git -C CSS_backend-main  fetch origin && git -C CSS_backend-main  -c core.longpaths=true worktree add --detach <scratchpad>/be origin/test
  git -C CSS_frontend-main fetch origin && git -C CSS_frontend-main -c core.longpaths=true worktree add --detach <scratchpad>/fe origin/test
  ```
  需要看 uat / prod 的代码线时用 `git show origin/main:<path>`、`git grep <pat> origin/main -- <path>`，不要 checkout。
- **隐私**：台账文档里不得出现任何真实号码 / 邮箱 / 姓名原值；展示数据形态时把数字替换成 `9`（如 `+99999999999`），只给计数、比例、长度、区号分布。
- test / uat 是脱敏数据（邮箱前加 1、**手机号尾部加 1**、口令统一），号码长度与有效性统计会偏差，结论里要注明；prod 是未脱敏真实数据，**不要**为巡检去连 prod。

### 2. 取得「当前 test 数据库」

按优先级任选其一，并在台账里写明数据来源与时间：

1. **本机快照（推荐，最快）**：`备份/数据库/test/` 下最新的 `test_main_<时间戳>.dump`（`.last_ts` 记录最新时间戳）。
   - 若本机 docker 里已有 `css-test-main` 库，先核对它的 `alembic_version` 与 dump 里的是否一致
     （`pg_restore -a -t alembic_version -f - <dump>`），以及 `pg_restore -l` 的表数量是否一致；一致才可直接用。
   - 不一致或快照太旧（> 1 天）→ 用 `docs/环境运维执行脚本/05-数据库运维/backup-env-db.sh test` 重新备份
     （需要 `SRC_PGPASSWORD`，向用户索取，不要自己找密码），再 `pg_restore --no-owner --no-acl` 恢复到本机**新建的**库里
     （不要覆盖用户已有的库）。
2. **直连（隧道）**：`docs/环境运维执行脚本/05-数据库运维/db-tunnel.sh test`，用只读账号 `css_dev` 连 `localhost:5433/css-test-main`
   （密码向用户索取或看本地私有文件，不要写进任何会提交的文件）。

OCR 库 `css-test-ocr` 也要扫一遍。

### 3. 排查步骤

1. **枚举所有可能承载电话的位置**（三种方式都要做，互相查漏）：
   - 按列名：`information_schema.columns` 里列名匹配 `phone|mobile|tel|cell|fax|whatsapp|msisdn|dial|contact`（注意排除 `contact_email`、`contact_name`、`*_id` 等非电话列，但要人工确认）；
   - 按内容：对所有 `varchar/text` 列用电话正则扫描（如 `^\s*\+?\(?[0-9]{1,4}\)?[ .\-]?[0-9][0-9 .\-()]{5,}[0-9]\s*$`），对 `json/jsonb` 列扫描键名含 `phone|mobile|tel|fax|whatsapp`；
   - 按代码：在后端（含 `sms_sender`、`email_sender`、`catalog_ocr_service`、`notifications`、`worker`、Kafka 消息体）与前端 Grep 电话相关字段与 `PhoneInput`。
   - 还要看视图、物化视图、触发器/函数中引用电话列的地方。
2. **逐列判定**：该列所在表是否有符合命名规范的国家列？国家列填充率与取值是否合法？号码列是否仍是 `+` 整串或带分隔符？
   每列给出：总行数、非空数、以 `+` 开头数、纯数字数、含分隔符数、长度范围、区号分布 Top、异常值（空串、过短、非号码）。
3. **追代码**：每个电话列的写入路径（model / DTO 校验 / service / repository / 导入 / 识别落库）与读取路径（响应 / PDF / 邮件 / 短信 / 登录查找 / 去重唯一性 / 导出）以及前端表单，记录 `文件:行号`（相对工作区根，如 `CSS_backend-main/core_app/src/app/...py:42`，并注明基线 commit）。
4. **列较多时**并行处理：按领域分组（用户与认证、公司、餐厅门店、入驻成员、客户、客户联系人、厂商、报价、识别导入……）交给子代理各写一篇，再用**另一个独立子代理逐篇复核**数字与代码引用（重新跑 SQL、打开文件核对行号），最后做一次覆盖率与跨文档一致性终审。

### 4. 维护台账（`docs/优化/`）

目录结构（不存在就创建）：

```
docs/优化/
├── README.md        体系说明
├── 待优化.md        索引：编号 / 标题 / 优先级 / 摘要（问题+处理方向）/ 文档链接
├── 已优化.md        索引：编号 / 标题 / 完成日期 / 摘要（做了什么）/ 文档链接
├── 待优化/          每个问题一篇「问题 + 方案」文档
└── 已优化/          完成后整篇移入，补「三、处理记录」
```

按以下规则更新：

- **新发现**的问题：在 `待优化/` 新建文档，编号取全台账（待优化 + 已优化）最大编号 + 1，三位数字；文件名 `NNN-<领域>-<主题>.md`；同时在 `待优化.md` 索引表加一行。
- **已有的待优化项**：执行该文「验收标准」里的 SQL 与代码检查：
  - **全部通过** → `git mv` 到 `已优化/`（文件名不变），把元信息表「状态」改为「已优化」，填写「三、处理记录」（完成日期、PR/提交、alembic revision、验收 SQL 实际结果），从 `待优化.md` 删除该行、在 `已优化.md` 加一行；
  - **部分进展** → 留在 `待优化/`，更新「一、现在是什么问题」里的数据/代码现状，在「三、处理记录」追加一条带日期的进展；
  - **无变化** → 只更新数据来源时间。
- **已优化项回归**（验收不再通过）→ 移回 `待优化/`，「三、处理记录」写明回归原因与日期，两份索引同步调整。
- 两份索引页的「最后巡检」行写本次日期、数据来源（快照时间 + alembic 头）与代码基线（commit）。

### 5. 每篇「问题 + 方案」文档的模板

```markdown
# <编号> <标题>

| 项 | 内容 |
|----|------|
| 状态 | 待优化 / 已优化 |
| 优先级 | P0/P1/P2（一句理由） |
| 涉及表.字段 | `表.列`, ... |
| 影响行数 | 号码非空行合计 N（按表列出） |
| 数据来源 | test 库快照 <时间>（alembic <头>） |
| 代码基线 | 后端 origin/test @<commit>；前端 origin/test @<commit> |
| 发现日期 | YYYY-MM-DD |

## 一、现在是什么问题
### 1. 表结构现状
### 2. 数据现状
### 3. 代码现状
### 4. 影响与风险

## 二、怎么处理（方案）
### 1. 目标表结构
### 2. 数据迁移
### 3. 后端改动
### 4. 前端改动
### 5. 环境与发布注意
### 6. 验收标准      ← 必须是可直接执行的 SQL + 代码检查点；在“未优化”状态下执行应当失败

## 三、处理记录
（待优化阶段写“暂无”；完成后补：完成日期、PR/提交、alembic revision、验收结果）
```

优先级口径：**P0** 登录 / 短信 / 身份唯一性相关；**P1** 对外展示与联系的业务主数据、会转成用户的数据；**P2** 快照 / 低频 / 已废弃 / 非结构化数据。

### 6. 环境注意（写方案时必须考虑）

- 代码线与数据线配对：test = main + ops + support-demo；uat / prod = 主线（ops → main）。**绝不建议从 test 合并到 uat。**
- 迁移要能在 uat（与 prod 同源数据）上演练；脱敏数据上的 dry-run 结论不能直接外推到 prod。
- 前端 `VITE_*` 是构建期变量，与本专项无关，但前端改动需要重建镜像才能上线。

### 7. 结束时向用户汇报

用中文简要汇报：本次数据来源与代码基线、新增几项（编号+标题）、移入已优化几项、仍待优化几项（按 P0/P1/P2 计数）、需要用户拍板的事项。
不要自动 commit / push；问用户是否需要提交（工作区仓库 `WenchaoChen1/CSS`，提交信息用 `docs(优化): ...`）。
