# 换新版本代码时的核对清单

> 场景：拿到一个新的代码导出（如未来的 v2026xxxx），要替换 `apps\` 下的项目重新部署。
> **设计目标：项目本体零修改。** 打镜像/compose/env/EC2 全在部署包里，正常情况下只做第一节的"换目录"。

## 一、换目录（必做，就这一步）

```powershell
cd C:\github-code\chain-serve\部署包\apps
# 复制方式:删旧目录、放入新项目(保持目录名 CSS_backend-main / CSS_frontend-main)
# junction 方式:删掉旧 junction,重指新路径:
Remove-Item .\CSS_backend-main, .\CSS_frontend-main -Force
New-Item -ItemType Junction -Path .\CSS_backend-main  -Target <新版后端根>
New-Item -ItemType Junction -Path .\CSS_frontend-main -Target <新版前端根>
```

注意新导出常见双层嵌套（`CSS_backend-main\CSS_backend-main\`），指向**真正的项目根**（含 core_app 的那层）。

## 二、配置漂移核对（每次换版本都过一遍，10 分钟）

项目零修改 ≠ 部署包零修改——新代码可能需要新配置。逐项核对：

- [ ] **后端新必填 env**：diff 新旧版的 `core_app/src/config/*.py`，出现无默认值的新字段就补进每个 `env\<env>\backend.env`（缺了会 pydantic ValidationError，四个入口全起不来）。⚠️ 别信项目的 `.env.example`，历史上它缺 `CATALOG_OCR_BASE_URL/API_KEY`。
- [ ] **前端新 VITE_ 变量*\*：在新前端 `src/` 里 `grep "import.meta.env"`，新变量补进 `env\<env>\frontend.env`。
- [ ] **新服务/新端口**：diff 新旧版根 `docker-compose.yml` 和 `core_app/docker-compose.yml`，上游若加了新服务（新容器、新中间件），要在 `compose\` 三个文件里补对应服务定义。
- [ ] **迁移链 vs 数据库**：新版 `migrations/versions/` 的 head 和目标库 `alembic_version` 的关系——不在链上就先 reconcile，绝不盲跑 `migrate`；含删表迁移时 RDS 先快照。（v20260705 的结论见 `v20260705\手动迁移操作文档.md` 第四节。）
- [ ] **worker 任务变化**：`internal/worker/app.py` 有新任务/新 cron 时，app 和 worker 必须同版本同发（本包同一 tag 同发，天然满足，只是别混用旧镜像）。
- [ ] **前后端配套**：前后端必须是同一版本线的导出（v20260705 起前端强依赖后端 /manufacturers/* 新端点）。

## 三、部署包内的两个"代偿补丁"要不要退役（可选核对）

本包替项目内联了两处修复，上游修好后可以去掉：

- [ ] **前端跳过 tsc**：在新前端跑 `npm install --legacy-peer-deps; npm run check:typescript`。若 0 错误 → 把 `compose\frontend.yml` 和 `compose\dev.yml` 里 dockerfile_inline 的 `RUN npx vite build` 改回 `RUN npm run build`（恢复类型检查）。
- [ ] **ai_assistant Debian Dockerfile**：若上游修复了 alpine 构建（或换了海外构建机），删除 `compose\backend.yml` 里 ai_assistant 的 `dockerfile_inline` 块即回退项目自带 Dockerfile。

## 四、发布顺序（换版本后的首次发布）

1. `.\bin\本地dev.ps1 build` + `up` 本地先验证能起、能登录。
2. `.\bin\打镜像推ECR.ps1`。
3. compose/env 若有改动 → `.\bin\同步部署文件到EC2.ps1`。
4. **RDS 快照** → EC2 上 `./bin/deploy.sh test deploy` → `./bin/deploy.sh test migrate`。
5. 验证：登录（kafka + salt）、`/api/docs`、前端页面、OCR 上传。

## 五、项目内唯一的例外

**前端 HMR 本地开发**（`npm run dev`）做不到零修改：需要项目 `vite.config.ts` 打 dev 反代补丁 + 项目根放 `.env`。只在需要改前端代码调试时打，不影响打镜像和部署（部署走容器构建，不依赖这两处）。补丁内容见 `v20260705\手动迁移操作文档.md` 步骤 4 与前文。
